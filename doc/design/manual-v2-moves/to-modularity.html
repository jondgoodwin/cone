Subtypes

Subtyping captures a simple but powerful idea: if we have two types named Base and Subtype, how do we determine when it is safe to substitute in a value of type Subtype whenever our program logic is looking for a value of type Base?

Here are two essential criteria (there are others):

  • Every possible value in Subtype can be mapped uniquely to its semantically identical value in Base.
  • The behavior of values in Subtype must correspond in every way to the behavior of equivalent values in Base. In our case, that means at minimum that for every method in Base, there exists an equivalent method in Subtype with the same type signature and constraints.

Many type pairs in Cone comply with these criteria and support a safe subtyping relationship:

  • Any variant type is a subtype of any trait or struct type that it complies with, even if it does not inherit from it.
  • Any non-nullable type is a subtype of its nullable equivalent (e.g., &Foo is a subtype of ?&Foo).
  • An owning reference is a subtype of the borrowed reference to the same value type (e.g., So[Foo] is a subtype of &Foo)
  • A pointer is a subtype of any reference whose object type is the same.
  • Some reference permissions are subtypes of others (e.g., ro is a subtype of imm or mut). Similarly, most permissions are a subtype of uni.
  • A smaller number type is a subtype of a larger version of the same type (e.g., u8 is a subtype of u32).
  • A struct is a subtype of any trait it conforms to.

An important characteristic of subtyping relationships is that it is trivially safe to transform a Subtype value into its equivalent Base value. However, the journey of a value back from Base to Subtype often requires some sort of pattern-matched guard, as there are likely to be values in Base that do not have a valid mapping from Subtype to Base. A successful pattern match guarantees we will get back a valid Subtype value when the reverse transformation is applied.

  • Fold clause. A public field may end with use and a list of members of its type, which become names of this struct reached through the field: delegated inheritance.

    • Two or more methods may share one overload name. This is called method overloading. Each method still has its own unique name; it declares the shared name it overloads by placing the overload keyword and that name between its own name and its signature:

    struct Rect {
  pub w f32;
  pub h f32;

  pub fn areaOf overload area(self) f32 {
    w * h;
  }
  pub fn areaScaled overload area(self, scale f32) f32 {
    w * h * scale;
  }
}

imm r = new Rect(2., 3.);
imm a = r.area();          // selects areaOf
imm b = r.area(4.);        // selects areaScaled
imm c = r.areaScaled(4.);  // calls the method directly by its own name

    Methods that overload one name should vary in their number of parameters or in the types of their parameters, because two candidates that would accept exactly the same arguments are an error. A call using the shared name is resolved by trying every method that overloads it and requiring exactly one of them to accept the call's receiver and arguments, allowing for default parameter values and permitted implicit coercions. No matching method is an error, and more than one matching method is an ambiguity error; an exact match is not preferred over a match requiring coercion, declaration order never breaks a tie, and return types take no part in the choice. A caller resolves an ambiguity by calling a method's own name or by converting arguments. Sharing an overload name across methods makes it convenient for a type to support a similar capability for a broad range of differently-typed values.

    A shared name may only be used as the name of a method being called. Everywhere else, use the method's own name.

    A method a trait provides to every type that declares it (a shared method, one the trait gives a body) is replaced by the type's own method of the same name, whatever its shape: the own method need not take or give what the trait's does, and the type simply has no copy of the shared one. Calls on the type, direct or from generic code over the trait, reach the type's own method; a type with none gets the shared one.

    A generic method joins a shared name on the same terms as a generic function: when every type parameter is bound to a function signature (A generic function that overloads a shared name).

    A member's name hides an outer one

    Inside a type, a field's or method's name hides any name of the same spelling further out, as an inner name hides an outer one everywhere. That includes a module the type's module imports, and it holds in the methods' signatures as well as their bodies. A signature has no self to reach a field or method through, so a module written there under a member's name is an error:

    mod scene;
import mesh;

struct Model {
  parts i64;
  fn mesh(self &) mesh.Mesh {   // error: in Model, 'mesh' is this method
    new mesh.Mesh(parts);
  }
}

    The error on the signature names two ways round it. One is to import the module under another name, which no member hides:

    mod scenery;
import mesh as meshes;

struct Model {
  parts i64;
  fn mesh(self &) meshes.Mesh {
    new meshes.Mesh(parts);
  }
}

    The other is to reach the module through the module's own name, which is one of the names in reach inside it and which no member hides either:

    mod staging;
import mesh;

struct Model {
  parts i64;
  fn mesh(self &) staging.mesh.Mesh {
    new staging.mesh.Mesh(parts);
  }
}

    An enum type's methods may be written anywhere in its body, before or after its variants: what makes a member common to every variant is that it is not a struct. Such a method applies to all variants, but can only access the enum's common fields.

    Where you want a set of variants that other modules can add to, an enum is the wrong construct: use a trait and structs that declare is against it. That versatility costs something, and the cost is worth knowing: an open trait has no tag, so a value of it carries a pointer to type metadata and a match has to check the possibilities one at a time. A closed set is not only exhaustive, it is faster, because a tag is an index.

    An enum may also declare members in common: fields every variant has, and methods every variant answers. Neither is something Rust's enums offer, and both are what let a caller do useful work with a value whose variant it has not yet recovered.

    enum Event {
	pub time datetime;                             // a field every variant has

	pub fn stamp(self &) datetime {time;}          // a method with a body: a default
	pub fn describe(self &) String;                // a method without one: a requirement

	pub struct ButtonEvent {
		pub button u8;
		pub pushed bool;
	}
	pub struct KeyEvent {
		pub key Unicode;
	}
	pub struct QuitEvent;
}

    All three variants above begin with the time field, ahead of any fields they declare themselves. A method with a body is a default, which each variant gets unless it declares that name itself; a method without one is a requirement, which every variant must implement, and calling it through a reference to the enum dispatches on the variant — see Method dispatch.

    Either way, what a variant has is its own copy of the method. It is called on a value, event.stamp(), or named through the variant, Event.KeyEvent.stamp. Naming it through the enum, Event.stamp, is an error: the enum keeps no copy of its methods, only of its static functions.

    A common member may be written anywhere in the body. What makes a member common is its kind, not its position: a struct is a variant, and anything else is common. The layout still puts common fields first in every variant.

    A generic variant takes its type arguments from where its value goes, as every generic does (Generics): imm none Option[i32] = None;. Where nothing says, they are written in brackets after the name, and the values after them: None[i32], Some[i32](5). Square brackets after a variant give type arguments and never values, so Some[5] and None[] are refused, naming the spelling that replaces them. In a pattern or after is a name stays a type: case is None[IoBuf].

    An empty variant's name is a value, so a method can be called on it directly: with pub fn get(self &) i32 in Lamp, Lamp.Red.get() constructs Red and calls get on it, as (Lamp.Red).get() does. Only a method reads this way (one that takes self); a variant that holds values is not a value by its name alone, so Shape.Circle.area() is still refused for the self it lacks. A generic enum's empty variant has nothing to take its type arguments from as a receiver, so they are written: Pending.Waiting[i64].key().

    Inside the enum's braces, every name the enum declares is bare: its variants, and its fields, methods and functions. That holds for a variant's own body too, since it is written there, so a method of one variant names another without the enum in front:

    enum Traffic {
	struct Stop {
		fn next(self &) Traffic {Go(5);}   // Traffic.Go
	}
	struct Go {
		pub delay i32;
	}
}

    A name the variant declares itself comes first: a field of Go spelled like a sibling variant is, inside Go's methods, the field. One exception to the rule: a variant of a generic enum reaches the enum's methods through self, as self.name(), since it receives them only when the enum is instantiated. In a generic enum the enum's bare name, and each variant's, is the instance being defined, at the enum's current type arguments: inside enum Maybe[T], Maybe is Maybe[T] and a variant's No builds Maybe.No[T] (see Generics). A variant that an extension copies from its base (Extending an enum) keeps what its names meant where it was written, so it still means the base's variants.

    An enum's private members are its module's. A member not declared pub is private to the module that declares the enum, as a struct's is. So code written anywhere inside the enum's braces — the enum's methods, its static functions, and every variant's methods — reads and writes the private fields of the enum and of every variant, calls their private methods, and gives private fields their values when it builds a variant, through any value and not only through self, and so does every other function and type of the module. Outside the module they stay private. So pub means what it means everywhere: part of the enum's interface to the rest of the program, and not a way for one variant to reach another.

    enum Gauge {
	struct Low {
		lo i32;
		pub fn above(self &, h &High) bool {h.hi > lo;}   // High's private field
	}
	struct High {
		hi i32;
	}
	pub fn level(g &imm Gauge) i32 {                      // a static function
		match g {
			case imm l Low {l.lo;}
			case imm h High {h.hi;}
		}
	}
}

    (This sentence is the compiler's current reading and is still to be reviewed.) An anonymous function written inside the braces is not part of this: like one written in a struct's method, it belongs to the module.

    A module that wants an enum's variants as names of its own says so with use, which names the enum and then, optionally, which variants:

    use PhoneType;                         // Home, Work and Mobile, bare
use Event KeyEvent as Key, QuitEvent;  // only these, one of them renamed
use Point {XyPoint, AngPoint};         // a list may be spread over lines in braces
use Colors but Blue;                   // every variant but one

    After use PhoneType;, Work means PhoneType.Work. The module that declares the enum is no exception: it writes use like any other module to have the variants bare. A use folds variants and nothing else of the enum, and a variant it leaves out is still reached through the enum. The enum may be named through a module, use shapes.Colors;. A folded name must not be one the module already has for something else, whatever brought that one in; two enums that each have a Quit are both folded by renaming one or leaving it out. Nor may a module fold the same variant in twice itself: writing use Colors; twice is an error. The same variant arriving by a wildcard import is the name the module already has, so use Option; is fine beside the Some and None every module already has.

    The names a use makes belong to the module that wrote it and are private to it. Written pub use, they are public names of the module: another module reaches them through it, shapes.Red, and an import of the module with .* brings them in bare. That is how Some, None, Ok and Error are bare in every program: the core library writes pub use Option; and pub use Result;, and every module imports it with .*.

    A pattern needs no use: below.

    Method dispatch

    Sometimes every variant should answer the same method with its own implementation. Declare the method on the enum without a body, and let each variant implement it:

    enum Number {
	pub fn double(self &mut Self);

	pub struct Real {
		pub n f32;
		pub fn double(self &mut Self) {
			n *= 2;
		}
	}

	pub struct Complex {
		pub r f32;
		pub i f32;
		pub fn double(self &mut Self) {
			r *= 2;
			i *= 2;
		}
	}
}

    Calling number.double() on a reference to a Number invokes the implementation belonging to whichever variant the reference points at. The tag says which variant it is, that selects the variant's vtable, and the vtable holds the method.

    The same goes for any other trait the enum complies with. A reference to a Number may be passed where a virtual reference to such a trait is expected, and the virtual reference it becomes carries the vtable of whichever variant it points at, chosen by the tag, exactly as a reference to that variant would. Narrowing it with is or match therefore names a variant, never the enum.

    The enum need not comply as a whole for a match to use a trait. A match on an enum may name a trait, case imm m Measured, which matches every variant that complies with it and binds a virtual reference to the trait built from the variant, whose vtable the tag chooses (Trait patterns).

    A method may also take self by value, and a variant's value calls its own copy:

    enum Reading {
	pub id i32;
	pub fn get(self) i32 {id;}
	pub struct Low {}
	pub struct High {pub n i32;}
}

Reading.High(1, 4).get()      // 1: High's own copy of get

    Note: on a value typed as the enum itself, which variant's copy runs would have to be read from the tag the same way, and that is not built for a value. Calling such a method on a value of the enum is an error today; match to recover the variant, or declare the method with a reference receiver, which dispatches as above, or name the enum as the receiver.

    One function over the whole enum

    The receiver a method names decides which it is. A method written with self & or self &Self belongs to the variants: it is copied into each, and inside a copy self is that variant. A method whose receiver names the enum — self &Lamp, self &mut Lamp, any other kind of reference, or by value self Lamp — is one function over the whole enum. It is not copied, nothing is dispatched on the tag, and inside it self is the enum, so match self, case is and self is Red work as they do anywhere else:

    enum Lamp {
	pub n i32 = 7;
	Red;
	Green;
	Off;

	pub fn describe(self &Lamp) i32 {      // one function over the whole enum
		match self {
			case Red   {10;}
			case Green {20;}
			case Off   {30;}
		}
	}
	pub fn next(self &mut Lamp) {          // may store any variant through self
		match self {
			case Red   {*self = Lamp.Green;}
			case Green {*self = Lamp.Off;}
			case Off   {*self = Lamp.Red;}
		}
	}
	pub fn get(self &) i32 {n;}            // copied into each variant, as above
}

imm l Lamp = Lamp.Green;
l.describe()               // 20
Lamp.Red.describe()        // 10: a variant's value calls it, widened to Lamp

    A method over the whole enum is called on a value of the enum or on a value of one of its variants, which is widened to the enum for the call, and by value it takes a copy. A variant's value cannot lend &mut Lamp, since the method could store another variant in it: declare the value as the enum, mut l Lamp = Lamp.Red. If a variant declares a method of the same name, a value typed as that variant calls the variant's own, and a value typed as the enum calls the enum's. Within one enum a name is declared once, so the two kinds cannot share a name there. A package that declares such a method defines it once, and an importer calls it. An enum that extends another does not inherit its base's methods over the base, since a value of the extension is not a value of the base. A generic enum's method over the whole enum, self &Option[T], is not available yet.

    Inside a variant, Self names the variant, so a variant holding the enum writes the enum's name: Branch(List[Tree]), not List[Self].

    Complying with a trait

    An enum may say in its declaration that it complies with one or more open traits, exactly as a struct does, with is after its name. What the trait requires and what it gives then reach every variant: a default the variant does not declare becomes its own copy, and a requirement is met by the variant's own method or by one with a body the enum gives every variant.

    trait Named {
	pub fn label(self &) i32;
	pub fn loud(self &) i32 {label() * 100;}
}

trait Measured {
	fn size(self &) i32 {7;}
}

enum Shape is Named {
	pub k i32;
	pub fn label(self &) i32 {k;}    // meets Named's requirement for every variant

	pub struct Circle {
		pub r i32;
		pub fn label(self &) i32 {r * 10;}
	}
	pub struct Square is Measured {        // a variant may name traits of its own
		pub s i32;
	}
}

fn loudOf(n &<Named) i32 {n.loud();}
fn shapeLoud(s &Shape) i32 {loudOf(s);}   // passes the variant's vtable, chosen by the tag

loudOf(&Shape.Circle(1, 7))     // 7000: Circle's own label, Named's loud
loudOf(&Shape.Square(2, 3))     // 200: the enum's label, Named's loud

    A variant may name traits of its own in the same way, beyond its enum: struct Square is Measured above. Its enum is its base without being written, and naming the enum in the list is an error, since a variant is already a member of the enum it is written inside.

    An enum's list and a variant's name only open traits, and none of them is a base in the sense a struct's first one is: the enum lays out itself and every variant, discriminant first, so a trait either one names may not require fields. Nor may any is list name an enum, whether first or later: an enum's variants are all declared inside it, and nothing outside may join the set. An enum that extends another takes its base's traits with the variants it copies and names none of its own.

    Trait patterns

    In a match on an enum, a pattern may name a trait instead of a variant. It matches every variant that complies with the trait: one that declares it with is, or has what it requires (Traits), including what the enum gives every variant. A variant that does not comply, Third below, is left to the cases after it. The match compiles to tests of the tags of the variants that comply, so it costs nothing beyond them, and it counts toward covering every value as the variants it names, so the match below needs no else:

    trait Measured {
  pub fn size(self &) i32;
}

enum Shape {
  struct Circle is Measured { pub r i32; pub fn size(self &) i32 {r * 10;} }
  struct Square is Measured { pub s i32; pub fn size(self &) i32 {s * 100;} }
  struct Third { pub t i32; }
}

fn measure(s &Shape) i32 {
  match s {
    case imm m Measured { m.size(); }   // Circle's or Square's own size, by their vtables
    case is Third { 7; }
  }
}

    The binding is a virtual reference to the trait, built from the variant the matched reference points at, so a call through it goes through that variant's vtable. As for a variant (Variant type partial matches), the matched value supplies the kind and the permission: on a &mut Shape, m is a &<mut Measured and may call what needs self &mut; on a &Shape it is read-only. It is a reference into the variant, so it follows the collection rule as a binding to a variant does, and it may not outlive the value it borrows. Because only a borrowed reference can lend a virtual reference, a pattern that binds a trait needs the matched value to be one (match &s, match &mut s); a value or an owner such as an Rc can be asked, case is Measured, and not bound. A pattern may not be written as a plain reference to the trait (&Measured), which has no vtable to carry. The patterns work in a bound if, imm m Measured = s, in let-else, and joined by or and guarded like any other.

    Which variants comply is decided as a generic's where T is Measured decides it: by declaring the trait, or structurally for a trait that requires something. A marker trait, which requires nothing, is complied with by declaring it alone. A method written over the whole enum (fn size(self &Shape)) is one function that no variant has a copy of, so it makes no variant comply; a trait that no variant complies with is an error, since the pattern could never match. Only a closed family can say which of its values comply, so an open trait has no trait patterns: a &<Measured can be narrowed to the concrete type it was made from, and only to that (Virtual references).

    Again, None is an inferred abbreviation for None[i32]. The abbreviation is only possible when the context makes it clear what sort of Option type we are working with: a declared variable, a return type, an assigned variable, a parameter, a field, the branches of an if and the other operand of == each say, by the general rule that a generic's type arguments are inferred wherever they can be (Generics). Nothing about it is particular to Option: Ok(5) takes its error type from the Result it is wanted as, and Some(5) is an i64 where an Option[i64] is wanted. Thus, this is ambiguous and therefore an error, and the message says to write None[T]:

    The closures are generic arguments ([F fn(x T) U]), each its own type, so a chain is compiled into one loop with every closure's body inline and no call through a pointer for any item. A closure that changes a variable (x => { n += 1; *x; }) is run once for each item the chain asks for and no more. Over a cursor that gives numbers (not a borrow), a map and a sum is vectorized as the hand-written loop is. Over a cursor that lends the loop is not vectorized, since each step answers an Option of a borrow, which is a pointer tested for null: the same loop a hand-written while over next() is.

    A type with a next that does not declare is Iterator[T] is still accepted wherever an Iterator is asked for as a bound (fn f[T, I Iterator[T]](it &mut I): fitting a trait is by shape), and each walks it. What it does not get is the shared methods, which come with the declaration; asking it for map is an error that says to declare it. Each step is a cursor of its own type (the whole chain's, so a chain is held in a variable of inferred type, or walked at once). The terminal methods take the cursor by &mut, so one called on a chain made in the same expression needs no name for it.

    Iterator and Iterable

    Two more of core's traits name the shapes a sequence of values is walked by, for code that is generic over them. A type is an Iterator[T] by having next, and an Iterable[T, I] by having iter. Neither is declared: a type with the method complies, as the cursors of str and of every collection do, and so does a struct of your own.

    pub trait Iterator[T] {
  pub fn next(self &mut) Option[T];     // the next value, None once there are no more
}

pub trait Iterable[T, I] where I is Iterator[T] {
  pub fn iter(self &) I;                // a cursor over what it holds, without consuming it
}

    A function asks for one as a bound, decided where it is called and compiled for the type's own methods, or as a virtual reference (&<mut Iterator[i64]), which takes any cursor through one compiled function:

    fn count[T, S Iterator[T]](it &mut S) usize {
  mut n = 0usize;
  while true {
    match it.next() {
      case imm v Some {n = n + 1usize;}
      case is None {break;}
    }
  }
  n;
}

fn total[S Iterator[&i64]](it &mut S) i64 { ... }   // a cursor that lends numbers
fn walk[T, I, C Iterable[T, I]](c &C) where I is Iterator[T] { ... c.iter() ... }

    T is what next gives, so a cursor that lends its values (a Deque's items(), a Dict's keys()) is an Iterator[&V]. The &V of a bound names no lifetime, and a cursor whose next returns the lifetime its own struct declares (Option[&'a V]) meets it, as a method with no other parameter has nothing to store through its receiver. The cursor's own signature is what a bound's call reads, so borrows given by two calls of next may be held together; through a virtual reference the trait's signature is read, which ties a result to the whole cursor. Iterable takes its cursor's type as a second argument, I, because a trait cannot yet name a type its implementer chooses; both arguments are found from the type passed. A type with no next (or iter), or with one that gives another type, is refused where the function is called.

    Fitting is by shape, and the trait's shared methods come with the declaration. A type that says struct Countdown is Iterator[i64] has, beside its own next, the steps that work on a whole sequence, map, filter, take, skip, fold, any, all, count, find, sum, min and max (Each and Iteration), which the trait writes once as generic defaults. A type with a next and no declaration meets a bound on the trait all the same and has none of them. A generic default has no slot behind a virtual reference (&<mut Iterator[i64] calls next), and a default that exists only where a condition holds (sum wants number items) has none either.

    The collection traits

    The collections package also declares five small traits, one for each thing a collection can do, so that a function asks for exactly the ability it uses; each is met structurally (Traits), by having the methods, so none of the collections declares one.

    • Collection (len, isEmpty: List, Deque, String, Dict, OrderedDict, Set);
    • Indexed[T] (get(i): List, Deque);
    • Stack[T] (push and pop at the back, peek: List, Deque);
    • Queue[T] (push at the back, popFront: Deque);
    • Map[K, V] (get, insert, remove, contains by a &K: Dict, OrderedDict).

    A function asks for one as a static bound (A generic trait as a constraint), fn drain[S Stack[i64]](s &mut S), fn drain[T, S Stack[T]](s &mut S) or fn drain[T, S](s &mut S) where S is Stack[T], called with &mut list or &mut deque; the bound is decided where the function is called, so the call is to the type's own methods. A trait is given all its type arguments ([S Stack] is refused), while Collection, which has none, is written alone, fn count[C Collection](c &C). The other form is a virtual reference, fn drain(s &<mut Stack[i64]), which takes the same arguments through one compiled function and a table of methods, for a value whose type is not known where the function is compiled; every trait works either way. Map's insert answers the old value, an Option (None for a new key). A Set's insert answers whether the element was new.

    import stdio use *;
import collections use *;

// A function asks for exactly the ability it uses
fn countOf[C Collection](c &C) usize { c.len(); }

fn drainSum[S Stack[i64]](s &mut S) i64 {
  mut total = 0i64;
  while true {
    match s.pop() {
      case imm v Some {total = total + v;}
      case is None {break;}
    }
  }
  total;
}

// The other form: one compiled function, called through a table of methods
fn peekTop(s &<mut Stack[i64]) i64 {
  match s.peek() {
    case imm v Some {*v;}
    case is None {-1i64;}
  }
}

fn main() i32 {
  mut list = List[i64].empty();
  list <- 1i64, 2i64, 3i64;
  mut deque = Deque[i64].empty();
  deque <- 10i64, 20i64;
  imm word = String.from("four");
  print <- countOf(&list);              // a List is a Collection
  print <- " ";
  print <- countOf(&deque);
  print <- " ";
  print <- countOf(&word);
  print <- "\n";
  print <- peekTop(&mut list);
  print <- "\n";
  print <- drainSum(&mut list);         // a List is a Stack
  print <- " ";
  print <- drainSum(&mut deque);        // so is a Deque
  print <- "\n";
  0i32;
}

    This prints 3 2 4, 3 and 6 30.

    An if used as a value needs its else, since every path must give a value. A match is not an if chain in this: it must cover every value it matches, statement or value, and its cases may do so (every variant of an enum, both values of a bool) without writing an else. An if chain of is tests that names every variant of an enum is a value without an else too, but is not asked to name them all.

    Flow typing

    A test of a variant tells the compiler what the tested name is, and it uses the name that way until something may have changed it. After if s is Circle, inside its block s is a Circle wherever a field or a method of Circle is named on it: s.radius reads it, s.radius = 2 writes it, s.grow() calls it. The name is narrowed:

    • in the block of an if, an elif, or the case of a match that names the variant, and on the right of an and whose left tests it (if s is Circle and s.radius > 3);
    • after a branch that leaves, for what follows: after if s is Circle { return 0; }, s is not a Circle;
    • by elimination: when the variants that remain are one, s is that one, in the else of a two-variant test, in the last case of a match, after an early exit;
    • by an assignment of a known variant: after state = State.Run(speed), state.speed reads the field.

    It is a name that is narrowed — a local variable or a parameter, held by value or through a reference — and only to name a member of the variant. Narrowing does not retype the name for anything else: it is still the original, whole value, passed and returned as the enum, and takesCircle(s) is still an error (bind it for that). A variant declared as a type, Ok(i32);, has no fields to name: the narrowed name has nothing more to offer, and a binding is how to reach what it holds. The test if x is a plain truth test, and never narrows: only the language's own tests do, is and a binding, never what a method returns (Option unwraps with them).

    A narrowing ends when the name may hold another variant: an assignment to the whole of it, a mutable borrow of the whole enum (a call that takes &mut Shape), a swap, a reference stored over (*s = ...), or a path where one branch did one of these. Writing a field within the variant is not a change, whether a field of the variant or a field the variants share. After a change the name is its whole type again, and a use that needed the variant says so, at the use, naming the change:

    fn step(state &mut Machine) {
  if state is Run {
    state.speed = state.speed + 1;   // Ok
    *state = Machine.Stop;          // the whole value is replaced: the narrowing ends
    state.speed;                    // Error: `state` is not known to be Run here: it was changed at ...
  }
}

    A name that is a reference others may share (& or &mut) is narrowed through a reference the compiler declares where the test was made, and the loan walk follows it as it follows a binding (Borrowed references): a call handed another name for the enum, a store through one, a swap, or a call whose body it cannot read is a change, refused at the next use of the narrowed name; a call that cannot reach the enum is none. Nothing follows the reference between the test and the block's start (or, inside one condition, the use), so a call or a store made in a later operand of the condition ends the narrowing, whatever it reaches: if s is Circle and toRect(t) and s.radius > 0 is refused at s.radius, naming the call. A name held by value, or through an imm, uni or mut1 reference, has no other name that can change it, so only its own assignments and mutable borrows are changes.

    A narrowing from before a loop is good for the loop's first pass. A use of it that a change later in the loop reaches again by the loop's back edge is an error, reported at the use. Test again inside the loop to narrow afresh, which is how a state machine reads its next state:

    while running {
  if state is Idle { start(); state = State.Run(1); }       // tested each pass
  else if state is Run { state.speed = state.speed + 1; }   // narrowed by its own test
}

    Note: Functions are implemented, except throws. Closures are implemented, except a closure that calls itself, and calling a closure once and consuming it (a body that moves one of the closure's state entries out); for closure references, calling a closure once, which consumes it, through an owner, and + joining any trait but the markers Sendable, Shareable and ShapeKeeping, are not built. Result is built as core's enum. Not built yet, and coming: throwing and catching exceptions (a throws signature, throw, catch), a plain value returned where a Result is expected, and the ? and || operators on a throwing call or a Result; their planned forms are gathered below. Generators are built: a function declared yields, with yield and yield each, among a module's functions or as a method of a struct, generic or not. A generator may not be inline, have a where clause, or be a method of a trait, an enum, an actor or a type that declares lifetimes. A pub generator of a library is walked by the packages that import it. each walks one, as it walks any value with a next. Two-way yield is an idea that is not built.

    The commas separate return types only where the signature stands on its own: a function's own signature, or a function type given as a field's or a variable's type. Inside a list — a parameter list, a function type's own parameter list, or any other list in parentheses or brackets — a comma after a function type's return type continues the list instead. A function type there that returns several values puts them in parentheses, as a tuple:

    // f takes a u32 and returns one u32; x is a second parameter
fn apply(f &fn(u32) u32, x u32) u32 {
}

// g returns two values, so they are written in parentheses
fn applyBoth(g &fn(u32) (u32, u32), x u32) u32 {
}

    Overloading

    Every function has its own name, unique within its namespace. A function may additionally declare that it overloads a shared name, by placing the overload keyword and that shared name between its own name and its signature. Overloading is useful when several functions perform essentially the same semantic operation, but do so using a different number or different types of parameter values.

    // 'addFloat' is this function's own name. It also overloads the shared name 'add'.
fn addFloat overload add(a Comp, b f32) Comp {
  ...
}

// 'addDyn' is this function's own name. It overloads the same shared name.
fn addDyn overload add(a Comp, b dyn) Comp {
   ...
}

    A shared name may only be used as the name of a function being called. A function's own name has no such restriction: it is the name to use when obtaining a reference to the function (e.g., by '&'), and it is the basis for the function's generated linker name. A shared name is as visible as the functions that overload it, so they must agree: the first declared decides whether the shared name is pub, and a later function that disagrees is a compile error, because callers of a public name would otherwise reach code its own declaration keeps private, or a public function would be hidden behind a private name.

    When a shared name is called, the compiler tries every function that overloads it and requires exactly one of them to accept the call's arguments, allowing for default parameter values and permitted implicit coercions. No matching function is an error, and more than one matching function is an ambiguity error. An exact match is not preferred over a match requiring coercion, needing fewer coercions does not win, declaration order never breaks a tie, and return types take no part in the choice. A caller resolves an ambiguity by calling a function's own name or by converting arguments so that only one function accepts them.

    Two functions may not declare the same own name, a shared name may not also be some other declaration's name, and two functions that overload one shared name may not accept exactly the same arguments.

    Methods overload a shared name the same way (Method name).

    Closures

    A closure may be viewed as a function that preserves its state from one invocation to the next. Because closures preserve their state, they are useful for:

    • Iterators, which retrieve a sequence of values one-at-a-time from a defined collection. An Iterator is already anything with a next method (Iterator and Iterable); what closures add is the adapters (map, filter, fold), written once as the methods every cursor declaring is Iterator[T] shares (Iterator adapters), and a source that runs its own loop around the body of an each (not built yet).
    • Generators that return a different value on each use. The generator a function declares with yields needs no closure (Generators).
    • Event-triggered callbacks, whose state guides what happens after an event is triggered.
    • Function-valued inputs of a library, such as the profile a sweep follows or the order a sort uses, whose numbers belong to the caller rather than to a fixed function.

    Closure Definition

    A closure is written where it is used, in the body of a function, in one of two forms.

    The full form

    The full form resembles a function definition. There are three key differences: the name is omitted, the return type may be omitted (and inferred), and the state the closure carries may be listed in square brackets after the parameters.

    fn (parameters) [state] return_type { body }

    For example:

    mut counter = fn(n i32) [mut cnt = 0] { cnt += n; cnt; };

// Closure use
counter(1);        // 1
counter(2);        // 3

    This closure takes one parameter, n. It infers that its return value is an integer, since the last expression is cnt, an i32.

    The state list holds the variables the closure owns. Each entry is a field of the closure, written as a field is: a name with an initial value, cnt = 0, whose type is the value's. Entries are separated by commas. An entry is imm unless written mut, so a closure that changes its state lists it mut. The list may be left out. The brackets sit after the parameters because a bracket never begins a type, so they cannot be taken for the return type.

    A parameter's type may be left out where the closure is given to something that says what the signature is (fn(x) { x + 1; }, below); nothing else may leave a type out. Three places say it: a parameter taken by &<fn(sig) or &<mut fn(sig) (a closure literal, lent), a generic parameter bound F fn(sig), and new So[fn(sig)](...) (an owner of a closure). A parameter of type So[fn(sig)] does not: it takes an owner, and a closure literal is not one, so a literal given straight to it is refused (for an untyped one, error 1391, "The type of a is not written, and nothing here says what it is"). Wrap it: c.set(new So[fn(a i64, b i64) bool]((a, b) => a < b)). An imm given an untyped closure is refused the same way, even where the imm is written with a &<fn(sig) type.

    The short form

    For a small closure the short form puts the parameter names, an arrow, and the body:

    x => x * 2
(a, b) => a.len() < b.len()
() => 5
n => total += n
u => 1.0 + depth * sin(u * ribs)

    The short form takes parameter names only, whose types come from the signature the closure is given to, and a body that is one expression, an assignment, or a block. It has no state list and no written return type; a closure that needs either is written in the full form. A comma after the body belongs to the list the closure is in, so f(x => x + 1, 3) is a call with two arguments.

    The arrow is =>, not ->, which would read as "returns".

    fn apply(f &<fn(x i32) i32, x i32) i32 { f(x); }

imm off = 10;
apply(x => x * 2, 21);                     // 42
apply(fn(x i32) i32 { x + off; }, 1);      // 11
apply(fn(x) { x + off; }, 1);              // 11: the type comes from the signature

    What a closure captures

    A closure's body may name variables of the function around it. Each one it names is borrowed: the closure holds a reference to it, & where the body only reads it and &mut where the body changes it, and the compiler works out which from the body. The variable around shows the change:

    mut total = 10;
mut add = fn(x i32) { total += x; };   // borrows total as &mut
add(3);
add(4);
total;                                 // 17

    Only a mut variable can be changed by a closure; changing any other is the ordinary "no permission to modify" error, reported inside the body. Because the closure holds a variable it changes by &mut, its body cannot lend that variable &uni (bump(&uni total) is refused): a shared reference does not see through to a unique one. The borrow is an ordinary one, so it holds the variable as borrows do. While a closure that reads a variable is still to be used, the variable cannot be changed or moved; after the closure's last use it can:

    imm limit = 100;
mut count = 1;
imm sum = fn(x i32) i32 { x + limit + count; };
sum(1);        // 102
count = 5;     // ERROR if sum is called again below this line; fine once it is not

    Borrowing is the default because a copy made silently would duplicate state: a closure that added to its own copy of total would leave total unchanged and would give no sign that it had. When a closure should hold its own value instead, it is listed.

    Giving the closure its own value

    A variable listed in the state list is no longer borrowed. The entry is a field with an initializer, so the ordinary rules for values decide what the closure holds:

    imm ribs = 3;
imm shape = fn(u i32) [ribs, base = 2 * 5 + 1] i32 { u * ribs + base; };
shape(2);                              // 2 * 3 + 11: 17

mut xs = new List[i32]();
imm count = fn(x i32) [buf = xs] i32 { x + i32.from(buf.len()); };   // xs is moved in

imm p = new Pt(4, 5);
imm viaRef = fn(k i32) [r = &p] i32 { r.x * k; };              // a borrow, written out

imm mesh = new Rc[imm, Pt](7, 8);
imm h = fn() [mesh] i32 { mesh.y; };   // a counted owner is copied: mesh is still held
    • A copy: [ribs]. An entry with no = starts from the variable of that name around the closure. A value that copies is copied and one that moves is moved, as it would be passed to a function.
    • A move: [buf = xs], for a value that moves. The closure owns it, and xs can no longer be used.
    • Shared ownership: list a handle of a region that counts its owners, such as an Rc or an Arc. The closure holds one count and the original holds another. The permission of the handle decides whether the closure may change what it points at (Rc[mut, T]).
    • New state: [mut n = 0], which has no variable around it to mirror.
    • A borrow, written out: [r = &p]. The closure then has the lifetime of the borrow, as it does for a borrow it makes itself.

    An entry's initial value is read in the code around the closure, not from the entries before it: in [a = 1, b = a] the a that b starts from is the one outside.

    Naming the state has other benefits: it tells the reader which variables are the closure's own, and an entry may be given a name of its own, as a field may. Listing is optional where borrowing will do.

    A closure written in a method that names a member of the object, hits or step, reaches it through the method's self, which it borrows as it borrows any variable. A closure sees exactly what the code around it sees, private members included, wherever it is later called from:

    struct Tally {
  hits i32;
  step i32;
  pub fn run(self &mut) i32 {
    mut bump = fn(x i32) i32 { hits += x * step; hits; };
    bump(1) + bump(2);
  }
}

    Whether the closure changes

    A closure is a value whose one method, (), is the body. That method's self permission is not written: it follows the body. A body that only reads what the closure holds and borrows has self &. A body that changes a captured variable or a mut state entry has self &mut.

    This decides what the closure may be used for. A closure whose () takes self &mut is held in a mut variable to be called, and goes only where a callable may change its state, &mut F and &<mut fn(sig) (Generics, Closure References). Given to a parameter that promises only to read it (&F, &<fn(sig)), it is refused, and the error says that this closure changes its state.

    The return type

    The return type is, in order of preference:

    1. the one written, fn(x i32) i64 { ... };
    2. the one the signature expected gives, where the closure is passed or assigned to one, every path being checked against it;
    3. read off the body's paths: the first return or final expression the check meets fixes it, and the others must fit it. A body whose last statement changes something (total += x;) returns nothing; any other last expression is the value;
    4. otherwise an error at the closure, "the paths give different types; write the closure's return type": fn(x i32) { if x > 0 { x; } else { 0u8; } }.

    return in a closure returns from the closure, never from the function around it.

    imm early = fn(x i32) i32 { if x > 5 { return 1; } x + 2; };
early(9);      // 1
early(3);      // 5

    A closure that holds nothing

    A closure that borrows nothing and has no state is a plain function. Where a function reference, &fn(sig), is wanted it becomes one: twice(x => x * 3, 1) to a parameter f &fn(x i32) i32. One that holds or borrows something is refused there; the parameter is then written &<fn(sig). An anonymous function written with the ampersand, &fn(x i32) i32 { x + 1; }, is not a closure: it is a function reference and sees no variable of the code around it.

    Where a closure may go

    A closure is a value of a struct of what it holds and borrows, so where it can go is decided by the rules for its fields, with nothing special for closures. A closure that borrows a variable cannot outlive it:

    • Down a call, passed to a function that uses it and returns, it may borrow any variable of the function around it, with one exception: a call that is also handed a &mut (or &uni) borrow, a method's receiver among them, of something that can hold borrows (a struct with a borrowed-reference field, a list of borrowed references) that the caller lent, since the call could store the closure's borrow there, where it would outlive the variable. That call is refused (error 1085) when the closure borrows a local of the function, or another argument is a borrow of a local, even though the callee only reads the closure. The error names the variable. A closure lists the variable, fn(x &i64) [k] bool { *x > k; }, to hold its own copy and borrow nothing. A receiver the function owns is not refused, and nor is one that cannot hold a borrow, such as a List[i64].
    • Kept in a local, it blocks moving or reshaping what it borrows until its last use.
    • Stored past the function or returned (in a field, in an owner such as So[fn(sig)], or as a returned borrow), it is refused if it borrows a local. The error names the variable and says to list it, so that the closure holds its own copy: fn (...) [k] ... { ... }.
    • Stored in the object that made it: a closure in a method that names a member borrows self, so it cannot be stored in self. The error says to copy the members it needs into its list ([tag = tag]), or to capture a counted handle to the object.
    • Sent to another thread or actor, or run in a parallel each, it must be Sendable, or Shareable for the loop, judged by what it holds (Sendable and Shareable). A closure that borrows a variable is neither; the error names the variable and says to list it. A closure holding an Rc is told to hold an Arc.
    fn returned() So[fn(x i32) i32] {
  imm k = 3;
  // ERROR: The closure borrows 'k' because its body names it: list it ...
  return new So[fn(x i32) i32](fn(x i32) i32 { x * k; });
}

fn listed() So[fn(x i32) i32] {
  imm k = 3;
  return new So[fn(x i32) i32](fn(x i32) [k] i32 { x * k; });   // its own copy of k
}

    The exception for a call down a function, with a holder of borrows that the caller lent:

    struct Seen {
  pub items List[&i64];
  pub fn count[F fn(x &i64) bool](self &mut, f F) i64 {
    mut n = 0i64;
    mut i = 0usize;
    while i < self.items.len() {
      if f(*self.items[i]) { n = n + 1; }
      i = i + 1usize;
    }
    n;
  }
}

fn refused(seen &mut Seen) i64 {
  imm k = 3i64;
  // ERROR 1085: seen holds borrows and the call could store the closure's borrow of 'k' in it
  seen.count(x => *x > k);
}

fn listed(seen &mut Seen) i64 {
  imm k = 3i64;
  seen.count(fn(x &i64) [k] bool { *x > k; });   // its own copy of k: nothing borrowed
}

fn owned() i64 {
  imm base = 5i64;
  imm k = 3i64;
  mut seen = new Seen(List[&i64].empty());
  seen.items.push(&base);
  seen.count(x => *x > k);   // fine: this function owns seen
}

    Rules that follow

    • A closure cannot call itself. The variable it is the value of is not a name inside it. Recursion uses a named function.
    • A closure is written in a function, never at the module level as a global's value or a field's default: there is nothing there to borrow.
    • On a GPU a closure is allowed in its static form only (Closures on the GPU).
    • While a collection is borrowed, a call of a closure that may change what it reaches is limited: see Calling a closure while a collection is borrowed.

    Closures are values

    Although closures may be viewed as functions with a persistent state, it is more useful and accurate to view them as a data value that carries an associated function (method):

    • A closure is syntactic sugar for an anonymous struct, whose fields are the state list's entries and a reference for each variable it borrows. The struct has no name that can be written, so a closure is held in a variable whose type is inferred, and given on as one of the references below.
    • Like any value, a closure may be allocated on the heap, in an owner such as So[fn(sig)].
    • A function that should accept any closure of a signature, without regard for the shape of its state, takes it as a closure reference, &<fn(sig), or as a generic over the signature, [F fn(sig)], which is compiled for each closure and inlined.
    • A closure may fill a trait with one required method as a struct does.

    Closure References

    Earlier, we introduced value-based closures. A closure is a value of a struct that has no name, and its size and fields depend on what it holds. Value-based closures struggle when we need a function to take any closure that has a specific calling signature, whatever struct holds its state. To satisfy this requirement, a closure may be passed as a reference to the signature it calls.

    Let's illustrate this with a simple event-handling example:

    struct Button {
  pub label i32;
  pub onClick So[fn(n i32)];
  pub fn setHandler(self &mut, f So[fn(n i32)]) { onClick = f; }
  pub fn press(self &mut, n i32) { onClick(n); }
}

imm w = new Window(7);       // a Window has an id field
mut b = new Button(1, new So[fn(n i32)](fn(n i32) { }));
b.setHandler(new So[fn(n i32)](fn(n i32) [id = w.id] { print <- id + n, "\n"; }));
b.press(5);      // 12

    Here we allocate a new click-handling closure using the single-owner region (ensuring it is automatically freed after being replaced or discarded). The closure's state remembers the window's id, which its logic uses when the button is pressed. The Button holds the closure as a So[fn(n i32)]: it accepts any closure, whatever its underlying state, so long as its function signature matches (it accepts one i32 and returns no value). The button calls the handler by the field's name, onClick(n).

    The forms of a closure reference

    The reference is written as the signature of the call, fn(x i32) i32, behind a reference or an owner. The signature stands for the idea "anything that can be called like this", a trait that needs no declaring, and the reference is a virtual reference to it.

    • &<fn(x i32) i32, a borrowed reference that may read what it points at. The closure's () takes self &.
    • &<mut fn(x i32) i32, a borrowed reference that may change what it points at: a closure that counts, or changes a variable it borrows.
    • So[fn(x i32) i32], an owner of a closure on the heap. The permission of an owner works as it does for any owner: So[fn(sig)] may change the closure's state, So[imm, fn(sig)] only reads it.
    • Rc[imm, fn(x i32) i32], shared owners of a closure that only reads; Rc[mut, fn(x i32) i32], shared owners of a state they all change, so every holder sees one count. Rc[fn(x i32) i32] with no permission is uni, the sole owner, as for any Rc, and moves when copied.

    These are the same permissions as elsewhere, so the call kind is the reference's permission, with no separate families of function types: a function that takes a callable it only reads takes &<fn(sig); one that lets it change takes &<mut fn(sig). The call is written as any call, and goes through the reference to the closure's code:

    fn apply(f &<fn(x i32) i32, x i32) i32 { f(x); }
fn applyMut(f &<mut fn(x i32) i32, x i32) i32 { f(x); }
fn run(f So[fn(x i32) i32], x i32) i32 { f(x); }
    What meets it

    Anything that has a pub () method of the signature, parameters and return type exactly (the parameters' names do not matter):

    struct Triple { pub k i32; pub fn `()`(self &, x i32) i32 { x * k; } }
struct Tally  { pub n i32; pub fn `()`(self &mut, x i32) i32 { n = n + x; n; } }
fn succ(x i32) i32 { x + 1; }

imm off = 10;
imm shift = fn(x i32) i32 { x + off; };
imm t = new Triple(3);
mut tally = new Tally(0);

apply(&shift, 5);              // 15: a closure
apply(&t, 5);                  // 15: a struct with a '()'
apply(&succ, 5);               // 6: a plain function
applyMut(&mut tally, 5);       // 5
applyMut(&mut tally, 7);       // 12, and tally.n is 12

    A plain function needs no state, so a reference to it meets any of the references above. A callable that reads meets &<mut fn as well, since a reference that may change can read.

    A callable that changes its state (its () takes self &mut) is refused behind &<fn(sig), which promises only to read, and the error says so: "&<fn(i32) i32 may only call a callable that reads its state; this closure changes it ... To let it change, the type is &<mut fn(i32) i32." Likewise a &<mut fn is not lent where a &<fn is wanted, nor is a So[fn(sig)], which may change: the callable behind it might. An owner meant to be lent to a reader is made So[imm, fn(sig)].

    A closure literal, lent

    A closure literal written as an argument to a parameter taken by &<fn or &<mut fn is lent as a temporary, dropped at the end of the statement. The permission lent is the parameter's, so a literal given to &<fn that changes a variable is refused by the message above. The literal's parameter types come from the signature:

    apply(x => x * 2, 21);                                    // 42
applyMut(fn(x i32) i32 { total += x; total; }, 10);       // total is changed

    A literal is lent only as an argument. To keep one, move it into an owner.

    An owner of a closure

    new So[fn(sig)](value) takes one value, a closure literal or a struct with a () of the signature, moves it into an allocation of its own, and gives the owner of that as the callable. The literal's parameter types may come from the signature. The same holds for Rc:

    mut owned So[fn(x i32) i32] = new So[fn(x i32) i32](fn(x i32) [mut sum = 100] i32 { sum += x; sum; });
owned(1);        // 101
applyMut(owned, 2);   // 103: an owner is lent as &<mut
run(owned, 3);        // 106: or handed on whole, moved

imm shared = new Rc[imm, fn(x i32) i32](new Triple(4));
imm again = shared;               // another holder of the same closure

    The owner holds whatever the closure holds, and finalizes it when the last owner dies. A closure that holds nothing is allocated like any other. A plain function is wrapped by giving its reference, new So[fn(sig)](&f); a function of another signature, or a value with no () of the signature, is an error.

    An owner outlives the function that made it, so the closure in it may not borrow a local. The refusal is the one in Closures: it names the variable and says to list it, so the closure holds its own copy.

    Naming a signature

    An alias gives a signature a name, and the name works wherever the signature does:

    alias Profile = fn(u i32) i32;

fn viaAlias(f &<Profile, u i32) i32 { f(u); }

    A bare fn(sig) is read as a signature in the brackets of a type (So[fn(i32) i32], Applied[fn(i32) i32]), as the target of an alias and as a generic's bound (Generics). It is not itself the type of a variable or a return value: write &<fn(..), So[fn(..)] or the alias. A signature is a trait, so it has no size, and a field of a generic type holds it by an owner or a reference, not by value:

    struct Applied[F] { pub f So[F]; }     // Applied[fn(i32) i32] holds a So[fn(i32) i32]
    A callable held in a field

    A field that holds a callable is called by its name, with no parentheses around it: b.onClick(5) calls the closure in onClick, and (b.onClick)(5) keeps working. A field and a method of one name cannot both exist, so there is nothing to choose between. A field that cannot be called, an i32 given arguments, is an error that says what the field holds.

    An owner whose state may change is called through a reference that may change, so a method that calls a So[fn(sig)] field takes self &mut, as press does above. The handler is replaced by assigning the field.

    Saying what is behind a reference

    A virtual reference hides the type behind it, so a reference to a callable or a trait is not Sendable or Shareable unless it says so. The markers follow the signature or the trait with a +, So[fn(x i32) i32 + Sendable], and a third, ShapeKeeping, says that a call through the reference reshapes nothing the caller holds a borrow into. All three are described together, with the other rules for what may cross a thread, in Sendable and Shareable.

    A literal that fills a trait

    A closure literal also fills a trait that has exactly one required method, wherever that trait is wanted: as a generic's bound, [S Shape], as a reference, &<Shape, and as an owner, So[Shape]. That is described under Traits.

    A signature as a generic bound

    A function may instead be generic over the signature, [F fn(x i32) i32]. That form is compiled for each closure and inlined, where the references above are compiled once and call through the closure's code (Generics). The reference is what a field or a variable of unknown closure holds; the generic is what a function that only calls it uses.

    Calling a closure while a collection is borrowed

    A call through a mutable virtual reference, a &<mut fn(sig) parameter, is assumed able to reshape any container, because the closure behind it may have captured one. A live view into a container that another path reaches (a &mut parameter, a field of self) is refused across the call (error 1339). A visitor that iterates a list while its closure may push to that list moves the block the iteration reads:

    fn visit[T](xs &List[T], f &<mut fn(x &T)) {
  each x in xs.iter() { f(x); }          // Error 1339: f may push to xs
}
fn grow(list &mut List[i64]) {
  mut push = fn(x &i64) { list.push(*x); };
  visit(list, &mut push);
}

    Lending the list &imm cures it: nothing can write it, so no closure handed in can have captured it by &mut (the caller's list is an imm variable). Marking the closure + ShapeKeeping, or copying what is needed out before the call, also works. A read-only &<fn is not affected.

    fn visit[T](xs &imm List[T], f &<mut fn(x &T)) {
  each x in xs.iter() { f(x); }          // Ok
}
imm nums = numbers();
mut sum = 0i64;
visit(&imm nums, fn(x &i64) { sum += *x; });   // sum is 27 for 1, 5, 9, 12

    A closure, read-only or not, may also write a mut global by its name, so a view into a global is refused across a call of a closure, read-only or not, and across a call of a function that makes one (A borrow into a mut global).

    See Elements of a collection and changing its shape and Virtual References.

    Generators

    A generator is a function that hands its caller values one at a time. It runs until it reaches a yield, gives the caller the value written there, and waits. When the caller asks for the next value it goes on from that yield, with its local variables as they were. It is a function whose result is a sequence, written as the loop that makes the sequence:

    fn count(n i64) yields i64 {
  mut i = 0i64;
  while i < n {
    yield i;
    i = i + 1i64;
  }
}

    After yields comes the type of each value handed out. Calling count(4i64) runs nothing. It gives a value that holds the parameters, and every call of its next runs the body up to the next yield. next gives Some(value) for each value handed out and None once the body ends, by its last statement or by a return, which takes no value:

    mut g = count(4i64);
while true {
  match g.next() {
    case imm v Some { printInt(v); }         // 0 1 2 3
    case is None { break; }
  }
}

each x in count(4i64) { printInt(x); }        // the same, 0 1 2 3

    A loop that leaves early, by break or return, leaves the generator suspended, and it dies there (see Dying).

    The value a generator gives is a struct made for it, of a type no source names. A message that has to spell it writes count.Gen. Since no source can write that type, a function cannot declare a generator as its result or a struct as a field. It is a move type: it is moved, not copied, so two walks of one generator never run. Having next(self &mut) Option[i64], it complies with core's Iterator[i64] as any cursor does, so it is passed to generic code bounded by that trait, or lent as a virtual reference:

    fn sum[S Iterator[i64]](s &mut S) i64 { ... }
fn sumVirtual(s &<mut Iterator[i64]) i64 { ... }
...
mut g = count(4i64);
sum(&mut g);

    A yield is a statement of its own. It stands in a block, or in the arms of an if or match written as statements, and in a loop, but not inside an expression: f(a(), if c { yield 1; 2; } else { 3; }) would have to keep the value of a() across the wait, and is refused. Compute it into a variable first.

    Yielding another generator's values

    yield each hands on every value of another generator, or of anything with a next, in turn, and goes on when they are all handed on. It joins sequences, and it makes a recursive walk as short as the recursion:

    fn joined(a i64, b i64) yields i64 {
  yield each count(a);
  yield 99;
  yield each count(b);
}

// In order, a tree kept in an array
fn inorder(nodes &Array[Node], at usize) yields &Node {
  imm n = &nodes[at];
  if n.left >= 0 { yield each inorder(nodes, usize.from(n.left)); }
  yield n;
  if n.right >= 0 { yield each inorder(nodes, usize.from(n.right)); }
}

    The generator being handed on is kept in the one that hands it on, in its own storage, when its size is known. A generator that hands on one of its own kind, as inorder does, would have to hold itself, so that one is kept on the heap, one for each yield each that needs it, made when the walk begins and freed when the generator dies. A value handed on is the sub-generator's own Some(value): it is moved up, not copied. Each value costs a step through every generator that hands it on.

    Generator methods

    A method may be a generator, called as any method is. In its body self is the receiver, exactly as in any method. The generator holds the receiver as it holds a parameter, so what the receiver was lent as keeps it lent for as long as the generator lives:

    struct Tree {
  nodes Array[Node, 7];

  fn walk(self &) yields &Node {            // in order
    yield each self.from(0);
  }

  fn from(self &, at usize) yields &Node {
    imm n = &self.nodes[at];
    if n.left >= 0 { yield each self.from(usize.from(n.left)); }
    yield n;
    if n.right >= 0 { yield each self.from(usize.from(n.right)); }
  }
}

each n in tree.walk() { printInt(n.val); }
    • A receiver borrowed with self & may be read, not changed, while the generator may still be resumed; one borrowed with self &mut may be neither read nor changed. The generator may change what it was lent, and may hand out borrows of it, yields &mut i64 among them. The borrow lasts until the generator dies, not until it is last called: a block around the generator ends it.
    • A receiver taken by value, fn run(self) yields i64, moves into the generator and dies with it, after its locals. As with any parameter, the body may borrow or copy it (and change it, if declared mut self), not move it out.
    • Self in the body is the type the method belongs to.
    • A bare name that is a field of the receiver's type means self.name, as it does in any method, unless a local or a parameter of the generator is named so, which shadows it. A bare name of a method of the type is refused: write self.name().
    • A function of a type with no receiver, fn range(from i64, to i64) yields i64, is a generator too, called as Span.range(3, 7).

    The method that makes the generator is the one written; the struct that is the generator is made beside the type and has no name in source (a message spells it Tree.walk.Gen). A method of a trait or of an enum cannot be a generator, since a trait's methods are copied into each type that implements it and an enum's into each of its variants; nor can an actor's, or a method of a type that declares lifetimes. Write a function that takes what the method would.

    Generic generators

    A generator may be generic, a function over a type or a method of a generic type or both. The struct that is the generator takes the type parameters, with their bounds as written, so each use is a generator of its own kind, made for the types it was called with, and checked as any generic is, where it is used:

    fn items[T](l &List[T]) yields &T { ... }

struct Bag[T] {
  all List[T];
  fn backward(self &) yields &T { ... }
}

each x in items(&ints) { ... }      // a generator over i64
each p in items(&points) { ... }    // another, over Point
each p in bag.backward() { ... }

    A generic generator may hand on another, itself included, with yield each, and a recursive one keeps its sub-generator on the heap in each instance as a plain one does. A type parameter of a generator does not name lifetimes ([T + 'a]) yet.

    Generators across packages

    A pub generator of a package, a function, a method or a method of a generic type, can be walked from another package as it is from its own. The struct that is the generator, and the frame that holds its locals across a yield, are made from its body, so the package's include file carries the generator's declaration whole, as it carries an inline or a generic function, and the importer makes the struct again from it. What the body names in the package, a private type, a private function or another private generator, is declared beside it and exported. A generator that is not pub stays inside the package, unless a body the include file carries names it; neither it nor the private names only it uses are in the file, and no other package can name them.

    Borrows across a yield

    A yield leaves the body, and the generator, a value, may be moved by its caller before it is resumed. What the body keeps across a yield is held in the generator's value, so:

    • A borrow of what the generator was lent, a parameter that is a reference, lasts across it. So does a copy of any value.
    • A borrow of one of the body's own local variables, or of a parameter the generator holds by value, does not last: it ends at the yield, and it is an error to use it after. The error names the yield.
    • What a yield hands the caller may borrow only what the generator was lent. It is a borrow of that, not of the generator, so a caller may keep a value handed out for as long as the generator lives, several of them at once.
    • So the body holds each borrow it has handed out, from the yield to the end of the body, as if a variable of its own held it. It may go on reading what it lent, or change another part of it, but it may not change the thing the borrow points into, or call anything that could change the shape of the collection it points into (a push or a clear on a list). The error is at the change. Copy the value to hand it out, or hand out the borrow once the body has done changing what it borrows.
    fn words(text &str) yields &str {   // each word borrows the text
  ...
  yield &text[start ..< i];
  ...
}

fn grows(xs &mut List[i64]) yields &i64 {
  yield xs[0usize];
  xs.push(1i64);   // ERROR: the caller may still hold the borrow just yielded,
                   // and the push could move the list's elements
}

fn bad(k i64) yields i64 {
  mut x = 5i64;
  imm r = &x;
  yield k;      // ERROR: r borrows a local, which cannot last across this yield
  yield *r;
}

    The parameters are held in the generator, and the body names them as a method names its fields. It may borrow or copy one, or change one declared mut, but it may not move one out. A parameter lives as long as the generator does, not as long as the body, and dies after the locals.

    Generators: leaving early, and two-way yield

    Dying

    The locals of the body die as they would in a function, in the order they were declared, last first, where the body ends. A generator that dies while it waits at a yield finalizes the locals it holds there, in the same order, and then its parameters. One never run holds only its parameters. A local moved on some paths only is finalized only if it still holds its value, as anywhere.
