Cone
Actors in depth

Note: The actors package runs on Windows and Linux (x86-64), not yet on macOS. Not built yet: a generic actor, and a queued method on a message type.

The Guide's bakery gave each part of a program an actor of its own, and let them talk. Building something real raises the questions the tour skipped: when is an answer sent back, when does an actor wait, how is one made and when does it die, and what may it hold? This page has the whole of it. Afterwards you can design an actor's behaviours, its start and its end, knowing exactly what each one costs. It begins with the four shapes a behaviour can take, all in one program:

mod shapes;

import stdio use *;
import actors;

actor Store {
  total: u64;

  // Fire and forget: no return type, no await
  pub async fn add(self, k: u64) {
    total = self.plus(k);
  }

  // A cheap query: a return type, no await
  pub async fn count(self) u64 { total }

  // Synchronous: an ordinary call, inside the actor
  fn plus(self: &, k: u64) u64 { total + k }
}

actor Client {
  store: Store;

  // Awaits, owes nobody: an await, no return type
  pub async fn run(self) {
    store.add(5u64);
    store.add(7u64);
    let c = await store.count();
    print <- "count ", c, "\n";
    let r = await self.report();
    print <- "report ", r, "\n";
  }

  // The full handshake: an await and a return type
  pub async fn report(self) u64 {
    let c = await store.count();
    c * 10u64
  }
}

fn main() {
  let client = Client(Store(0u64));
  client.run();
}

It prints, on every run:

count 12
report 120

Try this: move store.add(7u64) to after the await in run, and predict the count before you run it.

Four shapes of behaviour

Two things about a behaviour are independent, and each decides one thing. Whether it declares a return type decides whether an answer is sent back; whether it holds an await decides whether it may pause partway. So every behaviour has one of four shapes, and you can tell which from its declaration alone:

  • Fire and forget: no return type, no await. It runs once and ends; nothing is sent back, and nothing waits. The cheapest shape, and Store.add's.
  • A cheap query: a return type, no await. It runs once and answers with its value as it ends, to a caller that awaited it: Store.count.
  • Awaits, owes nobody: an await, no return type. It waits for other actors' answers, and answers no one: Client.run.
  • The full handshake: both. It waits for answers, then answers with its own value: Client.report, which run awaits in turn.

The count is 12 every time, never 5 or 0, because one sender's messages to an actor are handled in the order they were sent: both adds reach the store before the count does. Choose the cheapest shape that does the job. An answer costs a message back, and an await costs a pause, which Awaiting and futures takes apart in full.

Behaviours and synchronous methods

A method declared async fn is a behaviour: it runs asynchronously, when the actor is scheduled, and an await on one waits for its answer. async says when the behaviour runs, and pairs with await; fn is the declaration's verb, as it is a function's. async means nothing alone, and written without fn it is refused:

Error 1273: 'async' means nothing alone: an actor's behaviour is declared 'async fn name(self, ...)'.

A behaviour never starts on the sender's thread, as an asynchronous function may in some designs: a send only queues the message, so no thread but the one running the actor ever touches its state.

Synchronous methods

A method declared fn is synchronous: the actor's init and final, and any helper, such as Store.plus. It sees the actor's fields directly and runs inside the method that calls it, as a struct's method does. It is the actor's alone: never pub, and not carried by the handle. It holds no await. An await belongs at the top of a behaviour, and the synchronous work between awaits is pushed down, onto a helper or onto a type the actor owns (Await only in a behaviour).

The declaration

An actor is declared with actor, in a module that imports the actors package: the mailbox, the work-stealing scheduler, the counting that decides when an actor dies, and the quiet the program ends at. Its body is written as a struct's: fields, an init, behaviours, synchronous methods, a final:

actor Counter {
  count: u64;                       // its state: private to it

  fn init(self: &new, start: u64) {  // run by 'Counter(start)'
    *self = Self(count: start);
  }

  pub async fn add(self, n: u64) {  // a behaviour: sent as a message
    count = count + n;
  }

  pub async fn report(self: &, to: Printer) {   // carries another actor's handle
    to.show(self.doubled());
  }

  fn doubled(self: &) u64 {         // synchronous: called, inside the actor
    count * 2u64
  }

  fn final(self: &uni) {}           // when it dies
}

actor Printer {
  pub async fn show(self, n: u64) {
    print <- "doubled: ", n, "\n";
  }
}

fn main() {
  let c = Counter(0u64);       // the first actor starts the workers
  c.add(5u64);                     // a message: queued, and run later
  c.add(7u64);                     // run after the first
  c.report(Printer());         // prints doubled: 24
}

The rules of the declaration:

  • The fields are the actor's state, private to it: a field is never pub, and nothing outside the actor reaches one.
  • A method's self is the state, lent to a behaviour for the message it handles, and to a synchronous method by its caller. Written bare, it is self: &uni, which the method has alone while it runs, so it may lend a part of the state on as &uni. A weaker permission may be written instead: self: & (only reads it), &mut, &imm or &opaq. A method written with a weaker self cannot call a synchronous helper whose self is bare: give the helper the weaker permission too.
  • A behaviour that is not pub is a message all the same, which only its own module sends. A function without self is the actor's own, called from its methods as a struct's is.
  • A behaviour is not generic, and every parameter it takes is Sendable, since the message carries its arguments to the thread the actor runs on (What may cross a thread). A borrow is refused, unless it lasts the whole program, is written so (&'static imm T, &'static opaq T or &'static uni T) and reaches what may cross (A borrow that lasts the whole program). The refusal says what to pass instead: 
    Error 1194: Actor A's behaviour take takes r, a borrowed reference, which is not Sendable: no borrow may leave
its thread. A message carries its arguments to the thread the actor runs on; pass an owner that may cross, such
as a 'uni' one, or an 'Arc', or a borrow that lives for the whole program, written &'static imm, &'static opaq
or &'static uni.
  • A behaviour may return a value, which must be Sendable too, by the same rule, so a borrow in it is written 'static as a parameter's is. A plain send returns at once, before the behaviour runs, and the value is dropped, unless the behaviour was awaited or its future kept (Awaiting and futures).
  • An actor declares no static, macro, extern method or use, no type parameters, and names no abstraction. An actor conforms to an actor trait, its abstraction, by having the behaviours, with nothing written on the actor.

Making an actor

Counter(args) makes an actor and answers its handle. The actor is real before its init runs: the runtime's part of it is made first, and the init then runs, on the calling thread, on the state where it will stay. So the init, and any synchronous method it calls, may send to the actor itself, once *self = ... has filled the state. Before that, self holds nothing, and every use through it is refused, as in any initializer; after it, a send may stand anywhere, in an if, a loop or a match arm too, and the init may hand selfactor to another actor. The actor runs no message until its init has returned: a message sent meanwhile, by the init or by another actor already given the handle, waits in the mailbox and runs afterwards, in the order sent:

actor Starter {
  count: u64;

  fn init(self: &new) {
    *self = Self(count: 0u64);
    self.note(1u64);              // a send to itself: queued, run after the init
    self.helper();                // a helper the init calls may send too
    print <- "init ends ", count, "\n";
  }

  fn helper(self) {
    selfactor.note(2u64);
  }

  pub async fn note(self, k: u64) {
    count = count + k;
    print <- "note ", count, "\n";
  }
}

Starter() prints:

init ends 0
note 1
note 3

Both notes wait until the init has returned. A panic in the init is a panic, which ends the program.

The initializer's parameters must be Sendable too, since the state made from them runs on other threads. An actor may declare several initializers, as a struct may, each joining the overload name init. One that declares none is made by its state's implicit initializer, as the bakery's were: Store(0u64) takes the fields whose types are written, in order, a field with a default taking it where the argument is left out. That initializer is the module's own, as a struct's implicit one is where its fields are private, except for a pub actor with no fields at all. There is no other way to make an actor, and no creation function: spawn stays reserved.

The handle

The actor's name names its handle: a value holding one counted owner of the actor's mailbox, the runtime's part of it. Copying a handle (passing it, storing it, putting it in a message) makes another owner, and each going drops one. A handle carries the actor's behaviours and nothing else: calling one on it, c.add(5u64), sends that message, and reaching a field of the state or a synchronous method through it is refused as private. A handle is Sendable whatever the state holds: it may be sent to a thread, over a channel, in another actor's message, or kept in another actor's state. So the state may hold what may not cross threads (an Rc, a mut owner, borrows inside a method), since it never crosses as a value: only the runtime reaches it.

Actor traits: sending to whichever actor

A function that sends a chunk to "anything that accepts chunks" does not want to know which actor that is. An actor trait says what a sender needs, as behaviours and nothing else:

actor trait ChunkSink {
  pub async fn accept(self, c: Chunk);
  pub async fn total(self) u64;
}

It declares signatures only. An actor has no fields a caller outside it can read and no code a caller can run inside it, so a field, a fn and a body are refused, and each behaviour is pub, since a sender is outside the actor. The module declaring the trait imports actors, as for an actor.

Conformance is structural. An actor conforms to the trait where it has each of its behaviours, pub, by name, with the same parameter types and the same returned type. It writes nothing for it, and may have more: a fake with the same behaviours conforms with no declaration, and so does an actor written before the trait was. It is checked where a handle is converted, and the error names what is missing:

Error 1570: Actor Mute does not conform to actor trait ChunkSink, which it is converted to here: It has no behaviour
'pub async fn accept(c: Chunk)'. It has no behaviour 'pub async fn total() u64'. An actor conforms when it has every
behaviour of the trait, declared 'pub', under the same name, with the same parameter types and the same returned type.

The trait's name is a type, as an actor's is, and a value of it is a handle that holds any conforming actor. An actor's handle given where the trait's is wanted (an argument, a let with the type written, a field's value, a return) is converted, with nothing written at the conversion:

fn feedAll(sinks: &List[ChunkSink], n: u64) {
  each sink in sinks.iter() { sink.accept(Chunk(n)); }
}

let counter = Counter();
let doubler = Doubler();                  // another actor, with the same two behaviours
var sinks = List[ChunkSink].empty();
sinks.push(counter);
sinks.push(doubler);
feedAll(&sinks, 5u64);

The handle is two words: a counted owner of the actor's mailbox, copied and dropped as an actor's handle is, so it keeps the actor alive; and a pointer to the table of the actor's own sending methods for the trait, one table for each actor and trait, made where the conversion is. A call through the handle is the same call as a direct one with one more indirect jump, and has the same four shapes: sink.accept(c) sends, let t = sink.total() keeps the future, await sink.total() waits for the reply, and a plain sink.total(); drops it (Awaiting and futures).

Two handles are equal where they name the one actor: == compares the mailboxes. That is how a subscriber is removed from a list of them, and it holds for an actor's own handle as well; it is not a comparison of values, so a handle made twice from the same actor is equal to itself.

"Whoever asked" is a parameter. An actor trait of one behaviour is a reply address. Cone has no callbacks: a one-off answer is a behaviour's return, and anything the answerer should send back, more than once or to someone else, is an ordinary message to a handle it was given:

actor trait ReadDone {
  pub async fn done(self, n: u64);
}

actor Reader {
  pub async fn read(self, f: File, reply: ReadDone) { ... reply.done(n); }
}

Reader sends to reply without knowing what it is; a test can pass a fake, and another actor can be passed along to answer in its turn. A handle is Sendable and may be passed in a message, kept in another actor's state or put in a list; it keeps its actor alive, so a list of subscribers that should not hold them is not what an actor trait gives yet.

A generic actor trait

The trait may take type parameters, and each type of event, message or answer it is used at is an instance of it, as for any generic type, with a handle and a table of its own. The actors that conform are not generic (a generic actor is still refused); they conform to the instance their behaviours' types make:

actor trait Subscriber[Event] {
  pub async fn hear(self, e: Event);
}

actor Tally  { pub async fn hear(self, e: Click) { ... } }     // a Subscriber[Click]
actor Typist { pub async fn hear(self, e: Key)   { ... } }     // a Subscriber[Key]

let clicks: List[Subscriber[Click]] = ...;   // a Tally and a Clicker in one list
let keys: Subscriber[Key] = typist;
let bad: Subscriber[Key] = tally;            // Error 1570: ... put(e: Click) does not take and return
                                             // what the trait's hear(e: Key) does

What an await through a handle of an instance gives is the instance's type.

As a bound: no table

An actor trait may bound a type parameter, [S: ChunkSink] or [S: Subscriber[Click]], and an actor that conforms meets the bound, as does the trait's own handle. A generic function is made for the type it is given, so it calls that actor's own methods directly: no handle is made, no table, and no indirect call. A pipeline whose stages are fixed when the program is compiled pays nothing for the abstraction.

fn connect[S: ChunkSink](s: S, n: u64) {
  s.accept(Chunk(n));          // for a Counter, a call of Counter's own accept
}
connect(counter, 10u64);       // not connect(counter as a handle): none is made

An actor that does not conform given to such a parameter is refused, as for any bound (connect requires S is ChunkSink, and Mute is not ChunkSink). Convert it to the trait's handle, where the error names what it lacks.

Messages and their order

A send is one-way: it queues the message and returns. An answer comes back only to an await (Awaiting a behaviour's answer), or as a message sent back to a handle passed along, as report sends show to the printer above. Each sender's messages to one actor are handled in the order sent, and a message is never overtaken by one it caused. Messages from different senders interleave in whatever order they arrive, which is why the Guide's bakery could not say which customer would go short.

Each argument arrives moved into the behaviour's call, once. A value that may only move (a uni or Uni owner) arrives whole, and a counted one (a handle, an Arc, a lock-managed Arc[Mutex, T]) is counted once.

An actor's life

The actors package starts and stops by itself. The first actor made starts the worker threads, and when main returns, the module's finalizer waits until all is quiet, then stops them (How the runtime works has the details).

While an actor is queued to run, or running, the scheduler holds one owner more, taken by the send that found it idle and dropped when its mailbox is found empty. So an actor dies exactly once, when its last handle has gone and its mailbox is empty. A handle dropped with messages still queued leaves the actor alive until they are handled. At its death its state is finalized (its final, then its fields, handles to other actors among them), on whichever thread let go last, then the block is freed. Actors that hold handles to each other in a cycle never die by counting, as a cycle of Arc owners never does, until one of them lets go.

self and selfactor

An actor has two selves. self is its state, lent to the method while it runs; it never leaves the actor. selfactor is its handle: another owner of the actor, a value that may go anywhere a handle may: into a message, into another actor's state, or to an await on one of its own behaviours:

actor Doubler {
  pub async fn double(self, n: u64) u64 { n * 2u64 }

  pub async fn twice(self, n: u64) u64 {
    let once = await selfactor.double(n);  // a message to itself
    let again = await selfactor.double(once);
    again
  }
}

await doubler.twice(5u64) is 20. Each double is queued in the doubler's own mailbox, and runs because twice has paused and the actor is free. selfactor may be written in any of the actor's methods, its init among them once the state is filled, but not in its final, nor anywhere outside the actor.

Sending to itself

In the actor's own methods, self.m(args), where m is one of its behaviours, sends m to the actor itself, as selfactor.m(args) does: the message joins the end of the actor's own mailbox, the method goes on at once, and m runs later. A behaviour is never called, not even by its own actor: it runs only when its dispatcher takes up a message for it. A synchronous method is called, as a struct's is:

actor Echo {
  pub async fn start(self) {
    print <- "start\n";
    self.later(1u64);             // a send to itself: start goes on at once
    self.relay();                 // a synchronous helper, an ordinary call
    print <- "start ends\n";
  }

  async fn later(self, k: u64) {
    print <- "later ", k, "\n";
    if k == 2u64 {
      self.finish();
    }
  }

  fn relay(self) {
    later(2u64);                  // 'self.later(2)': a send, from a helper too
  }

  async fn finish(self) {
    let d = await self.double(21u64);
    print <- "finish ", d, "\n";
    self.show(d / 2u64 - 11u64);
  }

  async fn double(self, k: u64) u64 { k * 2u64 }

  async fn show(self, k: u64) {
    print <- "show ", k, "\n";
  }
}

Sent echo.start(), this prints:

start
start ends
later 1
later 2
finish 42
show 10

Both lines of start come before either later runs. await self.double(21u64) is a send and an await, as through selfactor, never a call run at once. A behaviour reached through anything but the method's own self (another borrow of a state, a parameter's, say) is refused, and so is one sent through self in the actor's final, as it dies. In its init it is a send like any other, run once the init has returned (Making an actor).

Private state

The state exists only inside its actor, and the compiler keeps it there. It is constructed in one place, as the actor is made, where its init fills it, *self = Self(count: 0u64). Any other construction of it, Self(...) in one of the actor's methods or as an allocation's value, by its fields' names or by its init, is refused, since the state it made would be in no actor, and the sends it or a helper made to its actor would reach nothing. Nor is the state copied out of its actor: it is a move type whatever its fields are, so let s = *self is refused, as taking any value out through a borrow is. And nothing outside reaches a field through the handle:

actor Keeper {
  count: u64;

  pub async fn start(self) {
    var s = Self(count: 5u64);    // refused: a state in no actor
  }

  pub async fn peek(self) {
    let s = *self;                    // refused: the state is not copied out
  }
}

fn main() {
  let k = Keeper(0u64);
  let n = k.count;                    // refused: private state
}

Error 1290: Actor Keeper's state exists only inside its actor, so it is constructed only as the actor is made
('Keeper(...)'), where its init fills it, '*self = Self(field: value)'. Constructed here, it would be a
state in no actor, and a send it made to its actor would reach none. For a value of this shape, declare a plain
struct.
Error 1120: May not move a value out through a borrowed reference, which does not own it.
Error 1042: `count` is part of actor Keeper's private state, which only its own methods reach, one message at a
time. Send it a behaviour that uses it.

For a value of the state's shape, declare a plain struct.

Inside an actor

A method of an actor may use what a single thread may: borrows, and Uni and Rc owners, whose count need not be atomic, since one worker at a time runs an actor and every hand-off of an actor between workers orders what the first did before anything the next does. Three things differ from a plain thread:

  • The collector package's Gc is not supported inside an actor (it is discouraged everywhere, and likely to be replaced). That collector is single-threaded, and an actor runs on every worker in turn, so a traced reference made, held, reached or dropped by an actor would corrupt it. The compiler refuses one made or held in an actor: a field of its state, a synchronous method's parameter, an allocation, a call that returns one, or a literal holding one in any method's body, init and final included, and a struct, tuple, array or enum holding one as well. The message says what to do instead: 
    Error 1389: A traced reference (a Gc, for example) cannot be used inside an actor or a parallel each: this makes
a Gc[mut, u64], which a collector traces, inside an actor's method. That collector's one chain of roots and its
heap are process globals, not safe on the threads an actor or a parallel each runs on. Use Gc only in code that
runs on a single thread; in an actor, allocate with 'new self[T](...)' and hold an ActorGc (the actors
package's), which the actor collects between its messages.
    An actor has a garbage-collected region of its own, whose references it makes, holds and copies freely (The actor's own garbage-collected region).
  • A thread-local global seen from an actor's method is the current worker's copy, not the actor's: its next message may run on another worker.
  • A method that blocks holds its worker while it does. Actors wait by being sent a message, or by awaiting: for another actor's answer, or for I/O.

What the declaration stands for

Underneath, the compiler turns an actor into four ordinary declarations, which the actors package runs:

  • The state, a struct of the body as written, named Counter.State.
  • The messages, an enum with one variant per behaviour, named for it, its fields the behaviour's parameters, named Counter.Msg.
  • The handle, Counter, whose one field is an Arc[opaq, actors.Mailbox[Counter.Msg]]. It has an initializer for each of the state's, which makes the actor's block with actors.makeActor, constructs the state in it in place, and starts the actor with actors.startActor; and a method per behaviour, as public as the behaviour, which calls actors.send.
  • The dispatch function, Counter.dispatch, which the runtime hands each message where it lies, and which moves each argument out of it into the behaviour's call.

An actor trait stands for four declarations too: an ordinary trait with the three methods an actor's handle has for each behaviour (the send, and for one that returns a value the awaited send and the future-giving one); the trait's handle, whose fields are the mailbox, its type erased, and the table; and a function that makes the handle from a reference to an actor's. The table is the compiler's ordinary vtable of the actor's handle as that trait, one for each actor and trait, whose slots are the handle's own methods that send.

Those names are what a diagnostic about them says; no source can write them, so nothing but the actor reaches its state, its messages or its mailbox. The mailbox's header and the state are one allocation; the mailbox's slots are in segments of their own, the first allocated with the actor, and a send allocates nothing. Actors and the declarations that use them may be written in any order: a message enum holds handles by value, a handle reaches the enum only through its owning reference to the mailbox, and a reference never needs what it points at to be laid out first.

You can now choose each behaviour's shape, make an actor and know when it dies, and keep its state its own. Some work is not a standing role at all but one big loop; next, the parallel each that runs it, in full.
