Cone
Function references, closures and generators: behaviour as a part

Sometimes the part you want to swap is not a type but a piece of behaviour: the order a sort uses, what a button does when it is pressed, the next value of a sequence. At the function's layer the interface is a signature, and anything that can be called that way may stand in. This page covers the ways Cone lets behaviour be handed around as a part: function references, closures that carry state, closure references that take any callable of a signature, and generators, functions whose result is a sequence. Afterwards you can write code that takes its behaviour from its caller, and choose how that behaviour is held and called.

mod behaviour;

import stdio use *;

// A function reference: any function of this signature will do
fn twice(f &fn(x i32) i32, x i32) i32 {
  f(f(x));
}
fn inc(x i32) i32 { x + 1; }

// A closure reference: any callable of the signature, whatever state it carries
fn sumOf(f &<mut fn(x i32) i32) i32 {
  f(1) + f(2) + f(3);
}

// A generator: a function that hands out a sequence, one value at a time
fn evens(n i32) yields i32 {
  mut i = 0;
  while i < n {
    yield i * 2;
    i += 1;
  }
}

fn main() {
  print <- "twice inc: ", twice(&inc, 5), "\n";

  mut calls = 0;
  imm total = sumOf(fn(x i32) i32 { calls += 1; x * 10; });
  print <- "sum: ", total, " in ", calls, " calls\n";

  each e in evens(4) {
    print <- e, " ";
  }
  print <- "\n";
}

It prints:

twice inc: 7
sum: 60 in 3 calls
0 2 4 6

Try this: give sumOf a struct with a () method of the same signature instead of the closure. sumOf does not change.

This is subtyping at the function's layer (Subtyping): the signature is the interface, and the parts are settled while the program runs, through a reference. The same signature may instead be a generic constraint, settled when the program is compiled, which is on the next page.

Function references: any function of a signature

Note: This is implemented: borrowing a reference to a named function, holding one in a variable, passing it to a parameter that spells out its signature, with the signature's parameters named or written as their types alone, calling through it, writing an anonymous function where the reference is wanted, and giving it a closure that holds and borrows nothing.

At the function's layer, the interface is a signature, and the subtypes are the functions that have it. A function reference lets part of some code's logic be done by any of several compatible functions, chosen while the program runs. The ampersand borrows a reference to any function:

fn incr(nbr u32) u32 {
  nbr + 1;
}

// The parameter's type is the signature it takes
fn dostuff(fnref &fn(u32) u32) u32 {
  fnref(4);         // Call the function
}

imm fnref = &incr;  // points to the function incr
dostuff(&incr);     // 5

As with any borrowed reference, a function reference may be copied between variables and functions. It carries no lifetime restrictions, as there is no risk of a global function going away. Its type is its signature. Its parameters may be written as their types alone, as here, or with names, as in &fn(nbr u32) u32: only the types are part of the type, so either spelling accepts a reference to incr. Its permission is opaq, the default and the only one permitted, which allows no dereference at all, so the function's code can be neither read nor changed through it.

A function-reference parameter may stand anywhere in a parameter list. Inside a list in parentheses (a function's parameters, or a function type's own) a function type's return type ends at the comma, which goes on to the next parameter. A function type there that returns several values writes them as a tuple, in parentheses:

fn combine(f &fn(u32) u32, g &fn(n u32) (u32, u32), x u32) u32 {
	mut a u32;
	mut b u32;
	a, b = g(f(x));
	a + b;
}

// A field whose function takes another function and a u32
struct Applier {
	pub run &fn(&fn(u32) u32, u32) u32;
}

Outside a list, as a field's or a variable's whole type, a comma after the return type adds another return type, as it does on a function's own signature: a field typed &fn(u32) u32, u32 holds a function returning two values.

A function reference is one code address, so it takes only a function: no state travels with it. Something that should take a function, a closure that carries state, or any struct with a () method of the same signature asks for one of two things instead:

  • a closure reference, &<fn(u32) u32 (or &<mut fn(u32) u32 where the callable may change its state), which is compiled once and calls through the reference; a reference to a plain function, &incr, is accepted where one is wanted;
  • the signature as a constraint, fn sortBy[T, F fn(a &T, b &T) i32](xs &mut Array[T], order &F), which is compiled for each type it is given and is given &byName, a closure, or a struct (A function signature as a constraint).

The one-word &fn(sig) stays what it is, and is what another Cone function taking a function takes. A C library's callback parameter takes the reference to a C-named function instead, &fn @c (sig).

Anonymous functions

When the function you want a reference to is small, it may be written right where the reference is wanted, with no name:

dostuff(&fn(nbr u32) u32 {nbr+1;});      // 5
dostuff(&fn(nbr u32) u32 {nbr+nbr;});    // 8

An anonymous function is a function that happens to be written in place. It is made at the module level, so it sees none of the variables around it, and it is the same function every time. A closure literal, written without the ampersand, fn(nbr u32) u32 {nbr+1;} or nbr => nbr+1, may name those variables. Given where a function reference is wanted, a closure that holds and borrows nothing becomes a plain function reference, so either spelling works for such a case:

dostuff(fn(nbr u32) u32 {nbr+1;});    // a closure, here a plain function
dostuff(nbr => nbr+nbr);              // the parameter's type comes from the signature

A closure that does name a variable of the code around it cannot be a function reference, which has no place to keep it, and is refused there: "This closure borrows step, so it is not a function and cannot be given where a function reference, '&fn(...)', is wanted: only a closure that holds and borrows nothing is one." The parameter is then declared &<fn(u32) u32, a closure reference.

A reference to a C-named function

A Cone function and a C-named one (an extern function C defines, a fn @c, a function of an @c module) are called differently: C passes a struct by value in registers or through a pointer as its ABI says (Structs by value), and Cone keeps its own convention for its own functions. So the calling convention is part of a function reference's type. A reference to a C-named function has the type &fn @c (Vec3) f32, marked as fn @c marks a function; a reference to a Cone function is the plain &fn(Vec3) f32. In a declaration a name always follows the attribute, and in a type it never does, so in a type a ( after @c opens the parameters: the type's @c takes no arguments. If a second C convention is ever needed, it gets its own attribute name, not @c(...) arguments in a type; &fn @c(system) is not a spelling.

struct Vec3 { pub x f32; pub y f32; pub z f32; }

extern fn @c vec3_len(v Vec3) f32;          // defined by C
fn @c doubled(v Vec3) f32 { v.x * 2.; }     // a Cone function C may call
fn sum(v Vec3) f32 { v.x + v.y + v.z; }     // Cone's own

fn doit(v Vec3) {
  imm a &fn @c (Vec3) f32 = &vec3_len;     // a C-named function's reference
  imm b &fn @c (Vec3) f32 = &doubled;      // so is this
  imm c &fn(Vec3) f32 = &sum;              // a Cone function's
  a(v);                                    // called as C passes a struct
  c(v);                                    // called as Cone does
}

Neither converts to the other, and there is no thunk to bridge them: giving one where the other is wanted, in an initializer, an assignment, an argument, a returned value or a struct's field, is a compile error, so a call through a reference never passes its values the wrong way. A C library's callback parameter is typed &fn @c, and the Cone function handed to it is written fn @c; handing C a plain Cone function is refused:

extern fn @c c_apply(n i32, f &fn @c (Vec3) f32) f32;   // C calls f

fn @c scale(v Vec3) f32 { v.x * 3.; }      // C-named, so C may call it
fn twice(v Vec3) f32 { v.x * 2.; }

fn doit() {
  c_apply(1, &scale);      // fine
  c_apply(1, &twice);      // ERROR: a Cone function, where a C-named one is wanted
}

Error 1503: `&fn(Vec3) f32` is a reference to a Cone function, and `&fn @c (Vec3) f32`, a C-named
function's, is wanted. C would call it in C's convention, which passes a struct differently from Cone's, so
its values would arrive wrong, and neither converts to the other. Make the function C-named,
`fn @c name(...)`, or put it in an `@c` module.

A closure has no C form, so it is never @c, and an anonymous function with a body has no name for @c to give C spelling to. A type's method keeps Cone's convention even when @c names its symbol (a vtable calls it by its Cone signature), so a reference to a method is a plain &fn. A closure reference (&<fn, So[fn]) calls what it holds in Cone's convention, so a C-named function's reference is not accepted where one is wanted: call the C function from a Cone function and make that the callable.

Closures: functions with state

Note: Closures are implemented, except a closure that calls itself, and calling a closure once and consuming it (a body that moves one of its state entries out). For closure references, calling a closure once, which consumes it, through an owner, and + joining any trait but the markers Sendable, Shareable and ShapeKeeping, are not built.

A function reference carries no state, and a function written in place sees nothing around it. A closure is the function that does: a function that keeps its state from one call to the next, and may use the variables of the code it is written in. Functions introduces closures; this section has their rules, and the next the references that take any closure of a signature. Closures are useful for:

  • the steps a cursor's chain applies to each item (map, filter, fold), written once as the methods every cursor declaring is Iterator[T] shares (adapters); a source that runs its own loop around the body of an each is not built yet;
  • sequences handed out one value at a time, though a generator needs no closure;
  • event-triggered callbacks, whose state guides what happens after an event;
  • function-valued inputs of a library, such as the profile a sweep follows or the order a sort uses, whose numbers belong to the caller rather than to a fixed function.

Writing one

A closure is written where it is used, in the body of a function, in one of two forms.

The full form resembles a function definition, with three differences: the name is left out, the return type may be left out (and inferred), and the state the closure carries may be listed in square brackets after the parameters: fn (parameters) [state] returnType { body }.

mut counter = fn(n i32) [mut cnt = 0] { cnt += n; cnt; };
counter(1);        // 1
counter(2);        // 3

This closure takes one parameter, n, and infers that it returns an integer, since its last expression is cnt, an i32. The state list holds the variables the closure owns. Each entry is a field of the closure, written as a field is: a name with an initial value, cnt = 0, whose type is the value's. Entries are separated by commas. An entry is imm unless written mut, so a closure that changes its state lists it mut. The list may be left out. The brackets sit after the parameters because a bracket never begins a type, so they cannot be taken for the return type.

A parameter's type may be left out where the closure is given to something that says what the signature is (fn(x) { x + off; }, below); nothing else may leave a type out. Three places say it: a parameter taken by &<fn(sig) or &<mut fn(sig) (a closure literal, lent), a generic parameter bound F fn(sig), and new So[fn(sig)](...) (an owner of a closure). A parameter of type So[fn(sig)] does not: it takes an owner, and a closure literal is not one, so a literal given straight to it is refused (for an untyped one, error 1391, "The type of a is not written, and nothing here says what it is"). Wrap it: c.set(new So[fn(a i64, b i64) bool]((a, b) => a < b)). An imm given an untyped closure is refused the same way, even where the imm is written with a &<fn(sig) type.

The short form, for a small closure, puts the parameter names, an arrow, and the body: x => x * 2, (a, b) => a.len() < b.len(), () => 5, n => total += n. It takes parameter names only, whose types come from the signature the closure is given to, and a body that is one expression, an assignment, or a block. It has no state list and no written return type; a closure that needs either is written in the full form. A comma after the body belongs to the list the closure is in, so f(x => x + 1, 3) is a call with two arguments. The arrow is =>, not ->, which would read as "returns".

fn apply(f &<fn(x i32) i32, x i32) i32 { f(x); }

imm off = 10;
apply(x => x * 2, 21);                     // 42
apply(fn(x i32) i32 { x + off; }, 1);      // 11
apply(fn(x) { x + off; }, 1);              // 11: the type comes from the signature

What a closure captures

A closure's body may name variables of the function around it. Each one it names is borrowed: the closure holds a reference to it, & where the body only reads it and &mut where the body changes it, and the compiler works out which from the body. The variable around shows the change:

mut total = 10;
mut add = fn(x i32) { total += x; };   // borrows total as &mut
add(3);
add(4);
total;                                 // 17

Only a mut variable can be changed by a closure; changing any other is the ordinary "no permission to modify" error, reported inside the body. Because the closure holds a variable it changes by &mut, its body cannot lend that variable &uni (bump(&uni total) is refused): a shared reference does not see through to a unique one. The borrow is an ordinary one (Borrowed references), so it holds the variable as borrows do: while a closure that reads a variable is still to be used, the variable cannot be changed or moved, and after the closure's last use it can.

imm limit = 100;
mut count = 1;
imm sum = fn(x i32) i32 { x + limit + count; };
sum(1);        // 102
count = 5;     // fine here; an ERROR if sum were called again below this line:
               // 'count' is borrowed (at 5:13), and that borrow is used again at 8:3 ...

Borrowing is the default because a copy made silently would duplicate state: a closure that added to its own copy of total would leave total unchanged and would give no sign that it had. When a closure should hold its own value instead, it is listed.

Giving the closure its own value

A variable listed in the state list is no longer borrowed. The entry is a field with an initializer, so the ordinary rules for values decide what the closure holds:

imm ribs = 3;
imm shape = fn(u i32) [ribs, base = 2 * 5 + 1] i32 { u * ribs + base; };
shape(2);                              // 2 * 3 + 11: 17

mut xs = new List[i32];
imm count = fn(x i32) [buf = xs] i32 { x + i32.from(buf.len()); };   // xs is moved in

imm p = new Pt(4, 5);
imm viaRef = fn(k i32) [r = &p] i32 { r.x * k; };              // a borrow, written out

imm mesh = new Rc[imm, Pt](7, 8);
imm h = fn() [mesh] i32 { mesh.y; };   // a counted owner is copied: mesh is still held
  • A copy: [ribs]. An entry with no = starts from the variable of that name around the closure. A value that copies is copied and one that moves is moved, as it would be passed to a function.
  • A move: [buf = xs], for a value that moves. The closure owns it, and xs can no longer be used.
  • Shared ownership: list a handle of a region that counts its owners, such as an Rc or an Arc. The closure holds one count and the original holds another. The permission of the handle decides whether the closure may change what it points at (Rc[mut, T]).
  • New state: [mut n = 0], which has no variable around it to mirror.
  • A borrow, written out: [r = &p]. The closure then has the lifetime of the borrow, as it does for a borrow it makes itself.

An entry's initial value is read in the code around the closure, not from the entries before it: in [a = 1, b = a] the a that b starts from is the one outside. Naming the state has other benefits: it tells the reader which variables are the closure's own, and an entry may be given a name of its own, as a field may. Listing is optional where borrowing will do.

A closure written in a method that names a member of the object, hits or step, reaches it through the method's self, which it borrows as it borrows any variable. A closure sees exactly what the code around it sees, private members included, wherever it is later called from:

struct Tally {
  hits i32;
  step i32;
  pub fn run(self &mut) i32 {
    mut bump = fn(x i32) i32 { hits += x * step; hits; };
    bump(1) + bump(2);
  }
}

Whether the closure changes

A closure is a value whose one method, (), is the body. That method's self permission is not written: it follows the body. A body that only reads what the closure holds and borrows has self &. A body that changes a captured variable or a mut state entry has self &mut. This decides what the closure may be used for. A closure whose () takes self &mut is held in a mut variable to be called, and goes only where a callable may change its state, &mut F and &<mut fn(sig) (Generics, Closure references). Given to a parameter that promises only to read it (&F, &<fn(sig)), it is refused, and the error says that this closure changes its state.

The return type

The return type is, in order of preference:

  1. the one written, fn(x i32) i64 { ... };
  2. the one the expected signature gives, where the closure is passed or assigned to one, every path being checked against it;
  3. read off the body's paths: the first return or final expression the check meets fixes it, and the others must fit it. A body whose last statement changes something (total += x;) returns nothing; any other last expression is the value;
  4. otherwise an error at the closure: fn(x i32) { if x > 0 { x; } else { 0u8; } } gives "The paths of this closure give different types, so its return type cannot be read off them: write the closure's return type, as in 'fn (x i32) i32 { ... }'."

return in a closure returns from the closure, never from the function around it:

imm early = fn(x i32) i32 { if x > 5 { return 1; } x + 2; };
early(9);      // 1
early(3);      // 5

A closure that holds nothing

A closure that borrows nothing and has no state is a plain function, so where a function reference is wanted it becomes one, and one that holds or borrows something is refused there (Anonymous functions, above, shows both, and the anonymous function written with an ampersand, which is not a closure at all).

Where a closure may go

A closure is a value of a struct of what it holds and borrows, so where it can go is decided by the rules for its fields, with nothing special for closures. A closure that borrows a variable cannot outlive it:

  • Down a call, passed to a function that uses it and returns, it may borrow any variable of the function around it, with one exception: a call that is also handed a &mut (or &uni) borrow, a method's receiver among them, of something that can hold borrows (a struct with a borrowed-reference field, a list of borrowed references) that the caller lent, since the call could store the closure's borrow there, where it would outlive the variable. That call is refused (error 1085) when the closure borrows a local of the function, or another argument is a borrow of a local, even though the callee only reads the closure. The error names the variable. A closure lists the variable, fn(x &i64) [k] bool { *x > k; }, to hold its own copy and borrow nothing. A receiver the function owns is not refused, and nor is one that cannot hold a borrow, such as a List[i64].
  • Kept in a local, it blocks moving or reshaping what it borrows until its last use.
  • Stored past the function or returned (in a field, in an owner such as So[fn(sig)], or as a returned borrow), it is refused if it borrows a local. The error names the variable and says to list it, so that the closure holds its own copy.
  • Stored in the object that made it: a closure in a method that names a member borrows self, so it cannot be stored in self. The error says to copy the members it needs into its list ([tag = tag]), or to capture a counted handle to the object.
  • Sent to another thread or actor, or run in a parallel each, it must be Sendable, or Shareable for the loop, judged by what it holds (Sendable and Shareable). A closure that borrows a variable is neither; the error names the variable and says to list it. A closure holding an Rc is told to hold an Arc.
fn returned() So[fn(x i32) i32] {
  imm k = 3;
  return new So[fn(x i32) i32](fn(x i32) i32 { x * k; });    // ERROR
}

fn listed() So[fn(x i32) i32] {
  imm k = 3;
  return new So[fn(x i32) i32](fn(x i32) [k] i32 { x * k; });   // its own copy of k
}

Error 1249: An owning virtual reference ('So[Trait]', 'Rc[Trait]') names no lifetime, so it may outlive any
borrow: the value made one may hold only global borrows, as if bounded by ''static'. This one holds a borrow
of 'k' (made at 4:32), which belongs to this function. The closure borrows 'k' because its body names it:
list it to give the closure its own copy instead, 'fn (...) [k] ... { ... }'.

And the exception for a call down a function, with a holder of borrows that the caller lent:

struct Seen {
  pub items List[&i64];
  pub fn count[F fn(x &i64) bool](self &mut, f F) i64 {
    mut n = 0i64;
    mut i = 0usize;
    while i < self.items.len() {
      if f(*self.items[i]) { n = n + 1; }
      i = i + 1usize;
    }
    n;
  }
}

fn refused(seen &mut Seen) i64 {
  imm k = 3i64;
  seen.count(x => *x > k);     // ERROR 1085: seen holds borrows, and the call could store k's borrow in it
}

fn listed(seen &mut Seen) i64 {
  imm k = 3i64;
  seen.count(fn(x &i64) [k] bool { *x > k; });   // its own copy of k: nothing borrowed
}

fn owned() i64 {
  imm base = 5i64;
  imm k = 3i64;
  mut seen = new Seen(List[&i64].empty());
  seen.items.push(&base);
  seen.count(x => *x > k);   // fine: this function owns seen
}

Rules that follow

  • A closure cannot call itself. The variable it is the value of is not a name inside it. Recursion uses a named function.
  • A closure is written in a function, never at the module level as a global's value or a field's default: there is nothing there to borrow.
  • On a GPU a closure is allowed in its static form only (Closures on the GPU).
  • While a collection is borrowed, a call of a closure that may change what it reaches is limited: see Calling a closure while a collection is borrowed.

Closures are values

A closure may be thought of as a function with persistent state, but it is more accurate to see it as a value that carries one method. It is a struct with no name, whose fields are the state list's entries and a reference for each variable it borrows; since the struct has no name that can be written, a closure is held in a variable whose type is inferred, and handed on as one of the references below. Like any value it may be put on the heap, in an owner such as So[fn(sig)]. A function that should accept any closure of a signature, whatever the shape of its state, takes it as a closure reference, &<fn(sig), or as a generic over the signature, [F fn(sig)], which is compiled for each closure and inlined. And a closure may fill a trait with one required method, as a struct does.

Closure references: any callable of a signature

A closure is a value of a struct that has no name, and its size and fields depend on what it holds. That is a problem when a function, or a field, should take any closure of one calling signature, whatever struct holds its state. A closure reference solves it: the closure is passed as a reference to the signature it calls. It is to a signature what a virtual reference is to a trait. Here a button holds whatever click handler it is given:

struct Window { pub id i32; }

struct Button {
  pub label i32;
  pub onClick So[fn(n i32)];
  pub fn setHandler(self &mut, f So[fn(n i32)]) { onClick = f; }
  pub fn press(self &mut, n i32) { onClick(n); }
}

imm w = new Window(7);
mut b = new Button(1, new So[fn(n i32)](fn(n i32) { }));
b.setHandler(new So[fn(n i32)](fn(n i32) [id = w.id] { print <- id + n, "\n"; }));
b.press(5);      // 12

The click handler is allocated in the single-owner region, so it is freed when it is replaced or discarded. Its state remembers the window's id, which its logic uses when the button is pressed. The Button holds it as a So[fn(n i32)], which accepts any closure, whatever its state, whose signature matches: one i32 in, no value back. The button calls the handler by the field's name, onClick(n).

The forms of a closure reference

The reference is written as the signature of the call, fn(x i32) i32, behind a reference or an owner. The signature stands for the idea "anything that can be called like this", a trait that needs no declaring, and the reference is a virtual reference to it:

  • &<fn(x i32) i32, a borrowed reference that may read what it points at. The closure's () takes self &.
  • &<mut fn(x i32) i32, a borrowed reference that may change what it points at: a closure that counts, or changes a variable it borrows.
  • So[fn(x i32) i32], an owner of a closure on the heap. The permission of an owner works as it does for any owner: So[fn(sig)] may change the closure's state, So[imm, fn(sig)] only reads it.
  • Rc[imm, fn(x i32) i32], shared owners of a closure that only reads; Rc[mut, fn(x i32) i32], shared owners of a state they all change, so every holder sees one count. Rc[fn(x i32) i32] with no permission is uni, the sole owner, as for any Rc, and moves when copied.

These are the same permissions as elsewhere, so the call kind is the reference's permission, with no separate families of function types: a function that takes a callable it only reads takes &<fn(sig); one that lets it change takes &<mut fn(sig). The call is written as any call, and goes through the reference to the closure's code:

fn apply(f &<fn(x i32) i32, x i32) i32 { f(x); }
fn applyMut(f &<mut fn(x i32) i32, x i32) i32 { f(x); }
fn run(f So[fn(x i32) i32], x i32) i32 { f(x); }

What meets it

Anything that has a pub () method of the signature, parameters and return type exactly (the parameters' names do not matter):

struct Triple { pub k i32; pub fn `()`(self &, x i32) i32 { x * k; } }
struct Count  { pub n i32; pub fn `()`(self &mut, x i32) i32 { n = n + x; n; } }
fn succ(x i32) i32 { x + 1; }

imm off = 10;
imm shift = fn(x i32) i32 { x + off; };
imm t = new Triple(3);
mut tally = new Count(0);

apply(&shift, 5);              // 15: a closure
apply(&t, 5);                  // 15: a struct with a '()'
apply(&succ, 5);               // 6: a plain function
applyMut(&mut tally, 5);       // 5
applyMut(&mut tally, 7);       // 12, and tally.n is 12

A plain function needs no state, so a reference to it meets any of the references above. A callable that reads meets &<mut fn as well, since a reference that may change can read. A callable that changes its state (its () takes self &mut) is refused behind &<fn(sig), which promises only to read: "`&<fn(i32) i32` may only call a callable that reads its state; this closure changes it (its `()` takes `self &mut`). To let it change, the type is `&<mut fn(i32) i32`." Likewise a &<mut fn is not lent where a &<fn is wanted, nor is a So[fn(sig)], which may change: the callable behind it might. An owner meant to be lent to a reader is made So[imm, fn(sig)].

A closure literal, lent

A closure literal written as an argument to a parameter taken by &<fn or &<mut fn is lent as a temporary, dropped at the end of the statement. The permission lent is the parameter's, so a literal given to &<fn that changes a variable is refused by the message above. The literal's parameter types come from the signature:

apply(x => x * 2, 21);                                    // 42
applyMut(fn(x i32) i32 { total += x; total; }, 10);       // total is changed

A literal is lent only as an argument. To keep one, move it into an owner.

An owner of a closure

new So[fn(sig)](value) takes one value, a closure literal or a struct with a () of the signature, moves it into an allocation of its own, and gives the owner of that as the callable. The literal's parameter types may come from the signature. The same holds for Rc:

mut owned So[fn(x i32) i32] = new So[fn(x i32) i32](fn(x i32) [mut sum = 100] i32 { sum += x; sum; });
owned(1);             // 101
applyMut(owned, 2);   // 103: an owner is lent as &<mut
run(owned, 3);        // 106: or handed on whole, moved

imm shared = new Rc[imm, fn(x i32) i32](new Triple(4));
imm again = shared;   // another holder of the same closure

The owner holds whatever the closure holds, and finalizes it when the last owner dies. A closure that holds nothing is allocated like any other. A plain function is wrapped by giving its reference, new So[fn(sig)](&f); a function of another signature, or a value with no () of the signature, is an error. An owner outlives the function that made it, so the closure in it may not borrow a local: the refusal is the one in Where a closure may go.

Naming a signature

An alias gives a signature a name, and the name works wherever the signature does:

alias Profile = fn(u i32) i32;

fn viaAlias(f &<Profile, u i32) i32 { f(u); }

A bare fn(sig) is read as a signature in the brackets of a type (So[fn(i32) i32], Applied[fn(i32) i32]), as the target of an alias and as a generic's bound (Generics). It is not itself the type of a variable or a return value: write &<fn(..), So[fn(..)] or the alias. A signature is a trait, so it has no size, and a field of a generic type holds it by an owner or a reference, not by value:

struct Applied[F] { pub f So[F]; }     // Applied[fn(i32) i32] holds a So[fn(i32) i32]

A callable held in a field

A field that holds a callable is called by its name, with no parentheses around it: b.onClick(5) calls the closure in onClick, and (b.onClick)(5) works too. A field and a method of one name cannot both exist, so there is nothing to choose between. A field that cannot be called, an i32 given arguments, is an error that says what the field holds. An owner whose state may change is called through a reference that may change, so a method that calls a So[fn(sig)] field takes self &mut, as press does above. The handler is replaced by assigning the field.

Saying what is behind a reference

A virtual reference hides the type behind it, so a reference to a callable or a trait is not Sendable or Shareable unless it says so. The markers follow the signature or the trait with a +, So[fn(x i32) i32 + Sendable], and a third, ShapeKeeping, says that a call through the reference reshapes nothing the caller holds a borrow into. All three are described together, with the other rules for what may cross a thread, in Sendable and Shareable.

The other two ways to take a callable

A function may instead be generic over the signature, [F fn(x i32) i32]. That form is compiled for each closure and inlined, where the references above are compiled once and call through the closure's code (A function signature as a constraint). The reference is what a field or a variable of unknown closure holds; the generic is what a function that only calls it uses. And a closure literal also fills a trait that has exactly one required method, wherever that trait is wanted (A closure written where a trait is wanted).

Generators: functions that are iterators

Note: Generators are built: a function declared yields, with yield and yield each, among a module's functions or as a method of a struct, generic or not. A generator may not be inline, have a where clause, or be a method of a trait, an enum, an actor or a type that declares lifetimes. Two-way yield is an idea that is not built.

A generator is a function that hands its caller values one at a time (Functions introduces them). It runs until it reaches a yield, gives the caller the value written there, and waits. When the caller asks for the next value it goes on from that yield, with its local variables as they were. It is a function whose result is a sequence, written as the loop that makes the sequence, and what it gives back is an Iterator:

fn count(n i64) yields i64 {
  mut i = 0i64;
  while i < n {
    yield i;
    i = i + 1i64;
  }
}

After yields comes the type of each value handed out. Calling count(4i64) runs nothing. It gives a value that holds the parameters, and every call of its next runs the body up to the next yield. next gives Some(value) for each value handed out and None once the body ends, by its last statement or by a return, which takes no value:

mut g = count(4i64);
while true {
  match g.next() {
    case imm v Some { print <- v, " "; }         // 0 1 2 3
    case is None { break; }
  }
}

each x in count(4i64) { print <- x, " "; }        // the same, 0 1 2 3

A loop that leaves early, by break or return, leaves the generator suspended, and it dies there (When a generator dies).

The value a generator gives is a struct made for it, of a type no source names; a message that has to spell it writes count.Gen. Since no source can write that type, a function cannot declare a generator as its result, nor a struct as a field. It is a move type: it is moved, not copied, so two walks of one generator never run. Having next(self &mut) Option[i64], it complies with core's Iterator[i64] as any cursor does, so it is passed to generic code bounded by that trait, or lent as a virtual reference:

fn sum[S Iterator[i64]](s &mut S) i64 {
  mut t = 0i64;
  each v in s { t = t + v; }
  t;
}

mut g = count(4i64);
sum(&mut g);         // 6

A yield is a statement of its own. It stands in a block, or in the arms of an if or match written as statements, and in a loop, but not inside an expression: f(a(), if c { yield 1; 2; } else { 3; }) would have to keep the value of a() across the wait, and is refused. Compute it into a variable first.

Yielding another generator's values

yield each hands on every value of another generator, or of anything with a next, in turn, and goes on when they are all handed on. It joins sequences, and it makes a recursive walk as short as the recursion:

fn joined(a i64, b i64) yields i64 {
  yield each count(a);
  yield 99;
  yield each count(b);
}
// joined(2i64, 2i64) hands out 0 1 99 0 1

struct Node {
  pub val i64;
  pub left i64;      // the index of the left child, or -1
  pub right i64;
}

// In order, a tree kept in an array
fn inorder(nodes &Array[Node], at usize) yields &Node {
  imm n = &nodes[at];
  if n.left >= 0 { yield each inorder(nodes, usize.from(n.left)); }
  yield n;
  if n.right >= 0 { yield each inorder(nodes, usize.from(n.right)); }
}

The generator being handed on is kept in the one that hands it on, in its own storage, when its size is known. A generator that hands on one of its own kind, as inorder does, would have to hold itself, so that one is kept on the heap, one for each yield each that needs it, made when the walk begins and freed when the generator dies. A value handed on is the sub-generator's own Some(value): it is moved up, not copied. Each value costs a step through every generator that hands it on.

Generator methods

A method may be a generator, called as any method is. In its body self is the receiver, exactly as in any method. The generator holds the receiver as it holds a parameter, so what the receiver was lent as stays lent for as long as the generator lives:

struct Tree {
  nodes Array[Node, 3];

  fn walk(self &) yields &Node {            // in order
    yield each self.from(0);
  }

  fn from(self &, at usize) yields &Node {
    imm n = &self.nodes[at];
    if n.left >= 0 { yield each self.from(usize.from(n.left)); }
    yield n;
    if n.right >= 0 { yield each self.from(usize.from(n.right)); }
  }
}

each n in tree.walk() { print <- n.val, " "; }
  • A receiver borrowed with self & may be read, not changed, while the generator may still be resumed; one borrowed with self &mut may be neither read nor changed. The generator may change what it was lent, and may hand out borrows of it, yields &mut i64 among them. The borrow lasts until the generator dies, not until it is last called: a block around the generator ends it.
  • A receiver taken by value, fn run(self) yields i64, moves into the generator and dies with it, after its locals. As with any parameter, the body may borrow or copy it (and change it, if declared mut self), not move it out.
  • Self in the body is the type the method belongs to.
  • A bare name that is a field of the receiver's type means self.name, as it does in any method, unless a local or a parameter of the generator is named so, which shadows it. A bare name of a method of the type is refused: write self.name().
  • A function of a type with no receiver, fn range(from i64, to i64) yields i64, is a generator too, called as Span.range(3, 7).

The method that makes the generator is the one written; the struct that is the generator is made beside the type and has no name in source (a message spells it Tree.walk.Gen). A method of a trait or of an enum cannot be a generator, since a trait's methods are copied into each type that implements it and an enum's into each of its variants; nor can an actor's, or a method of a type that declares lifetimes. Write a function that takes what the method would.

Generic generators

A generator may be generic, a function over a type or a method of a generic type or both. The struct that is the generator takes the type parameters, with their bounds as written, so each use is a generator of its own kind, made for the types it was called with, and checked as any generic is, where it is used:

fn items[T](l &List[T]) yields &T {
  each x in l.iter() { yield x; }
}

each x in items(&ints) { print <- *x, " "; }      // a generator over i64s

A generic generator may hand on another, itself included, with yield each, and a recursive one keeps its sub-generator on the heap in each instance as a plain one does. A type parameter of a generator does not name lifetimes ([T + 'a]) yet.

Generators across packages

A pub generator of a package, a function, a method or a method of a generic type, can be walked from another package as it is from its own. The struct that is the generator, and the frame that holds its locals across a yield, are made from its body, so the package's include file carries the generator's declaration whole, as it carries an inline or a generic function, and the importer makes the struct again from it. What the body names in the package, a private type, a private function or another private generator, is declared beside it and exported. A generator that is not pub stays inside the package, unless a body the include file carries names it; neither it nor the private names only it uses are in the file, and no other package can name them.

Borrows across a yield

A yield leaves the body, and the generator, a value, may be moved by its caller before it is resumed. What the body keeps across a yield is held in the generator's value, so:

  • A borrow of what the generator was lent, a parameter that is a reference, lasts across it. So does a copy of any value.
  • A borrow of one of the body's own local variables, or of a parameter the generator holds by value, does not last: it ends at the yield, and it is an error to use it after. The error names the yield.
  • What a yield hands the caller may borrow only what the generator was lent, as items above hands out borrows of the list. It is a borrow of that, not of the generator, so a caller may keep a value handed out for as long as the generator lives, several of them at once.
  • So the body holds each borrow it has handed out, from the yield to the end of the body, as if a variable of its own held it. It may go on reading what it lent, or change another part of it, but it may not change the thing the borrow points into, or call anything that could change the shape of the collection it points into (a push or a clear on a list). The error is at the change. Copy the value to hand it out, or hand out the borrow once the body has done changing what it borrows.
fn grows(xs &mut List[i64]) yields &i64 {
  yield xs[0usize];
  xs.push(1i64);   // ERROR 1339: the caller may still hold the borrow just yielded,
                   // and the push could move the list's elements
}

fn bad(k i64) yields i64 {
  mut x = 5i64;
  imm r = &x;
  yield k;         // ERROR 1168: r borrows a local, which cannot last across this yield
  yield *r;
}

The parameters are held in the generator, and the body names them as a method names its fields. It may borrow or copy one, or change one declared mut, but it may not move one out. A parameter lives as long as the generator does, not as long as the body, and dies after the locals.

When a generator dies

The locals of the body die as they would in a function, in the order they were declared, last first, where the body ends. A generator that dies while it waits at a yield finalizes the locals it holds there, in the same order, and then its parameters. One never run holds only its parameters. A local moved on some paths only is finalized only if it still holds its value, as anywhere.

Calling a closure while a collection is borrowed

Seen from a closure: a call through a &<mut fn(sig) parameter is assumed able to reshape any container, because the closure behind it may have captured one. A visitor that walks a list while its closure may push to that list would move the block the walk reads:

fn visit[T](xs &List[T], f &<mut fn(x &T)) {
  each x in xs.iter() { f(x); }          // ERROR 1339: f may push to xs
}
fn grow(list &mut List[i64]) {
  mut push = fn(x &i64) { list.push(*x); };
  visit(list, &mut push);
}

Error 1339: This call could change the shape of a 'List' while a borrow into it (made by 'iter' at 4:13,
through a path other references share) is still to be used by this call or by a value around it: '()' is
handed something that reaches a 'List' it may change, and its body is not visible here, so it is assumed to
change its shape (a virtual reference marked '+ ShapeKeeping' keeps the borrow across the call). A 'List'
that changes shape may move or free what it lent. Reach it through an 'imm' or 'uni' reference, or copy what
is needed out before this call.

Lending the list &imm cures it: nothing can write it, so no closure handed in can have captured it by &mut (the caller's list is an imm variable). Marking the closure + ShapeKeeping, or copying what is needed out before the call, also works. A read-only &<fn is not affected.

fn visit[T](xs &imm List[T], f &<mut fn(x &T)) {
  each x in xs.iter() { f(x); }          // Ok
}

imm nums = numbers;                      // 1, 5, 9 and 12, in an imm variable
mut sum = 0i64;
visit(&imm nums, fn(x &i64) { sum += *x; });   // sum is 27

A closure, read-only or not, may also write a mut global by its name, so a view into a global is refused across a call of a closure, read-only or not, and across a call of a function that makes one (A borrow into a mut global).

You can now hand behaviour around as a part: a function by reference, a closure with its state, any callable of a signature, or a sequence a generator makes. Each of these is chosen while the program runs; the next page makes the same choices while it is compiled, with generics, and adds macros.
