Cone
Actors

Every program so far has run on one core of your machine, while the others sat idle. This page puts them to work, so that more gets done, faster. Cone's way to do it is the actor, and it may be the first thing in this Guide you have not met before: a worker with a job of its own, which keeps its own data and handles the work sent to it, one piece at a time. You call it like a method, and Cone does the rest. Here is a bakery whose two tills sell from one stock room at once:

mod bakery;

import stdio use *;
// The actors package runs actors, on every core
import actors;

const price = 3;          // dollars a loaf

// An actor is declared like a struct. Its fields are its own:
// only its behaviours, below, can reach them
actor StockRoom {
  loaves: i32 = 100;

  // A behaviour, marked 'async fn'. Calling it sends the stock room
  // a message, which it handles when its turn comes
  pub async fn take(self, wanted: i32) i32 {
    let given = if wanted <= loaves { wanted } else { loaves };
    loaves -= given;
    given                              // the answer, sent back
  }

  pub async fn left(self) i32 { loaves }
}

// A till serves a customer from the stock room's loaves
actor Till {
  stock: StockRoom;                      // how this till reaches the stock room

  pub async fn serve(self, wanted: i32) i32 {
    // await: ask the stock room, and carry on here when it answers
    let got = await stock.take(wanted);
    got * price                        // what the customer pays
  }
}

// The shop runs the day
actor Shop {
  stock: StockRoom;
  east: Till;
  west: Till;

  pub async fn open(self) {
    // Two customers, served at once, one at each till
    let ana = east.serve(30);
    let ben = west.serve(40);
    print <- "Ana pays $", await ana, "\n";
    print <- "Ben pays $", await ben, "\n";
    print <- "Left on the shelf: ", await stock.left(), "\n";
  }
}

fn main() {
  // naming the actor makes it, and gives back a handle to reach it through
  let stock = StockRoom();
  let shop = Shop(stock, Till(stock), Till(stock));
  shop.open();      // one message; the program ends when the work is done
}

It prints:

Ana pays $90
Ben pays $120
Left on the shelf: 30

Try this: stock the shelf with 50 loaves, and run it a few times. Someone now goes short, and which of them can change from run to run, since either till may reach the stock room first. Between them, though, they always pay for exactly 50 loaves: never one more.

Workers with a job of their own

Doing several things at once has always had one hard part: two pieces of a program changing the same data at the same moment. Picture both tills reading "50 loaves" off the shelf, and each selling 40. If you have written threaded code, you know the usual cure, a lock around every shared value, and how hard it is to get every one of them right.

An actor takes the shared data away. The count of loaves belongs to the stock room, and nothing else can touch it; the tills ask the stock room instead. Their requests wait in its mailbox, and it handles them one at a time. Two requests can never tangle inside it, whichever order they arrive in, and that is why the Try this never sells a loaf twice.

Some work is a one-off, started, finished and its answer collected, and the next page has the simplest tool for that. But much of a running system is not like that. The stock room has state, and an ongoing responsibility: to take on whatever requests are sent to it, and answer each as and when it can, for as long as the shop is open. An actor is that kind of worker.

Underneath, Cone keeps a pool of worker threads, one for each core, and whenever an actor has a message waiting, a free thread runs it. You never start a thread, wait for one to finish, or take a lock. You decide which parts of the work belong together, give each part to an actor along with the data it needs, and let them talk. Cone has other ways to make work happen at the same time, and the Concurrency part has them all; actors and parallel each are the two to build on first.

Declaring an actor

An actor is written like a struct, with actor in place of struct, in a module that imports the actors package. Its fields are its state, and they are never pub: only its own behaviours reach them. Code outside that tries is refused, with a message that says what to do instead:

`loaves` is part of actor StockRoom's private state, which only its own methods reach, one message at a time. Send it a behaviour that uses it.

A method marked async fn is a behaviour: a message the actor understands. Inside one, the fields are used by name, and changed freely, since nothing else runs in this actor while it does.

StockRoom() makes the actor and gives back its handle, the value you reach it through. As with a struct, the fields are filled in order from the arguments, and a field with a default, such as loaves i32 = 100, takes it when the argument is left off. A handle may be copied as often as you like: the shop and both tills hold the one stock room's handle, and whatever any of them sends lands in the same mailbox.

Beside its behaviours, an actor may have what a struct has: an init, run inside the actor when its name makes it; plain fn methods, helpers its behaviours call directly, with no message; and a final, run when it dies. Inside a behaviour, selfactor is the actor's own handle, which it can send a message to, or hand to another actor:

actor Oven {
  baked: i32;

  fn init(self: &new, start: i32) {          // run by 'Oven(0)', inside the actor
    *self = Self(baked: start);
  }

  fn batch(self: &, trays: i32) i32 {         // a helper: an ordinary call, no message
    trays * 12
  }

  pub async fn bake(self, trays: i32) i32 {
    baked += self.batch(trays);
    baked
  }

  pub async fn bakeTwice(self, trays: i32) i32 {
    await selfactor.bake(trays);           // a message to itself
    await selfactor.bake(trays)
  }
}

An actor lives as long as something holds its handle or its mailbox holds a message, so a handle dropped with messages still queued leaves the actor alive until they are handled. Actors holding each other's handles in a cycle never die, until one lets go. Actors in depth has the four shapes a behaviour can take, and the rest of an actor's life.

Calling a behaviour sends a message

east.serve(30) looks like a method call, and that is how you write it. What it does is put a message in the till's mailbox and return at once, without waiting for the till. It is the same idea as the send operator, a send dressed as a method call: you write the call, and Cone carries the message, and schedules the till to handle it on whichever thread is free. One actor's messages to another are handled in the order they were sent.

main starts the day with shop.open(), a message like any other, so main reaches its end almost at once. The program then waits until no actor has anything left to do, and stops.

async and await

A behaviour is asynchronous: it runs later, when the actor gets to the message, which is what async says. A send is one way, so when the sender needs the answer, it writes await. In serve, await stock.take(wanted) sends take to the stock room, and the till's behaviour pauses there until the answer comes back. Pausing does not hold up a core: the thread goes off to other work, and the till may even handle its other messages meanwhile. When the answer arrives, the behaviour carries on from where it stopped, with the stock room's answer as the await's value.

So serve reads top to bottom, like any function, though it runs on two actors and, perhaps, two cores. The awaits mark the seams where it waits on another actor. Only a behaviour that declares a return type sends an answer, so only such a behaviour can be awaited, and await stands only inside a behaviour. That is why the bakery has a Shop: main is a plain function, so it starts things off with a send, and the waiting happens in an actor.

Awaiting each call as it is made, await east.serve(30), would have the shop wait for Ana before it even began on Ben. Instead, let ana = east.serve(30) sends the message at once and keeps its future: a value standing for the answer to come. Both customers' messages are out before either answer is needed, so the two tills serve them at the same time, and the shop awaits the futures afterwards. The stock room's count is right by the time the shop asks for it, because each till had its answer from the stock room before it answered the shop.

So how a behaviour is called says what becomes of its answer: await waits for it here, a variable keeps its future for later, and a call written as a statement of its own sends the message and drops the answer. Whether there is an answer at all is the behaviour's to say: one with no return type sends none, and awaiting it is refused, with the advice to declare a return type, a status, if the caller needs to know it finished. An await also lets go of every borrow the behaviour holds, since the actor handles other messages while it waits. Awaiting in depth has the rest.

What you can send

A message carries its values to another actor, which may be running on another core, and each kind of value crosses in its own safe way.

Numbers are copied. east.serve(30) puts a copy of 30 in the message.

A value that moves just flows. A String, a list, or any other value that moves rather than copies is handed over whole: it moves into the message, and from then on only the receiver has it. Here the shop hands a customer's name to an order book:

actor OrderBook {
  names: List[String];

  pub async fn add(self, name: String) {
    names <- name;                // the book keeps the String
  }
}

let name = String.from("Ana");
book.add(name);                   // the String moves into the message

Once the name has gone, the shop cannot use it: name after the send is refused, with This variable's value has been moved out. It is no longer there to use. So two actors never hold the same String at once, and nothing needs guarding.

Handles are shared, as the tills share the stock room's.

What nobody changes, everybody may share. A larger value that every actor reads, such as a price list, is made once as an Arc, from the sync package, and handed to as many actors as need it. Every copy reaches the one price list, and the imm in Arc[imm, Prices] says no one may change it, so every actor may read it at once:

import sync use Arc;

struct Prices {
  pub loaf: i32;
  pub bun: i32;
}

actor Till {
  prices: Arc[imm, Prices];        // one price list, read by every till

  pub async fn serve(self, loaves: i32, buns: i32) i32 {
    loaves * prices.loaf + buns * prices.bun
  }
}

// Made once, and handed to as many tills as you like
let prices = Arc[imm, Prices](loaf: 3, bun: 1);
let east = Till(prices);
let west = Till(prices);

The compiler checks all of this for you, from what each behaviour's parameters hold, with nothing for you to write; a value that could not travel safely is refused where the behaviour is declared. A borrow (&x) is the usual one, since it points into memory its own thread may free, and an Rc, whose count only one thread may keep. The actor's own fields are never sent, so they may hold anything. When several actors truly must change one value, give that value to an actor of its own, as the bakery gives the loaves to the stock room. The rest of what may cross is in What may cross a thread, and the locks for the rare case that needs one, permissions such as Arc[Mutex, T] that take a lock whenever the value is borrowed, are in Lock permissions.

Note: The actors and sync packages run on Windows and Linux (x86-64), not yet on macOS. What is not built yet, among it a time limit on an await and waiting for whichever of several answers comes first, is listed in Actors in depth and Awaiting in depth.

You can now give each part of a program to an actor of its own, call it like a method, and let the actors work side by side on every core. When the work is one big loop rather than standing roles, there is something simpler still: one word in front of an each.
