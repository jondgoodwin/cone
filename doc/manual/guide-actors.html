Cone
Actors

Every program so far has run on one core of your machine, while the others sat idle. This page puts them to work, so that more gets done, faster. Cone's way to do it is the actor, and it may be the first thing in this Guide you have not met before: a worker with a job of its own, which keeps its own data and handles the work sent to it, one piece at a time. You call it like a method, and Cone does the rest. Here is a bakery whose two tills sell from one stock room at once:

mod bakery;

import stdio use *;
// The actors package runs actors, on every core
import actors;

const price = 3;          // dollars a loaf

// An actor is declared like a struct. Its fields are its own:
// only its behaviours, below, can reach them
actor StockRoom {
  loaves i32 = 100;

  // A behaviour, marked 'async do'. Calling it sends the stock room
  // a message, which it handles when its turn comes
  pub async do take(self, wanted i32) i32 {
    imm given = if wanted <= loaves { wanted; } else { loaves; };
    loaves -= given;
    given;                              // the answer, sent back
  }

  pub async do left(self) i32 { loaves; }
}

// A till serves a customer from the stock room's loaves
actor Till {
  stock StockRoom;                      // how this till reaches the stock room

  pub async do serve(self, wanted i32) i32 {
    // await: ask the stock room, and carry on here when it answers
    imm got = await stock.take(wanted);
    got * price;                        // what the customer pays
  }
}

// The shop runs the day
actor Shop {
  stock StockRoom;
  east Till;
  west Till;

  pub async do open(self) {
    // Two customers, served at once, one at each till
    imm ana = east.serve(30);
    imm ben = west.serve(40);
    print <- "Ana pays $", await ana, "\n";
    print <- "Ben pays $", await ben, "\n";
    print <- "Left on the shelf: ", await stock.left(), "\n";
  }
}

fn main() {
  // new makes an actor, and gives back a handle to reach it through
  imm stock = new StockRoom();
  imm shop = new Shop(stock, new Till(stock), new Till(stock));
  shop.open();      // one message; the program ends when the work is done
}

It prints:

Ana pays $90
Ben pays $120
Left on the shelf: 30

Try this: stock the shelf with 50 loaves, and run it a few times. Someone now goes short, and which of them can change from run to run, since either till may reach the stock room first. Between them, though, they always pay for exactly 50 loaves: never one more.

Workers with a job of their own

Doing several things at once has always had one hard part: two pieces of a program changing the same data at the same moment. Picture both tills reading "50 loaves" off the shelf, and each selling 40. If you have written threaded code, you know the usual cure, a lock around every shared value, and how hard it is to get every one of them right.

An actor takes the shared data away. The count of loaves belongs to the stock room, and nothing else can touch it; the tills ask the stock room instead. Their requests wait in its mailbox, and it handles them one at a time. Two requests can never tangle inside it, whichever order they arrive in, and that is why the Try this never sells a loaf twice.

Some work is a one-off, started, finished and its answer collected, and the next page has the simplest tool for that. But much of a running system is not like that. The stock room has state, and an ongoing responsibility: to take on whatever requests are sent to it, and answer each as and when it can, for as long as the shop is open. An actor is that kind of worker.

Underneath, Cone keeps a pool of worker threads, one for each core, and whenever an actor has a message waiting, a free thread runs it. You never start a thread, wait for one to finish, or take a lock. You decide which parts of the work belong together, give each part to an actor along with the data it needs, and let them talk. Cone has other ways to make work happen at the same time, and the Concurrency part has them all; actors and parallel each are the two to build on first.

Declaring an actor

An actor is written like a struct, with actor in place of struct, in a module that imports the actors package. Its fields are its state, and they are never pub: only its own behaviours reach them. Code outside that tries is refused, with a message that says what to do instead:

`loaves` is part of actor StockRoom's private state, which only its own methods reach, one message at a time. Send it a behaviour that uses it.

A method marked async do is a behaviour: a message the actor understands. Inside one, the fields are used by name, and changed freely, since nothing else runs in this actor while it does.

new StockRoom() makes the actor and gives back its handle, the value you reach it through. As with a struct, the fields are filled in order from the arguments, and a field with a default, such as loaves i32 = 100, takes it when the argument is left off. A handle may be copied as often as you like: the shop and both tills hold the one stock room's handle, and whatever any of them sends lands in the same mailbox.

Calling a behaviour sends a message

east.serve(30) looks like a method call, and that is how you write it. What it does is put a message in the till's mailbox and return at once, without waiting for the till. It is the same idea as the send operator, a send dressed as a method call: you write the call, and Cone carries the message, and schedules the till to handle it on whichever thread is free. One actor's messages to another are handled in the order they were sent.

main starts the day with shop.open(), a message like any other, so main reaches its end almost at once. The program then waits until no actor has anything left to do, and stops.

async and await

A behaviour is asynchronous: it runs later, when the actor gets to the message, which is what async says. A send is one way, so when the sender needs the answer, it writes await. In serve, await stock.take(wanted) sends take to the stock room, and the till's behaviour pauses there until the answer comes back. Pausing does not hold up a core: the thread goes off to other work, and the till may even handle its other messages meanwhile. When the answer arrives, the behaviour carries on from where it stopped, with the stock room's answer as the await's value.

So serve reads top to bottom, like any function, though it runs on two actors and, perhaps, two cores. The awaits mark the seams where it waits on another actor. Only a behaviour that declares a return type sends an answer, so only such a behaviour can be awaited, and await stands only inside a behaviour. That is why the bakery has a Shop: main is a plain function, so it starts things off with a send, and the waiting happens in an actor.

Awaiting each call as it is made, await east.serve(30), would have the shop wait for Ana before it even began on Ben. Instead, imm ana = east.serve(30) sends the message at once and keeps its future: a value standing for the answer to come. Both customers' messages are out before either answer is needed, so the two tills serve them at the same time, and the shop awaits the futures afterwards. The stock room's count is right by the time the shop asks for it, because each till had its answer from the stock room before it answered the shop.

What you can send

A message carries its values to another actor, which may be running on another core, and each kind of value crosses in its own safe way.

Numbers are copied. east.serve(30) puts a copy of 30 in the message.

A value that moves just flows. A String, a list, or any other value that moves rather than copies is handed over whole: it moves into the message, and from then on only the receiver has it. Here the shop hands a customer's name to an order book:

actor OrderBook {
  names List[String];

  pub async do add(self, name String) {
    names <- name;                // the book keeps the String
  }
}

imm name = String.from("Ana");
book.add(name);                   // the String moves into the message

Once the name has gone, the shop cannot use it: name after the send is refused, with This variable's value has been moved out. It is no longer there to use. So two actors never hold the same String at once, and nothing needs guarding.

Handles are shared, as the tills share the stock room's.

What nobody changes, everybody may share. A larger value that every actor reads, such as a price list, is made once as an Arc, from the sync package, and handed to as many actors as need it. Every copy reaches the one price list, and the imm in Arc[imm, Prices] says no one may change it, so every actor may read it at once:

import sync use Arc;

struct Prices {
  pub loaf i32;
  pub bun i32;
}

actor Till {
  prices Arc[imm, Prices];        // one price list, read by every till

  pub async do serve(self, loaves i32, buns i32) i32 {
    loaves * prices.loaf + buns * prices.bun;
  }
}

// Made once, and handed to as many tills as you like
imm prices = new Arc[imm, Prices](loaf: 3, bun: 1);
imm east = new Till(prices);
imm west = new Till(prices);

The compiler checks all of this for you, from what each behaviour's parameters hold, with nothing for you to write; a value that could not travel safely is refused where the behaviour is declared. When several actors truly must change one value, give that value to an actor of its own, as the bakery gives the loaves to the stock room. The rest of what may cross, and the locks for the rare case that needs one, are in What may cross a thread.

You can now give each part of a program to an actor of its own, call it like a method, and let the actors work side by side on every core. When the work is one big loop rather than standing roles, there is something simpler still: one word in front of an each.

Not implemented: actor trait, a generic actor, a time limit on an await of a reply, cancelling a paused behaviour, and waiting for whichever of several replies arrives first. Of the lock permissions, not implemented: a borrow that tries the lock and gives up rather than waiting, a time limit on the wait, taking the locks of several values at once, and anything preventing a deadlock, which Cone does not do.

Declaring one: state and behaviours

An actor is declared with actor, and it runs on the actors package, which a module declaring one imports. Its body is written as a struct's: fields, an init, behaviours, synchronous methods, a final:

import actors;

actor Counter {
  count u64;                       // its state: private to it

  fn init(self &new, start u64) {   // run by 'new Counter(start)', in the actor
    *self = new Self(count: start);
  }

  pub async do add(self, n u64) {  // a behaviour: sent as a message
    count = count + n;
  }

  fn doubled(self &) u64 {         // synchronous: called, inside the actor
    count * 2u64;
  }
}
  • The fields are its state, private to it: a field is never pub, and nothing outside the actor reaches one.
  • A method declared async do is a behaviour: a message, run later, when the actor is scheduled. async do is one keyword of two words.
  • A method declared fn is synchronous: the actor's init and final, and any helper, which runs inside the method that calls it, as a struct's method does. It is the actor's alone.

Whether a behaviour declares a return type decides whether a reply is sent; whether it holds an await decides whether it waits. So a behaviour is fire and forget (neither), a cheap query (a return type), one that awaits and owes nobody, or the full handshake (both). (Behaviours and methods, The four behaviour shapes, The declaration.)

From Making an actor: The initializer's parameters must be Sendable too, since the state made from them runs on other threads. An actor may declare several initializers, as a struct may, each joining the overload name init. One that declares none is made by its state's implicit initializer: new Counter(5u64) takes the fields whose types are written, in order, a field with a default taking it where the argument is left out. That initializer is the module's own, as a struct's implicit one is where its fields are private, except for a pub actor with no fields at all. There is no other way to make an actor, and no creation function: spawn stays reserved.

Making one and sending it messages

fn main() {
  imm c = new Counter(0u64);       // the first actor starts the workers
  c.add(5u64);                     // a message: queued, and run later
  c.add(7u64);                     // run after the first
}                                  // then the program waits until all is quiet, and stops the workers

new Counter(args) makes an actor and answers its handle. Calling a behaviour on the handle, c.add(5u64), sends that message: a send is one-way, it queues the message and returns. Each sender's messages to one actor are handled in the order sent. A handle may be copied: passed, stored, kept in another actor's state, or put in a message, as the bakery's tills hold the StockRoom above. An actor dies when its last handle has gone and its mailbox is empty.

The runtime starts and stops by itself: the first actor made starts the worker threads, one per logical processor by default, and when main returns the program waits until no actor is queued or running, then stops them. (Making an actor, Messages, self and selfactor, How the runtime works.)

From Messages: A send is one-way: it queues the message and returns. An answer comes back only to an await, or as a message sent back to a handle passed along. Each sender's messages to one actor are handled in the order sent, and a message is never overtaken by one it caused. Each argument arrives moved into the behaviour's call, once: a value that may only move (a uni or So owner) arrives whole, and a counted one (a handle, an Arc, a lock-managed Arc[Mutex, T]) is counted once.

From An actor's life: While an actor is queued to run, or running, the scheduler holds one owner more, taken by the send that found it idle and dropped when its mailbox is found empty. So an actor dies exactly once, when its last handle has gone and its mailbox is empty: a handle dropped with messages still queued leaves the actor alive until they are handled. At its death its state is finalized (its final, then its fields, handles to other actors among them), on whichever thread let go last, then the block is freed. Actors that hold handles to each other in a cycle never die by counting, as a cycle of Arc owners never does, until one of them lets go.

From self and selfactor: An actor has two selves. self is its state, lent to the method while it runs; it never leaves the actor. selfactor is its handle: another owner of the actor, a value that may go anywhere a handle may — into a message, into another actor's state, or to an await on one of its own behaviours:

actor Doubler {
  pub async do double(self, n u64) u64 {n * 2u64;}

  pub async do twice(self, n u64) u64 {
    imm once = await selfactor.double(n);  // a message to itself
    imm again = await selfactor.double(once);
    again;
  }
}

await doubler.twice(5u64) is 20. (The rest, sending to itself with self.m() and where selfactor may be written: Sending to itself.)

Awaiting a reply

A message is one-way: whatever the behaviour returns is dropped. Inside an actor's own behaviour, await sends a message and waits for what the behaviour it sends returns:

actor Store {
  total u64;

  pub async do add(self, k u64) {           // fire and forget
    total = self.plus(k);
  }

  pub async do count(self) u64 {total;}     // a cheap query

  fn plus(self &, k u64) u64 {total + k;}   // synchronous: an ordinary call
}

actor Client {
  store Store;

  pub async do run(self) {                  // awaits, owes nobody
    store.add(5u64);
    store.add(7u64);
    imm c = await store.count();
    say("count", c);
  }
}

Sent client.run(), with a Store whose total starts at 0, this prints count 12: both adds reach the Store before the count does, since one sender's messages are handled in the order sent. What an await does:

  1. It asks. The behaviour after await is sent, as any message is.
  2. The behaviour pauses. The worker does not wait with it: it goes on to other work.
  3. Other messages run. The actor handles the rest of its mailbox meanwhile, so its state may have changed by the time the behaviour resumes.
  4. The reply resumes it, with the value as the await's.

An await stands only in a behaviour, never in a fn, and it pauses only the behaviour it is written in. The method still reads as one scope: every value it holds when it pauses dies where it would if the method had never paused. An I/O operation is awaited the same way (HTTP an actor awaits). (Awaiting in depth: what crosses an await, an await inside a statement, futures.)

From Futures: storing a call's value: A call of a behaviour that returns a value, written where its value is kept — bound to a local, passed on, returned — sends the request at once and gives back a future: a value standing for what the behaviour will return. An await on the future waits for that value. So several requests can be in flight at once, and their answers collected later:

actor Stock {
  pub async do price(self, item u64) u64 {item * 3u64;}
}

actor Basket {
  stock Stock;

  pub async do total(self) u64 {
    imm apples = stock.price(4u64);     // sent: a future comes back at once
    imm pears = stock.price(5u64);      // both requests are in flight
    imm a = await apples;               // waits for the first
    imm p = await pears;                // then for the second
    a + p;
  }
}

await basket.total() is 27. Both requests are sent before either is waited for, so Stock may work on the second while Basket waits for the first. A behaviour is declared once, and how it is called says what becomes of its value:

  • await stock.price(4u64) sends it and waits here: the await's value is the behaviour's, and no future is made.
  • imm f = stock.price(4u64) sends it and keeps its future, an actors.Future[u64], for an await later.
  • stock.price(4u64);, a statement of its own, sends it and forgets it: its value is dropped.

An await on a future pauses only if the value has not arrived. If it has, the behaviour goes on at once. (A future handed to another actor, a future of a value that moves, and one that never arrives: Futures.)

From A behaviour that returns nothing: Whether a reply is sent is the behaviour's declaration to say, never its caller's: one with no return type sends none, so there is nothing to await, and an await on it is refused. A caller that needs to know a behaviour has finished needs to know whether it worked, too: the behaviour declares a return type, a status, and the caller awaits that.

actor Log {
  pub async do flush(self) {}             // owes its caller nothing
  pub async do commit(self) bool {true;}  // answers with a status
}

actor Writer {
  log Log;
  saved bool;

  pub async do save(self) {
    await log.flush();            // refused: flush sends no reply
    saved = await log.commit();   // waits until commit has run, and learns whether it worked
  }
}

What may be sent

A message carries its arguments to the thread the actor runs on, so every parameter of a behaviour, and of an actor's initializer, must be Sendable, and one that is not is refused where it is declared. The compiler works out Sendable from what a type holds, with nothing to write:

  • Sent freely: numbers and other plain values; a value that moves, which arrives whole (a So owner, a List of such values); an Arc[imm, T], an Arc[Mutex, T]; another actor's handle.
  • Refused: a borrow (&x, &mut x, but for a borrow of something that lasts the whole program, written so), an Rc, and anything holding one. The refusal names the part of the type that binds it to its thread.

The actor's state is not asked, since it never crosses as a value: it may hold an Rc, and its methods may borrow freely. (Race condition safety, Sendable and Shareable.)

Sharing read-only data: Arc

Immutable data is shared between threads through the sync package's Arc region (import sync use Arc), whose count is atomic: Arc[imm, T] owners may be copied and dropped on any thread, and the value is freed once, after the last. An Rc owner's count is not atomic, and it must stay on one thread. (Sharing immutable data: Arc, and regions in depth.)

Sharing and changing: lock permissions

When several threads or actors must change one value, a lock permission guards it. A lock permission is a type, written where a permission goes, and its value is the lock: Mutex and Rwlock, the sync package's, on Arc, and Rwcell, core's, for one thread, on Rc:

import sync use Arc, Mutex;

alias Counter = Arc[Mutex, Count];
imm c = new Counter(0u64);
imm point = new Arc[Mutex, Point](x: 2, y: 3);

An Arc[Mutex, T] may be copied, and handed to another thread or actor. But it gives no direct access to its value: the value is reached only by borrowing (Borrowed references), and obtaining the borrow takes the lock first:

imm n = c.n;            // refused: a read without the lock
c.n += 1u64;            // refused
imm v = (&*c).n;       // a borrow takes the lock: allowed

A borrow that may write takes the lock for writing; a read-only borrow takes it for reading (a Rwlock lets several readers in at once). A borrow that finds the lock held waits. The lock is given back at the borrow's last use:

imm point = new Arc[Mutex, Point](x: 2, y: 3);
{
  imm pointref = &mut *point;  // takes the lock
  pointref.x += pointref.y;     // the point is reached only while it is held: the last use
  show(point);                  // the lock was given back after that statement, so a
}                               // borrow in show does not wait for this block's end
bump(&mut *point);              // taken and given back within the statement

So nothing reaches the value unlocked, and nothing is left locked by forgetting to unlock it. An await ends every borrow the behaviour holds, so no lock is held while a behaviour waits; to reach the value again, the behaviour borrows it again. Cone does not prevent deadlock: a thread borrowing through a Mutex it already holds through another borrow waits forever. (Lock permissions in depth, Permissions in depth.)
