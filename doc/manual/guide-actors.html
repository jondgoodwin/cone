Cone
Actors

A program that does several things at once is usually a program that is hard to get right. Cone's answer is the actor: a small worker that keeps its own state and is reached only by messages. Here is a café run by four of them.

// Actors: each keeps its own state, and they work by sending messages
//
// A Till keeps the cafe's takings. Two Baristas make drinks, at the same
// time, and ring them up on the Till. The Manager hands out the orders
// and waits for the answers it needs.

mod cafe;

import stdio use *;
import sync use Arc;
import actors;

// The price list: shared by everyone, changed by no one
struct Menu {
  pub latte u64;
  pub tea u64;
}

actor Till {
  takings u64 = 0;                     // the till's own state: no one else can touch it

  pub async do ring(self, price u64) { // a behaviour: it arrives as a message
    takings = takings + price;
  }

  pub async do total(self) u64 {       // it returns a value, so it can be awaited
    takings;
  }
}

actor Barista {
  till Till;                           // a handle: how this actor reaches the till
  menu Arc[imm, Menu];                 // the shared price list

  pub async do make(self, lattes u64, teas u64) u64 {
    imm bill = lattes * menu.latte + teas * menu.tea;
    till.ring(bill);                   // sent, and not waited for
    bill;                              // the reply, for whoever awaits it
  }
}

actor Manager {
  till Till;
  ana Barista;
  ben Barista;

  pub async do open(self) {
    imm first = ana.make(2, 1);        // both orders go out at once,
    imm second = ben.make(1, 3);       // and the baristas work on them together
    print <- "Ana's order: ", await first, "\n";
    print <- "Ben's order: ", await second, "\n";
    print <- "In the till: ", await till.total(), "\n";
  }
}

fn main() {
  imm menu = new Arc[imm, Menu](latte: 4, tea: 3);
  imm till = new Till();
  imm ana = new Barista(till, menu);
  imm ben = new Barista(till, menu);
  imm manager = new Manager(till, ana, ben);
  manager.open();                      // returns at once: the actors do the work
}                                      // and the program ends when they are all done

It prints:

Ana's order: 11
Ben's order: 13
In the till: 24

What to notice

  • An actor is declared like a struct: its fields are its state, and nothing outside the actor can reach them.
  • A method declared async do is a behaviour. Calling one sends the actor a message and returns at once: till.ring(bill) does not wait for the till.
  • A behaviour that returns a value can be awaited. Keeping the call in a variable first, as first and second do, lets both baristas work at the same time.
  • The till's handle and the menu are shared by several actors, and nothing in the program takes a lock.
  • main makes the actors and sends one message; the program ends when every actor has finished its work.

Why actors: many hands, each with its own work

A computer has several cores, and a program that keeps only one of them busy leaves the rest idle. A program also spends much of its time waiting, for a file, for the network, for another part of itself. Doing several things at once helps on both counts: many hands make light work, and a hand that is waiting can let another get on.

The trouble has always been the shared desk. When two threads change the same value at once, the result depends on which got there first, and a program that works a thousand times can fail on the next. The usual cure is a lock around every shared value, and then the trouble becomes remembering every lock, and taking them in the right order.

An actor gives every worker a desk of its own. Its state is private: only its own behaviours touch it. Other code asks it to do things by sending messages, which wait in its mailbox and are handled one at a time. Because only one message runs at a time, the actor never needs a lock, and because each sender's messages arrive in the order they were sent, the actor sees its work in a sensible order. In the café, the Till is the only one who ever touches the takings; the baristas just send it ring messages, and it adds them up one after another.

Behind the scenes, Cone runs the actors on a pool of worker threads, one for each core, and moves an actor onto a free thread whenever it has a message to handle. You never start a thread, join one, or take a lock. You decide which parts of the work belong together, give each part to an actor along with the state it needs, and let them talk.

Declaring an actor

An actor is written with actor, and its body looks like a struct's. A module that declares one imports the actors package, which is what runs them:

actor Till {
  takings u64 = 0;                     // the till's own state: no one else can touch it

  pub async do ring(self, price u64) { // a behaviour: it arrives as a message
    takings = takings + price;
  }

  pub async do total(self) u64 {       // it returns a value, so it can be awaited
    takings;
  }
}

The fields are the actor's state. They are never pub, and code outside the actor that tries to read one is refused, with a message that says what to do instead:

`takings` is part of actor Till's private state, which only its own methods reach, one message at a time. Send it a behaviour that uses it.

Each method declared async do (one keyword of two words) is a behaviour: a message the actor understands. Inside one, the fields are used by name, and may be changed freely, since nothing else is running in this actor while it does.

new Till() makes the actor and gives back its handle, the value you send it messages through. Its fields are filled in order from the arguments, as a struct's are, and a field with a default, like takings u64 = 0, takes its default when the argument is left out. So new Barista(till, menu) fills a barista's two fields.

Sending a message

Calling a behaviour on a handle sends that message:

till.ring(bill);                   // sent, and not waited for

The call puts the message in the till's mailbox and returns at once; the barista goes straight on to its next line. Some time later, on whichever worker thread is free, the till takes the message out and runs ring. Messages one actor sends to another are handled in the order they were sent.

The program starts and stops the runtime by itself. The first actor made starts the worker threads. manager.open() in main is a send like any other, so main reaches its end almost at once; the program then waits until no actor has anything left to do, and stops.

Asking, and waiting for the answer

A plain send is a one-way street: whatever the behaviour returns is dropped. When the sender needs the answer, it writes await in front of the call:

print <- "In the till: ", await till.total(), "\n";

The await sends total to the till and pauses the manager's behaviour until the reply comes back. Pausing does not tie up a thread: the worker goes on to other work, and the manager can even handle its other messages meanwhile. When the reply arrives, the behaviour carries on from where it stopped, with the till's answer as the value of the await.

Only a behaviour that declares a return type sends a reply, so only such a behaviour can be awaited. And await stands only inside a behaviour, which is why the café has a Manager: main is a plain function, so it starts things off with a send, and the waiting happens in an actor.

Awaiting each call as it is made would have the manager wait for Ana before even asking Ben. Instead it keeps each call's future, a value standing for the reply to come, and awaits them afterwards:

imm first = ana.make(2, 1);        // both orders go out at once,
imm second = ben.make(1, 3);       // and the baristas work on them together
print <- "Ana's order: ", await first, "\n";
print <- "Ben's order: ", await second, "\n";

Both messages are sent before either answer is needed, so Ana and Ben work at the same time, on different threads. By the time the manager asks for the total, both baristas have rung up their bills, since each sent its ring to the till before it replied.

Sharing data safely

Actors work together by passing values to each other, and each kind of value crosses from one actor to another in its own safe way. The café uses most of them.

Numbers are copied. ana.make(2, 1) puts copies of 2 and 1 in the message. The manager keeps its own, and Ana gets hers.

A value that moves arrives whole. A list, a String or any other value that moves moves into the message, and from then on only the receiver has it:

actor Till {
  takings u64 = 0;

  pub async do ringAll(self, prices List[u64]) {
    each price in prices {
      takings = takings + price;
    }
  }
  // ...
}

actor Manager {
  till Till;

  pub async do close(self) {
    imm prices = new List[u64] <- 4, 3, 4;
    till.ringAll(prices);              // the list moves into the message
    print <- "In the till: ", await till.total(), "\n";
  }
}

This prints In the till: 11. Once the list has gone, the manager cannot touch it: using prices after the send is refused, with This variable's value has been moved out. It is no longer there to use. So two actors never hold the same list at the same time.

Handles are shared. An actor's handle may be copied as often as you like: passed to new, stored in another actor's fields, or sent in a message. All three of the café's other actors hold the one till's handle, and every message any of them sends lands in the same mailbox.

What never changes may be shared by everyone. The price list is made once, as an Arc[imm, Menu], from the sync package. Every copy of it reaches the one menu, and imm means no one may change it: a barista that tries, menu.latte = 5, is refused. With nobody able to write, every actor may read it at once.

The compiler checks all of this for you. Every parameter of a behaviour must be a type that can safely travel to another thread, and it works that out from what the type holds, with nothing for you to write. A type that cannot travel is refused where the behaviour is declared, with a message that names the part of it at fault (What may be sent, below).

When several actors truly must change one value, the usual answer is to give that value to an actor of its own, as the café gives the takings to the till, and send it messages. Values guarded by a lock exist too, for the rare case that needs one (lock permissions, below).

Dividing one big job

Actors also split up a single large piece of work. Here four Worker actors each add up a quarter of the numbers from 1 to 4000, at the same time, and send their partial sums to one Tally:

actor Tally {
  waiting u64;                         // how many partial sums are still to come
  total u64 = 0;

  pub async do add(self, partial u64) {
    total = total + partial;
    waiting = waiting - 1;
    if waiting == 0 {
      print <- "total = ", total, "\n";
    }
  }
}

actor Worker {
  tally Tally;

  pub async do sum(self, from u64, to u64) {
    mut partial = 0u64;
    each n in from .. to {
      partial = partial + n;
    }
    tally.add(partial);                // a message to another actor
  }
}

fn main() {
  imm tally = new Tally(4);
  each k in 0u64 ..< 4u64 {
    imm worker = new Worker(tally);
    worker.sum(k * 1000 + 1, k * 1000 + 1000);
  }
}

It prints total = 8002000. Which worker finishes first changes from run to run, but the total never does: the tally handles one partial sum at a time, so its running total needs no lock, and it knows the job is done when its count of sums still to come reaches zero. Each worker lives on after main lets go of its handle, until its message has been handled. For the common case of one loop spread over every core, the next page has something simpler still.

Declaring one: state and behaviours

An actor is declared with actor, and it runs on the actors package, which a module declaring one imports. Its body is written as a struct's: fields, an init, behaviours, synchronous methods, a final:

import actors;

actor Counter {
  count u64;                       // its state: private to it

  fn init(self &new, start u64) {   // run by 'new Counter(start)', in the actor
    *self = new Self(count: start);
  }

  pub async do add(self, n u64) {  // a behaviour: sent as a message
    count = count + n;
  }

  fn doubled(self &) u64 {         // synchronous: called, inside the actor
    count * 2u64;
  }
}
  • The fields are its state, private to it: a field is never pub, and nothing outside the actor reaches one.
  • A method declared async do is a behaviour: a message, run later, when the actor is scheduled. async do is one keyword of two words.
  • A method declared fn is synchronous: the actor's init and final, and any helper, which runs inside the method that calls it, as a struct's method does. It is the actor's alone.

Whether a behaviour declares a return type decides whether a reply is sent; whether it holds an await decides whether it waits. So a behaviour is fire and forget (neither), a cheap query (a return type), one that awaits and owes nobody, or the full handshake (both). (Behaviours and methods, The four behaviour shapes, The declaration.)

From Making an actor: The initializer's parameters must be Sendable too, since the state made from them runs on other threads. An actor may declare several initializers, as a struct may, each joining the overload name init. One that declares none is made by its state's implicit initializer: new Counter(5u64) takes the fields whose types are written, in order, a field with a default taking it where the argument is left out. That initializer is the module's own, as a struct's implicit one is where its fields are private, except for a pub actor with no fields at all. There is no other way to make an actor, and no creation function: spawn stays reserved.

Making one and sending it messages

fn main() {
  imm c = new Counter(0u64);       // the first actor starts the workers
  c.add(5u64);                     // a message: queued, and run later
  c.add(7u64);                     // run after the first
}                                  // then the program waits until all is quiet, and stops the workers

new Counter(args) makes an actor and answers its handle. Calling a behaviour on the handle, c.add(5u64), sends that message: a send is one-way, it queues the message and returns. Each sender's messages to one actor are handled in the order sent. A handle may be copied: passed, stored, kept in another actor's state, or put in a message, as the café's baristas hold the Till above. An actor dies when its last handle has gone and its mailbox is empty.

The runtime starts and stops by itself: the first actor made starts the worker threads, one per logical processor by default, and when main returns the program waits until no actor is queued or running, then stops them. (Making an actor, Messages, self and selfactor, How the runtime works.)

From Messages: A send is one-way: it queues the message and returns. An answer comes back only to an await, or as a message sent back to a handle passed along. Each sender's messages to one actor are handled in the order sent, and a message is never overtaken by one it caused. Each argument arrives moved into the behaviour's call, once: a value that may only move (a uni or So owner) arrives whole, and a counted one (a handle, an Arc, a lock-managed Arc[Mutex, T]) is counted once.

From An actor's life: While an actor is queued to run, or running, the scheduler holds one owner more, taken by the send that found it idle and dropped when its mailbox is found empty. So an actor dies exactly once, when its last handle has gone and its mailbox is empty: a handle dropped with messages still queued leaves the actor alive until they are handled. At its death its state is finalized (its final, then its fields, handles to other actors among them), on whichever thread let go last, then the block is freed. Actors that hold handles to each other in a cycle never die by counting, as a cycle of Arc owners never does, until one of them lets go.

From self and selfactor: An actor has two selves. self is its state, lent to the method while it runs; it never leaves the actor. selfactor is its handle: another owner of the actor, a value that may go anywhere a handle may — into a message, into another actor's state, or to an await on one of its own behaviours:

actor Doubler {
  pub async do double(self, n u64) u64 {n * 2u64;}

  pub async do twice(self, n u64) u64 {
    imm once = await selfactor.double(n);  // a message to itself
    imm again = await selfactor.double(once);
    again;
  }
}

await doubler.twice(5u64) is 20. (The rest, sending to itself with self.m() and where selfactor may be written: Sending to itself.)

Awaiting a reply

A message is one-way: whatever the behaviour returns is dropped. Inside an actor's own behaviour, await sends a message and waits for what the behaviour it sends returns:

actor Store {
  total u64;

  pub async do add(self, k u64) {           // fire and forget
    total = self.plus(k);
  }

  pub async do count(self) u64 {total;}     // a cheap query

  fn plus(self &, k u64) u64 {total + k;}   // synchronous: an ordinary call
}

actor Client {
  store Store;

  pub async do run(self) {                  // awaits, owes nobody
    store.add(5u64);
    store.add(7u64);
    imm c = await store.count();
    say("count", c);
  }
}

Sent client.run(), with a Store whose total starts at 0, this prints count 12: both adds reach the Store before the count does, since one sender's messages are handled in the order sent. What an await does:

  1. It asks. The behaviour after await is sent, as any message is.
  2. The behaviour pauses. The worker does not wait with it: it goes on to other work.
  3. Other messages run. The actor handles the rest of its mailbox meanwhile, so its state may have changed by the time the behaviour resumes.
  4. The reply resumes it, with the value as the await's.

An await stands only in a behaviour, never in a fn, and it pauses only the behaviour it is written in. The method still reads as one scope: every value it holds when it pauses dies where it would if the method had never paused. An I/O operation is awaited the same way (HTTP an actor awaits). (Awaiting in depth: what crosses an await, an await inside a statement, futures.)

From Futures: storing a call's value: A call of a behaviour that returns a value, written where its value is kept — bound to a local, passed on, returned — sends the request at once and gives back a future: a value standing for what the behaviour will return. An await on the future waits for that value. So several requests can be in flight at once, and their answers collected later:

actor Stock {
  pub async do price(self, item u64) u64 {item * 3u64;}
}

actor Basket {
  stock Stock;

  pub async do total(self) u64 {
    imm apples = stock.price(4u64);     // sent: a future comes back at once
    imm pears = stock.price(5u64);      // both requests are in flight
    imm a = await apples;               // waits for the first
    imm p = await pears;                // then for the second
    a + p;
  }
}

await basket.total() is 27. Both requests are sent before either is waited for, so Stock may work on the second while Basket waits for the first. A behaviour is declared once, and how it is called says what becomes of its value:

  • await stock.price(4u64) sends it and waits here: the await's value is the behaviour's, and no future is made.
  • imm f = stock.price(4u64) sends it and keeps its future, an actors.Future[u64], for an await later.
  • stock.price(4u64);, a statement of its own, sends it and forgets it: its value is dropped.

An await on a future pauses only if the value has not arrived. If it has, the behaviour goes on at once. (A future handed to another actor, a future of a value that moves, and one that never arrives: Futures.)

From A behaviour that returns nothing: Whether a reply is sent is the behaviour's declaration to say, never its caller's: one with no return type sends none, so there is nothing to await, and an await on it is refused. A caller that needs to know a behaviour has finished needs to know whether it worked, too: the behaviour declares a return type, a status, and the caller awaits that.

actor Log {
  pub async do flush(self) {}             // owes its caller nothing
  pub async do commit(self) bool {true;}  // answers with a status
}

actor Writer {
  log Log;
  saved bool;

  pub async do save(self) {
    await log.flush();            // refused: flush sends no reply
    saved = await log.commit();   // waits until commit has run, and learns whether it worked
  }
}

What may be sent

A message carries its arguments to the thread the actor runs on, so every parameter of a behaviour, and of an actor's initializer, must be Sendable, and one that is not is refused where it is declared. The compiler works out Sendable from what a type holds, with nothing to write:

  • Sent freely: numbers and other plain values; a value that moves, which arrives whole (a So owner, a List of such values); an Arc[imm, T], an Arc[Mutex, T]; another actor's handle.
  • Refused: a borrow (&x, &mut x, but for a borrow of something that lasts the whole program, written so), an Rc, and anything holding one. The refusal names the part of the type that binds it to its thread.

The actor's state is not asked, since it never crosses as a value: it may hold an Rc, and its methods may borrow freely. (Race condition safety, Sendable and Shareable.)

Sharing read-only data: Arc

Immutable data is shared between threads through the sync package's Arc region (import sync use Arc), whose count is atomic: Arc[imm, T] owners may be copied and dropped on any thread, and the value is freed once, after the last. An Rc owner's count is not atomic, and it must stay on one thread. (Sharing immutable data: Arc, and regions in depth.)

Sharing and changing: lock permissions

When several threads or actors must change one value, a lock permission guards it. A lock permission is a type, written where a permission goes, and its value is the lock: Mutex and Rwlock, the sync package's, on Arc, and Rwcell, core's, for one thread, on Rc:

import sync use Arc, Mutex;

alias Counter = Arc[Mutex, Count];
imm c = new Counter(0u64);
imm point = new Arc[Mutex, Point](x: 2, y: 3);

An Arc[Mutex, T] may be copied, and handed to another thread or actor. But it gives no direct access to its value: the value is reached only by borrowing (Borrowed references), and obtaining the borrow takes the lock first:

imm n = c.n;            // refused: a read without the lock
c.n += 1u64;            // refused
imm v = (&*c).n;       // a borrow takes the lock: allowed

A borrow that may write takes the lock for writing; a read-only borrow takes it for reading (a Rwlock lets several readers in at once). A borrow that finds the lock held waits. The lock is given back at the borrow's last use:

imm point = new Arc[Mutex, Point](x: 2, y: 3);
{
  imm pointref = &mut *point;  // takes the lock
  pointref.x += pointref.y;     // the point is reached only while it is held: the last use
  show(point);                  // the lock was given back after that statement, so a
}                               // borrow in show does not wait for this block's end
bump(&mut *point);              // taken and given back within the statement

So nothing reaches the value unlocked, and nothing is left locked by forgetting to unlock it. An await ends every borrow the behaviour holds, so no lock is held while a behaviour waits; to reach the value again, the behaviour borrows it again. Cone does not prevent deadlock: a thread borrowing through a Mutex it already holds through another borrow waits forever. (Lock permissions in depth, Permissions in depth.)
