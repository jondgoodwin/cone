Namespaces

A module spans the files of its folder, its designated file declares it with mod, and a subfolder holding its own designated file is a submodule of it, as is a file of the folder that opens with its own mod. Every file that makes a module opens with its mod line, and its imports come right after it. A module reaches its own submodules by name, folds their names in with a use statement, and reaches a sister by importing her, but never a name of its parent: modules depend on each other in one direction only. A module may name on its mod line the names a bare import of it folds. A module is never declared inside a source file: nesting is by files and folders. Only a package's generated include file writes a module block, for each submodule it reaches. A module may be C-named with @c on its mod line.

Many things are given names: variables, functions, types, fields, methods, etc. The collection of all names defined for a scope is called a namespace. Blocks and types are two different kinds of namespaces.

Namespaces facilitate a modular architecture by:

  • hiding implementation details visible within the namespace behind the simpler, durable API shown outside. This is called encapsulation.
  • lowering the accidental risk of name collisions, where two different items (possibly created by different authors) are given the same name.

The rules governing names vary according to the type of namespace it belongs to. Let's review those here, beginning with the introduction of a new kind of namespace: the module.

Modules

A module is a global namespace. You have seen code examples for modules already:

// A type declaration
struct Handler {
  pub id u32;
}

// a global variable
imm handler = new Handler(0);

// A function
fn main() {
  // do some stuff
}

As this example shows, modules hold global variables, functions, and type declarations. They can also hold other named things, such as macros and even other named modules. Further, modules can import names from other modules: an import binds the other module's name, and its use clause folds that module's public names in as names of this one.

Every program or library has a single main module. That main module may import other modules or types offering reusable, isolated capabilities it depends on.

A module is a folder's files

A module's source files are the files of a folder. One of them is the folder's designated file: the file named for the folder, as geometry/geometry.cone is for geometry. It is the file that declares the module, with mod written as its first statement:

mod geometry;

pub struct Point {
  pub x f32;
  pub y f32;
}

Point the compiler at that file and it finds the rest itself. Every other .cone file in the folder belongs to the same module, unless it opens with a mod of its own and so is a module of its own, and so does every file of every subfolder that holds no designated file of its own, at any depth. Nothing lists them: putting files in a folder is what brings them together, and moving a file to another folder moves it to another module. Such a subfolder groups files without making a namespace of them, so a large module can be organized by topic with no new names to write and none to path through.

The folder names the module. A name written after mod may restate the folder's name and may not change it, because a name on the filesystem is one that any tool can read without parsing Cone. That name is what another module binds when it imports this one, the name a path through the module is written with, and the name the module's declarations carry in the symbols the linker sees.

Only the designated file declares the module, and it must. Because the declaration claims it, it comes before everything else in that file, and a module declares itself once. A file the folder brought in declares nothing: a file whose first statement is a mod is not brought in at all, but is a module of its own, and a mod anywhere later in a file is an error.

The folder is the only thing that brings a file into a module: nothing written in one file brings another in, so a file's module can be told from where the file sits. include, which once brought a named file in, is retired.

Two files of one module may not share a name, however deep in the folder tree they sit, and a file belongs to one module: a file another module already holds cannot be brought into a second one.

A module's own name is one of the names in reach inside it. That matters where a local variable, a parameter or a type's member hides a name the module declares or a module it imports, since it is the only way to reach past the nearer one without renaming anything (a method named like an imported module is the common case):

mod counters;

imm total = 0;

fn addTo(total i32) i32 {
  counters.total + total;   // the parameter hides the global; the module's name reaches it
}

A file the compiler is pointed at that is not its folder's designated file is a module of one file: a complete program or library as it always was, named after the file, with the files beside it none of its business. It opens with a mod line too, naming the file, as mod counters; opens counters.cone. For now a mod declaration in such a file may still rename its module.

A module's header: the mod line, then the imports

Every file that makes a module opens with its mod line: a folder's designated file, a one-file module, and a file the compiler is pointed at or an import reaches that is a module of one file. The line names what the filesystem already names, the folder or the file, so that the name is the first thing a reader of the file sees. A file that makes a module and opens with anything else, a mod trait included, is an error. The other files of a folder's module have no mod line, since the folder is what names the module they join.

A module's imports come right after its mod line, ahead of everything else it declares, and so they are all in its designated file. Comments may sit anywhere among them:

// geometry: points, and the shapes built on them

mod geometry;

// What this module uses
import stdio;
import units use metre;

pub struct Point {
  pub x f32;
  pub y f32;
}

An import written after any other declaration, a standalone use included, is an error. So is an import anywhere in the module's other files: they have no mod line, so there is no place for one. A use is not an import, and any file of the module may write one. So the top of the designated file says which module it opens and everything that module depends on, and the build tool, Congo, reads nothing more of it to find a package's modules and what they import.

Submodules

A subfolder that holds its own designated file is not organizing files: it is a submodule, a module of its own inside the module whose folder holds it. One rule decides both kinds of subfolder — does it hold the file named for it? — and it is the same rule that made the folder a module in the first place.

geometry/
  geometry.cone      the module 'geometry'
  shapes.cone        a file of 'geometry'
  detail/util.cone   also a file of 'geometry': 'detail' holds no detail.cone
  scaling/
    scaling.cone     the module 'geometry.scaling'
    matrix.cone      a file of 'geometry.scaling'

Its parent reaches into it by writing a path, the same way a path reaches into any module: scaling.twice(n) from inside geometry. What the parent may reach is what the submodule declares pub, because a submodule is a module and its private names are its own.

A parent folds a submodule's names in with use. A submodule is never imported — its subfolder or its file is what brings it in — so a parent that wants its child's names bare writes a use statement naming the submodule, and the same clause an import's use takes follows the name:

mod geometry;

use scaling;                     // every public name of scaling: twice(n), not scaling.twice(n)
use measure inches as toInches;  // one name, spelled another way here
use units { metre, yard };       // a list, written as a block
use shapes but Hexagon;          // every public name but one
use scaling.fixed;               // a submodule's pub submodule, reached by a path
pub use detail;                  // detail's public names, re-exported as geometry's

Only a submodule's public names fold, and naming a private one is an error, whether in a list or after but, where there is nothing to leave out; so is the submodule's final or clone, in a list or after but, which a star never folds. The folded names are this module's own and private to it unless the statement is written pub use, which re-exports them: the parent's neighbours then reach them as names of the parent, while the submodule itself may stay private. A submodule is folded once: a second use of it is an error, so say everything in one.

A standalone use folds what a module reaches without importing it: an enum, below, or a submodule. A module brought in by import is folded by that import's own clause, import math3d use Point3;, and naming it in a use statement is an error — one spelling for each situation.

A submodule is private to its parent unless it says otherwise. Written pub mod scaling; it can be named from outside its parent as well, as geometry.scaling.twice; written mod scaling; only geometry may name it. The pub goes on the submodule's own declaration, since the parent declares nothing about a subfolder or a file, and it means what it means everywhere else: this entry is visible outside this namespace. It opens a submodule to the rest of its package, never beyond: a program importing the package reaches a submodule's names only where the package's root re-exports them with pub use, since the package's include file declares each submodule in a private block.

A submodule of one file needs no folder. A folder is only worth making when a module has more than one file, so a file of a module's folder whose first statement is a mod declaration is a submodule by itself:

geometry/
  geometry.cone      the module 'geometry'
  shapes.cone        a file of 'geometry': no 'mod' of its own
  units.cone         'mod units;' -- the module 'geometry.units'
  scaling/
    scaling.cone     the module 'geometry.scaling'
    matrix.cone      a file of 'geometry.scaling'

units is a submodule in every respect scaling is: private to geometry unless it is written pub mod units;, reached by a path, units.metre(), folded by use units;, and imported by its sisters by name. Its own imports follow its mod, as a designated file's do. It does not join geometry, and none of geometry's files join it. It is named for its file: mod units; is written in units.cone, and any other name there is an error.

When it grows past one file, move units.cone to units/units.cone and put the new files beside it. Nothing that names it changes: not its name, not a path through it, and not the symbols the linker sees. A units.cone that declares a module beside a units/ folder that holds its own units.cone is an error, since that is two modules of one name.

A module must sit directly in its parent module's folder — as a file there, or as a folder that is a direct child of it — so the module tree has the shape of the folder tree. A designated file further down — inside a folder that holds none of its own — is an error rather than a deeper submodule, and so is a file that opens with mod inside such a folder.

Two submodules of one module may name each other, by importing. The module that holds them is the registry they are found in: they are public to each other and to it, and invisible outside it unless it publishes them. So import scaling; written inside a sister of scaling finds her there — see importing a sister module — and nothing arrives unasked, because a name nobody imported is not a name of the module.

A submodule does not import its parent's names. A module depends on each of its own submodules, so a submodule that depended on its parent — import Point; inside scaling, naming geometry's Point — would make the two depend on each other, and that is an error (see one-direction dependencies). What a parent and its submodules share belongs in a sister of theirs, which each of them imports. A submodule cannot name its parent either — containment runs one way.

The reach between sisters is one level and does not accumulate as you go down. A module sees its own parent's submodules, and not its grandparent's.

import

Note: Without a build description, a module found beside the importing file is only declared, so a program importing one cannot be linked.

After a program's source code gets big enough, it may become easier to work with when partitioned across multiple files. The files of one module need nothing to stitch them together: a module is the files of its folder, and the compiler finds every one of them itself. Two mechanisms reach beyond a module: import, for another Cone module, described here, and extern, for what is defined in another compiled unit — a separately built Cone package, or code written in another language such as C — described in Talking to C.

include is retired

A file joins a module by being in the module's folder, so no statement brings one in. include, which once did, is a reserved word, and the compiler reports an include statement wherever it is written. Put the file in the folder of the module it belongs to instead.

Importing a module

Use import to import another module that has its own namespace. For example:

import math3d;
import opengl;

An import may fold the module's names in with a use clause, as Namespace folding describes.

Where an import is written

An import comes right after its file's mod line, with the file's other imports, so that every dependency a module has is stated at its declaration; one written after any other declaration is refused. A file of a folder's module other than its designated file has no mod line, and its imports come first.

File names and Paths

An import names a module, or where the module's name is not found, a file path. If the file path includes characters that are not legal for a Cone name (such as periods or slashes), it should be enclosed in double quotes (and make use of the appropriate escape sequences where needed). If the file's extension is not specified, .cone is assumed.

In the simplest case, the file path specifies just the name of a source file to be found in the same folder as the source file which imports it. If a file of that name is not found there, the compiler will look for it in a folder of the same name (e.g., "useme/useme.cone"). This behavior allows source files to be organized across nested folders, where related source files are grouped together.

If desired, the file path may explicitly specify folders in front of the source file name. This can be an absolute path name, such as "/libs/math/trigfns". It can also be relative to the source file doing the importing, for example "nomnom/useme" or "../lib/useme".

If the file is not found in the current folder, the compiler searches the package search path for it: first each folder given to the compiler with --path, in order, and then the packages folder. The packages folder holds one folder per package, whose source is its src folder: src/name.cone is the designated file of the package's module, and the folder's other files and submodules are the package's by the module rules. It is where the packages that come with Cone live: stdio, which import stdio reaches; core, which every module imports without asking; and libc and posix, raw bindings to the C library and to the POSIX functions beyond it (the C library's own on Linux, a mapping onto the C runtime on Windows), which core rests on for malloc; and, over those two, fs (files and folders), path (paths taken apart and put together) and env (environment variables), written over ISO C and POSIX. What is Windows-only beneath them is posix's: on Windows its POSIX names map onto the Windows C runtime, and its folder listing (opendir, readdir) and lstat are written over the runtime's _findfirst64 (on Linux they are the C library's); path reads the paths of the system it is built for (Windows' drive letters, shares and both separators, or POSIX's /). Beside them, process runs a program and waits for it (its arguments, a working folder, a time limit; its exit code and what it wrote to standard output and standard error, captured apart): its interface belongs to no one system, its insides are written over kernel32 (CreateProcessW, pipes, a job object) on Windows and over posix_spawn on Linux, since neither ISO C nor POSIX alone can do it on both. The compiler finds its packages folder from where it is installed: the nearest packages folder holding core, in the compiler's own folder or one above it. The CONE_PACKAGES environment variable names another. This allows the name of an imported module to correspond to some externally-hosted packaged library.

A name is looked for in that order, and a sister comes before all of it, since the enclosing module is asked before any file is looked for. So inside a submodule whose sister is named stdio, import stdio reaches her, and a package in a --path folder is found ahead of the packages folder's package of the same name.

A package built from a build description searches for nothing. After a sister, an import is found where the description's import line for its name says, and an import the description provides nothing for is an error, import stdio included. The file such a line names is only declared, as another package's include file is: its name is the import's. Its functions are called, and its globals read, in the object of the package it stands for, which is linked in beside the program's; only its inline bodies are compiled into the importer. It is a module file like any other, so it may import in its turn: those imports are found where the description's package lines say, and what they bind is the include file's own, not the importer's.

More than one module may import the same module. The imported module will only be loaded once. Its information is then reused by all modules that imported it.

A module imports another module once. Writing the same import a second time does nothing. A second import of the same module that says something different — it folds in other names, spells one differently, or is pub where the first is not — is an error, which names both. Say everything in the one import.

A module's own submodule is not imported, and importing one is an error: the subfolder or the file that holds it is what brings it in, so its name is already there to be written. Its names are folded in with a use statement instead, which takes the same clause an import's use does.

Compiled apart, and without a build description

Separate compilation is built through a build description, which the build tool, Congo, writes for each package: a library compiled from one exports what its importers need, and a program whose import line names that library's include file links with the library's object. A library's compile generates its include file, and Congo compiles every program and package against the include files of the packages it imports. Above is how a program built that way finds its imports.

A program compiled without a build description finds them by the package search path instead. A module found on the search path is compiled into the program that imports it. One found beside the importing file is only declared, so a program importing one cannot be linked.

Importing a sister module

A submodule imports one of its sisters by writing her name, not a path to her file:

mod engine;
import wheels;

pub fn drive(n i64) i64 {
  wheels.turn(n);
}

A module is the registry its own modules are found in. They are public to each other and to it, and invisible outside it unless it publishes them — so an import written inside one of them looks the name up in the enclosing module and finds a sister there, with no file to search for and nothing loaded. It is the same mechanism that reaches a separately built library; only the registry that answers is different.

What is in reach is the enclosing module's modules and no further up than that. A module two levels down does not see its parent's sisters.

A module inside such a tree is reached by its name, never by a path to its file. Writing import "../wheels/wheels" is an error, and so is a module importing the module that contains it: containment runs one way.

A name of the parent is not imported

The enclosing module's namespace holds more than its modules: what it declares, and what its own imports bind. But a submodule may not import any of it:

mod scaling;
import Point;               // error: Point is the parent's, and the parent
                            // contains scaling, so the two would loop

A module depends on each of its own submodules, so a submodule that depended on its parent would close a loop, which is an error naming both. The same holds for a module the parent imported, reached through the parent: the submodule imports it by its own name instead. What a parent and its submodules share goes in a sister of theirs, which each imports:

mod scaling;
import shapes use Point;    // shapes is scaling's sister, and holds Point

Re-exporting what you import

What an import brings in belongs to the module that wrote it. A module importing that module sees only what it passed on, which it does by writing pub:

pub import wheels;          // 'wheels' is a public name here, so 'engine.wheels.turn' resolves
pub import rims use *;      // and so is 'rims', and every name folded in from it
import tyres pub use *;     // every name folded in from tyres is public, and 'tyres' is not
import bolts use *;         // while these are this module's own business

pub before import reaches every name the import binds: the module's own name, and each name it folds in. pub use reaches only the names the use clause folds in, so a module can pass on a library's names without passing on the library. Writing both is allowed and means what pub import means alone. pub says what it says everywhere else — this name is visible outside the module that holds it — and it never makes public something that was not public where it was declared.

A name made public this way travels on: a module that imports engine with use * receives what engine passed on, and nothing that it kept for itself. That holds round a cycle of imports too: where two modules import each other, what each re-exports reaches the other, as it would if neither imported the other back.

Module-qualified names

import is bringing in a module with its own namespace. By default, the names of an imported module are kept separate from the names in the module doing the importing. The only name that the importing module automically obtains is the name of the module it is importing — unless that module names a default fold on its mod line, which an import writing no use clause of its own folds in as well.

Since the namespaces of the modules stay separated by default, the importing module normally refers to names inside the imported module using a module-qualified name:

import opengl;

fn setColor(col Color) {
  opengl.setColor(col);
}

opengl.setColor references the setColor function to be found in the imported opengl module. The period separates the module name from the name of the function defined in that module. It is the same operator that reaches a member of a value: one period, for a path through a namespace and for a member of a value alike.

Module-qualified names can only access names the module declared pub. Every other name is private to its module and is not accessible to any other module.

Importing under another name

as after the module binds it under a name of the importer's choosing instead of its own:

import geometry as geo;

pub fn far(a geo.Point, b geo.Point) i64 {
  geo.dist2(a, b);
}

The new name is used exactly as the module's own would have been: for its types, its functions, and the modules inside it (geo.metric.cm). The module's own name, geometry, is not a name here at all. Every form of import takes as — a name or a quoted path, a package or a sister, pub or not — and it comes before any use clause, which folds what it would have folded without the rename:

import geometry as geo use dist2 as d2;

A module's default fold still applies to a renamed import that writes no clause, and pub import units as u; makes u a public name of the importing module, as Re-exporting describes for the module's own name.

The rename is a name of the importing module like any other, so it may not collide with one of its declarations, with the name another import binds, or with a name a use clause folds in. A module is still imported only once, so a second import of it is an error whatever name each binds it under. A use clause may not fold the module's own name back in, which would undo the rename.

The usual reason to rename is a name that is wanted for something else. A type's field or method hides a module of the same name inside the type, its methods' signatures included, so a method named after the module it returns a type of needs the module imported under another name; see Implicit field and method access.

Namespace folding

By default, an imported module does not pollute the namespace of the module importing it. This is often what you want. However, it can become tedious to read (and type) module-qualified names when they are used a lot by the importing module's code. To address this, an import may end with a use clause, which folds some or all of the module's public names into the importing module. It is the same clause a global variable carries, with the imported module in the place of the variable's type. The names being folded can be for anything: type, function, global variable, macro, etc. However, names folded in may not collide with any name the importing module already uses.

To fold in just a few specific names, list them after use, separated by commas:

import math3d use Point3, Mat3;

fn move(pos &Point3, delta Point3) {
  pos += delta;
}

Use as to give a folded name another spelling here, for instance when its own is already in use:

import math3d use Point3 as Point;

fn move(pos &Point, delta Point) {
  pos += delta;
}

A long list may be written as a block instead, which means the same thing:

import math3d use {
  Point3 as Point,
  Mat3,
  Quaternion,
};

Or one can fold in all public names from the module using *, and leave some out with but:

import math3d use *;
import opengl use * but Point3;   // math3d's Point3 is the one wanted here

An import's own use clause replaces whatever default fold the imported module names: import bigint; folds what mod bigint use BigInt; says, and import bigint use *; folds every public name instead.

The use clause is the only way an import folds names in. import math3d.*; and import math3d.Point3; are errors, each naming the clause to write instead.

A folded name is private to the importing module unless the import says otherwise, as Re-exporting describes. A name the module does not have, or does not make public, cannot be folded in, and it is an error to list one. Naming either after but is an error too: seen from outside the module a private name is as absent as a missing one, and * never folds it, so there is nothing to leave out. Nor does * fold the module's finalizer final or a clone, which belong to the module's own lifecycle, so naming one of those after but, or in a list, is an error as well. So is folding in a name the importing module already has for something else, whether it declared that name or folded it in from somewhere else: rename one with as, or leave it out with but. Writing the same thing in twice is an error too: listing a name twice, or listing it from two modules that each re-export it. A module imports another only once, so a second import of it, even an identical one, is an error. What a wildcard brings is different, since nothing was written twice: if two modules you fold in with * each re-export one function, say, folding in both is fine, and so is listing the function from one while the other's * brings it too. The name is bound once, and if either fold made it public, it is public.

A module's default fold

A package named for the one thing it provides would put that name in every path twice: bigint.BigInt. So a module may say, on its own mod line, what an importer gets when it imports the module and asks for nothing in particular. A package holding one thing then just becomes the thing:

mod bigint use BigInt;

pub struct BigInt {
  pub digits i64;
}

pub fn helper(n i64) i64 {
  n + 100;
}

Now a module that writes a bare import bigint; has BigInt directly, and bigint as well, so bigint.helper still reaches what the default leaves out. With extends, the clause comes last:

mod bigint extends base use BigInt;
  • The list is the default, however many names it holds. mod units use metre, foot; makes a bare import fold both. * and * but may be written too. Adding a name later only adds to what importers see.
  • An importer's own clause replaces the default entirely. import bigint use *, import bigint use helper or import bigint use * but BigInt folds what it says, and nothing of the default.
  • Here use runs the other way. Everywhere else, use folds names into the module where it is written. On the mod line it names what importers fold.
  • It is not an export list. pub still decides what is reachable, and every name the clause lists must already be a public name of the module: one the module has not got, or keeps private, is an error at the mod line. The clause only chooses which public names a bare import folds.
  • The importer decides the rest. The names are the importer's, private to it unless it writes pub import bigint;, which re-exports them with bigint. A default name that collides with one of the importer's own is an error there, settled by writing a clause of its own. For the same reason neither as nor pub may be written in the clause on a mod line.

The default applies wherever a module is imported with no clause of its own: a sister, or a module found by its file. A use of a submodule is not an import, and still folds every public name.

Folding an enum's variants in

An enum's variants are names of the enum, reached as Colors.Red. A module that wants them as names of its own writes a use statement naming the enum, and optionally which variants — the same statement that folds a submodule's names in:

use Colors;                  // Red, Green and Blue are names of this module
use shapes.Shape Circle;     // one variant of an enum another module declares
pub use Suit;                // and names other modules may reach through this one

The names are this module's own and private to it unless the statement is written pub use, which is how a module re-exports an enum's variants: another module reaches them through it, and an import of it with use * brings them in bare. The core library does exactly this for Option and Result, which is why Some, None, Ok and Error are bare in every program. See Naming a variant.

Types as Namespaces

Declarations for struct and enum types are also namespaces. At a minimum, these hold the names of the type's fields and methods. They may also hold the names for the type's static functions, its static variables and the names of other types (e.g., enums). An enum's namespace holds its variants, which is why a variant is reached through its enum, Colors.Red, unless a module folds it in with use. What a type's names may be, and who may reach them, is in Encapsulation.

Static Functions

In addition to methods, a type may declare useful static functions that are not methods and do not work with a specific object of that type. A static function is declared among the type's methods, and what makes it static is that it has no self parameter. It is not marked static: that word declares a static variable, and before a function it is an error.

struct Counter {
  count i32;

  pub fn zeroFactory() Counter {
    new Counter(0);
  }
}

To make use of the function outside the type, qualify the name with the name of the type:

mut cnt = Counter.zeroFactory();

Function Blocks

All logic blocks inside functions and methods are namespaces that hold local (and parameter) variables.

Every block's names are:

  • unique. no two variables in a block may be declared with the same name. However, variables in a block might shadow same-named variables in outer scopes.
  • order-dependent. Logic may not reference a local variable until after it is declared.
  • private. Only the block logic may see and use local variables.

alias

Note: an alias of a type is implemented. An alias of a function, a global, a module or a method is not yet.

To give some type a second name, declare an alias in the appropriate module's global scope (it may not be placed anywhere else):

alias Noderef = Rc[mut, Node];

In this example, wherever Noderef is used in this module, it will be understood to mean Rc[mut, Node].

What follows the = is the alias's target. It is resolved when the program is compiled, and is never a computation: an alias names something that already exists, it does not make a value.

An alias is a second spelling for one type, not a second type: it creates no distinct type and nothing is asserted by using one name rather than the other. To declare a type of your own that enriches an existing one with methods, which is a distinct type, see Enriching a concrete type.

Because it is a second spelling and not a second thing, it also qualifies what it names. Where alias Sample = Reading; names a struct, Sample.make(1) reaches the same static function Reading.make(1) does.

An alias may be declared pub, which makes the name visible outside its module; the type it names keeps its own visibility, so an alias never lends out something private. A chain of aliases is ordinary — one alias may name another — but a chain that comes back to itself names no type at all, and is refused where it is written.

typedef, the statement's former spelling, is retired. It remains a keyword, and the compiler reports a typedef statement where it is written.
