Cone
Owning References and Regions

Note: Contents after a trynew of anything but an array are not implemented. Making text from bytes, bytes as &str, does not yet check that the bytes are UTF-8, nor that nothing still writes them while the text is used. The RcPool and SoPool pools, and the &eventPool mut ... allocation shown for them, are not implemented: how a value is allocated in a dynamic region such as a pool is an open design question, and only the generational Pool exists. A trynew in a region value, an arena for one, is refused: whether an allocation in a region can fail is not settled. The allocRegion method behind new x[T](...) is provisional: its name and its shape are not settled. A pool's Ref is not yet paired with its own pool: used with another pool of the same type, it is checked there, and cannot reach outside that pool's memory. An Arc value has no weak references. The region declaration the first examples of Region Strategies show is not implemented: a region is a struct that declares RegionRef. Nor is .weak on an owning reference: a weak reference is made with Weak[T].of(owner) from an Rcw owner. The &arena mut 5 allocation and the Arena['a] and ArenaRef+'a' spellings below are not implemented; the arena package's DynArena hands out keys. How a value is allocated in a dynamic region such as an arena or a pool is an open design question: the packages allocate with a.alloc(value), new a[T](...) and p.add(value), and no other spelling is read.

What is a Region?

Until now, the values we have worked with have all been stored in global and local variables:

  • All global variable values are stored at fixed memory locations, established by the linker.
  • Local variable values are allocated and de-allocated within an execution stack in LIFO order. Each execution thread has its own stack.

When we want to dynamically allocate memory for a value during runtime that we need to survive beyond the scope it is allocated in, neither global and local variables can handle this requirement. This is when we need to make use of the "heap", the large amount of free memory available to use outside of what has been reserved for global variables, code and any stacks.

Unusual among languages, Cone conceptually partitions the heap into regions. Each region has its own strategy for allocating and automatically reclaiming memory that holds values. Every program value on the heap is wholly located within and governed by its owning region.

The reason Cone supports multiple regions is because there is no one perfect strategy for allocating and automatically freeing memory. Each strategy (e.g., tracing GC, ref-counting, single-owner, pools or arenas) carries different trade-offs in terms of throughput, latency/responsiveness, memory use and leakage, data structure flexibility, and programmer convenience.

Instead of restricting a program to the limitations of only one memory management strategy, as most languages do, Cone dynamically partitions memory into regions, each with its own approach to memory allocation and collection. For every new data object, Cone allows the programmer to specify, at allocation time, which region the object belongs to, according to how well it matches the object's usage profile.

Owning vs. Weak References

There are two kinds of region-managed references:

  • Owning references. When you allocate a new value within a region, you get back an owning reference that points to the new object. For some regions, multiple alias copies may be created which are also owning references. For safety reasons, a region's automatic memory management strategy ensures that the object's memory is freed only when when the last owning reference to the object expires. This timing ensures that an owning reference is always safe to de-reference and that an object will only be freed once.
  • Weak references. A weak reference points to an object that may or may not still exist in the region's memory. Before we can de-reference a weak reference, we first need to confirm it still exists.

Creating Owning References

Let's ask a region to allocate a new value and give us back an owning reference:

imm node = new Rc[mut, Node](1);

Like every construction, an allocation begins with new. What follows it is the type of the owning reference we want back, specifying:

  • Region which allocates the value and manages its lifetime. In this case, the value is allocated in the Rc region. Later, we will explore some of the different kinds of regions supported by Cone. The region may be Rc or So from core, the sync package's Arc (Rc whose count several threads may change at once), the collector package's garbage-collected Gc (custom allocators; discouraged, single threaded and outside actors only), the rcweak package's Rcw, or any struct declaring is RegionRef. The region's own methods, and whether it declares Move, decide when a value is freed; its finalizer runs just before (finalizers).
  • Permission. This governs what you may do with the reference. It can be a static or lock permission. uni is assumed for an owning reference when no permission is specified.
  • Value type, the type of the value allocated: in this case, a Node.

The parentheses hold the arguments of the value's initializer, chosen as they are for any construction: here, Node's implicit initializer, which takes its fields in order. Empty parentheses may be left off. What we get back is an owning reference of the type written, Rc[mut, Node], which this example stores in the variable node.

Allocating a Finished Value

The parentheses may instead hold one finished value of the value type, which is moved into the new allocation, as though every type had an initializer taking a finished value of itself. A value no initializer constructs — a number, an array, a tuple, an enum or its variant, a reference — is always allocated this way, and its allocation takes exactly one value, converted to the value type as a variable's initial value is: a number literal takes on the value type, and an enum's variant becomes its enum.

imm count = new Rc[u64](5);                            // the literal is a u64
imm grid = new Rc[mut, Array[i32, 3]]([1, 2, 3]);
imm pair = new So[(i32, f32)]((1, 2.0));
imm maybe = new So[Option[i32]](Some(3));
imm name = new Arc[imm, String](String.from("x"));     // a call's result
imm list = new Rc[mut, List[Fin]](items);              // items is moved in

A struct's allocation is told apart by type: when exactly one argument is given and its type is the struct itself (through an alias as well), it is the finished value, moved in, and no initializer runs; otherwise the arguments go to the struct's initializers, as for any construction. A reference to the struct, or a value that would only convert to it, is not the struct itself.

imm s = new Seeded(4);                  // Seeded's init runs
imm byInit = new Rc[Seeded](5);         // Seeded's init runs again, on 5
imm moved = new Rc[Seeded](s);          // s is moved in; no init runs

A value is constructed once: new Point(p), where p is already a Point, is an error, since a finished value needs no construction; use p as it is.

An alias of an owning reference type allocates the same way, so a program that names its reference type once writes its allocations with that name:

alias Node = Gc[mut, NodeValue];
imm leaf = new Node(1);              // a Gc[mut, NodeValue]

To make a virtual reference, allocate the concrete type and let the reference coerce where the virtual one is wanted: imm shape Rc[mut, Shape] = new Rc[mut, Circle](5);

Allocating with Contents

An allocation takes contents after <-, as a value's construction does (the append operator). An array's contents fill it in the region's memory, an element at a time, each value evaluated as its element is filled: no array is made elsewhere and copied in, so an array of a million elements is allocated and filled with no copy of it anywhere. They are the same contents a value construction of the array takes, the scalars of one written with several sizes, and the allocation takes nothing in parentheses beside them. A collection's contents are appended through the new reference once it is made, as they are appended to a value it constructs.

imm zeros = new Rc[mut, Array[i32, 1000, 1000]] <- fill 0;
imm grid = new So[Array[i32, 2, 3]] <- 1, 2, 3, 4, 5, 6;
imm names = new Rc[mut, List[i32]](10) <- 1, 2, 3;

Allocating a Dynamically Sized Body

Some types have no size to hold: a value of one is never in a variable, a field or a parameter, only behind a reference, which carries what is missing. A trait's virtual reference carries a vtable. The body of bytes, str, is reached by a reference that carries their count: a pointer and a usize, in every region and for a borrow alike (&str, So[str], Rc[str], Arc[str], Gc[str]), 16 bytes where a reference to a type with a size is 8. str declares Immutable, so a reference to it written with no permission is imm (&str is &imm str, Rc[str] is Rc[imm, str]) and mut is refused on it. The region's header sits before the first byte as it does for any value, and the owner points at the byte, so one hop reaches the text.

There is no value of such a body to construct or to move in, so its allocation takes a borrow of one in the parentheses and copies the bytes the borrow holds, as many as it has, into the memory the region gives: the region is asked for the header and those bytes. A borrow of the body is made from a slice of bytes with as, and converts to a slice implicitly; both are the same pair and as checks only that, so the way back is the written as, since bytes need not be UTF-8.

imm bytes &Array[u8] = "hello";
imm view = bytes as &str;                    // a borrow of the bytes: 5 of them
imm text = new Rc[str](view);                // a copy, in Rc's memory
imm same = trynew So[str](view);             // an Option, None if memory ran out
printStr(text);                              // lent as a borrow, which is the &str printStr takes

A string literal is a &imm str: a borrow of its text, in read-only memory, that lasts as long as the program, so it may be sent to another thread. The text is followed by a zero byte for C that the count leaves out, and an owner of str keeps one after its bytes too (C strings). Wherever an owner of str is wanted, in any region, a literal (and only a literal) is copied into one without new; any other &str is copied with new as above.

imm name So[str] = "Padma";                  // new So[str]("Padma"), copied from read-only memory
fn greet(who Rc[str]) {..}
greet("Jayne");                              // the same copy, into an Rc

A growable String is a literal's other destination: where one is wanted a literal is copied into it (imm s String = "core";), by the static function fromLiteral a type declares to say so. And s.freeze() moves a String's bytes into a So[str] without copying them (collection types).

Where a read-only borrow of such a type is wanted, &String for one, the literal is borrowed from a temporary made the same way: &String.fromLiteral("core"), written out. The temporary lasts to the end of the statement and is dropped there, like any temporary a borrow points at (a function's parameter and an init's, in new File("x"), are given one alike); a local's initializer keeps it to the end of the block, as imm r = &make() does. It is lent only to a borrow that cannot write (&mut String is refused, since what is written to the temporary is lost with it), and only inside a function's body, where a statement ends it: a global, a constant, a field's default, a returned value or an if arm is not given one. A parameter's default is made at each call that leaves the argument out, as if the caller had written the literal there: fn shout(s &String = "core") called as shout() lends a temporary of its own (and a String by value is made for the call).

fn shout(s &String) {..}
shout("core");                               // a temporary String, lent to the call, dropped at the semicolon
imm r &String = "core";                      // the temporary lasts as long as the block

The other dynamically sized body is Array[T], the array type without a size, whose elements are any type T and whose count is known only at run time. It is held the same way: So[Array[T]], Rc[Array[T]], Arc[Array[T]] and Gc[Array[T]] are each a pointer and a count, one hop to the elements, and its borrow is the slice, &Array[T] (owned arrays). Its allocation copies the elements of a slice, so it is allowed only where the elements copy, and a List's freeze() moves its block into one instead. The owner's death finalizes each element, and a Gc object counts the bytes its elements really take.

imm primes = new Array[i32, 4] <- 2, 3, 5, 7;
imm owned = new Rc[imm, Array[i32]](&primes);   // a copy: a pointer and a count, 16 bytes
imm kept = list.freeze();                       // a So[Array[T]] holding a list's elements, moved

An owner of a body is a counted owner or a single one by its region and permission, like any other: copies, parameters and fields are counted (an owner of str, written with no permission, is imm and copies, though an So owner still moves), a uni owner moves, and the last to go gives the block back through the region's free. A collector's region marks it through its pointer. Each owner carries its own count, which is right because the body never grows.

Owning Reference Types

Wherever a type is written — a variable, a field, a parameter, a return type, an alias, a generic's argument, an allocation — an owning reference type is written the same way: the region, then in square brackets an optional permission and the value type.

alias Link = Rc[mut, Node];    // shared and mutable
fn first(n Rc[Node]) i64 {..}  // no permission written: uni, the only owner
mut list = List[Gc[imm, Leaf]].empty();

Left out, the permission is uni, which may become any other, so Rc[Node] is Rc[uni, Node]. The region is a struct declaring is RegionRef; a permission given to anything else is an error. A generic region takes its own brackets first, then the reference's: R[A][mut, Node], and allocates as any other, new R[A][mut, Node](1). When the value type is an open trait, the reference is a virtual reference, which carries a vtable beside its pointer (Rc[mut, Shape]); when it is a body whose length the reference carries, it is a pointer and a count (So[str]); for any other value type, an enum included, it is a single pointer.

A match pattern never spells an owning reference type: it names the variant, Circle, and the matched value supplies the region and the permission, so on an Rc[mut, Shape] it binds an Rc[mut, Circle]. The older plus-sign spelling, +Rc-mut Circle, is refused there too.

Creating Multiple References to the Same Value

The creation of the first owning reference to a new value always comes from an allocation, as shown above. Additional owning references to that value may then be created by copying an existing reference via assignment or function calls:

imm node = new Rc[imm, Node](4);
imm node2 = node;            // node2 and node point to same value

How References and Allocations Expire

Owning references keep the value they point to alive. So long as a value has at least one owning reference that points to it, the value's region will not dispose of the value and reclaim its memory space. Only when all references to a value expire does the region have the right to free the value (although how quickly this happens varies by region).

So, when does the lifetime of an owning reference expire? When the data structure it is bound to expires or changes its value. If the reference is never stored anywhere, it is consumed by the expression it is part of and expires nearly immediately. If the reference is stored in a variable, it expires no later than the end of the lexical scope that variable is declared within (and sooner, obviously, if the variable takes on a new value). If the reference is pointed at by another reference, then the lifetime of the former depends on the lifetime of the latter.

When all references to an allocated value expire and the region has decided to reclaim the value's space, the region will automatically invoke the value's finalizer, if it has been defined.

Memory Allocation Errors

Although unlikely, it is still possible for memory allocation requests to fail. This typically happens when not enough contiguous, free memory exists to satisfy the request.

Failure to allocate memory triggers a different response depending on how the allocation is written.

  • new: the program will panic and shut down, naming the line of the allocation and the size it asked for: out of memory allocating 24 bytes.
  • trynew: the allocation gives back an Option of the owning reference, Some holding it when the memory was obtained and None when it was not. Any of the mechanisms provided for handling nullable values may be applied in an attempt to recover from this problem. Only an allocation may fail this way, so trynew takes an owning reference type, never a value type. An array's contents after it are filled only when the memory was obtained: on None, none of their values is evaluated. Contents after a trynew of anything else, such as a list, are refused for now: allocate it with trynew alone, then append on Some, as below.
imm maybe = trynew Rc[mut, Node](1);    // an Option[Rc[mut, Node]]
match maybe {
  case imm n Some[Rc[mut, Node]] { use(n); }
  else { recover(); }
}

imm names = trynew Rc[mut, List[i32]](10);   // not: trynew ... <- 1, 2, 3
match names {
  case imm s Some[Rc[mut, List[i32]]] { s <- 1, 2, 3; }
  else { recover(); }
}

Using a Reference

By and large, region-managed references may be used in all the same ways as borrowed references. They may be dereferenced, compared, and handled in the same way as owning references.

Region Strategies

To allocate a new value, we ask a region to get it done:

imm pt = new Rc[imm, Point](1, 2);  // the 'Rc' region counts references

There are many kinds of regions, each using a different strategy for allocating memory and then later safely reclaiming that memory after an object has no references that point to it. Variations in their strategies can deliver noticeably different behavior with regard to:

  • Throughput. Strategies vary greatly in runtime cycles consumed by allocating, freeing, and reference bookkeeping.
  • Responsiveness. Some strategies offer excellent responsiveness to realtime demands, while others can experience erratic "lag spikes" while bookkeeping activity takes place.
  • Data flexibility. Some strategies support all kinds of data structures. Others limit the structures they handle well to non-cyclic or hierarchical graphs.
  • Determinism. Some strategies promptly release unneeded memory and resources. Others may wait a long time between last use and release, causing memory and resources to be tied up longer than desired.
  • Memory use. Some strategies use a limited amount of memory effectively. Others have higher ratios of memory allocated-to-used or fragment memory more.
  • Runtime footprint. Some strategies are easily implemented with little code. Others may require the presence of large, complex runtime logic.

Cone offers a wide selection of library-implemented regions, because no one strategy handles all these criteria well. This power of choice ensures each allocated object can select the optimal region that best serves the way the program needs that object to behave.

This page does not list every possible region that can be used by a Cone program, as new ones can be defined within the language itself. Instead, this page summarizes the five popular region strategies used to allocate new objects pointed at by an owning reference. The focus is to describe the mechanism used by each of these region strategies and assess how they compare on the above criteria. In reality, each of these region strategies may be implemented by multiple concrete regions that vary somewhat in how they work (e.g., Rc might only work within a single thread, whereas Arc might allow multiple threads to share references to the same object).

Single Owner

The single-owner region strategy's mechanism, strengths and weaknesses derive from a very simple constraint: there is only ever one owning reference to an object it allocates. That reference may be passed around from function to function or from thread to thread, but it does so using move mechanics to ensure no copy of the reference is ever made. Because there is only one reference to the object, the memory for that value can be automatically finalized and freed when the reference expires.

Here is the simple definition of a single-owner region:

region So is Move {    // Move ensures move semantics on references, i.e. no aliasing
    pub fn alloc(size usize) Option[*u8] {
	    malloc(size);  // May use any general-purpose memory allocator
    }
	pub fn free(self &uni So) {
	    free();
	}
}

Written as the core package's So is, a region is a struct that declares RegionRef (how a region is written):

struct Solo is RegionRef, Move {    // Move ensures move semantics on references, i.e. no aliasing
    fn alloc(size usize) *u8 {
        RawBlocks.alloc(size, 16usize);  // May use any general-purpose memory allocator
    }
    fn free(self &uni Solo) {
        RawBlocks.release(self as *u8);
    }
}

Single owner is a good choice if you are looking for:

  • Better throughput garbage-collected or ref-counted region strategies (as there is no runtime bookkeeping cost). Throughput will likely be worse than arenas.
  • Determinism, as reclamation happens immediately after the last reference expires. Indeed, single owner is the only region strategy that allows the programmer to decide exactly when the object is to be explicitly destroyed and to support exception handling in the event of an unsuccessful destruction.
  • Efficient use of memory.
  • Negligible runtime footprint.

The key shortcomings are:

  • Data structures are limited to hierarchical graphs. It cannot be used to construct cyclic or many directed-acyclic graphs, as these require the use of multiple references to the same node.
  • Use of these references must comply with the more-constrained move mechanics. Where moves are forbidden, workarounds (such as swaps) must be employed to extract a reference.
  • Multiple owning references cannot point to the same object. That said, multiple borrowed references may be temporarily obtained to this object. These are considered temporary, because the lifetime of those borrowed references is constrained to the scope they were created in.

Reference Counting

As the name suggests, the Rc region keeps a running counter of the number of references to each allocated object. When the object is first allocated, its counter starts at 1. Every time a copy is made of an Rc owning reference, the counter is incremented. Whenever an owning reference goes out of scope, the counter is decremented. When the counter reaches 0, the object is reclaimed.

Here is the simple definition of a reference counting region, where aliasing happens automatically:

region Rc {
    pub cnt u32;
    pub fn alloc(size usize) Option[*u8] {
	    malloc(size);
    }
	pub fn init(self &uni Rc) {
	    cnt = 1;
	}
	pub fn aliasRef(self &uni Rc) {
	    ++cnt;
	}
	pub fn dealiasRef(self &uni Rc) {
	    if (--cnt == 0) {
		  free();
	    }
	}
	pub fn free(self &uni Rc) {
	    free();
	}
}

Written as a struct that declares RegionRef, the form built today:

struct Counted is RegionRef {
    cnt u32;                       // the count is the bookkeeping kept with each value
    fn alloc(size usize) *u8 {
        RawBlocks.alloc(size, 16usize);
    }
    fn init(self &new) {
        *self = new Counted(1u32);   // a new value starts with one owner
    }
    fn aliasRef(self &uni Counted) {
        cnt = cnt + 1u32;
    }
    fn dealiasRef(self &uni Counted) bool {
        cnt = cnt - 1u32;
        cnt == 0u32;               // true: that was the last owner, so free the value
    }
    fn free(self &uni Counted) {
        RawBlocks.release(self as *u8);
    }
}

Variations on this algorithm may be built to support multi-threaded use (with atomics, as Arc does) and leverage move semantics and explicit aliasing (to improve throughput).

Reference counting is a good choice if you are looking for:

  • Memory utilization for non-cyclic data structures.
  • Semi-determinism, as reclamation happens immediately after the last reference expires.
  • Runtime footprint, as the mechanism is very simple.

The biggest shortcomings are:

  • Throughput is typically the worst, due to expensive allocation and free algorithms, and frequent cache-damaging reference counts updates.
  • Memory leaks due to cyclic reference counts that keep unused data islands alive forever.

To prevent cycle-based memory leaks, one can use a variation that supports weak references to make any cycle breakable. A weak reference may be obtained from any owning reference:

childnode.parent = parentnoderef.weak;

Today that variation is the rcweak package's Rcw, which counts strong owners and weak references, and a weak reference is made from a strong owner with Weak[T].of(owner) (Rcw and Weak):

childnode.parent = Weak[Parent].of(parentnoderef);

Atomic Reference Counting: Arc

Arc is Rc whose count several threads may change at once: each change of its count is one atomic instruction. Owners of one value may be copied and dropped on different threads, and the value is finalized and freed exactly once, after the last of them goes. Its strengths and weaknesses are Rc's, with an atomic instruction in place of each plain count change.

Arc is in the sync package. It is not in core, whose names every module has, so a module names it once it folds it in, import sync use Arc (or use *), and a module that does not keeps Arc free for its own use. It is allocated as Rc is, new Arc[imm, T](...).

An Arc[imm, T] owner is the one to share between threads: hand it to thread.start, or send it over a channel. An Arc[mut, T] owner would let two threads change the value itself unsynchronized, so it may not cross. A value several threads change is shared as an Arc[Mutex, T] or an Arc[Rwlock, T], whose lock permission makes every change wait for the lock.

import stdio use *;
import thread;
import sync use Arc;

struct Table {
  pub scale i64;
  fn final(self &uni) { printStr("table gone\n"); }
}

fn work(t Arc[imm, Table]) i64 { t.scale * 2i64; }

fn main() i32 {
  imm shared = new Arc[imm, Table](21i64);
  imm a = thread.start(shared, &work);      // the thread gets an owner of its own
  imm b = thread.start(shared, &work);
  printInt(a.join() + b.join());
  printStr("\n");
  0i32;
}

This prints 84 and then table gone, once.

Arc declares the built-in trait ThreadSafe, which Rc does not: the region's own statement that its owners may be held by several threads, which only a region ref may declare. The thread check reads it. An Arc[imm, T] owner may be handed to another thread, while an Rc[imm, T] one, whose count is not atomic, is refused, and so is an Arc[mut, T] one (Race condition safety).

The count's memory ordering is what makes the finalizer safe. A copy adds one to the count with relaxed ordering. A drop subtracts one with release ordering, and the drop that reaches zero reads the count again with acquire ordering before the value dies, so everything every owner did with the value happens before its finalizer.

Arc has no weak references: the rcweak package's Weak is made only from an Rcw owner.

Tracing Garbage Collection

A tracing GC region captures metadata about every object it allocates, including detailed information about its references to other allocated objects. Periodically, the region's runtime garbage collector will trace out all references reachable from a root set of objects (including execution stacks). Any allocated value that cannot be traced from the root is considered unreachable, and therefore is safe to automatically finalize and free.

Its region ref declares neither aliasRef nor Move, and has no dealiasRef. So copying one of its references costs nothing, and an owning reference going away does nothing at all: it is the collector, not the reference, that decides when a value dies.

Tracing GC is a good choice if you are looking for:

  • Data structure flexibility, supporting all kinds of data in the same way.
  • Better throughput than Rc (though slower than other regions due to its regular mark-and-sweep bookkeeping costs).
  • Stable memory use over long runtimes.

The biggest shortcomings are:

  • Poor responsiveness, due to unpredictable stop-the-world lag spikes.
  • Poor determinism, as there can be a sizeable lag between last use and free.
  • Large and complex runtime footprint, resulting from the need for sophisticated and tunable incremental, generational, and multi-threading algorithms for optimizing performance.
  • Memory greedy, as optimal performance can require 4-6x more memory than the amount used.

Two collectors exist, both as library code: the collector package's Gc, the general one, and an actor's own, ActorGc.

Gc, the general collector

The collector package's Gc is the general incremental collector: import collector; and then new Gc[mut, T](...). It is an incremental mark and sweep. It runs a step at a time inside allocation, whole on Gc.collect(), or generationally (Gc.setGenerational(true)). Details of the collectors that exist are with the traced allocators.

It is single threaded, and for use outside actors only: a Gc reference held in an actor's state or used in an actor's method is refused, as it is in a parallel each. It is discouraged. It is likely to be replaced, so new code does not build on it.

ActorGc, an actor's own region

Inside an actor, the actors package's ActorGc is a region of the actor's own. It is collected only between that actor's messages, by a copying collector, so a collection stops no other actor and needs no write barrier and no stack scan. An actor's state leads to this region (see region values below), and new self[T](...) in the actor's methods allocates there. The reference it gives is an ActorGc[mut, T]:

import stdio use *;
import actors;

struct Node { pub n i64; pub next Option[ActorGc[mut, Node]]; }

actor Keeper {
  head Option[ActorGc[mut, Node]];

  fn init(self &new) { *self = new Self(None[ActorGc[mut, Node]]); }

  pub async do push(self, n i64) {
    head = Some[ActorGc[mut, Node]](new self[Node](n, head));   // in the actor's own region
  }

  pub async do total(self) {
    mut sum = 0i64;
    mut at = head;
    while {
      match at {
        case imm k Some[ActorGc[mut, Node]] { sum = sum + k.n; at = k.next; }
        else { break; }
      }
    }
    printInt(sum);
    printStr("\n");
  }
}

fn main() {
  imm k = new Keeper();
  k.push(1i64);
  k.push(2i64);
  k.push(3i64);
  k.total();
}

This prints 6. A bare new ActorGc[mut, T](...) names no actor, so it has no region to be in, and panics. How the region is collected, what it costs an actor, and how a collection made in it works are described with the actor's own region.

Arena

An arena region begins life pre-allocating a large (and growable) slab of memory. This is the arena. Every new allocation takes a bite out of this arena using a fast bump pointer. Allocations are never individually freed. The entire arena is freed as a single event when the arena dies (a scratch arena at the end of its function, a dynamic one with whatever holds it), and each value in it that needs finalizing is finalized then, newest first.

Arena region is a good choice if you are looking for:

  • Blazing-fast throughput. Bump pointer allocation is much faster than malloc. Even better, there are no free nor runtime bookkeeping costs.
  • Excellent realtime responsiveness, as memory management never causes lag spikes.
  • Data structure flexibility, supporting all kinds of data in the same way.
  • Minimal runtime footprint.

The biggest shortcomings are:

  • Memory use grows without bounds, due to individual objects never being freed. A growable collection made in an arena (new a[List[i32]](16)) leaks the block it outgrows whenever it cannot grow in place, until the arena dies, and the larger the block, the more is held.
  • Poor determinism for finalizers, as objects are only finalized when the arena dies.

An arena region is a surprisingly good fit for a limited-lifetime program that allocates a lot of small objects but wants optimal performance. This applies well to many command-line tools, including compilers.

Allocating in an arena

An arena is a value of the arena package: mut a = Arena.empty(). A value is allocated into it with a.alloc(value), which returns a borrowed &mut reference to the value there. The same allocation is written with new, the arena in its head and the type in brackets, new a[Node](1, 2), which the compiler reads as a.alloc(new Node(1, 2)) and so answers what that call does. Writing new a[mut, Node](1, 2) does the same: mut is all an arena lends. Either way the value is built where it stays: the construction's arguments are evaluated, the arena takes room, and the construction runs in that room, with no copy of a value built elsewhere.

import stdio use *;
import arena use *;

struct Node {
  pub a i64;
  pub b i64;
  fn final(self &uni) { printStr("final "); printInt(a); printStr("\n"); }
}

fn main() i32 {
  mut ar = Arena.empty();
  imm x = ar.alloc(new Node(1, 2));         // a borrowed &mut Node
  imm y = new ar[Node](3, 4);               // the same call, written with new
  imm z = new ar[mut, Node](5, 6);          // mut is all an arena lends
  x.a = 10;
  printInt(x.a + y.b + z.a);
  printStr("\n");
  0i32;
}                                           // the arena dies: z, y, x finalized, newest first

This prints 19, and then final 5, final 3 and final 10.

A trynew in an arena is refused for now: whether an allocation in a region can fail is not settled. A block the arena cannot get is a panic.

An arena is itself a region: a type that gets its memory from a region (a collection) and is made with new a[T](...) is handed that arena's, so new a[List[i32]](16) keeps the list's words and its block in the arena. The block grows in place while it is the arena's last and the room is there, otherwise it is copied to a new one, twice the size asked when the arena's current block has no room for it, and the old one abandoned, held until the arena dies, and giving one back does nothing (the details).

A scratch arena

An arena held in a local variable is a scratch arena. Its references are borrows with that variable's lifetime, so they may be passed down to any function called while the scratch lives, and a function handed the arena, &mut Arena, can allocate into it for its caller. Returning one, or assigning it where it would outlive the arena, is refused.

The arena declares NoLoanMut, so an allocation loans nothing else of it and any number of allocations may be live at once (see borrowed references). What an allocation held in a local keeps is the arena's life: the arena being moved, replaced or ended while one is still used is refused, whether the reference is held bare or inside a value the local holds. A value holding one is checked as the bare borrow is.

import stdio use *;
import arena use *;

struct Node { pub a i64; pub b i64; }

fn fill(ar &mut Arena) &mut Node { ar.alloc(new Node(7, 8)); }

fn main() i32 {
  mut ar = Arena.empty();
  imm x = ar.alloc(new Node(3, 4));
  imm y = fill(&mut ar);                    // lent to a function that allocates
  printInt(x.a + y.b);                      // 11: both are live at once
  printStr("\n");
  0i32;
}

These are refused:

fn make() &mut Node {
  mut ar = Arena.empty();
  ar.alloc(new Node(3, 4));                 // returned borrow outlives the arena
}

struct Holder { pub n &mut Node; }
fn hold() Holder {
  mut ar = Arena.empty();
  new Holder(ar.alloc(new Node(3, 4)));     // a value holding one is checked as the bare borrow is
}

fn main() {
  mut ar = Arena.empty();
  imm x = ar.alloc(new Node(3, 4));
  ar = Arena.empty();                       // replacing the arena while x is used
  printInt(x.a);
}

A dynamic arena

An arena that is itself a value may live as long as a local variable does, a scratch arena whose references are ordinary borrows, or travel: a dynamic arena, the package's DynArena, may be returned, stored and passed, its values with it. A reference into a dynamic arena cannot be a borrow, which ends with a scope, so it is a key: a reference carrying the arena's invariant lifetime, which reaches nothing on its own.

mut a = DynArena.empty() mints a brand of its own, an invariant lifetime, and a.alloc(value), or new a[T](...), returns a key of that lifetime, &'=a mut T, which goes anywhere. The arena is the lock: a[key] reaches what a key names, and only where the two carry the same invariant lifetime, which the compiler checks at no cost at run time. In set position (a[key] = v, a field or a method through it) it writes the value. Each arena made has a lifetime of its own, so one arena's key never opens another's:

import stdio use *;
import arena use *;

struct Node['=a] { pub val i64; pub next Option[&'=a mut Node['=a]]; }
struct Chain['=a] { pub ar DynArena['=a]; pub first Option[&'=a mut Node['=a]]; }

fn build(n i64) Chain['=a] {
  mut ar = DynArena.empty();            // a brand of its own
  mut head Option[&'=a mut Node['=a]] = None[&'=a mut Node['=a]];
  mut i = 0i64;
  while i < n {
    head = Some(ar.alloc(new Node(i, head)));
    i = i + 1;
  }
  new Chain(ar, head);                  // the arena leaves with its keys
}

fn sum(c &Chain['=a]) i64 {
  mut total = 0i64;
  mut at = c.first;
  while {
    match at {
      case imm k Some[&'=a mut Node['=a]] {
        total = total + c.ar[k].val;    // read through the arena
        at = c.ar[k].next;
      }
      else { break; }
    }
  }
  total;
}

fn main() i32 {
  imm c = build(5);
  printInt(sum(&c));                    // 10
  printStr("\n");
  mut a = DynArena.empty();
  imm key = a.alloc(5);                 // a key to an i32
  a[key] = 2;                           // in set position: write
  printInt(*a[key]);                    // 2
  printStr("\n");
  0i32;
}

A key used with another arena's, b[key], is refused, and so is reaching through a key on its own, *key.

First-class Arenas

The sizeable performance advantage of arena regions, is offset by their inability to reclaim memory until the entire arena is freed. This means memory waste and determinism worsen steadily the longer a program runs. This can be particularly problematic when using a global arena whose lifetime lasts for the lifetime of the program.

Dynamic (first-class) arenas offer a nice solution to this problem. A dynamic arena may be created at any time, used to allocate a bunch of temporary objects, and then destroyed soon after, when we have no further need for any of those objects. Short-lived arenas offer the same performance advantage, but dramatically improve determinism and memory efficiency.

If object references obtained from a dynamic arena never need to live longer the lifetime of the scope where they were obtained, we can just produce a borrowed reference for every object allocated within the dynamic arena. However, if we need either the object references or the dynamic arena to span multiple lifetime scopes, borrowed references may be too restrictive.

Weak references may be used to solve this flexible lifetime requirement. Every request to allocate a new object in the arena returns a weak reference. We know the object is still alive as long as the arena is alive, so to access the object, we only need to prove the arena is still there:

mut arena = Arena.empty();     // A new dynamic arena
imm objref = &arena mut 5;  // Allocate a new i32 object in the new arena region
arena[objref] = 2;          // Change the value of the object

The arena package's DynArena is the form built today: every request to allocate a new object in the arena returns a key, a reference of the arena's own brand, &'=a mut T, which reaches nothing on its own (a dynamic arena):

import stdio use *;
import arena use *;

fn main() i32 {
  mut ar = DynArena.empty();      // A new dynamic arena
  imm objref = ar.alloc(5i64);    // Allocate a new i64 object in it: a key
  ar[objref] = 2;                 // Change the value of the object
  printInt(*ar[objref]);          // 2
  printStr("\n");
  0i32;
}

Although it may look like we are "indexing" the arena by an object reference, there is no runtime indexing logic taking place. This construction simply allows the compiler to verify at compile-time that the arena is still alive, and therefore the object reference is still valid.

The compiler can also verify that the object reference came from that arena, as both share the same hidden lifetime information. This lifetime information must be explicitly noted should one wish to pass the arena or object references to other functions or methods:

fn dowork(arena Arena['a], objref ArenaRef+'a') { ... }

Built today, the brand is written '=a on the arena and on the key:

import stdio use *;
import arena use *;

fn dowork(ar &mut DynArena['=a], key &'=a mut i64) {
  ar[key] = ar[key] + 1;
}

fn main() i32 {
  mut ar = DynArena.empty();
  imm objref = ar.alloc(2i64);
  dowork(&mut ar, objref);        // the same lifetime '=a names both
  printInt(*ar[objref]);          // 3
  printStr("\n");
  0i32;
}

Notice that same lifetime annotation is specified for both the arena and the object reference. This ensures use of dynamic arena references is always safe.

Pool

The mechanism for pools derives from this constraint: all objects in a pool have the same type and size. A pool region begins with a pre-allocated (and growable) memory area that is logically partitioned into identically-sized slots. Allocating space for a new object is efficient: it either reuses a slot found on a linked-list of free slots, or else uses a bump pointer to carve out a new slot from the unused area.

The generational Pool

The pool package's Pool is a generational pool: mut p = Pool[T].empty(). It is a value, like an arena.

  • p.add(value) returns a Ref[T], a slot and a generation. A Ref owns nothing and is copied freely.
  • p.get(r) answers Some borrow of the value, or None once p.remove(r) has finalized it, even after another value takes its slot.
  • p[r] and &mut p[r] borrow the value, ending the program if it has been removed.
import stdio use *;
import pool use *;

struct Event {
  pub kind i64;
  fn final(self &uni) { printStr("removed "); printInt(kind); printStr("\n"); }
}

fn main() i32 {
  mut p = Pool[Event].empty();
  imm a = p.add(new Event(1));          // a Ref[Event]: a slot and a generation
  imm b = p.add(new Event(2));
  imm copy = a;                         // a Ref owns nothing and is copied freely
  printInt(p[a].kind);                  // p[r] borrows the value
  printStr("\n");
  p.remove(a);                          // finalizes it
  p.add(new Event(3));                  // takes a's slot again
  match p.get(copy) {                   // the old Ref still finds nothing
    case imm e Some { printStr("alive\n"); }
    case is None { printStr("gone\n"); }
  }
  match p.get(b) {
    case imm e Some { printInt(e.kind); printStr("\n"); }
    case is None { printStr("gone\n"); }
  }
  0i32;
}

This prints 1, removed 1, gone and 2, and when the pool dies removed 3 and removed 2. Reading p[a] after p.remove(a) ends the program with a panic.

A borrow from p[r] or &mut p[r], or the Option that p.get(r) or p.getMut(r) returns, held in a local keeps the pool from being changed (a remove, or an add, which may move every value), moved or ended while the borrow is used, and none may be returned or stored where it would outlive the pool. A pool reached through a shared path (a &mut Pool parameter, a field of self, an Rc owner) is protected the same way: a remove through it is refused while such a borrow is used.

ECS-based Pools

With games, we often want to create pool-allocated entities that we can deterministically kill at any time, much like single-owner objects. However, we also want other entities to be able to refer to them over an extended period of time (e.g., one character following or tracking another). The lifetime constraints of borrowed references make them unsuitable for these shared references, as they need to survive beyond the scope they are created in. An owning reference is also unsuitable, as the entity it points to could be destroyed at any time, leaving unsafe or invalid reference(s) behind.

The solution is once again to use weak references for these shared references. The weak reference is interrogated to see if it still points to the same live object. If so, a borrowed reference is produced allowing access to the object. Under the covers the weak reference determines whether the same object is alive, using some technique like generational indexing, a variation on reference counting, or subscription lists.

The pool package's Pool[T] uses generational indexing. Adding a value hands out a Ref[T], a slot and a generation, which owns nothing and is copied freely, and the pool checks it on each use: p.get(r) answers Some borrow of the value, or None once the value has been removed (the generational Pool):

import stdio use *;
import pool use *;

struct Npc { pub hp i64; pub target Ref[Npc]; }

fn main() i32 {
  mut world = Pool[Npc].empty();
  imm orc = world.add(new Npc(10, Ref[Npc].none()));
  imm elf = world.add(new Npc(8, orc));          // the elf follows the orc
  match world.get(world[elf].target) {
    case imm t Some { printInt(t.hp); printStr("\n"); }
    case is None { printStr("target gone\n"); }
  }
  world.remove(orc);                             // the orc dies
  match world.get(world[elf].target) {
    case imm t Some { printInt(t.hp); printStr("\n"); }
    case is None { printStr("target gone\n"); }
  }
  0i32;
}

This prints 10 and then target gone.

Pools of Counted or Owned Values

A pool region must be created before using it to allocate values:

mut eventPool RcPool[Event];

This example creates a new region called eventPool. All its allocated object have the type Event (which might be an enum type). This pool is an RcPool, which means references to pool-allocated objects are reference-counted, thereby determining when to free the object. An SoPool would use single-owner references, and so on.

Once a pool region is defined, the region may be specified to allocate a new value:

imm newevent = &eventPool mut Event.QuitEvent;

Pools are a good choice if you are looking for:

  • Decent throughput. Pool-based allocation and free is faster than any strategy other than arenas.
  • Memory efficiency. Pools are very good at reusing reclaimed memory.
  • Responsiveness and determinism varies according to the reference freeing mechanism: SoPool and RcPool will do pretty well.
  • Minimal runtime footprint.

The biggest shortcoming is:

  • All values must have the same type.

When a program has a large number of objects of the same type being regularly allocated and freed, as is true in many games, pools can be very useful strategy. This is particularly true when functions process all objects sequentially in a cache-friendly way.

Fine-tuning

Rarely needed: what may head a new in place of a type, and the order of the steps of an allocation.

Allocating in a Region Value

A construction whose head is a region value rather than a type, new a[Node](1), allocates in that value's region: an arena's, or, for new self[Node](1) in an actor, the actor's own garbage-collected ActorGc. The compiler reads new a[Node](1) as a.alloc(new Node(1)), so what comes back is what that call returns (an arena returns a borrowed &mut reference to the value). Region values says what may head such a construction; Allocating in an arena and ActorGc show it at work.

Region Values: the Head of a new

A construction whose head is a region value rather than a type, new a[Node](1, 2), allocates in that value's region. The head must be a region value, or a value that leads to one:

  • A region value is a value whose type is a struct whose first field is a public *MemRegion, as an Arena's and a DynArena's are.
  • A value that leads to one has a type with an allocRegion method giving the region value, and new x[T](...) is x.allocRegion().alloc(new T(...)). The head's call is made again to hand the region to a type that gets its memory from one, so it should lend nothing still borrowed when it is called again.

Any other head is refused. An actor's state leads to the actor's own garbage-collected region (ActorGc), which is how new self[T](...) allocates there.

import stdio use *;
import arena use *;

struct Node { pub a i64; pub b i64; }

struct Scene {
  pub ar Arena;
  pub fn allocRegion(self &mut) &mut Arena { &mut ar; }
}

fn main() i32 {
  mut s = new Scene(Arena.empty());
  imm n = new s[Node](1, 2);                // s.allocRegion().alloc(new Node(1, 2))
  printInt(n.b);                            // 2
  printStr("\n");
  0i32;
}

The Order of an Allocation

Every allocation runs its steps in the same order. First the initializer's arguments are evaluated, in the order written, or the finished value is. Then the region obtains the memory, and nothing more (its alloc). Then the region's initializer fills its bookkeeping in place, then a lock permission's does the same for its part, and then the value's initializer fills the value in place, where it was allocated, or the finished value is stored there, or an array's contents fill it, each value evaluated then. Last, the owning reference goes where the expression puts it.

An initializer, or a value of an array's contents, may itself allocate, even in a garbage-collected region, whose collector may run while it does: such a region's new object is held as a root and its value reads as empty from the moment its memory is obtained, so a collection finds it, and nothing it half holds, until it is filled.

imm p = new Rc[mut, Pair](make(1), make(2));  // make(1), make(2), then alloc, then Pair's init
imm q = new Rc[mut, Pair](makePair());        // makePair(), then alloc, then the store

  • Moves in depth: a single owner’s reference moves.
  • Weak references: breaking a cycle of counted owners.
  • Collections in a region or arena: where a collection’s block comes from.
  • Roll your own: how a region is written, and the traced allocators.
  • Lock permissions in depth: Arc[Mutex, T] and Arc[Rwlock, T].
  • The actor’s own garbage-collected region.
  • Text: str, cstr and String.
