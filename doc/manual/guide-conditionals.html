Cone
Conditionals: if and match

A program rarely runs straight through: it looks at its values and decides what to do next. Cone gives you two ways to decide. if asks a yes-or-no question; match looks at one value and picks the first of several cases it fits. Here are both at work on numbers, dates and times:

// Conditionals: if and match
//
// 'if' chooses a block by a condition; 'match' chooses one by the first
// pattern a value fits. Both are expressions: the block that runs gives
// the value.

mod deciding;

import stdio use *;

// if, elif, else: the whole 'if' is the function's value
fn sign(x i32) i32 {
  if x < 0 { -1; } elif x == 0 { 0; } else { 1; }
}

// Conditions combine with 'and', 'or' and 'not'
fn isLeap(year i32) bool {
  year % 4 == 0 and (year % 100 != 0 or year % 400 == 0);
}

// A match on a number: a value, a comparison, 'or', a range, a guard
fn describe(n i32) {
  imm what = match n {
    case 0 { "zero"; }
    case < 0 { "negative"; }
    case 2 or 3 or 5 or 7 { "a small prime"; }
    case 1 .. 9 if n % 2 == 0 { "small and even"; }
    case 1 .. 9 { "small and odd"; }
    else { "ten or more"; }        // numbers cannot be counted: 'else' is required
  };
  print <- n, " is ", what, "\n";
}

// A case's block can decide again
fn daysIn(month i32, year i32) i32 {
  match month {
    case 4 or 6 or 9 or 11 { 30; }
    case 2 { if isLeap(year) { 29; } else { 28; } }
    else { 31; }
  }
}

// Two values at once, the hour and the minute of a time such as 1745.
// '_' takes any value.
fn sayTime(t i32) {
  match t / 100, t % 100 {
    case 0, 0 { print <- "midnight"; }
    case 12, 0 { print <- "noon"; }
    case _, 0 { print <- t / 100, " o'clock"; }
    case _, < 30 { print <- "just after ", t / 100; }
    else { print <- "nearly ", t / 100 + 1; }
  }
  print <- "\n";
}

fn main() {
  print <- "signs: ", sign(-7), " ", sign(0), " ", sign(12), "\n";

  imm year = 2024;
  imm kind = if isLeap(year) { "a leap year"; } else { "a common year"; };
  print <- year, " is ", kind, ", so February has ", daysIn(2, year), " days\n";

  describe(0);
  describe(-4);
  describe(7);
  describe(8);
  describe(9);
  describe(42);

  sayTime(0);
  sayTime(1200);
  sayTime(900);
  sayTime(915);
  sayTime(1745);
}

It prints:

signs: -1 0 1
2024 is a leap year, so February has 29 days
0 is zero
-4 is negative
7 is a small prime
8 is small and even
9 is small and odd
42 is ten or more
midnight
noon
9 o'clock
just after 9
nearly 18

What to notice

  • An if or a match has a value: the last expression of the block that ran. sign's whole body is one if, and kind and what are set from one.
  • Conditions are written plainly, with no parentheses around them, and combine with the words and, or and not.
  • A case can name one value, several joined by or, a comparison such as < 0, or a range such as 1 .. 9, and an if after the pattern adds a further condition.
  • Cases are tried from the top, and the first that fits wins: 7 is "a small prime" before the range cases ever see it.
  • A match on a number ends in else, because no list of cases can name every number.
  • match t / 100, t % 100 looks at two values at once; each case gives a pattern for each, and _ takes any value. (The functions themselves come back in full on Functions.)

Choosing with if

if takes a condition and a block. When the condition is true the block runs; when it is false, the block after else runs instead, if there is one. Between the two, any number of elif ("else if") conditions can be tested in turn. At most one block of the chain runs: the first whose condition holds, or else the else.

What makes Cone's if pleasant to use is that it is an expression, not just a statement. A block's value is its last expression, so the value of an if is the value of whichever block ran. That is why sign needs no variable and no return: its body is a single if, and the function gives back whatever that if gives. In main,

imm kind = if isLeap(year) { "a leap year"; } else { "a common year"; };

sets kind once, to the right text, where many languages would declare it first and assign it in two places. An if used this way needs its else, since every path must give a value; leave it out and the compiler says so ("if requires an 'else' clause"). Both branches give text here, as they must: the branches of an if used as a value agree on the type of the value.

The same if works as a plain statement, run for what it does rather than for a value, and then the else is optional:

imm temp = 31;
if temp > 30 and temp < 40 {
  print <- "hot\n";
}

Asking the question: conditions

A condition is usually a comparison: == and != for equal and not equal, and <, <=, >, >= for order. Comparisons combine with the words and, or and not. not binds most tightly, then and, then or, which is why isLeap puts its or in parentheses: a year is a leap year when it divides by 4 and (it does not divide by 100 or it divides by 400).

and and or stop as soon as the answer is known. For 2023, year % 4 == 0 is already false, so the parenthesised part is never worked out.

A condition is an ordinary value, a bool, true or false. isLeap simply returns one, and you can keep one in a variable: imm isOne = (count == 1);. A number may stand as a condition too: 0 counts as false and any other number as true.

Choosing with match

When one value can go several ways, a chain of elifs starts to repeat itself. match names the value once and then lists the cases, which reads like a table. The cases are tried from the top; the block of the first one that fits runs, and its value is the match's value. describe keeps that value in what.

The patterns a number can be tested against are few and familiar:

  • A value: case 0 fits when the number is 0.
  • A comparison, with the number itself left out: case < 0 fits every negative number.
  • Several patterns joined by or: case 2 or 3 or 5 or 7, or the months with thirty days in daysIn.
  • A range: 1 .. 9 runs through 9, so 9 fits it, while 1 ..< 9 stops before 9. These are the same two range operators that each counts with on the next page.
  • A guard: an if and a condition after any pattern, which must also hold. case 1 .. 9 if n % 2 == 0 takes the even numbers of the range, and the plain case 1 .. 9 after it takes the rest.

Order matters because the first fitting case wins. 7 lies in 1 .. 9, but the prime case comes first, so 7 is "a small prime". Read a match from the top and you know exactly which case each value reaches.

Ranges are not only for numbers. Anything that can be put in order can be matched against a range, characters included:

fn kindOf(c char) i32 {
  match c {
    case 'a' .. 'z' { 1; }     // a lower case letter
    case 'A' .. 'Z' { 2; }     // an upper case letter
    case '0' .. '9' { 3; }     // a digit
    else { 0; }
  }
}

Every value has somewhere to go

A match must say what happens for every value it can be given. For a bool, or for the variants of an enum (on Enums), the compiler can count the cases and check that none is missing. Numbers and characters are too many to count, so a match on one ends in else, the case that fits anything left over. Forget it and the compiler stops you:

Error 1417: This match does not cover every value, and nothing but an enum's variants and true and false can be counted: end it with 'else {}', which may say that no other value can happen.

When the other values need no action, the else can be empty, and says just that:

fn report(errors i32) {
  match errors {
    case 0 { print <- "all clear\n"; }
    else {}                    // nothing to say otherwise
  }
}

This is a small price for a large comfort: no value ever slips through a match unhandled.

Two values at once

sayTime splits a time such as 1745 into its hour and its minute and matches both:

match t / 100, t % 100 {
  case 0, 0 { print <- "midnight"; }
  case 12, 0 { print <- "noon"; }
  case _, 0 { print <- t / 100, " o'clock"; }
  ...
}

The values are written after match with commas between them, and each case gives one pattern for each value, in the same order. A case fits when every value fits its pattern, and _ is the pattern that takes any value. No tuple or other structure is made to hold the two; the commas are all it takes. Each value is worked out once, before any case is tried. The result reads like a small decision table, which is exactly what it is.

In detail

The rest of this page is the complete reference for if, conditions and match on values; skip to the next page if the program above was enough.

Note: Not built: an Option as an if condition (if maybeInt { ... }), because Option has no isTrue yet. Test it with is, == None or a binding (Option types).

A program rarely runs straight through. It decides which code to perform, and it repeats code until some work is done.

Control flow statements direct the flow of execution from one block to another:

  • if .. elif .. else. Choose which block to execute based on evaluating one or more conditional expressions.
  • pattern matching. Choose which block to execute based on which pattern first matches some value
  • while, break and continue. Repeatedly execute some block while certain conditional expressions are true, or until a break.
  • each iteration. Repeatedly perform some block for each every value in some iterated sequence.
  • exception handling. Support different control flows for successful processing vs. thrown exceptions.

if, elif, else, and if as a value

if decides which code block to perform based on the truth of one or more conditional expressions. Consider:

fn abs(x i32) i32 {
  mut result i32;
  if x < 0 {
    result = -x;
  } else {
    result = x;
  }
  result;
}

if is used by this function to correctly return the positive, absolute value of x. x < 0 is a conditional expression that evaluates to true whenever x is a negative number. When the conditional evaluates as true, the subsequent block is performed, which converts x to its positive equivalent. When the conditional is not true, the block after the else is performed instead, which captures the value of x. The else clause is optional; it need not be specified if there is no alternative action to perform when the condition is false.

Before covering the logic of conditional expressions, let's summarize various ways to use if.

if as expression

As with blocks, if can be used as an expression. This (along with implicit return) provides us with another way to write this function:

fn abs(x i32) i32 {
  if x < 0 {
    -x;
  } else {
    x;
  }
}

Where the value of an if is wanted as a known type — a variable's declared type, a function's return type, the parameter it is passed to, or the field it gives a value to — each branch's value is coerced to that type. So two string literals, which are each a &str, are each taken as the slice wanted:

imm label &Array[u8] = if orbiting {"orbit";} else {"flight";};  // each branch a &Array[u8]

Where no type is wanted, the branches must agree on one: either the same type, or a supertype they share. The same holds for the value of a block and of a match.

An if used as a value needs its else, since every path must give a value. A match is not an if chain in this: it must cover every value it matches, statement or value, and its cases may do so (every variant of an enum, both values of a bool) without writing an else. An if chain of is tests that names every variant of an enum is a value without an else too, but is not asked to name them all.

Note: A call gives its arguments their parameters' types when the function or method it calls is a single declaration that is not generic. The arguments of an overload set, such as those of print <-, a generic function's arguments, and an operator's operands are given no type, since their own types are what choose what is called: there, the branches must agree on their own, or be given a type first, as in imm s &Array[u8] = if ...;.

Multiple conditions

If we have more than one condition to test, each corresponding to a different block to perform, every condition after the first is preceded with elif (short for "else if"). For example:

fn abs(x i32) i32 {
  if x < 0 {
    -x;
  } elif x == 0 {
    0;
  } else {
    x;
  }
}

Conditions: comparing, and/or/not, what counts as true

Conditional expressions are often just simple comparisons, as shown above. However, complex conditional expressions can be formulated that use logical operators, pattern matching, functions or methods. Let's walk through the possibilities, beginning with the basics.

True vs. False

A conditional expression must evaluate to true or false. If it does not, an attempt is made to find and use the value type's isTrue method. Several types (but not all) support this method. For example:

  • Integers. isTrue evaluates 0 as false, and all other integer values as true. 
    if 0 {
  a += 1;  // This statement will never execute, because 0 evaluates to false
}
  • Floats. isTrue evaluates 0 and -0 as false, and all other values (NaN included) as true.
  • Option type. An Option has no isTrue method, so it is not a condition on its own. Test it with is (if m is Some), or bind the value inside (if imm n Some = m), as Option Types shows.

Equivalence

With most values, we can compare whether they are the same by using an equivalence operator. The == operator returns true if two values have the same content and type. != (not equal) is true if they do not. For example:

x == 3.0        // Returns true if the local variable x's value is 3.0
x+1 != y        // Returns true if x is not exactly 1 greater than y
true != false   // Returns true

As with the arithmetic operators, the == and != operators are implemented as type-specific methods. Thus, each type can establish its own rules for equivalence. For example, two floating point numbers could be evaluated as equal if they are within some margin of error (resulting from floating point calculation rounding errors). Similarly, two lists might be equal if they have the exact same contents. A type must implement the == method to ensure its values can be compared.

Two borrowed values compare the values they refer to. To ask instead whether two of them point to the same place, use the identity operator === (or !==).

Ordered Comparison

Comparison operators determine whether one value is greater or less than some other value. They work only on types that are comparable, such as numbers.

x >= 2          // Returns true if x is greater than or equal to 2 (>, <, <= are variants)
2 <= 2.0        // Returns false any time the types do not agree

Boolean Operators

Sometimes a conditional expression requires checking multiple conditions and then combining those results together into a single true/false determination. The boolean operators 'and', 'or' and 'not' ('!') are used to accomplish this. These operators are distinctly different than the bitwise logic operators ('&', '|', and '~') introduced in an earlier section.

For example:

0==3 or not 2<3 and 3==3   // Returns true ('and' is evaluated before 'or')

The logical operators work mostly how you would expect:

  • As mentioned earlier, they treat 0 and false as false. All other values are considered true.
  • The boolean operators 'and' and 'or' will stop evaluating any time the answer is known for sure. Thus, the .isEmpty method will never be performed in this expression: 
    false and list.isEmpty
  • The logical operators have a lower precedence than evaluation operators, but higher than assignment. 'not' has the highest precedence, then 'and', then 'or'.

Expression usage

Conditional expressions need not only be found on control flow statements like if. They may also be incorporated as part of any arbitrary expression. For example:

imm isOne = (a == 1);    // isOne will be either true or false

match, lightly: values, ranges, or, guards

As with if, pattern matching is about deciding which code path to perform. Its approach is to match a single value against multiple patterns. The code block associated with the first matching pattern is performed.

Let's illustrate this with a simple (but mathematically unusual) example:

fn power(n i32, pow i32) i32 {
  match pow {
    case ==0 { 1; }
    case ==1 { n; }
    case ==2 { n * n; }
    else { -1; }
  }
}

This example calculates its value differently based on the value of pow. If pow is zero, we return 1. If pow is 1, we return n. If pow is two, we return n squared. Finally, if pow is any other value, we return -1.

The structure of this form of pattern matching is straightforward:

  • Any normal expression can be used after match. This expression's evaluated value is what patterns are matched with. If desired, an assignment expression can be used here to capture this matchee value for later use in matched code blocks.
  • Any number of pattern blocks may follow. Each is comprised of the case keyword, followed by a match pattern, which is followed by a block. When a match pattern matches, the evaluated value of its block is the match's value
  • Using the else pattern will always match any value. If specified, it must be the last pattern used.

A match on an enum's variants, and on an Option, comes back with your own data.

Covering every value

Every match must cover the values it matches, statement or value alike, or end in else. The compiler counts what simple, clear logic can count, and asks for an else wherever it cannot:

  • A match on an enum is covered when every variant has a case. A case names a variant alone (case Circle), binds it (case imm c Circle) or ors several (case Rect or Dot); each counts toward every variant it names. A trait (case imm m Measured) names every variant that complies with it (Trait patterns).
  • A match on a bool is covered by case true and case false.
  • A match on several values is covered when every combination of its columns is (below).
  • Anything else — numbers, characters, text, floats, a comparison, a range, a value held in a variable, a guarded case — matches some values, and which only running says. The compiler does not try to prove it covers them all. End such a match with else, which may say only that no other value can happen: else {}.

A match with a case that uses a function's pattern always ends in else, whatever its other cases cover: which values a function matches only running it says, and the compiler does not try to prove it. The else may say that no other value can happen, and is not an error when the other cases already cover every value.

A match that is not covered is an error that names what is missing, so a statement match that handles some variants needs else {} to say the rest need no action. The opposite is an error too: a case that can never run, because the cases before it match every value it matches (a variant, or a number or character, named twice, a variant after a trait that names it, a trait after the variants it names, a case after the cases cover everything), and an else after cases that already cover everything. Open traits never count: a match on a trait that other modules may add structs to needs its else.

fn name(s &imm Shape) i32 {
  match s {
    case imm c Circle { c.radius; }
    case Rect or Dot { 0; }          // every variant: no else
  }
}
fn side(n i32) i32 {
  match n {
    case 0 { 1; }
    case 1 ..< 10 { 2; }
    else { 3; }                       // numbers cannot be counted
  }
}

A versatile range of patterns are supported, able to match wholly to specified values, partially, or using a first-class pattern. Pattern matching also supports de-structuring portions of the original value into bound variables.

Whole Value Matches

These patterns involve straightforward comparisons between the matchee value and one or more pattern values.

Equivalence

The simplest form of matching uses a value as the pattern. This can be a constant value (as above) or any expression that evaluates to some value, for example:

match val {
  case ==anotherval.len { 4; }
  else { 0; }
}

The type of the pattern value must match the type of the matchee value. An equivalence match is performed between these values as if using the '==' operator.

The == may be left out: a value on its own is an equivalence pattern, so case 0 means case ==0, case true means case ==true, and a named constant, case LIMIT, is compared the same way. A name on its own that is a variant of the matched value's enum is that variant's pattern instead: case Circle on a Shape means case is Circle (see Variant type partial matches).

match val {
  case 0 { 4; }
  case LIMIT { 5; }
  else { 0; }
}

A string matched against a slice of bytes is compared as two slices are, element by element, so case "box" holds when the slice holds exactly those three bytes:

match word {
  case "box" { 1; }
  case "ball" or "bat" { 2; }
  else { 0; }
}

An equivalence pattern counts toward covering every value only as the literal true or false on a bool, with or without ==. A variant named on its own counts, as case is does. A number, a character, a string or a named constant does not: the match ends in else.

Comparisons

Comparison patterns make use of the comparison operators (including !=). The left hand value is not specified, as it is understood to be the match value:

match n {
  case <0 { -1; }
  case >0 { 1; }
  else { 0; }
}

A negative value after < needs a space between them, as in case < -1: <- is the send operator.

A condition is not a pattern. A value on its own is compared with the matched value, so a condition written where a pattern is expected, such as case not b or case n > 3, is refused (Error 1117, "A condition is not a pattern"). The comparison case >3 and an if guard say it.

Range pattern

The range pattern checks whether the matchee value lies within a specified range. This is specified by placing either the .. or ..< range operator between two expressions. The two mean what they do in a number range of each and in a subslice: .. includes its end and ..< stops before it. Anything that can be ordered, characters among them, can be matched against a range:

match n {
  case 0 ..< 3 { 1; } // matches 0, 1, or 2 (but not 3)
  case 3 .. 6 { 2; }  // matches 3, 4, 5 or 6 inclusively
}

match c {
  case 'a' .. 'z' { 1; }  // a lower case letter
  case 'A' ..< 'Z' { 2; } // an upper case letter but Z
  else { 0; }
}

A range pattern is not a step: by belongs to each alone.

Pattern Expressions

Let's introduce ways to enhance the match patterns already described as part of a more comprehensive pattern expression.

Multiple patterns

It is possible to list more than one possible pattern to match, using or between each pattern:

match n {
  case 2 or 3 or 5 or 7 { 2; }
  case -6 or -1..1 or 6 { 1; }
  else { 0; }
}

Each pattern joined by or may be any of the whole value patterns, or an is test. A pattern that binds a variable stands alone.

Several values

Several values can be matched at once by writing them after match, separated by commas. No tuple is made: the commas are all it takes. Each case then gives one pattern for each value, separated by commas, and matches when every value matches its pattern. The values are evaluated once each, left to right, before any pattern is tried. _ is the pattern that takes any value; it belongs to this form alone (a match of one value ends in else):

match key, value {
  case 0, _ { 0; }
  case _, 0 { 1; }
  else { 2; }
}

match state, byte {
  case Start, 'G' { 1; }
  case Start, _ { 0; }
  case Done, _ { 2; }
}

A pattern of a column is any pattern of a single value, or included (case Start or Done, 'G'), followed by one if guard for the case. A pattern of a column does not bind a variable. The second match above (where state is an enum of just Start and Done) has no else: it is covered, because every combination of the variants is. The compiler counts the combinations of the values it can count (variants and bools), and a case that tests a number or a character in a column counts toward none. The first Start case tests a character, so it is case Start, _ that covers Start; without it the match would need its else.

if Guards

An 'if' clause may be specified following all patterns as an additional guard. The condition expression after the 'if' must evaluate to true in order for the match to take place.

match nbr {
  case ==4 if cnt > 0 { 0; } // matches only if nbr==4 and cnt>0
  case ==4 { 1; } // matches when nbr==4 and cnt<=0
  else { 2; }  // matches when nbr != 4
}

A guard may follow a pattern that binds a variable, and may use it:

match opt {
  case imm x Some if x > 0 { x; }
  case imm x Some { 0; }
  case is None { -1; }
}

Because a guard can fail, a case with a guard does not account for its variant when deciding whether a match covers every value. Above, the unguarded Some case does.

First-class patterns

Whole and partial matching patterns handle many situations, but not all. First-class patterns make it possible to support more sophisticated matching algorithms: a pattern is an ordinary function, or a method, that tests the matched value, and nothing about it is special to the language. Nothing is declared to make a function a pattern, and a library's patterns are written and used the same way as one's own.

A pattern is used with the using keyword and the call of the function, written without the matched value: the matched value is the first argument of the function, and, of a method, the argument after self. The arguments written are the ones that follow. What the function gives back says what the pattern does:

  • a bool only tests. case using isOdd() calls isOdd(n), and the case is taken when it is true;
  • an Option tests and binds. case imm rest using prefix("GET ") calls prefix(line, "GET "), and the case is taken when it gives Some, rest being what it holds. The name comes first, as in case imm n Ok, and may be mut.
fn prefix(s &str, p &str) Option[&str] {
  if s.startsWith(p) { Some(&s[p.len ..]); } else { None[&str]; }
}
fn isOdd(n i32) bool { n % 2 == 1; }

fn route(line &str) i32 {
  match line {
    case imm path using prefix("GET ") { get(path); }   // prefix(line, "GET ")
    case imm path using prefix("PUT ") { put(path); }
    case "HEAD" { head(); }
    else { 0; }
  }
}

fn kind(n i32) i32 {
  match n {
    case 0 { 100; }
    case using isOdd() { 1; }          // isOdd(n)
    case using between(10, 20) { 2; }  // between(n, 10, 20)
    else { 3; }
  }
}

A binding gets what the function gave back, as a variant's does: the contents of the Some, a copy of plain data, a move of what owns something (which is finalized as the arm ends, as any bound value is). A pattern with several results gives them as a struct, bound whole and read by field name, or a tuple, read by position, m.left or f.0; a function with several outcomes gives an enum, matched as any is.

Cases are tried from the top, and a function runs only when its case is reached, at most once for it. A case of another kind before it that matches means it is never called, and the cases after it are tried when it does not match. What a pattern costs shows where it is declared, not at the case, and whether a pattern is inline is its author's choice. A method pattern may keep a state that its calls change, since each call is made as written, in this order.

A pattern never advances anything. It tests the matched value and gives back what is left of it, as prefix does, and the case moves on, by assigning the rest (text = rest;), as it would change any state. Nothing is half consumed by a pattern that did not match.

A bool test may be joined to other patterns with or (case using isOdd() or using isPrime()) and followed by an if guard, as any pattern is; a case that binds stands alone and may have a guard that uses the binding. A match a, b may test a column with a function but binds nothing in it. The matched value of a bound case may be a call, which is made once, as for every pattern.

A match with a function's pattern ends in else, whatever its other cases cover (Covering every value): which values a function matches only running it says. It may say that nothing else can happen, else {}. A match as a jump table (Jump tables) takes its cases up to the first function's pattern, and the pattern and the cases after it are tried in order.

The same patterns bind in an if, an elif, and a declaration that leaves when it does not match, with the matched value after the =, as the variants' bindings do (Binding past an early exit); a function that only tests is simply the condition of the if, if isOdd(n) { ++nbr; }:

if imm rest using prefix("GET ") = line { get(rest); }
elif imm other using prefix("DEL ") = line { del(other); }
imm path using prefix("PUT ") = line else { return -1; };   // leaves unless it matches

That is what lets a parser be written as a match over the text that is left. Each case below tests a sign or a number, hands back the rest, and the case moves on:

fn expr(text &str) Option[i64] {
  mut rest = blank(text);
  mut acc = 0i64;
  mut sign = 1i64;                 // the sign before the number that is due
  mut open = true;
  while open {
    match rest {
      case imm after using digits() { acc = acc + sign * value(rest, after); rest = blank(after); }
      else { return None[i64]; }
    }
    match rest {
      case imm p using lit("+") { sign = 1; rest = blank(p); }
      case imm p using lit("-") { sign = -1; rest = blank(p); }
      case using atEnd() { open = false; }
      else { return None[i64]; }
    }
  }
  Some(acc);
}

Flow typing

A test of a variant tells the compiler what the tested name is, and it uses the name that way until something may have changed it. After if s is Circle, inside its block s is a Circle wherever a field or a method of Circle is named on it: s.radius reads it, s.radius = 2 writes it, s.grow() calls it. The name is narrowed:

  • in the block of an if, an elif, or the case of a match that names the variant, and on the right of an and whose left tests it (if s is Circle and s.radius > 3);
  • after a branch that leaves, for what follows: after if s is Circle { return 0; }, s is not a Circle;
  • by elimination: when the variants that remain are one, s is that one, in the else of a two-variant test, in the last case of a match, after an early exit;
  • by an assignment of a known variant: after state = State.Run(speed), state.speed reads the field.

It is a name that is narrowed — a local variable or a parameter, held by value or through a reference — and only to name a member of the variant. Narrowing does not retype the name for anything else: it is still the original, whole value, passed and returned as the enum, and takesCircle(s) is still an error (bind it for that). A variant declared as a type, Ok(i32);, has no fields to name: the narrowed name has nothing more to offer, and a binding is how to reach what it holds. The test if x is a plain truth test, and never narrows: only the language's own tests do, is and a binding, never what a method returns (Option unwraps with them).

A narrowing ends when the name may hold another variant: an assignment to the whole of it, a mutable borrow of the whole enum (a call that takes &mut Shape), a swap, a reference stored over (*s = ...), or a path where one branch did one of these. Writing a field within the variant is not a change, whether a field of the variant or a field the variants share. After a change the name is its whole type again, and a use that needed the variant says so, at the use, naming the change:

fn step(state &mut Machine) {
  if state is Run {
    state.speed = state.speed + 1;   // Ok
    *state = Machine.Stop;          // the whole value is replaced: the narrowing ends
    state.speed;                    // Error: `state` is not known to be Run here: it was changed at ...
  }
}

A name that is a reference others may share (& or &mut) is narrowed through a reference the compiler declares where the test was made, and the loan walk follows it as it follows a binding (Borrowed references): a call handed another name for the enum, a store through one, a swap, or a call whose body it cannot read is a change, refused at the next use of the narrowed name; a call that cannot reach the enum is none. Nothing follows the reference between the test and the block's start (or, inside one condition, the use), so a call or a store made in a later operand of the condition ends the narrowing, whatever it reaches: if s is Circle and toRect(t) and s.radius > 0 is refused at s.radius, naming the call. A name held by value, or through an imm, uni or mut1 reference, has no other name that can change it, so only its own assignments and mutable borrows are changes.

A narrowing from before a loop is good for the loop's first pass. A use of it that a change later in the loop reaches again by the loop's back edge is an error, reported at the use. Test again inside the loop to narrow afresh, which is how a state machine reads its next state:

while running {
  if state is Idle { start(); state = State.Run(1); }       // tested each pass
  else if state is Run { state.speed = state.speed + 1; }   // narrowed by its own test
}

Fine-tuning

What a match takes

The form of the expression after match decides what the match does with it, and a bound if, if imm c Circle = s, reads its value the same way. (Borrowing and moving are explained in Moves in depth and Borrowed references in depth.)

  • A place — a variable, a field of one, a dereference, an element at a name or a literal, match r — is matched as the value it holds. Every test reads it where it stands and takes nothing, so a match that only tests moves no resource away, and r is whole after it. An arm that binds is the one that takes: the binding holds the payload by value, a copy of a copy type, or a move of one that owns, which consumes r on the paths that reach that arm. A mut binding changes what the arm took and never r.
  • A borrow — match &r, &imm r, &mut r, &uni r — binds a reference of that kind into r, which stays frozen to the match for as long as the bindings are used. That is how a match changes r: match &mut r.
  • Any other value — a call, match f() — is a temporary the match owns: it is made once, every pattern reads it, and it is finalized as the match ends.

A binding takes only what it binds. Where the payload is plain data (a number, a borrowed reference, a struct of them), the arm copies it and the place is whole after the arm, even where the enum holds an owner in another variant. A bound if guard (case imm x Some if x > 0) reads its binding before the arm is chosen, so it takes nothing from the matched value at all, a place or a call's temporary alike: it sees a copy of plain data, and a payload that owns something through a read-only borrow of it. A guard that fails leaves the value whole for the cases after it, and the arm that runs is the one that takes.

Jump tables

Nothing is written for this: it is what the cases mean. It matters only when you tune a hot match.

A match on one integer, character or enum compiles to a single switch on that value in every build, which the back end makes a jump table, a binary search or a bit test as the cases lie. Nothing is written for it: it is what the cases mean. The cases that count are those before the first that does not test the value against constants: a constant (a literal or a named constant), a range, or of those, and, on an enum, a variant, a binding of one, and a trait that names variants (Trait patterns). Those cases are the switch; the rest, from the first case with an if guard, a comparison such as > 3, a text or a range too wide to list (more than 128 values), a function's pattern, or from the else, is tried in order as the default. A match that covers an enum with no else has its last case as the default. Cases are still tried top to bottom: a value two cases share belongs to the first.

fn kind(c char) i32 {
  match c {
    case 'a' or 'e' or 'i' or 'o' or 'u' { 1; }   // these four cases are the switch
    case 'b' .. 'd' { 2; }
    case '0' .. '9' { 3; }
    case ' ' { 4; }
    case 'Ā' .. '\U0010ffff' { 5; }          // too wide: tried after the switch, in order
    else { 0; }
  }
}
