Cone
Streams in depth

Note: Built: the codec core (the streams package, with deflate, zstd and the hashes meeting it), the Reader and Writer of one actor, and the stages between actors (the stages package). Not built yet: TLS records and HTTP/1 framing as stages (the sample below starts at the socket), and a stage that serves several streams at once; about thirty packages still have a feed and pull of their own, to be refitted onto this.

A file, a socket, a compressed body and a hash all move bytes in pieces, and a program wants to join them without each pair of them meeting in its own way. Cone gives a stream three layers, and one rule that holds in all of them: a buffer is owned by exactly one stage at a time, and moves between stages; it is shared only by saying so. This page takes the layers in turn, each with a small example, and ends with how a stream is cancelled.

Layer 1: a codec with no I/O in it

A transform takes bytes in and gives bytes out, and knows nothing of where they come from or go. The streams package's Transform is three calls and a status: feed what has arrived, in any pieces; pull output into a buffer's spare room and learn what it waits for (NeedInput, MoreOutput, Done or Failed); and finish when no more input will come. Inflate, deflate, the zstd pair and the hashes meet it, so one loop serves them all:

var inf = deflate.Inflater.make(deflate.Format.Gzip);
var out = List[u8].withCapacity(size);
var at = 0usize;
while at < gz.len() {
  let n = if gz.len() - at < 65536usize {gz.len() - at} else {65536usize};
  inf.feed(&gz.view()[at ..< at + n]);          // 64 KiB of the compressed stream, split anywhere
  at = at + n;
  var more = true;
  while more {
    let st = inf.pull(&mut out, 65536usize);      // output, until it waits for input
    if st != Status.MoreOutput { more = false; }
  }
}

(That is packages/stages/examples/streamrates.cone, which times each codec alone.) A failure keeps its own type, and failure() gives it as an AnyError for whoever passes it on.

Layer 2: reading and writing inside one actor

Parsing wants a view of the bytes that have arrived, in place, and to say when it has used them. A Reader holds the unconsumed bytes in the buffers they arrived in. peek(n) lends the first n bytes as one slice (copying only when they cross the edge between two buffers), and consume(n) uses them up. Because peek borrows the reader and consume changes it, the checker refuses a consume while the view is alive: a parser cannot read from a buffer that has just gone home.

var r = Reader.make(65536usize);       // holds at most 64 KiB unconsumed
r.push(buf);                           // a read completed: its buffer joins
match r.peek(4usize) {                 // the first four bytes, or None (too few yet)
  case let Some(v) {
    let magic = v[0usize];             // the view is a borrow of r...
    r.consume(4usize);                 // ...so this line is refused: a view is live
  }
  case is None {}
}

A Writer is the other side: spare() to write into, advance(n) to say how much was written, and the full buffer handed on. The HTTP/1 header reader is written on a Reader.

Layer 3: stages between actors

Between two actors a stream is a run of owned chunks (an IoBuf each), handed on by a call and given back by another. Two actor traits say what a stage is to its neighbours, and neither names the other's actor: ChunkSink takes chunks (accept, which sink <- chunk spells; end; attach) and ChunkSource gets emptied ones back (giveBack). The library's own stages are generic actors: TransformStage[T] for any transform and HashStage[D] for a digest that passes the chunk on untouched. The ends of a pipeline in the OS are actors too, over aio: FileSink writes the chunks to a file and FileSource reads a file into a stream, SocketSource reads a connection into one. Each stops when the cancel group it works in is cancelled.

Credit is the buffers. A stage sends only while its window of bytes (256 KiB by default) has room; the buffers come from a pool, are taken only when there is data, and are sized to it; and the consumer gives the same buffer back when it has finished with the chunk, which is the acknowledgement that lets the next go. A slow consumer therefore holds a fast producer to its window; an idle stream holds almost nothing. The end, and an error, travel forward as the call end(how) after the last chunk: Finished, or Failed with an AnyError. Whoever sends the end lets go of the sink with it, so a sink may keep the source it was attached with (and need not drop it at its own end) without a reference cycle keeping the pair alive. A stage that awaits in accept (a file write) keeps its stream's order with an ChunkInbox, so one stream's chunks are handled in order and a stalled stream holds up no other.

A pipeline is built from the sink end back, each stage made with the one after it. Here a gzip stream arrives on a socket, is inflated, hashed and written to a file (packages/stages/examples/streamsample.cone, compiled and run):

let sink = FileSink(String.from(name), fileTx);   // fileTx: OneshotSender[Result[u64, AnyError]]
let hash = HashStage[cryptohash.Sha256](sink, cryptohash.Sha256.make(), Checker(want));
let inf = TransformStage[deflate.Inflater](hash, deflate.Inflater.make(deflate.Format.Gzip));
let src = SocketSource(inf);
src.start(SocketAddr.localhost(port));

The same job without a stream reads the whole body, inflates it in one call, hashes the result and writes the file in one call (streamsample.cone runs both, on the same input). The stream holds a few windows of it at a time instead of the body and its inflated form whole, and it overlaps the inflate with the hash and the write.

Cancelling a stream

Work that is cancelled stops, and a stream is no exception. Everything that runs in a cancel group sees its cancel, and a stage works in the group of the message it handles: a chunk and the end arrive in the group the sender works in, a buffer given back in the consumer's. So a pipeline is cancelled from the consumer back by building it so. The consumer has a group, the source runs in a child of it, and the consumer quits by cancelling its own:

let consumers = CancelGroup.make();
let upstream = consumers.child();
actors.withGroup(&upstream, fn() [src] { src.start(port); });
...
consumers.cancel();        // the sink quits: from a behaviour, or from outside

The next stage up sees the cancelled group on the next buffer given back (or chunk arriving) and stops: it ends downstream with Failed (a hash stage also answers its digest sink with an error), gives the input it holds back, and lets go of its upstream handle, so the actors do not keep each other alive even when the producer never sends an end. The stage above sees the chunks it gave back, in the same group, and does the same, all the way to the source. Buffers already out downstream still come home to their pool. A stage in no group never sees a cancel. A source that watches its group (actors.isCancelled()) can stop sooner; one that does not simply finds, after its window, that no buffers come back.

A parallel each inside a stage's codec runs in a child group of its own, so a piece that finds what it wanted can cancel the loop without cancelling the stream (A message carries its sender's cancel group).
