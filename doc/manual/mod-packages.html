Packages and the Build

A package is a folder with a manifest that the build tool, Congo, builds: each package on its own, from a build description that lists its modules and files; a library built so is named in its symbols, writes its include file, and links with a program compiled against that file.

The largest layer

A package is modularity at the size of a library: the unit that is compiled on its own, given a version, depended on by other packages, and shared. Everything the earlier pages describe for a module holds inside a package, since a package is a module and the modules inside it. What this page adds is how packages are laid out, built and linked by the build tool, Congo, and the one rule that holds at every size: dependencies run in one direction.

Packages and Congo

A package is one top-level module and the modules inside it, built on its own and shared as a unit. It is a folder holding a manifest, congo.toml, and the source under src, whose root module's designated file is named for the package:

hello/
    congo.toml
    src/hello.cone
    tests/

[package]
name = "hello"
version = "0.1.0"
output = "executable"

The manifest gives the package's name, its version (MAJOR.MINOR.PATCH), and whether it builds into an executable or a library. It lists no dependencies: the package's import statements are its dependencies. Under src the module rules apply unchanged, with src/hello.cone as the root's designated file.

A package may also have a gpu folder beside src, holding the part of it that runs on a GPU as well: more submodules of the root, each a file opening with its own mod or a folder holding its designated file, which src reaches by name as it reaches any submodule, and which may not use src in return. The GPU Compute page has the rules.

The build tool, Congo, builds packages. congo new hello makes the folder above; congo run, from anywhere inside it, builds it and runs it; congo build only builds, and --release optimises. A single file with no manifest is run with congo run hello.cone. Congo finds each package a program imports by its name, in a list of package folders, compiles each one on its own, and links them. A package is imported through its include file, which compiling the package generates from its source: build/debug/hello.cone, beside its object. Congo compiles every package before what imports it, and compiles each importer against that generated file; nothing is written by hand. The packages that come with Cone, core, stdio, libc and posix, are packages of this shape, the last two C packages (below). Imports between packages may not loop: a package never imports, directly or through others, a package that imports it. Nor may the modules inside one (below). Congo checks both before it compiles anything.

A C package wraps a C library. Its source is a C-named module, src/name.cone, declaring what the library defines, and its include file is generated from it as any package's is. Its manifest names the C library under [link], and Congo links that library into every program that imports the package:

[package]
name = "winstr"
version = "0.1.0"
output = "library"

[link]
libraries = ["shlwapi"]      # shlwapi.lib on Windows, -lshlwapi elsewhere
paths = ["clib"]             # folders to look in first, relative to the package

A program imports it by name, import winstr;, with no C declarations of its own. Any package may have a [link] table, a program's included.

What differs by system goes in a section of [link] for that system: [link.windows], [link.linux] and [link.macos], each with the same keys (libraries, paths and runtime). The plain [link] applies on every system, and the section for the system being built for adds to it, each list the plain one's entries and then the section's; a section for another system adds nothing. A package with nothing in common writes no plain [link]:

[link.windows]
libraries = ["libssl", "libcrypto", "crypt32"]

[link.linux]
libraries = ["ssl", "crypto"]

A package's build description

A package can be built on its own. The build tool, Congo, reads each file's mod line and imports, and hands the compiler a build description: a file ending in .conebuild that names each module of the package, lists its files, and says where each of its imports is found. The compiler is given that file in place of a source file:

build: debug
output: library
import core: "core.cone"
import stdio: "stdio.cone"
geometry: {
    "../../src/geometry.cone"
    "../../src/shapes.cone"
    import stdio: "stdio.cone"
    scaling: {
        "../../src/scaling/scaling.cone"
    }
}
  • The settings come first. build is debug or release, and output is executable (the default) or library.
  • Then the package lines, one import name: "path" for every package the package depends on, directly or through another package, each naming that package's include file. They are where an include file's own imports are found: an include file is a module file like any other, so it may import, and a package whose functions take or return another package's types imports that package in its include file. They do not add to what the package's own modules import. The line for core, where there is one, is also where the prelude every module imports is loaded from. Congo writes the description into the build folder, beside the include files the earlier compiles generated.
  • Then the package's module, a name and a braced body. In it, a quoted path is a file of the module, name: { ... } is a module inside it, and import name: "path" says where this module's import name is found. A relative path is relative to the description's own folder, and is written with /, since the description is read as Cone source and a backslash begins an escape.
  • The description names each module, and a mod line opening any of a module's files must restate that name. Only the first file listed may declare the module, as only a designated file may; a module inside the package is private to it unless its own mod line says pub, exactly as a submodule is.
  • Nothing is searched for. A file the description does not list is not compiled, and an import is found only where its import line says.
  • A library's module names its symbols. Built with output: library, every declaration of the package is spelled after its module — a function area as geometry.area — as a program importing geometry spells it. A program's module is not, so its main is the entry point the linker expects.
  • A library exports what its importers need. Its public functions and globals, and the public functions of its public types, are visible to the linker, so a program compiled against the library's include file links with the library's own object. So is a private function, global or type that an inline, generic or macro body, or a trait's default, names: the importer builds its own copy of that body, and the copy calls what it names. Everything else the package defines stays private to its object.
  • A generic is made by every package that uses it. Each object holds the versions of a generic that its own code uses, the library's and the program's alike, as it holds the table a type's trait methods are reached through. Where two objects hold the same one, linking keeps a single copy.

The include file declares each function, method and global the library defines with extern and no body. Its module is Cone-named like the library's, so each declaration is spelled as the library defines it; a generic is written whole.

Modules depend on each other in one direction

Imports never go round in a loop, between the modules of a package as much as between packages. A module depends on each module it imports, on the module holding a name it imports, on the module it extends, and on each of its own submodules. If those dependencies ever lead from a module back to itself, the program is in error, and the error names the modules round the loop:

Import loop between modules: geometry -> geometry.scaling -> geometry.
Imports between modules must not loop (geometry contains geometry.scaling;
geometry.scaling imports Point of geometry at scaling.cone:3). A module may
not depend on a module that contains it: move what they share into a sister
both import.

So every program's modules have an order, each after everything it depends on. That is the order their initializers run in, and their finalizers run in the reverse.
