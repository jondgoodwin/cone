Cone
Moves: values with one holder

Most values copy: hand one on, and both sides have their own. But a value that owns something, an open socket, a file, a block of memory, must not be copied, or two holders would each close it or free it. Such a value moves: handing it on leaves nothing behind. This page covers which types move, what a move leaves behind, and how to get a value out of a struct or an array. Afterwards you can write types that own a resource and pass them around, knowing each is cleaned up exactly once:

mod sockets;

import stdio use *;

// A socket closes itself when it is finalized, so there may never be two
struct Socket {
  pub id i32;
  fn final(self &uni) { print <- "close ", id, "\n"; }
}

fn send(s Socket) {
  print <- "send on ", s.id, "\n";
}                          // s is finalized here: the socket closes

fn main() {
  imm a = new Socket(1);
  imm b = a;               // a's socket moves to b; a is left with nothing
  send(b);                 // and moves on into send
  imm c = new Socket(2);
  print <- "end of main\n";
}                          // c closes here; a and b hold nothing to close

It prints:

send on 1
close 1
end of main
close 2

Try this: after send(b), add print <- a.id;. The compiler refuses it: This variable's value has been moved out. It is no longer there to use.

The Guide met moving with text (Copy or move): a String owns the memory its text is in, so it moves. This page is the whole story, and it is the ground the rest of this part stands on: a single owner is a value that moves, and a borrow, next, is the way to use a value without moving it.

Why some values move

A copy is a second, independent value: change it, and the original is as it was. For numbers that is exactly right. For some values, a second copy would be trouble:

  • The value stands for a resource. A handle to an open file or socket is a way to reach something outside the program. Copy the handle and close the file through one copy, and the other copy now reaches nothing, or worse, a different file opened later in its place.
  • No faithful copy is obvious. A complex value may not carry enough to rebuild itself, or rebuilding it may mean allocating memory, opening resources or setting up dependencies that a silent copy should not do.
  • One holder is cheaper. A value that never has two holders can be freed the moment its holder goes, decided when the program is compiled, with nothing counted or traced while it runs. That is the single-owner strategy.
  • It can travel between threads. Changeable data with exactly one holder can be handed to another thread with no lock and no atomic operation, since nobody is left behind to race with.

So the rule is simple: a value of a type that moves has exactly one holder at a time. It may be handed from variable to variable and function to function, but each hand-off leaves the giver with nothing.

Which types move

Whether a value copies or moves is decided by its type, never by how it is used. Every type is exactly one of two things, named by two built-in marker traits, Copy and Move, and the compiler grants the one these rules give. A type moves if:

  1. It says so, by naming Move among the traits it declares: 
    struct Handle is Move {
   pub id i32;
}
    A type declaring AtomicValue, the marker of an atomic value, moves too: a copy would be a second value that no atomic operation on the first could reach.
  2. It has a finalizer. A type that needs a final method to clean up after it almost certainly owns something, and each copy would clean it up again. The Socket above moves for this reason alone.
  3. Any of its fields moves. If part of a value cannot be copied, the whole value cannot be. A struct holding a List of itself is one, without declaring is Move, and so is an enum with a variant that holds a List of the enum, and each of two types that hold a List of the other.
  4. It is an enum and any of its variants moves, by any of these rules, since a value of the enum may be that variant.
  5. It is an owning reference that may not be shared: one whose permission forbids aliasing, or whose region declares Move, as So does (Regions). A struct holding a So field moves by the rule before.

Anything else copies. Not built yet: the design also has a type move when any of its fields is a reference to other data, since there is no obvious safe way to copy such a value automatically. Today a struct whose fields are borrowed references (&, &mut, &imm) or shared owning references (Rc[mut, T], Rc[imm, T]) is copied; only an owning So or a uni field makes it move.

A type may also declare is Copy. That is an assertion, not an instruction: it changes nothing about a type that copies anyway, and the compiler refuses it on a type the rules make a move type, one that also declares Move, or has a finalizer, a field that moves, a base it enriches that moves, or (for an enum) a variant that moves:

struct Point is Copy {     // accepted: nothing here moves
   pub x i32;
   pub y i32;
}
struct Log is Copy {       // Error 1167: Log is declared Copy, but its 'final' makes it move:
   fn final(self &uni) { } //   each copy would be finalized.
}

A clone method takes no part in any of this. A type may declare one and call it by name, imm q = p.clone();, but no copy calls it, so it does not make a move type copyable, and a type with a finalizer still moves. A clone method written with the new permission is refused.

Moving is a trait, rather than an attribute, because it is a fact other code may ask about, which is what a trait is for; an attribute is an instruction to the compiler about representation or linkage that no code asks about. A generic asks by requiring where T is Copy or where T is Move (Generic constraints). There is no compile-time if to ask it inside a body: v is Move in an expression is the test of an enum's variant, and on a value that has no variants it is refused.

What a move leaves behind

A move may well copy the value's bytes; what it guarantees is that only one holder can use them afterwards. It does that by deactivating the source: once a value has moved out of a variable, the variable may not be used again, neither read nor borrowed, until it is given a new value. That holds whether the value was assigned to another variable, handed to a function, or handed on as the value of a block, an if or a loop:

imm socket = new Socket(1);
imm moved = { socket; };   // the block hands socket on: it moves
consume(socket);           // Error 1048: This variable's value has been moved out.

A value returned by a function is handed to the caller; there is no source left to deactivate. Assigning a new value to a deactivated variable makes it usable again.

Moves on some paths: drop flags

A value moved on one branch and not another may or may not be there when the branches join, and the compiler assumes the worse: the variable may not be used again, read or borrowed, until it is given a new value. A move inside a loop is the same, since a value moved in one pass is not there in the next:

fn early(done bool) {
  imm socket = new Socket(1);
  if done {
    consume(socket);       // moved on this path only
  }
  peek(&socket);           // Error 1048: This variable's value has been moved out.
}

fn looping() {
  imm socket = new Socket(1);
  mut n = 0;
  while n < 3 {
    consume(socket);       // Error 1048: This variable's value may have been moved out on a path
    n = n + 1;             //   that reaches here (a branch, or an earlier pass of a loop).
  }
}

The value is still finalized exactly once, and only on a path that still holds it. On the path that moved it, its new holder finalizes it; on the path that did not, it is finalized at the end of its scope, as any value is. The paths may part in one branch of an if or a match, in a loop that may not run, or before an early return or break. To know which happened, the compiler keeps a hidden drop flag beside such a variable, set where its value arrives and cleared where it moves out, and the end of the scope tests it. A variable moved on every path, or on none, needs no flag and costs nothing:

struct Socket is Move {
  pub id i32;
  fn final(self &uni) { print <- "close ", id, "\n"; }
}

fn consume(s Socket) { print <- "consume ", s.id, "\n"; }

fn run(done bool, id i32) {
  imm socket = new Socket(id);
  if done {
    consume(socket);     // moved on this path only
  }
  print <- "end of run\n";
}                        // socket is closed here only if done was false

run(true, 1) prints consume 1, close 1 (consume's parameter is finalized at its end) and end of run. run(false, 2) prints end of run and then close 2. Neither closes a socket twice. The same flag serves a variable given a new value on only some paths, or assigned over (When a value dies).

From scope to scope

A moving value can be pictured as surfing from scope to scope, its life lengthened each time it is handed on. When it fails to surf out of its last scope, it is finalized at that scope's end, since nothing can use it any more.

Not built yet: destroying a moving value early by assigning it to the anonymous variable, _ = socket;, after which socket would be deactivated. Today the name _ is not recognised (Error 1019: The name _ does not refer to a declared name). On a value that copies it would have no effect.

Moving a value out of a struct, an array or a reference

Moving a whole struct or array is always allowed, and takes every field or element with it. Moving one piece out is a different matter, because something would be left with a hole in it:

  • A field of a struct, or an element of a tuple. The struct could no longer be used as a whole, and there would be no sound answer to what finalizing it should finalize. This holds wherever the struct is (a variable, a parameter, a self taken by value, a temporary, or reached through a reference) and wherever the value would go (into a variable, a call, a literal, or back to a caller, directly or as the value of a block, an if or a loop). It holds for a value reached through a field too, such as what an owning reference held in a field points at, or an element of an array held in a field.
  • An element of an array (imm first = arr[0];, take(arr[1]), grid[1][0]), whether the array is a variable, a parameter, a temporary or the one a sole owner points at (take(owner[0]), for owner a So). The elements left behind would never be finalized. The refused move leaves the array as it was.
  • Through a borrowed reference, by dereferencing it or by reaching a field or element through it, whatever its permission. A borrowed reference does not own the value: the place it borrows from does, and still holds the value after the borrow ends. This applies wherever the value would go, including into a method whose self is taken by value.
  • Through a shared owning reference, one whose permission allows copies of it, such as Rc[mut, T], Rc[imm, T] or Rc[ro, T], or one into a region that declares neither aliasRef nor Move, whose references are shared freely. The other holders would still point at the value. A sole owner may give its value up: a So reference, or a Rc[uni, T] one (which is what Rc[T] means), since a unique reference is the only holder there is. Moving the value out deactivates the reference, as moving out of a variable does, and leaves the owner hollow: its memory is still freed, but nothing that moved is finalized there.
struct Connection {
  pub s Socket;
  pub b i32;
}

imm conn = new Connection(new Socket(1), 10);
imm s = conn.s;        // Error 1166: May not move field 's' out of the struct that holds it.
                       //   Swap a value in with '<=>', or move the whole struct.
imm conn2 = conn;      // allowed: the whole struct moves, its socket with it

fn first(arr Array[Socket, 2]) {
  imm s = arr[0];      // Error 1121: May not move a value out of an element of an array,
}                      //   which would be left with a hole in it.
fn borrowed(r &mut Socket) {
  consume(*r);         // Error 1120: May not move a value out through a borrowed reference,
}                      //   which does not own it.
fn shared(r Rc[mut, Socket]) {
  consume(*r);         // Error 1120: May not move a value out through a shared owning
}                      //   reference, which does not solely own it.
fn sole(owner So[Socket]) {
  consume(*owner);     // allowed: the sole owner gives its value up
}

One case is a move of the whole value in disguise, and is allowed: a match that takes what a variant holds out through its binding (all of a variant declared as a type, such as Some, or the one field of a struct variant), where the matched value is held only by the match (the answer of a call, such as names.pop(), or a variable the match consumes), and the variant holds nothing else and has no finalizer of its own. The move counts as moving the matched value, so nothing is left with a hole in it and nothing is finalized twice:

match names.pop() {
  case mut s Some { imm last = s; print <- last.view(), "\n"; }
  case is None { }
}

A variant with two fields, or with a finalizer of its own, is still refused, and so is taking the contents twice. This is what lets each take an item that moves out of a cursor's Option, as drain does.

Getting a value out anyway: swap and :=

Those are real limits on keeping moving values in structs and arrays, and two operators get around them by never leaving a hole. The swap operator, <=>, exchanges two values, and works on values that copy or move alike. To take a moving value out of a field or element, swap some other value of its type in, use what came out, and swap it back if you like. Neither value is ever copied, and the struct always holds something valid:

mut conn = new Connection(new Socket(1), 10);
mut x = new Socket(2);
conn.s <=> x;                    // conn now holds socket 2, and x socket 1

The left-assignment operator, :=, stores a new value and gives back the one it replaced. (Ordinary assignment, as an expression, gives a copy of the new value, which a moving value cannot give.)

mut y = conn.s := new Socket(3); // conn now holds socket 3, and y the one it held before

When a value dies

Moves decide who holds a value; its holder decides when it dies, and so when its finalizer runs. For a value with a finalizer, a socket, a file, a lock, the moment matters, so here it is exactly. A local dies at the end of its block, the newest first. The rest follows:

mod lifecycle;

import stdio use *;

struct Log {
  pub n i32;
  fn final(self &uni) { print <- "  final ", n, "\n"; }
}

fn make(n i32) Log { print <- "  make ", n, "\n"; new Log(n); }
fn take(l Log) { print <- "  take ", l.n, "\n"; }

fn main() {
  print <- "a field of a temporary:\n";
  imm n = make(1).n;            // the Log dies at the end of this statement
  print <- "moved into a call:\n";
  take(make(2));                // take's parameter finalizes it
  print <- "a condition:\n";
  if make(3).n > 0 {            // dies once the condition is decided, before the branch
    print <- "  branch\n";
  }
  print <- "assigned over:\n";
  mut v = make(4);
  v = make(5);                  // 5 is made, then 4 finalized, then 5 stored
  print <- "end of main:\n";
}                               // v, holding 5, dies here

It prints:

a field of a temporary:
  make 1
  final 1
moved into a call:
  make 2
  take 2
  final 2
a condition:
  make 3
  final 3
  branch
assigned over:
  make 4
  make 5
  final 4
end of main:
  final 5

A temporary is a value an expression produces that nothing takes: it is not bound to a variable, stored in a field or element, passed by value, returned or moved. A call's result whose field is read, an owning reference read through, an owner lent to a call as a borrowed reference, a value thrown away by a statement: each is a temporary, and dies at the end of the statement that produced it, the newest first. One produced by the condition of an if or a while dies once the condition is decided, before the branch runs, so each pass of a loop finalizes its own; and one produced by the right operand of and or or, which runs on some paths only, dies at the end of that operand. A value moved out of a temporary owner belongs to its new holder, and the owner's memory is freed without it. A temporary that a variable's initializer borrows lives on to the end of the variable's block instead (Borrowing a temporary).

A temporary that a raw pointer made from it may outlive is not finalized at all. Nothing follows a raw pointer, so the compiler leaves the value as it is rather than finalize it and leave the pointer dangling. An ordinary borrow of the same temporary does not keep it:

fn mk(n i32) R {..}
fn id(r &R) &R {..}          // answers the borrow it is handed

imm p = id(&mk(2)) as *R;    // p may outlive the temporary: R's final never runs for it
imm q = id(&mk(3));          // an ordinary borrow: R's final runs at the end of this statement

A value assigned over dies as it is replaced: the new value is evaluated first, then the old one is finalized, then the new one is stored. This is so for a variable, a field or an element of one, and a value reached through a reference (*r = v). Where the variable holds nothing to replace, because it was never given a value or its value moved out, nothing is finalized; where that depends on the path, its drop flag decides.

A value allocated in a region is finalized when the region lets it go: when its single owner goes, or, for a counted region, its last owner (When a value is freed). It dies as above, and only then is its memory freed, so a finalizer may still use everything its value owns. A value moved out of a region's object belongs to its new holder, which finalizes it; the object's memory is freed without finalizing what was moved out. Only the whole value moves, never one of its fields (above), so no object dies partly moved out.

An enum's value is finalized as the variant it holds would be: the tag says which. An enum may declare its own final, which runs for every variant, and a variant may declare one too: the variant's finalizer runs first, then the enum's, then the finalizers of the variant's fields (the enum's common fields among them), then the owning references those fields hold are released: the more specific type before the more general. An enum none of whose variants has anything to finalize costs nothing when its value dies: dropping an Option[i32] does no work, while dropping an Option[String] finalizes the string when it holds one, and the owner held in a Some is let go with its Option:

struct Handle { pub fd i32; }
struct Named { pub n i32; fn final(self &uni) { print <- "field final\n"; } }

enum Resource {
  fn final(self &uni) { print <- "released\n"; }       // runs for every variant, after its own
  struct File {
    pub handle Handle;
    pub name Named;
    fn final(self &uni) { print <- "close ", handle.fd, "\n"; }   // runs first, for a File
  }
  struct Nothing {}
}

imm r Resource = Resource.File(new Handle(7), new Named(1));   // dies: close 7, released, field final
imm s Resource = Resource.Nothing;                             // dies: released

A global variable lives until the program shuts down. Whatever it holds is then finalized by its module's finalizer, after the module's own final: a value whose type finalizes, a tuple or an array of them, or an owning reference, which is released (Dynamic initialization of global variables, where a module's own initializer and finalizer are described):

mod globals;

import stdio use *;

struct R {
  pub n i32;
  fn final(self &uni) { print <- "final "; print <- n; print <- "\n"; }
}

imm one R;
imm pair (R, R);
imm many Array[R, 2];
imm owned So[R];

fn @initpure init() {
  one = new R(1);
  pair = (new R(2), new R(3));
  many = [new R(4), new R(5)];
  owned = new So[R](6);
}

fn main() {
  print <- "main ends\n";
}

This prints main ends, and then, after main returns, final 1 through final 6, one to a line.

A generic type that moves for some instances

A generic type that holds a value of its type parameter already moves exactly when the parameter does, by the rule for fields: a Box[i32] holding an i32 copies, and a Box[Handle] holding a Handle moves. A generic type that holds no value of its parameter, but stands for one, has no such field. A future is the usual case: it holds a shared reference to a cell where the result will be put, and a shared reference copies whatever it points at. Such a type says when it moves with a condition on the Move entry of its is list, after the word if:

struct Handle is Move {
   pub id i32;
}
struct Cell[T] {
   pub v T;
}
struct Future[T] is Move if T is Move {
   pub c Rc[imm, Cell[T]];
}

imm f = new Future[i32](new Rc[imm, Cell[i32]](new Cell[i32](5)));
imm f2 = f;     // a copy: i32 does not move, so neither does Future[i32]
imm f3 = f;     // another copy; f is still there

imm g = new Future[Handle](new Rc[imm, Cell[Handle]](new Cell[Handle](new Handle(7))));
imm g2 = g;     // moves g: Handle moves, so Future[Handle] does
imm g3 = g;     // Error 1048: This variable's value has been moved out.

In plain words: a future of something that moves moves too, so the result inside it can be taken only once, and a future of something that copies can be copied freely. The actors package's Future[T], a behaviour's value kept to be awaited later, is declared this way (Storing a future).

Each instance decides the condition with its own type arguments. Where it holds, the instance is Move; where it does not, the instance copies, unless another rule makes it move: a condition can add Move, never take it away. The condition is written as a where clause is: clauses T is Name, joined with and and or and grouped by parentheses, each about one of the type's own parameters, so struct Pair[A, B] is Move if B is Move asks about the second only. Copy takes no condition, since a type copies wherever nothing makes it move, and a type with no type parameters takes none either, since every use of it is the same type.

The condition belongs to the one entry it follows. A where clause after the is list says something else, a requirement on the whole type: struct Future[T] is Move where T is Move makes every instance move, and refuses Future[i32] outright (Error 1186: Future requires T is Move, and i32 is not Move).

You can now tell which of your types move, and pass a value that owns something from place to place knowing it is finalized exactly once. But moving a value just to look at it, and moving it back, would be tiresome. Next comes the way to use a value without taking it: borrowing.
