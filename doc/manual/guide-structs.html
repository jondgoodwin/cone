Structs and methods

Numbers alone describe little. A program gathers the values that belong together into data of its own: a point with its coordinates, a rectangle with its corner and size. A struct does that, and its methods say what can be done with one. This page also covers the two simplest ways to group values without declaring anything: tuples and arrays. Here is a program that works with points and rectangles:

// Structs and methods
//
// A struct gathers values that belong together into a type of your own.
// Its methods are functions that belong to the type: each takes the value
// it works on as 'self', and here each one hands back an answer or a new
// value rather than changing the old one.

mod shapes;

import stdio use *;

struct Point {
  pub x f32 = 0.;               // a field may have a default value
  pub y f32 = 0.;

  // A function of the type, with no 'self': called as Point.origin()
  pub fn origin() Point {
    new Point();                // both fields take their defaults
  }

  // A method: 'x' and 'y' here are self.x and self.y
  pub fn len(self) f32 {
    (x * x + y * y).sqrt;
  }

  // A method that builds a new Point; the old one is left as it was
  pub fn scaled(self, k f32) Point {
    new Point(x * k, y * k);
  }

  // A method named for an operator gives the type that operator: a + b
  pub fn `+`(self, other Point) Point {
    new Point(x + other.x, y + other.y);
  }

  pub fn `-`(self, other Point) Point {
    new Point(x - other.x, y - other.y);
  }

  pub fn `==`(self, other Point) bool {
    x == other.x and y == other.y;
  }

  pub fn show(self) {
    print <- "(", x, ", ", y, ")";
  }
}

// A struct may hold another struct as a field
struct Rect {
  pub corner Point;
  pub w f32 = 1.;
  pub h f32 = 1.;

  pub fn area(self) f32 {
    w * h;
  }

  pub fn grown(self, extra f32) Rect {
    new Rect(corner, w + extra, h + extra);
  }

  pub fn center(self) Point {
    corner + new Point(w / 2., h / 2.);
  }

  // A tuple: two values handed back at once
  pub fn size(self) f32, f32 {
    w, h;
  }
}

fn main() {
  imm a = new Point(x: 3., y: 4.);    // fields named...
  imm b = new Point(1., 2.);          // ...or listed in order
  imm o = Point.origin();

  print <- "a is "; a.show(); print <- ", length ", a.len(), "\n";
  print <- "a + b is "; (a + b).show(); print <- "\n";
  print <- "a - b, doubled, is "; (a - b).scaled(2.).show(); print <- "\n";
  if a == o { print <- "a is the origin\n"; } else { print <- "a is not the origin\n"; }

  imm box = new Rect(corner: b, w: 4., h: 2.);
  imm bigger = box.grown(1.);
  print <- "box area ", box.area(), ", bigger area ", bigger.area(), "\n";
  print <- "bigger's center is "; bigger.center().show(); print <- "\n";

  imm w f32;
  imm h f32;
  w, h = bigger.size();
  print <- "bigger is ", w, " by ", h, "\n";

  // An array: a fixed number of values of one type
  imm path = [o, a, new Point(6., 0.)];
  mut walked f32 = 0.;
  each i in 1usize ..< 3usize {
    walked += (path[i] - path[i - 1usize]).len();
  }
  print <- "walking the path covers ", walked, "\n";

  mut far f32 = 0.;
  each p in path {
    if p.len() > far {
      far = p.len();
    }
  }
  print <- "the farthest point is ", far, " from the origin\n";
}

It prints:

a is (3, 4), length 5
a + b is (4, 6)
a - b, doubled, is (4, 4)
a is not the origin
box area 8, bigger area 15
bigger's center is (3.5, 3.5)
bigger is 5 by 3
walking the path covers 10
the farthest point is 6 from the origin

What to notice

  • A struct declares named fields, each with a type, and new Point(...) builds a value: fields named, listed in order, or left to their defaults.
  • A method is a function inside the struct whose first parameter is self. Inside it, x means self.x.
  • These methods never change the value they are called on: scaled and grown give back new values, and a and box stay as they were.
  • A method named `+` or `==` gives the type that operator.
  • A tuple hands back several values at once; an array holds a fixed number of values of one type, read by index from 0, and walked by each.

Values that belong together

A struct gives a group of values a name, and the name is a new type, used like any other: for a variable, a parameter, a return value or a field of another struct. Point has two fields, x and y, each declared like a variable, with a name and a type. Rect holds a Point as one of its fields, so structs build on each other.

A value is built with new, the struct's name, and the fields' values in parentheses. They may be named, new Point(x: 3., y: 4.), or listed in the order the fields are declared, new Point(1., 2.). A field with a default value, as all of Point's have, may be left out, so new Point() is the origin. A field is read with a dot, a.x.

The pub in front of each field and method makes it public: code anywhere may use it. Without pub it is private to the module that declares the struct. That is how a type keeps its promises: when a field's value must obey some rule, it is left private, and the type's own methods, which keep the rule, are the only way to change it.

Methods: what a value can do

A method is a function written inside the struct, whose first parameter is named self: the value the method is called on. a.len() calls len with a as its self. Inside a method a field or another method can be named on its own, so x is short for self.x. A method's name belongs to its type, so Point's len and some other type's len never get in each other's way.

Every method in this program takes self as a value and gives back an answer, or a new value. scaled builds a new Point and grown a new Rect, and the values they were called on are just as they were. That makes a program easy to follow: a and box are the same after every call as before it. Methods that do change their value, and the initializers and finalizers that run when a value is made and when it dies, are in In detail below.

Since a method gives back a value, the next method can be called straight on it: (a - b).scaled(2.).show().

A function inside the struct that has no self belongs to the type rather than to a value. It is called through the type's name: Point.origin().

An operator is a method too. A method named `+` (in backticks, because the name is punctuation) gives the type the + operator, so a + b calls a.`+`(b), exactly as it does for numbers. `==` gives it ==, and != comes with it. A struct that declares no == cannot be compared at all, since only the type knows what makes two of its values equal.

Tuples and arrays

Not every group of values needs a name. A tuple is a few values, each with its own type, held together: size gives back two, and the caller catches them with a parallel assignment, w, h = bigger.size(). A variable may hold a tuple whole, and its elements are read by number, from 0:

mut pair (i32, i32) = 7, 3;
print <- "pair is ", pair.0, " and ", pair.1, "\n";      // pair is 7 and 3
pair = pair.1, pair.0;
print <- "swapped, ", pair.0, " and ", pair.1, "\n";     // swapped, 3 and 7

An array holds a fixed number of values, all of one type. [o, a, new Point(6., 0.)] is an array of three points, whose type is Array[Point, 3]. An element is read by its index, an unsigned number counting from 0: path[i], where i is a usize. Every index is checked, and one past the end stops the program with a panic that names it: index 3 is out of bounds for a count of 3. each p in path walks the elements in order.

An array's size never changes, and that is why most programs reach for a list instead, which grows: Collections comes to lists, dictionaries and the rest, which are structs built on arrays.

Structs: declare, build, read fields

A struct holds one or more named values (fields), each with its own type. The struct's fields are located together in memory. A field's value can be individually accessed using the field's name.

Let's illustrate by declaring a new struct type:

struct Complex {
  pub real f32;
  pub imag f32;
}

This defines a new struct type called Complex that holds two fields of data. The fields named real and imag are both 32-bit floating point numbers.

Variables can be declared and initialized using this new type, each with its own values in these two fields:

imm comp1 = new Complex(real: 3.2, imag: 0.0);
mut comp2 = new Complex(real: 0.0, imag: 1.0);

This section focuses on using structs to hold field-oriented data. Later sections and pages enrich what can be done with a struct by adding methods, inheritance, or traits.

Declaration

Before we can make use of a specific data structure, we need to declare it, giving it a name and specifying its fields:

struct Point {
    pub x f32 = 0.;
    pub y f32 = 0.;
}

The struct's declared name is effectively new, custom-defined type. This type name can be used to declare any number of variables containing values of this type (e.g., imm pt1 Point).

Field declarations look like variable declarations, specifying the field's:

  • Permission. The actual permission that governs field access is derived from both the field's and struct's permissions using a mechanism called viewpoint adaptation. If unspecified, mut is assumed, which effectively means the struct value's permission governs access.
  • Name. Each field must be given a unique name. However, names used in one struct will not be confused with same-named fields in other types, nor with variable or function names.

    A field is private unless it is declared pub. A private field is private to the module that declares the struct: any of that module's code may access it, through any value of the struct, and code outside the module may not. Fields should be left private if we don't want logic outside the module to depend on this implementation detail or be able to change its value directly. This is particularly important when the field's value should be subject to additional invariant constraints that are properly enforced by the struct's methods. A struct whose fields must be kept even from the rest of its module is declared in a module of its own.

    A pub field of a pub struct may not have a type private to the module, since code outside the module would reach into a type it cannot name.

    The anonymous name _ may be used for any data segment of the struct that we don't want or need access to.

  • Type. This can be any type: numeric, bool, an array, some other struct, etc. The name Self may be used to refer to the struct type currently being defined. There is one important restriction: A field's type may not be the same as the struct type we are declaring (or any recursive variation on this). A field's type, however, may be a reference to the struct type, or to a type that holds it, whichever of them is declared first: a reference is a pointer whatever it points at. So may be a List of the struct, which holds its elements in a block of its own: 
    struct Node {
  pub id i64;
  pub kids List[Node];
}
    Such a struct moves, as any struct with a field that moves does (move semantics), without declaring is Move. So does an enum with a variant that holds a List of the enum, and each of two types that hold a List of the other.
  • Fold clause. A public field may end with use and a list of members of its type, which become names of this struct reached through the field: delegated inheritance.
  • Default value. The default value must be a constant: a literal, null for a pointer field among them, a named constant, a constant expression computed from them (Red | Green), or a reinterpretation of one to a number or pointer type with as, such as 4096usize as *u8, or an array, struct or tuple of such constants. A variant of an enum that holds no value is one too (kind Kind = Kind.Os, next Option[i32] = None); a variant that holds a value is not. Specifying default values makes initialization of a newly created struct more convenient.

Initialization

A new struct value is constructed with new: the struct name followed by the arguments of one of its initializers in parentheses. Every struct has an implicit initializer that takes its fields' values. Values may be marked with field names or just listed in declared order:

imm pt = new Point(x: 3., y: 4.);   // Using field names
imm pt2 = new Point(3., 4.);        // When field names are omitted, order matters.
imm pt3 = new Point();              // Uses x,y's declared default values of 0.
imm pt4 = new Point;                // The same: empty parentheses may be left off

Several constraints apply to the implicit initializer:

  • It must be given a value for every field lacking a default value.
  • Only code in the module that declares the type may use it to give a value to a private field. A private field with a default value may be left to its default from anywhere.

A struct may also declare initializer methods of its own, which may compute the value they build. The arguments of a construction select the initializer that takes them. Where a declared initializer and the implicit one both take values listed in order, the declared one is used; naming the fields reaches the implicit one.

A construction fills its value where it goes: declaring a variable with one hands the initializer the variable's own memory, so no copy is made.

Field Access

Use the . operator to access a struct field's value, specifying the struct value on the left and the field name on the right:

imm dist = (pt.x*pt.x + pt.y*pt.y).sqrt;

A field's value may also be altered in this way:

pt.y = pt.x;

The compiler applies field privacy and permission constraints to prevent invalid field accesses. A private field can only be accessed by code in the module that declares the type. Changing of a field's value is only allowed if the struct/field permissions allow mutability.

It is also possible to use the & operator to borrow a reference to a specific field within a struct value.

Empty structs

It is perfectly legal to define a struct with no fields. Nearly always, such types may be used like any struct type for variables, fields, parameters, etc.:

  • Although its values take up no space, empty struct values can nonetheless be passed around.
  • Methods may be defined for an empty struct and used by its values.

The most significant restriction is that it is not possible to allocate a zero-sized value on the heap, which means you cannot create an owning reference to a value of an empty struct.

The language's pre-defined void type is defined internally as an empty struct.

A struct may also hold a static variable, one copy shared by all its values (pub static mut made = 0;), and a struct whose contents are hidden is @opaque: Static variables in a struct and Opaque Types.

Methods and self

Methods associate functional behavior to a defined type, offering capabilities consistent with and helpful for values of that type. For example (as mentioned earlier), `+` is one of several methods defined for the i32 type. It adds two integers together and returns the result.

This example defines several methods as part of the Point struct declaration:

struct Point {
  pub x f32;
  pub y f32;

  // Calculate distance between two points
  pub fn distance(self, pt2) f32 {
    (self-pt2).len;
  }

  // Subtract two points
  fn `-`(self, pt2) Point {
    new Point(pt2.x - x, pt2.y - y);
  }

  // Calculate length of point
  pub fn len(self) f32 {
    lensq().sqrt; // lensq() is equivalent to self.lensq()
  }

  // A private method
  fn lensq(self) f32 {
		x*x + y*y;
  }
}

There's a lot to unpack here, which we will get to soon. The end result is that the above type definition for Point now makes it possible to write logic that uses these methods: 

imm from = new Point(x: 1., y: 1.);
imm to   = new Point(x: 4., y: 5.);
imm dist = from.distance(to);     // == 5.0. Pythagoras would be proud

Methods may be added to any named type declaration (e.g., struct, trait, enum, number type), but not directly to any structural type (e.g., tuple, array, reference). To apply methods to a structural type, wrap the structural type as a field in a struct, and then add methods to that struct.

An enum type's methods may be written anywhere in its body, before or after its variants: what makes a member common to every variant is that it is not a struct. Such a method applies to all variants, but can only access the enum's common fields.

Adding methods to a type after its declaration, with extend, is planned and not built (Extensibility).

Method definition

A method definition looks (and behaves) like a function definition: It has a name, named parameter(s), return value type(s), and a statement body. What distinguishes a type's methods from its associated functions is that the first parameter is named 'self'.

Method name

As with fields, the names given to methods will not conflict with another type's method or field names, nor with the names of variables or functions outside the type. However, a type cannot have a method and field with the same name.

Two or more methods may share one overload name. This is called method overloading. Each method still has its own unique name; it declares the shared name it overloads by placing the overload keyword and that name between its own name and its signature:

struct Rect {
  pub w f32;
  pub h f32;

  pub fn areaOf overload area(self) f32 {
    w * h;
  }
  pub fn areaScaled overload area(self, scale f32) f32 {
    w * h * scale;
  }
}

imm r = new Rect(2., 3.);
imm a = r.area();          // selects areaOf
imm b = r.area(4.);        // selects areaScaled
imm c = r.areaScaled(4.);  // calls the method directly by its own name

Methods that overload one name should vary in their number of parameters or in the types of their parameters, because two candidates that would accept exactly the same arguments are an error. A call using the shared name is resolved by trying every method that overloads it and requiring exactly one of them to accept the call's receiver and arguments, allowing for default parameter values and permitted implicit coercions. No matching method is an error, and more than one matching method is an ambiguity error; an exact match is not preferred over a match requiring coercion, declaration order never breaks a tie, and return types take no part in the choice. A caller resolves an ambiguity by calling a method's own name or by converting arguments. Sharing an overload name across methods makes it convenient for a type to support a similar capability for a broad range of differently-typed values.

A shared name may only be used as the name of a method being called. Everywhere else, use the method's own name.

A method a trait provides to every type that declares it (a shared method, one the trait gives a body) is replaced by the type's own method of the same name, whatever its shape: the own method need not take or give what the trait's does, and the type simply has no copy of the shared one. Calls on the type, direct or from generic code over the trait, reach the type's own method; a type with none gets the shared one.

A generic method joins a shared name on the same terms as a generic function: when every type parameter is bound to a function signature (A generic function that overloads a shared name).

self Parameter

A method's first parameter is always named self. If the type of self is not specified, it is assumed to be the same as the type we are specifying (Self). If a type is specified for self, it must either be the same as Self, or some kind of reference to Self. A method whose self is a borrowed reference may still be called on a value held in a variable, which is borrowed for the call (see Implicit Coercion of 'self'). A method may also ask for the owner of its value (below).

Implicit parameter types

As with the self parameter, a method's other parameters need not specify their type. If omitted, Self is assumed.

Implicit field and method access

Nearly always, a method's logic needs access to the data object referred to by self. Often, it may also want to invoke other methods in the same type. As one would expect, such capabilities are easily achieved through the use of self:

imm len = (self.x * self.x + self.y * self.y).sqrt;
self.clear();

Fortunately, a more concise approach is possible, by omitting "self." altogether:

imm len = (x * x + y * y).sqrt;
clear();

Using the more concise syntax depends on not defining any local variables in the method that would conflict with the type's field or method names (a member's name hides an outer one).

Working on one value: with blocks

A with block is a block that focuses its logic around one value, named this, whose fields and methods it reaches with a bare dot:

with &mut point {
	.x /= len;      // the same as point.x /= len
	.y /= len;
}

with blocks and this has the form in full, with the prefix operators that act on this.

Making and cleaning up: init and final, briefly

Initializers and finalizers are specialized methods a type may optionally define. Their use bookends the life of a type's objects. Initializers help create new objects. Finalizers help destroy them.

Many types don't need initializer or finalizer methods. For those that do, here's how to define them. 

struct Seeded {
  pub seed i32;
  pub fn init(self &new, n i32) {
    *self = new Seeded(seed: n * 10 + 1);
  }
}

imm a = new Seeded(5);        // the declared initializer: seed is 51
imm b = new Seeded(seed: 5);  // the implicit initializer: seed is 5

fn final(self &uni) {
  file.close;
}

An initializer is named init, fills self with another initializer (typically the implicit one, by naming the fields), and returns nothing. A finalizer is named final, and runs by itself when a value dies, to close or give back what the value holds. A type with a finalizer moves rather than copies (Copy or move). The full rules are at the end of this page.

A method named clone takes no part in copying: it may be declared and called by name as an ordinary method, but no copy, whether by assignment or by a function call's parameters, calls it (Clone method).

Static variables

Static variables in a function

A variable declared inside a function is ordinarily created afresh on every call and released when the call ends. A variable declared static is one copy instead, shared by every call of the function, initialized once before the program starts running, and kept across calls:

fn tick() i32 {
  static mut calls = 0;
  calls = calls + 1;   // 1 on the first call, 2 on the second, ...
  calls;
}

The same word means the same thing at every scale. Inside a type, a static variable is one copy shared by every value of that type, rather than a field held by each value. At the top of a module, it is the module's one copy, which is what a global variable is already. A generic type or module has one copy per instantiation: each instantiation, such as Box[i32], is a type or module in its own right with its own static, since the static's type may name the generic parameter. Because a static's initial value is written into its storage before anything runs, it must be a literal, as a global variable's must.

static applies to a variable and to nothing else: a function has no copy per call to share, and neither does a type or a statement.

Static variables in a struct

A field is held by every value of the struct, one copy each. A variable declared static inside the struct is one copy shared by all of them. It is not a field: no value carries it and no initializer sets it. From outside the struct it is reached through the type's name, in the same way as the struct's functions; inside the struct's own methods and functions it is reached by its bare name.

struct Tally {
  pub n i32;
  pub static mut made = 0;

  pub fn make(n i32) Tally {
    made = made + 1;       // shared by every Tally
    new Tally(n);
  }
}

imm a = Tally.make(1);
imm b = Tally.make(2);
imm count = Tally.made;   // 2

Like a global variable, a static must be initialized with a constant value (a literal, a named constant or a constant expression), and it obeys pub as any other member of the struct does. A generic struct's static belongs to each instantiation separately: Crate[i32] and Crate[f32] are two types, and each has its own copy.

Operators and special methods

Note: Most of this has been implemented, including the final method and the append operator's list of entries (values, n of x, fill x, pairs and each), after a value and after a construction. The &- operator is not, nor are an each entry fed by iterator methods (.filter(...).map(...)), which wait for the adapters. A computed property's setter is not built: x.prop = v as a call of a setter is refused (1016).

Many operators are implemented as method calls. For instance, x+3 is treated as if it were: x.`+`(3) A type need only implement the `+` method to make the + operator meaningful to values of that type. If a program tries to apply the + operator to a value whose type has not implemented the `+` method, a compiler error results.

Let's explore the implications across a number of operators.

Value Operator Methods

A type may support any of the arithmetic operators (+, -, *, / and %) by implementing them as methods. The integer and floating point types do this, of course, but really any type that effectively encodes numbers or number structures can do this. This might include: complex numbers, "big" integers, rationals, unit-based numbers, vectors or matrices.

The Point type example above took advantage of this by implementing the subtraction method:

fn subPoint overload `-`(self, pt2) Point {
	new Point(pt2.x - x, pt2.y - y);
}

Note: Whenever a name includes non-alphanumeric (or underscore) characters, it must be enclosed in backticks. This is why the shared operator name is shown as `-`.

With this method implemented, one may simply subtract two Points in an expression: pt1 - pt2.

Unary negation may also be implemented using the `-` operator. The difference between the negation method and the subtraction method is that the former needs only the self parameter. Because both methods overload one operator name, each declares its own name as well:

fn negPoint overload `-`(self) Point {
  new Point(-x, -y);
}

A call written as -pt or pt1 - pt2 selects whichever of these methods accepts the operands. Exactly one of them must, as described for method overloading.

Logic and Shift Operator Methods

Similarly, a type may support any of the logic and shift operators (!, &, ^, ~, << and >>) by implementing them as methods.

Comparison Operator Methods

To support operator-based comparison of two values, implement the appropriate comparison operator(s) (==, <, <=, >, or >=) as methods. It is not necessary to implement the inequivalence operator (!=), as this is supported automatically if `==` is implemented.

These same methods are what a comparison of two references uses, since == on references compares the values they refer to. A method declared for references (fn `==`(self &, other &Point) bool) is used as it is; otherwise the references are de-referenced and the value method is used. The identity operators === and !== are not methods: they ask whether two references point to the same place, and no type implements or overrides them.

An enum is given its == (and so its !=) rather than implementing one: it compares the tags, and then, where the variant carries fields, calls the == that variant implements.

isTrue "truthy" Method

Conditional expressions depend on a boolean value of true or false. If a conditional expression returns a value of some type other than bool, Cone will check whether the type implements the isTrue method. If so, it will use that method to convert a conditional expression's to true or false.

In effect, this is how Cone supports the notion of type-specific "truthy" values. For example:

  • Integer values are false if 0, true otherwise.
  • Floating point values are false if 0 or -0, true otherwise.
  • Pointers are false if null, true otherwise.
  • Option values are false if None, and true if Some.

Value Mutation Methods

Several operator methods may be implemented that change an existing mutable value in memory. When the value is held by some variable, the compiler effectively obtains a mutable reference to the variable, and calls the method using the mutable reference.

This can be illustrated with a simple example. Let's say that a type wants to override the simple assignment operator with a method that performs a deep (rather than the default shallow) copy of the value. The signature of the method will accept a mutable reference to the target:

fn `=`(self &mut, value) Self {
}

When assignment is performed for a value of this type (a = b), it will obtain a mutable borrowed reference to the lval 'a' and then call the method like this: &uni a.`=`(b).

Arithmetic, Logic, Bitwise Assignment Operators

A custom type may also support any of the arithmetic assignment operators (+=, -=, *=, /= and %=) by implementing them as methods.

If a type does not implement the arithmetic assignment operators, the compiler will attempt to implement them using the arithmetic methods. Thus, pt1 += pt2 would be treated as if it were: pt1 = pt1 + pt2.

Similarly, the logic and shift assignment operators may also be implemented as methods. If not, they will be handled in the same way as the arithmetic assignment operators.

Increment and Decrement Operators

A type may implement the increment or decrement operators (++ and --) as methods. When used as prefix operators, their names are `++` and `--`. When used as postfix operators, their names are `_++` and `_--`.

Computed Properties

For public fields, there is often no reason to implement getters and setters to offer direct access to their values, because it is faster to access the fields directly. However, if it would be unsafe to offer direct access to certain fields, in order to preserve specific data invariants, one should make them private and then potentially offer appropriate getter and setter methods that preserve the invariants.

Implementing a getter and setter is easy:

struct Counter {
	count u32 = 0;

  // a getter
  pub fn counter() u32 {
    count;
  }

  // a setter (notice the use of a mutable reference, since the value will be changed)
  pub fn count(self &mut, cnt u32) {
    count = cnt;
  }
}

And here we use them:

mut x = new Counter();
x.counter; // 0
x.counter = 10; // uses the "setter" to set the value
x.counter; // 10

Since we can omit the parentheses when using a getter or setter, their use looks just like access to a public field. This makes it possible to start off with a type that makes a field public, and then later changes it to private because of an invariant. By implementing getters and setters instead, the API can be preserved even as the implementation evolves.

Collection Operators

By wrapping an array, or a pointer to elements it allocates, within a struct, one can create all sorts of collections: indexed collections like vectors and dictionaries, as well as stacks, queues, sets and more. The difference between them is largely determined by which methods are implemented for working with various elements of the collection. Most collections will typically implement the len method to find how many elements are currently in the collection, and iter to enable iteration through the collection's elements.

A couple of operators make it easier to work with collections: [] for indexed access and <- to add or remove an element. Each collection type implements methods that determine how these operators work.

The <- operator, which appends and streams entries into a collection, has a chapter of its own: The send operator (and a collection's contents).

[] Indexed Access Operator

As we saw with arrays, the [] operator is used to access a specific collection element according to its index. Implementing the [] method as both a getter and setter makes indexed access possible for other kinds of indexed collections. The index need not even be an unsigned integer, as it is for an array. Dictionaries, for example, often use strings as the index.

A type's [] method returns a borrowed reference to the element, &T, which a read goes through, and its &[] method the mutable one, &mut T, which &mut x[i] asks for. Written to, the index is in set position, and a type declaring &[] lends through it: x[i] = v stores through the reference &[] returns, as do x[i].f = v, x[i] += 1, x[i].f += 1, and a method taking self &mut called on x[i]. A dynamic arena's ar[key] = v is one.

The place may go on through any chain of fields and indexes, however long, and every index in it lends through its type's &[]: a[g].b[i].n = 5, a[g].b[i] = v, a[g].b.push(v), a[g].b[i].reset() and &mut a[g].b[i].f all write through the elements, as the one index does. The elements are reached only if everything on the way may be written: through a & reference, or in an imm variable, they are refused.

A swap, x <=> y, writes through both of its sides, so the indexes of each are in set position: u.fields[0].n <=> u.fields[1].n and l[0] <=> l[1] swap two elements of one list, which two &mut borrows of it, held together, may do (borrowed references). Only the elements change, never the list's shape.

() "Function call" Operator

It is actually possible to "call" an object as if it were a function. Doing so will actually invoke the () method for the object.

Closures as anonymous structs

A closure is really just syntactic sugar for an anonymous struct that implements the () method. The closure fn(n i32) [mut cnt = 0] { cnt += n; cnt; } is roughly equivalent to:

struct Cntstr {
  cnt i32;
  fn `()`(self &mut, n i32) i32 {
    cnt += n;
    cnt;
  }
}

mut counter = new Cntstr(0);
counter(1);        // 1
counter(2);        // 3

As this example demonstrates, the closure itself is defined by the Cntstr struct. The closure's state is defined by its field(s): the entries of its state list, and a reference for each variable of the code around it that its body borrows. The functional logic is captured within a single method named (), whose self permission follows the body.

Any explicitly callable struct is effectively also a closure: it meets the same closure references and the same signature constraints.

Tuples

A tuple is like a struct, as it holds multiple co-located values, each with its own type. Unlike a struct, neither the tuple itself, nor its elements, are named. Tuples match as equivalent if they have the same number of elements whose individual types match in the same order.

Tuples are particularly valuable for returning multiple values (without having to use a pre-defined struct). For example:

fn getxy(point Point) f32, f32 {
  point.x, point.y;
}

fn main(point Point) {
  imm x f32;
  imm y f32;
  x, y = getxy(point);
}

The getxy function returns a tuple holding two floating-point values. Notice that the tuple type is defined by a comma-separated list of types. Similarly, the tuple value itself is composed using comma-separated values. (Note: In some other contexts, such as a parameter or field tuple, it will be necessary to wrap comma-separated list of types or value within parentheses.)

When getxy is called by main, the two returned values are separately stored into the x and y variables. Notice the types of the tuple's elements match those of the variables used to store its values.

Another benefit lies with parallel assignment, which assigns several values to several variables at once, as x, y = getxy(point); does above. Every value on the right is worked out before any variable changes, so it can swap two values with no temporary variable:

  x, y = y, x;

A tuple held in one variable

A variable may itself be of a tuple type, and hold the whole tuple. Assigning a tuple value to it (one variable to the left of =, not several) stores every value, just as its initial value would be stored. Each value is coerced to its element's type, so a number literal with no suffix takes the element's number type. Parentheses around the values change nothing.

  mut p (i64, i64) = 5, 6;
  p = 7, 8;
  p = (1, 2);

The tuple must match the variable's type: as many values as it has elements, each one's type matching its element's. So p = 1, 2, 3; is an error.

A tuple whose values are all constants is itself a constant, so it may be the initial value of a global or a static variable, a named constant's value, or a field's default:

imm origin (i64, i64) = 0, 0;
const Unit (f32, f32) = 1, 1;

Accessing a single element of a tuple

Similar to structs, the dot operator can be used to access a specific element of a tuple. Since elements don't have names (like fields), use an integer constant to specify which element to extract (with '0' as the first element):

  y = getxy(point).1;

A number after the dot is always an element's number, never part of a decimal number, so a further dot starts the next member: t.1.0 is element 0 of element 1 of t, and pair.0.len() calls a method on element 0.

A tuple type given a name by alias is the tuple itself, so its elements are reached the same way:

alias Pair = (i32, i32);
fn first(a Pair) i32 { a.0; }

Arrays

Note: Implemented: the array type, with one size or several, array literals, nested arrays, elements given by expressions, a string as an array of u8, construction with contents (new Array[T, n] <- fill x), copying, getting and setting one element by index, each over an array, and a run-time bounds check on every index. Not implemented: the len method (a slice's is), the $- operator, multi-element segments and fills, comparison, and pattern matching. An index out of range is caught only at run time, even when it is a constant.

An array holds a specified number of values, all of the same type. The size of the array (its number of elements) is a fixed, constant value and is not resizable. The array's elements are located next to each other in memory. Elements are individually accessed using an unsigned integer index.

For example:

mut numbers Array[f32, 3] = [3.1, 4.1, 5.92];
imm nbr = numbers[1];     // nbr is 4.1
numbers[0] = 2.;          // numbers is now [2., 4.1, 5.92]

Here, numbers is an array containing three floating-point numbers as its elements. As the redundant type specification Array[f32, 3] indicates, the type of its elements is f32 and the length of the array is 3. The [] operator enables access to a specific element.

The array type

An array type is written Array[T, n]: the element type first, then the size. The size is an integer literal from 0 through 4294967295, and is part of the type: an Array[f32, 3] and an Array[f32, 4] are different types. Array looks like a generic type taking a number, and is built into the language; a module that declares its own Array names that one instead. An array type may be written wherever a type may: a variable, a field, a parameter, a return value, the type a reference refers to, or a generic's type argument (Option[Array[u8, 4]]). In a generic function or method the size may be a number parameter, Array[f32, N], and nothing computed from it (Value Parameters).

An array type may give several sizes, one for each dimension. Such an array is an array of arrays, the first size the outermost, so Array[f32, 2, 3] is the same type as Array[Array[f32, 3], 2]: two rows of three. Its first index picks the row and its second the element in that row, and the elements are stored row by row, the last index varying fastest, as in C's float m[2][3]:

imm matrix Array[f32, 3, 3] = [[1., 0., 0.], [0., 1., 0.], [0., 0., 1.]];
imm val = matrix[1][1];  // 1.

That is how the array itself is laid out. A library type built over an array decides what its elements mean: geomath's Mat3 holds its nine values column by column in an Array[f32, 9].

Warning: Typically, when you want a collection type capability, you won't reach directly for an array, because of the fixed-size limitations and because you cannot implement methods directly on arrays. More likely, you will use one of the library-based collection types. If you look under the covers of these, you will see these are basically struct types that wrap around a specific array, or a pointer to elements they allocate (as well as possibly other fields), and lend their elements as an array reference. Being structs, they offer implemented methods to work with the collection and its elements.

Initialization

To create or initialize an array, specify the values of all its elements separated by commas and enclosed within square brackets (as the above example demonstrates). When this array constructor is used to initialize a global variable, the element values must be constants. When used as part of a function's logic, element values may be specified using expressions: 

imm pair = [nbr * nbr, nbr + nbr];

An alternative way to create an array of bytes is to fill it from a string literal, where the array's type says how many bytes it is:

imm hello Array[u8, 12] = "Hello world!";

A string is encoded as an sequence of utf-8 code points. The length is the number of bytes it occupies, and the array must be exactly that long: any other length is an error. The type of each element is u8. For C-compatibility, the zero terminator ('\0') is placed at the end of the string, but not counted in its length. A string literal that is not filling an array is not an array: it is a borrowed reference to its text, &str (A String as a Slice of Bytes describes how it converts to a slice of bytes, and owning references how it is copied into an owner).

Contents

An array may also be constructed with its contents: new, its type, then <- and the values that fill it, in order. This is the send operator's list, which any collection takes, and the same forms may be used: values listed, n of x for n values, and fill x for as many as are left to fill. A value that is repeated is evaluated once for each element. This example creates a 100-byte string, where all bytes are spaces:

imm spaces = new Array[u8, 100] <- fill ' ';
imm row = new Array[f32, 4] <- 1.0, 3 of 0.0;

An array's size is fixed, so its contents give exactly that many values, and the count before of is a constant, from 0 through 4294967295. An array has no initializer, so the construction takes no parentheses, and a global's contents, like its array literal's elements, are constants.

The contents of an array written with several sizes are its scalars, the values of the element type written first, row by row, in the order the array stores them, so each entry counts scalars and n of x and fill run on across the rows. The contents give exactly as many as the product of the sizes, which may be at most 4294967295. Written nested, the array's elements are its rows, and its contents are those rows, each constructed in turn; inside the outer list, a row's own list is parenthesized. The two spellings are still one type, so either construction is assigned, passed and returned where the other is wanted:

imm grid = new Array[i32, 2, 3] <- 1, 2, 3, 4, 5, 6;     // rows [1, 2, 3] and [4, 5, 6]
imm cube = new Array[u8, 2, 3, 4] <- fill 0u8;           // all 24 bytes
imm rows = new Array[Array[i32, 3], 2] <- fill new Array[i32, 3] <- (1, 2, 3);

An alias of an array type keeps the spelling it names. A generic's type parameter stands for a type, not a spelling, so through it an array's contents are its rows. An array written with several sizes whose element type is itself an array, Array[Array[u8, 4], 2, 3], takes no contents: whether they would be its bytes or its four-byte arrays is not decided, so it is written nested to be constructed with contents.

An allocation takes the same contents, and fills the array in the region's memory (owning references).

Getting the length

Note: Not built, as the note above says: len on an array value is refused (Error 1025: Invalid operation on an array), so the example below does not compile. A slice's len is built (Slices).

To get a count of how many elements are in an array, use the len method:

imm hello Array[u8, 5] = "Hello";
imm length = hello.len;   // =5

Indexing

A single element within an array may be accessed using an unsigned integer index value enclosed in square brackets. The specified index may be an expression. An index of 0 refers to the first element.

Indexing can be used to get or set the specified element:

mut c_array Array[u8, 4] = "coal";
c_array[2] = c_array[1];    // the 3rd element is now the same as the second
// c_array now holds the array value "cool"

Array indexing is automatically bounds-checked by its known size. Any attempt to supply an invalid index results in a compile-time or run-time error. At run time it is a panic naming the index, the size and the line: index 4 is out of bounds for a count of 4.

Note: It is also possible to use the ampersand operator to borrow a reference to a specific indexed element in an array.

Indexing from the end

Sometimes it is more convenient to index an element based on its position relative to the end of the array. This can be accomplished in a verbose way: 

imm nbrs = [2, 4, 6];
imm four = nbrs[my.len - 2]; // =4 - the 2nd from the end

The less verbose equivalent uses the $- operator:

imm four = nbrs[$-2];

$- is equivalent to my.len -

Iterating over an array

Using indexing and the len method, one can now easily iterate over every element in an array:

imm numbers = [3.5, 4.0, 5.5, 3.0];
mut average = 0.0;
mut i = 0;
while i < numbers.len {
  average += numbers[i++];
}
average /= numbers.len;      // == 4.0

A cleaner, more concise approach uses an each block instead:

imm numbers = [3.5, 4.0, 5.5, 3.0];
mut average = 0.0;
each nbr in numbers {      // nbr borrows each element
    average += nbr;
}
average /= 4.0;              // the number of elements: == 4.0
Multi-element copying

Multiple elements of an array may be copied into another array using a range index.

mut greetings Array[u8, 11] = "Hello Jeter";
greetings[7,4] = greetings[1,4]; // "Hello Jello"
greetings[6..10] = "Peter";      // "Hello Peter"
greetings[6..<11] = "Helen";      // "Hello Helen"
greetings[6..] = "Jayne";        // "Hello Jayne" (end is assumed if unspecified)

As the examples show, several range operators are supported. The first number is always the index of the first element in the segment. The meaning of the number after the range operator varies:

  • , - The second number specifies how many elements are in the array segment.
  • ..< - The second number specifies the index of the element after the last element in the array segment.
  • .. - The second number specifies the index of the last element in the array segment. If unspecified, it is assumed to be the last element of the array.

Both array segments must have the same element type and length. Array segments can only be used for copying elements from one array to another using assignment or variable initialization. An array segment cannot be passed as an argument in a function call or used in a comparison.

Note: One can also use the ampersand operator to borrow an array reference (slice) to a specific set of elements in an array.

Multi-element fills

Using the same range operators, a single value can be repeatedly filled into a segment's elements:

mut numbers = [0, -1, -2, -3];
numbers[1 ..< 3] = 2;
// numbers == [0, 2, 2, -3]

The type of the fill value must be the same as the type of the array's elements.

Copying and comparing

Copying a struct

Like numbers, struct values may be passed around between variables and functions:

fn main() {
	mut pt1 = new Point();
	pt1 = change(pt1);
}

fn change(mut pt Point) Point {
	pt = new Point(1., 2.);
	pt;
}

Copies of the data structures are made as they are passed around (e.g. into and returned by change). Any changes made to a copy won't change the original struct value. This may not always be the behavior that you want, though. If a struct is too big to pass around efficiently, or you want changes to apply to the source structure, make use of references to a struct instead.

Copying an array

Like numeric values, array values may be passed around between variables and functions:

imm hello Array[u8, 5] = "Hello";
fn main() {
  mut dessert = jello(hello);
}

fn jello(mut saying Array[u8, 5]) Array[u8, 5] {
  saying = "jello";
  saying;
}

In this example, a copy of the hello variable's array is passed to the function jello. It replaces that copy's contents with the string "jello" and returns it to main. The mutable local variable dessert now holds a copy of the array string "jello".

When arrays are passed around, we always make copies of the array (just like we do with numbers). Any changes made to a copy won't change the original array. The exception is an array whose element type has move semantics: such an array moves rather than copies, whether its type is written out or inferred from an array literal.

This may not always be the behavior that you want, though. If instead you want to pass around a reference to an array, such that any changes do change the original array, obtain and pass an array reference.

Comparing structs

It is not possible to check whether two structs have the same value if the struct defines only fields. However, two struct values may be compared if the struct implements the comparison methods. Also, it is possible to perform partial matching of a struct against some pattern.

Comparing arrays

Two arrays may be compared, so long as they have the same element type.

To be equivalent the arrays must have the same length and every element must be the same. To make element comparison possible, the element's type must support the == method.

imm somebody = "John";
if somebody == "Jane" {
  ....
}

Comparing for order (e.g., <) is also handled by comparing the two arrays element-by-element, stopping the first time two elements are not the same. The number of elements compared is the minimum of the lengths of the two arrays. If the element check shows them as equivalent, the lesser-sized array comes first in order.

The match statement or is operator supports additional array comparison capability, particularly for partial pattern matching.

Fine-tuning

Rarely needed on a first reading. These use borrowed references and owners, which Borrowed references and Memory explain.

A method that asks for its owner

A method may also ask for the owner of its type: a borrow of an owner, written self &So[Self], self &Rc[Self], self &Arc[Self] or the borrow of any other owning reference to the type. Such a method is found only through an owner of that kind, which is borrowed for the call and is still the caller's afterwards; a plain value, a borrow or an owner of another kind has no such method, just as for any method that does not accept the receiver. It is tried after the ordinary selection, so a type's other methods are unaffected. Inside the method self reads through the owner to the value, so self.n is the field, and the owner itself is what the method can hand on or inspect (as str's cstr() does, which needs the owner's zero after the text: C Strings).

struct Node {
  n i64;
  pub fn viaSo(self &So[Node]) i64 { self.n + 1; }   // only an So[Node] has this method
  pub fn plain(self &) i64 { n; }                    // any Node, however held
}
imm a = new So[Node](10);
imm x = a.viaSo();                                   // 11; the So is borrowed, 'a' is still ours
imm y = Node(10).viaSo();                            // **ERROR** a Node value is no owner

A member's name hides an outer one

Inside a type, a field's or method's name hides any name of the same spelling further out, as an inner name hides an outer one everywhere. That includes a module the type's module imports, and it holds in the methods' signatures as well as their bodies. A signature has no self to reach a field or method through, so a module written there under a member's name is an error:

mod scene;
import mesh;

struct Model {
  parts i64;
  fn mesh(self &) mesh.Mesh {   // error: in Model, 'mesh' is this method
    new mesh.Mesh(parts);
  }
}

The error on the signature names two ways round it. One is to import the module under another name, which no member hides:

mod scenery;
import mesh as meshes;

struct Model {
  parts i64;
  fn mesh(self &) meshes.Mesh {
    new meshes.Mesh(parts);
  }
}

The other is to reach the module through the module's own name, which is one of the names in reach inside it and which no member hides either:

mod staging;
import mesh;

struct Model {
  parts i64;
  fn mesh(self &) staging.mesh.Mesh {
    new staging.mesh.Mesh(parts);
  }
}

Opaque Types

Sometimes it is valuable to work with types where we have no idea about the size or layout of any values of that type. This is useful when interfacing with some external system which knows the layout and size of the type's data, but is reluctant to share (or we don't really care).

We call such types opaque, because we cannot directly view their contents. Declaring an opaque type is easy:

struct @opaque SocketHandle;
   // don't specify any fields as part of the type
   // Methods may be defined.

As one might expect, it is illegal for a variable or field to specify an opaque type. An opaque value cannot be created or passed around. We cannot access its fields. We cannot even determine its size.

Where opaque types are used is when pointed-at by references or pointers. Such references can be obtained, passed around, and stored, like any reference. We can call methods on a pointed-at value of an opaque type (typically implemented by the external system that knows the data layout and can work with such values). However, we may not use pointer de-referencing to read or mutate the pointed-at value.

Initializers and finalizers in brief

A type may define one or more initializers, beside the implicit one every struct has, which takes its fields' values. A construction, new with the type and the initializer's arguments in parentheses, runs the one initializer its arguments select:

imm pt = new Point(1.);

An initializer is named init, several of them joining the overload name init. A method named clone takes no part in copying: it may be declared and called by name as an ordinary method, but no copy, whether by assignment or by a function call's parameters, calls it (Clone method).

A type may also define a single finalizer called final. This is automatically invoked immediately before any value of that type is destroyed, and its memory space reclaimed.

Detailed advice on how to define initializers and finalizers follows.

Initializers

Note: A method taking self &new is an initializer only if it is named init or joins the overload name init; under any other name it is refused. So a clone method written against the new permission is refused too (Clone method). A method named clone may be declared and called as an ordinary method, but no copy calls it, and it does not make a type copyable.

Every new value of a struct is constructed by one of its initializers, written new, the type, and the initializer's arguments in parentheses:

imm pt = new Point(1., 2., 3.);

Every struct has an implicit initializer, which takes the values of its fields, in the order they are declared or by name, a field left out taking its default value (see structs). A struct may also declare initializer methods of its own, which can use any sort of logic for initializing a new value, even of private fields. They are useful when the implicit initializer would be:

  • Insufficient, because initialization needs to perform some logic that is more than simply assigning value(s).
  • Impossible, because parts of the type are private and can only be set by code in the module that declares it.
  • Inconvenient, because listing every field would be unnecessarily verbose in comparison to using an initializer.

Here is a simple initializer:

fn init(self &new) {
  *self = new Self(x: 1., y: 1., z: 1.);
}

An initializer is a method, but it has a few differences from typical methods:

  • Its name is init, so you need not specify the initializer's name when using it to create a new value. A type may declare more than one initializer as an overload set: each has its own name and joins the overload name init (fn polar overload init(self &new, r f32, theta f32)). A construction's arguments select the initializer that takes them. Where a declared initializer and the implicit one both take values listed in order, the declared one is used; if none takes them, or several declared ones do, the construction is an error. Only the implicit initializer takes values by name, so naming the fields always reaches it: 
    struct Seeded {
  pub seed i32;
  pub fn init(self &new, n i32) {
    *self = new Seeded(seed: n * 10 + 1);
  }
}

imm a = new Seeded(5);        // the declared initializer: seed is 51
imm b = new Seeded(seed: 5);  // the implicit initializer: seed is 5
  • self is a borrowed reference using the new permission. Here's why: An initializer is called when memory has been set aside for the new value, but it does not yet hold a valid value. The borrowed reference effectively points to this location. It uses the new permission to signal that the reference does not yet point to a valid value. This prevents the initializer from accessing any of the fields until after they have been initialized. The permission is written only on an initializer's self.
  • Initializers don't return a value. After the initializer has finished running, the construction that invoked it holds the value it wrote through self. Thus, having the initializer return a value would be superfluous and confusing.
  • The initializer's logic uses another initializer to fill self. Essentially, an initializer's logic performs these steps in order:
    1. Figure out what the values should be for every field (if needed). The fields of self are inaccessible at this point, as self is not pointing to a valid value. This means it is also impossible to call any other methods on self.
    2. Initialize the entire value of self at one time, *self = new Self(...), with an initializer other than this one: typically the implicit one, reached by naming the fields (as the above examples do). Values listed in order that this initializer itself takes would select it again, and filling self that way is an error. It must be done on every path before the initializer returns.
    3. Perform any additional work on the value that the logic requires, if needed. At this point, the initializer may access the value's fields or call any other method on the value.
  • self does not escape. It is used only through itself: *self, a field of it, or a method called on it. It may not be passed to a function, stored, copied or returned.
  • An initializer runs only in a construction. It is never called by name on a value, which it would overwrite.

The following code invokes the initializer defined above:

imm pt = new Point();  // x,y,z of the new Point value are 1.0

A construction fills its value in place, where the value goes. Declaring a variable with a construction hands the initializer the variable's own memory, and allocating one hands it the memory the region obtained; a value constructed where it has no place yet, as an argument to a function, or a field of another construction, is built in a temporary and copied there.

A value is constructed once. new Point(p), where p is already a Point, is an error: a finished value needs no construction. An allocation takes one as its value, moving it in.

An enum's variant is constructed with parentheses, Some(x), and an empty one by its name alone, None (Enums).

Constructing a value in a region, and a clone method, are below.

Finalizer

When a object is destroyed at the end of its life, its finalizer logic, if defined, is automatically invoked. Only types that acquire a dependent relationship with other system object(s) need to define a finalizer. The finalizer releases, gives back, or safely breaks all such dependencies (e.g., closing file/network handles, de-subscribing to services, etc.) before the value's memory is reclaimed.

Here's a finalizer:

fn final(self &uni) {
  file.close;
}

Key to a finalizer definition:

  • The method's name must be final. Only one may be defined.
  • self is a borrowed reference using the uni permission. No other parameters should be specified.
  • Finalizers don't return a value.
  • The logic may access the value and call methods. However, a finalizer's logic should run quickly without blocking, while still breaking all dependencies. After the finalizer finishes, the object will cease to exist.

A value dies the same way wherever it lives — a local variable at the end of its scope, a parameter at the end of its function, a field inside the value holding it, a temporary at the end of its statement: its finalizer runs first, then the finalizers of its fields, in the order they are declared, then the owning references its fields hold are released, in the order they are declared, and so on down, however deep. A tuple's elements die in order, as fields do, and so do an array's, first element first.

A temporary is a value an expression produces that nothing takes: it is not bound to a variable, stored in a field or element, passed by value, returned or moved. A call's result whose field is read, an owning reference read through, an owner lent to a call as a borrowed reference, a value thrown away by a statement: each is a temporary, and dies at the end of the statement that produced it, the newest first, as locals die at the end of their block. A temporary produced by the condition of an if or a while dies once the condition is decided, before the branch runs, so each pass of a loop finalizes its own; and one produced by the right operand of and or or, which runs on some paths only, dies at the end of that operand. A value moved out of a temporary owner belongs to its new holder, and the owner's memory is freed without it, as above.

imm n = open(name).length;   // the file open returns is closed here, once its length is read
take(open(name));            // moved: take closes it
if open(name).length > 0 {   // closed here, before the branch runs
  ...
}

A temporary a variable's initializer borrows lives longer, to the end of the block the variable is declared in, as Rust extends it: so the borrow is good for as long as the variable can be used. That is a temporary the initializer borrows directly (&make()), a part of one (&make().x), what a temporary owner owns (&*makeOwner()), or a temporary owner the initializer lends where a borrowed reference is declared (imm r &R = makeOwner()), whether the borrow is the whole initializer or an element of a tuple, an array or a variant literal it builds ((&make(), 1), Some[&R](&make())), or the value of a block, of an if's arm or of a match's arm in one of those places (if c { &make(); } else { &other(); }), as Rust 2024 extends them. Such a temporary dies at the end of its block, with the block's locals, the latest first; one an arm makes, only where that arm ran. A temporary passed to a function, or a method's receiver, is not extended, even in an initializer: it dies at the end of its statement, and a variable still holding a borrow of it may not be used after that. A borrow of a temporary anywhere else (show(&make())) points at it until then.

imm r = &make();             // the temporary lives to the end of the block
imm s &R = makeOwner();       // so does the owner, and what it owns
imm t = pick(makeOwner());    // the owner dies here: t may not be used after this statement

A temporary that a raw pointer made from it may outlive is not finalized at all. Nothing follows a raw pointer, so the compiler leaves the value as it is rather than finalize it and leave the pointer dangling. An ordinary borrow of the same temporary does not keep it:

fn mk(n i32) R {..}
fn id(r &R) &R {..}          // answers the borrow it is handed

imm p = id(&mk(2)) as *R;    // p may outlive the temporary: R's final never runs for it
imm q = id(&mk(3));          // an ordinary borrow: R's final runs at the end of this statement

A value dies on the path that still holds it, and only there. Where a variable's value was moved out, or given, on only some of the paths that reach the end of its scope — in one branch of an if or a match, in a loop that may not run, before an early return or break — the compiler keeps a hidden flag beside the variable, set where its value arrives and cleared where it leaves, and the end of its scope finalizes it only when the flag says the value is still there. A variable whose every path agrees has no flag, and costs nothing for it.

imm f = File.open(name);
if verbose {
  log.keep(f);      // f moves to the log on this path
}
                    // f is closed here only if verbose was false

A value assigned over dies as it is replaced: the new value is evaluated first, then the old one is finalized, then the new one is stored. This is so for a variable, a field or an element of one, and a value reached through a reference (*r = v). Where the variable holds nothing to replace — it was never given a value, or its value moved out — nothing is finalized; where that depends on the path, its flag decides.

A value allocated in a region is finalized when the region lets it go: when its single owner expires, or, for a counted region, its last owner. It dies as above, and only then is its memory freed, so a finalizer may still use everything its value owns. A value moved out of a region's object belongs to its new holder, which finalizes it; the object's memory is freed without finalizing what was moved out. Only the whole value moves: a field of it may not be moved out (move semantics), so no object dies partly moved out.

A value typed as an enum is finalized as the variant it holds. An enum may define its own final, which runs for every variant, and a variant may define one too: the variant's finalizer runs first, then the enum's, then the finalizers of the variant's fields (the enum's common fields among them), then the owning references those fields hold are released — the more specific type before the more general, as with inheritance in other languages. An enum none of whose variants has anything to finalize, such as Option[i32], costs nothing when its value dies.

A global variable lives until the program shuts down. Whatever it holds is then finalized by its module's finalizer, after the module's own final: a value whose type finalizes, a tuple or an array of them, or an owning reference, which is released (Dynamic initialization of global variables). A module has an initializer and a finalizer of its own too, described there.

struct R {
  pub n i32;
  fn final(self &uni) { print <- "final "; print <- n; print <- "\n"; }
}
imm one R;
imm pair (R, R);
imm many Array[R, 2];
imm owned So[R];
fn @initpure init() {
  one = new R(1);
  pair = (new R(2), new R(3));
  many = [new R(4), new R(5)];
  owned = new So[R](6);
}

After main returns, this prints final 1 through final 6, one to a line.

Constructing in a region

An allocation constructs its value the same way, in the region. new Rc[mut, Node](1) runs Node's initializer on the memory the region allocated, after the region's own initializer has filled its bookkeeping. One given a finished Node instead, new Rc[mut, Node](n), moves it in and runs no initializer:

import stdio use *;
import libc;

struct Counted is RegionRef {
  owners usize;
  fn alloc(size usize) *u8 { libc.malloc(size); }
  fn init(self &new) {
    print <- "region init\n";
    *self = new Counted(1usize);
  }
  fn aliasRef(self &uni Counted) { owners = owners + 1usize; }
  fn dealiasRef(self &uni Counted) bool {
    owners = owners - 1usize;
    owners == 0usize;
  }
  fn free(self &uni Counted) {
    print <- "free\n";
    libc.free(self as *u8);
  }
}

struct Node {
  pub n i32;
  pub fn init(self &new, k i32) {
    print <- "node init\n";
    *self = new Node(n: k * 10);
  }
  fn final(self &uni) { print <- "node final "; print <- n; print <- "\n"; }
}

fn main() i32 {
  {
    imm a = new Counted[mut, Node](1);    // Node's initializer runs, on the region's memory
    print <- a.n;
    print <- "\n";
  }
  {
    imm done = new Node(5);
    imm b = new Counted[mut, Node](done); // a finished Node moves in: no initializer runs
    print <- "moved in\n";
  }
  0i32;
}

The first block prints region init, node init, 10, node final 10 and free. The second prints node init (for new Node(5)), region init, moved in, node final 50 and free. The allocator is described in custom allocators.

Clone method

As discussed in Moves in depth, it is not always obvious how to create a faithful copy of some types' values. When this difficulty exists (e.g., a value that contains references to other values), a type may define a clone method whose logic is capable of creating a faithful copy.

A clone method is essentially an initializer whose second parameter is a value or another borrowed reference to the value we want to copy:

fn clone(self &new, from &) {
  *self = new Self(x: from.x, y: from.y, z: from.z);
}

A clone method takes no part in copying: whenever copies are automatically made (e.g., assignment or function calls), no copy calls it, so declaring one does not make a type copyable. It is an ordinary method, called by name. A clone method written against the new permission, as above, is refused under that name (see the note at Initializers).
