Cone
I/O from an actor: awaiting sockets, files, timers and HTTP

Note: aio, actorhttp, the HTTP and TLS packages, and iocore and iobuf beneath them run on Windows and on Linux. Batching of datagrams (many in one call) is not built yet.

A program that talks to the world spends most of its time waiting: for a connection, for bytes from a peer, for a disk, for a clock. A thread that blocks while it waits is a core doing nothing. In Cone an actor's behaviour awaits the operation instead, exactly as it awaits another actor's answer: the actor goes on with its other messages, and the rest of the behaviour runs when the answer comes. This page covers the packages that do it and each kind of operation: sockets, datagrams, files, timers, names, file metadata, child processes and HTTP. Afterwards you can write a server, a client or a pipeline that keeps every core busy while it waits. Here three timers wait on one actor at once:

mod kitchen;

import stdio use *;
import time use Duration;
import sync use *;
import actors;
import aio;

actor Timer {
  // Waits without holding a thread, then says so
  pub async fn ring(self, what: &'static imm str, ms: i64, done: Sender[i64]) {
    let r = await aio.sleep(Duration.fromMillis(ms));
    match r {
      case let Err(e) { print <- what, ": the timer failed\n"; }
      else { print <- what, " is ready after ", ms, " ms\n"; }
    }
    var d = done;
    d <- ms;                      // tell main this one is done
  }
}

fn main() {
  var tx: Sender[i64];
  var rx: Receiver[i64];
  tx, rx = Channel[i64].make();

  // Three timers on one actor: none of them holds a worker while it waits
  let t = Timer();
  t.ring("The tea", 300i64, tx.clone());
  t.ring("The toast", 200i64, tx.clone());
  t.ring("The egg", 400i64, tx.clone());

  // A behaviour paused on I/O does not keep the program running,
  // so main waits until all three have rung
  each i in 1 ..= 3 {
    rx.recv();
  }
}

It prints, in the order the timers come due rather than the order they were sent:

The toast is ready after 200 ms
The tea is ready after 300 ms
The egg is ready after 400 ms

One actor handled all three messages, and each ring paused at its await so the next could start. Note the last lines of main. A program ends when no actor is queued or running, and an actor paused on I/O is neither: without the wait, the program would end at once and the timers would never ring (The I/O thread, and the program's end). Here main waits on a channel, a queue between threads which each timer sends to as it finishes; a long-running server waits the same way for word that it is done.

The I/O packages

What is built is in library packages, which the standard library chapter lists. From the plainest to the most capable:

  • Blocking, synchronous I/O: fs (files and folders), path and env (beneath them, the posix package is the C library's own POSIX functions on Linux and maps POSIX onto the Windows C runtime on Windows), and process, which runs a program and waits for it, written over Windows' own kernel32 or over posix_spawn on Linux. Fine for a tool that does one thing at a time; a thread that calls them waits.
  • Asynchronous I/O, completion-based: iocore, the loop the rest are built over: a thread hands it a job and later gets exactly one answer for it, carrying the buffer back. With it come iobuf (owned buffers), timewheel (its timers), time and calendar and diag (where an operation's time went). The I/O loop underneath opens it up.
  • HTTP and TLS over it (HTTP, TLS and URLs): http1, HTTP/1.1's connection core, sans-IO; httpconn, which joins it to real sockets on a loop, client and server; tls, TLS 1.2 and 1.3 over OpenSSL, also sans-IO, with a server's certificate checked by the operating system; url, URLs as data; and httpclient, which fetches an http:// or https:// URL in one call, with connection pooling, retries and redirects.
  • I/O an actor awaits: aio. An actor's behaviour may await a socket's operation (listen, accept, connect, read, write), a file's (open, read at an offset, write at an offset), a timer (aio.sleep(d)), a name looked up (aio.resolve(host)), a file's metadata (aio.stat(path)) or a child process (aio.run(args)), and pauses there until the operation's answer comes. TCP sockets, UDP sockets and files.
  • HTTP an actor awaits: actorhttp. An actor's behaviour may await client.get(url), for http:// or https://, and gets the whole response, or the response as it arrives, in chunks or as server-sent events; and an actor may serve: await each request of a listening server and answer it, whole or streamed (below).

Most programs need only the last two, and the rest of this page is about them. The iocore loop underneath, for a program that drives it itself, is the next page's.

Awaiting I/O

The aio package makes each operation; awaited, the behaviour pauses, the actor goes on with its other messages, and when the operation has finished, the rest of the behaviour runs with its answer. A server and a client, each an actor, the client sending five bytes to the server over a TCP connection on this machine:

// The Socket an answer holds, swapped out of it: Socket.none() if it failed
fn socketOf(r: Result[Socket, IoError]) Socket {
  var res = r;
  var s = Socket.none();
  match &mut res {
    case var &mut Ok(ok) {s <-> *ok;}
    case let &mut Err(e) {sayKind("failed", (*e).kind());}
  }
  s
}

actor Client {
  pub async fn send(self, port: u16) {
    let conn = socketOf(await aio.connect(SocketAddr.localhost(port)));
    var buf = IoBuf(64usize);
    buf.append("hello");
    let sent = await conn.write(buf);          // pauses until all of it is sent
    match sent {
      case let Err(e) {sayKind("write failed", e.kind());}
      else {}
    }
  }                                           // conn closes here
}

actor Server {
  client: Client;

  pub async fn serve(self) u64 {
    let listener = socketOf(await aio.listen(SocketAddr.localhost(0u16)));
    let addr = await listener.localAddr();     // the port the system chose
    match addr {
      case let Ok(a) {client.send(a.port());}
      case let Err(e) {sayKind("no address", e.kind());}
    }
    let conn = socketOf(await listener.accept());
    let none = await conn.read(IoBuf.empty());           // a buffer with no room
    match none {
      case let Err(e) {sayKind("no room", e.kind());}
      else {}
    }
    var total = 0u64;
    var more = true;
    while more {
      let got = await conn.read(IoBuf(4096usize));
      match got {
        case let Ok(b) {
          if b.len() == 0usize {
            say("end of stream", total);                 // the peer closed
            more = false;
          } else {
            say("received", u64.from(b.len()));
            total = total + u64.from(b.len());
          }
        }
        case let Err(e) {
          sayKind("read failed", e.kind());
          more = false;
        }
      }
    }
    total
  }
}

(say prints a word and a number on a line, sayKind a word and the name of an error's kind (errorKindName(k)); IoBuf is iobuf's, SocketAddr, IoError iocore's, IoErrorKind and errorKindName ioerror's, and Socket aio's.) Sent serve(), the server prints:

no room: invalid input
received 5
end of stream 5

Each await there pauses one behaviour, and only it. While the server waits for a connection, the client waits for its connect; the worker threads run neither until an answer comes.

What an operation answers

Each operation declares its own answer, and the await's value is exactly that: await adds nothing to it. An operation that can fail answers as a synchronous call that can fail does, with a Result: the success, or the operating system's failure, an IoError, whose kind() says what went wrong the same way on every system (below). A behaviour that returns a Result itself passes such a failure on to whoever awaits it with ?: await conn.write(buf)? waits, then takes the count out of the answer or returns its failure.

  • aio.listen(addr), aio.connect(addr), listener.accept(): a Socket. Cone does not yet move a value out of a matched variant's field, so it comes out by a swap, as socketOf does.
  • conn.read(buf): the buffer, given back with what arrived appended to it. The buffer is moved into the read, which is how the system may write into it while the behaviour waits, and the read's answer is how it comes back. At the end of the stream, when the peer has closed, it comes back as it went, its length unchanged. A buffer with no room fails (InvalidInput), as above. A failed read's buffer goes home to its pool.
  • conn.read(): the same, with no buffer given: the I/O side takes one when bytes have come (Reading with no buffer).
  • conn.write(buf): the count written, which is all of the buffer; the buffer goes home.
  • s.localAddr(): the address the socket is bound to.
  • aio.openFile(path, access): a File, out of the Result by a swap as a Socket is. f.readAt(offset, buf) and f.writeAt(offset, buf) answer as read and write do (Files).

Why an operation failed: IoError and IoErrorKind

An IoError says what went wrong in two ways. Its kind() is an IoErrorKind, the same on every system, which is what a program matches on. The kinds are the ioerror package's (import ioerror use IoErrorKind;), a small package of its own that the synchronous fs shares (its FsError): NotFound, PermissionDenied, AlreadyExists, NotADirectory, IsADirectory, DirectoryNotEmpty, ReadOnlyFilesystem, StorageFull, FileTooLarge, InvalidFilename, CrossesDevices, ResourceBusy, ConnectionRefused, ConnectionReset, ConnectionAborted, NotConnected, AddressInUse, AddressNotAvailable, HostUnreachable, NetworkUnreachable, NetworkDown, BrokenPipe, TimedOut, Cancelled, Truncated, InvalidInput, OutOfMemory, Unsupported, and Other for what none of them names. They are Rust's io::ErrorKind, trimmed to what Windows and Linux give here; ioerror's errorKindName(k) gives a kind's words, and its osKind(code) sorts the system's own numbers.

Its code is the system's own number for the failure, kept for diagnostics: Windows' error number on Windows, the errno on Linux, so the same failure has a different number on each (a refused connection is 1225 on Windows and 111 on Linux, both ConnectionRefused). Its message() is the system's words for it. IoError(code) is the system's error of a number got elsewhere, its kind read from the number.

let r = await aio.connect(SocketAddr.localhost(port));
match r {
  case let Ok(s) {...}
  case let Err(e) {
    if e.kind() == IoErrorKind.ConnectionRefused {say("nobody listening", u64.from(port));}
    else {sayKind("connect failed", e.kind());}
  }
}

Three kinds are the I/O runtime's own. Cancelled and TimedOut are an operation ended by its cancel group or its deadline (next), and carry code 0; a system's own timeout (a connect the system gave up on) is TimedOut too, with the system's number, and an operation the system aborted (ERROR_OPERATION_ABORTED, ECANCELED) is Cancelled, with its number. Truncated is a datagram cut to the room of the buffer that took it (UDP sockets).

An operation's answer should be used. An await on one that is a statement of its own drops the failure unread, so it is warned. The program still compiles, and the answer is dropped as any unused value is:

  pub async fn careless(self, conn: Socket) {
    await conn.write(IoBuf(64usize));   // warned: the answer is thrown away
  }

Warning 3006: The Result[u64, IoError] this 'await' gives is thrown away. An operation's answer says whether it
worked, a failure among what it may say, so a failure here goes unread. Use it (bind it and match on it, or '?' it),
or write '_ = ...;' to discard it on purpose.

An operation is made by the call (conn.read(buf)) and started by the await; one made and never awaited does nothing, and is dropped. That is why one behaviour cannot start two operations and await them both: three timers at once took three ring messages above. An operation that did not finish, cancelled or past its deadline, answers like one that failed (next).

Cancelling an operation, and limiting it

A read from a peer that never sends would wait for ever. So every operation can be limited, and is answered exactly once, with one of four outcomes: done (the Ok answer), failed (an Err of the system's failure), cancelled, or timed out. The last two are Errs too, of the kinds Cancelled and TimedOut, with code 0 (above). e.isCancelled() and e.isTimedOut() ask for those kinds, and aio.isCancelled(e) and aio.isTimedOut(e) are the same questions. The buffer an operation was given goes home to its pool.

An operation is limited by the In form of its call, which takes an IoLimits: conn.readIn(buf, lim), conn.writeIn(buf, lim), listener.acceptIn(lim), aio.connectIn(addr, lim), a file's f.readAtIn(offset, buf, lim) and f.writeAtIn(offset, buf, lim), and a UDP socket's u.recvFromIn(buf, lim) and u.sendToIn(addr, buf, lim). An IoLimits holds a cancel group (iocore's CancelGroup, made with CancelGroup.make(); Cancel groups has the other ways) and an absolute deadline, an Instant: IoLimits.within(group), IoLimits.until(deadline), or both with IoLimits(Some[CancelGroup](group), deadline). The operation ends when the group is cancelled, or at the deadline, the tighter of it and the group's (a group made with CancelGroup.until(d), or a childUntil(d) of one, carries a deadline of its own, and a child's is never later than its parent's). A group is a value: it goes in a message to another actor, or to a thread, and its one cancel() ends every operation in it, in whichever actors they are.

actor Reader {
  pub async fn fetch(self, conn: Socket, group: CancelGroup) u64 {
    let until = Instant.now() + Duration.fromSeconds(5i64);
    let got = await conn.readIn(IoBuf(4096usize), IoLimits(Some[CancelGroup](group), until));
    match got {
      case let Ok(b) {u64.from(b.len())}
      case let Err(e) {
        if aio.isCancelled(e) {say("cancelled", 0u64);}
        else if aio.isTimedOut(e) {say("too slow", 0u64);}
        else {sayKind("failed", e.kind());}
        0u64
      }
    }
  }
}

Whoever holds group, in this actor (a message to itself, which runs while fetch is paused), in another, or on a plain thread, may call group.cancel(), and the read ends. A cancel and the operation's completion that race are settled by iocore: the answer is whichever came first, never both. Cancelled is a state: an operation started in a group already cancelled, or with a deadline already past, is answered at once. Closing a socket, by dropping it, cancels the operations in flight on it.

A cancel does not undo what a write already sent, or a read already took: an operation that ended cancelled or timed out may have done part of its work, and its answer does not say how much.

One operation can be ended alone, with no group: conn.cancelRead() ends the read (or accept) in flight on the socket, answered Cancelled with its buffer given back, and conn.cancelWrite() the write in flight. They work from any actor or thread, and with nothing in flight they do nothing. They reach an operation that has been started by its await and is the socket's own on its side (next); the same two are on a UdpSocket and a File.

Sockets

A Socket moves: it may be sent in a message to another actor. Dropping it closes the socket, after whatever operations were started on it before. A socket in a paused behaviour waits with the behaviour, as any value does (What crosses an await), so it stays open until the behaviour ends.

One record for each socket

A Socket, a UdpSocket and a File each have a record, made with it and freed when it is closed and nothing is using it, with a side for each direction: a read side (a read, an accept, a datagram's receive) and a write side. An operation takes the side when it is made, keeps its buffer, its limits and the place its answer is written in, and gives the side back when the awaiting behaviour has taken the answer. A read or write that finds its side free allocates nothing: no closure, no job block, no reply box; a loop of reads on one socket takes the same side each time. Two reads at once on one socket, or an operation made and held while another is made, find the side busy and take a block of their own for that one operation: correct, and one allocation. aio.opStats() counts how many operations began on a record's own side and how many on such a block, and how many records are open. A File takes many reads at once by design, and all but the first of them use blocks.

Reading with no buffer

conn.read(buf) gives the read a buffer to wait with, and a connection that is idle for minutes holds that buffer all the while: a thousand idle connections pin a thousand buffers (4 MiB of 4 KiB ones), and the system locks their pages. conn.read() gives it none. The behaviour holds no buffer, the connection holds none, and the I/O side takes one from the pools when bytes have come: 4 KiB, or conn.read(room) with a usize asks for room for at least that many bytes (a layer reading TLS records asks for 16 KiB; aio itself knows nothing of TLS). The answer is the same as read(buf)'s, the buffer with what arrived in it, and empty at the end of the stream; its limited form is conn.readIn(lim) (and readIn(room, lim)).

  pub async fn serve(self, conn: Socket) {
    var more = true;
    while more {
      let r = await conn.read();          // no buffer is held while this waits
      match r {
        case let Ok(b) {if b.len() == 0usize {more = false;} else {handle(b);}}
        case is Err {more = false;}
      }
    }
  }

Underneath, a read with no buffer waits in one of two ways. Waiting without a buffer is a zero-byte receive, which ends when bytes are there, followed by a receive with a buffer that takes them; it costs a second trip through the system, about 4 µs a round trip on loopback. Waiting with a buffer is a receive started at once, which is cheaper when bytes are already coming. The read chooses by its socket's last read: one answered within the quiet time (2 ms; aio.setReadQuiet(d) sets it) marks the socket calm, and its next read takes a buffer at once, while any other socket's read, and the first read of every socket, waits without one. A read that began with a buffer and has waited the quiet time without a byte gives the buffer back and waits without one, so a connection that was busy and goes quiet pins nothing from then on. A deadline or a group bounds the whole read, both ways of waiting. A read that is cancelled, or timed out, or whose socket is closed, is answered as every operation is, once.

UDP sockets

aio.bindUdp(addr) binds a UDP socket on the I/O thread (port 0 has the system choose one, which u.localAddr() tells) and answers a UdpSocket, out of the Result by a swap as a Socket is. A UdpSocket is a kind of its own beside Socket and File: read, write and accept are not on it, and recvFrom and sendTo are not on the others, so a call of the wrong kind does not compile. It is not connected: each datagram names where it goes.

  • u.recvFrom(buf): one datagram, appended to the buffer, which is moved in. The answer is a Datagram, whose buf is the buffer given back, its length grown by the datagram's, and whose from is the sender's SocketAddr. A datagram of no bytes is a datagram, not an end: the length does not grow. A buffer with no room fails (InvalidInput), as a read's does.
  • A datagram longer than the buffer's room is cut: the answer is an Err whose IoError is of the kind Truncated (aio.isTruncated(e) or e.isTruncated(); its code is the system's number for a datagram too long, WSAEMSGSIZE or EMSGSIZE). The rest of the datagram is lost, the next one is whole, and the buffer goes home to its pool as a failed read's does, the bytes that fitted with it.
  • u.sendTo(addr, buf): all of the buffer as one datagram to addr, the count its length, the buffer going home. UDP promises no delivery: the answer says the system took the datagram. One too large for the network fails with the same number, of the kind Other.

Both take In forms, u.recvFromIn(buf, lim) and u.sendToIn(addr, buf, lim), and answer exactly once. A UdpSocket moves and closes when dropped, as a Socket does. One receive at a time per socket is the supported use; datagrams that arrive while none is outstanding wait in the socket's buffer, which the operating system bounds.

actor Echo {
  pub async fn once(self, u: UdpSocket) {                   // u: bound earlier, by bindUdp
    let r = await u.recvFrom(IoBuf(1500usize));
    match r {
      case let Ok(d) {
        var reply = IoBuf(64usize);
        reply.append("got it");
        let sent = await u.sendTo(d.from, reply);          // back to the sender
      }
      case let Err(e) {
        if aio.isTruncated(e) {say("too long", 0u64);}     // longer than 1500 bytes
      }
    }
  }
}

Files

aio.openFile(path, access) opens a file on the I/O thread, with iocore's Access: Read an existing file; Create a new one, or an existing one emptied, to read and write; Update an existing one or a new one, its bytes kept, to read and write. It answers a File, or the system's failure (a name that is not there is NotFound). The path is copied. f.readAt(offset, buf) and f.writeAt(offset, buf) work at a byte offset, with no position kept in the file, so any number may be in flight on one file at once. A read appends what is there to the buffer, up to its room, and from the end of the file or past it comes back with the buffer as it went; a buffer with no room fails (InvalidInput), as a socket's does. A write answers the count written, all of its buffer. Both take the In forms above, and answer exactly once, done, failed, cancelled or timed out. openFile has no In form: opening is one call to the system, which cannot be cancelled once begun.

actor Patcher {
  pub async fn patch(self, name: Path) u64 {
    let f = fileOf(await aio.openFile(&name, Access.Update));   // fileOf: as socketOf
    var b = IoBuf(5usize);
    b.append("hello");
    let w = await f.writeAt(100u64, b);                     // five bytes at offset 100
    match w {
      case let Ok(n) {u64.from(n)}                          // 5
      case let Err(e) {sayKind("write failed", e.kind()); 0u64}
    }
  }                                                         // f closes here
}

A File, like a Socket, moves: it may be sent in a message to another actor, and dropping it closes the file, after the operations started on it before, cancelling any still in flight. On Windows the operations are the completion port's; on Linux they run on a thread of the blocking pool (pread and pwrite), and answer the same. fileio, the file service with classes and a queue-depth governor, is a package of its own, not built yet.

Sleeping

aio.sleep(d) and aio.sleepUntil(at) are timers an actor awaits, as the kitchen above does: the behaviour pauses, its actor and its worker go on with other messages, and the rest of the behaviour runs when the time comes. d is a Duration, counted from the await; at is an absolute Instant (one already past is answered at once, as is a zero Duration). Both answer Result[void, IoError]: Ok when the time has come, an Err of kind Cancelled or TimedOut when the limits ended it first. Their In forms, aio.sleepIn(d, lim) and aio.sleepUntilIn(at, lim), take the IoLimits of the other operations. A group's cancel ends the sleep as Cancelled, at once if the group is cancelled already. A sleep due after the deadline (the limits' own, or the group's, the tighter) is answered TimedOut at the deadline instead; one due at or before it is Ok at its time, as iocore's timer in a cancel group is (the time chapter shows the same on a loop).

  pub async fn pause(self, group: CancelGroup) {
    // Half a second, unless the group is cancelled first
    let r = await aio.sleepIn(Duration.fromMillis(500i64), IoLimits.within(group));
    match r {
      case let Err(e) {say("cancelled", 0u64);}
      else {say("half a second has passed", 0u64);}
    }
  }

Names, file metadata and child processes

Three things have no completion form of their own, and run on a thread of iocore's blocking pool: the behaviour pauses, a pool thread does the work, and the answer comes back as the other operations' do.

  • aio.resolve(host, port) looks a name up (or an address written as text): a List[SocketAddr], every address found, each with the port (default 0). A name with no address fails NotFound (its code Windows' WSAHOST_NOT_FOUND, 11001, or getaddrinfo's EAI_NONAME); another failure of the lookup is Other.
  • aio.stat(path) asks a file's metadata: iocore's FileStat, with its size, attributes, modified time and isDir(). A path that is not there is NotFound.
  • aio.run(args, opts, dir) and aio.runLine(line, opts, dir) run a child process and wait for it, as the process package's synchronous run and runLine do, with the same Options and the same Output: its exit code (an answer, not an error), and what it wrote to its standard output and standard error, apart. The Err is a program that could not be started, an IoError of the system's number (NotFound for no program of that name). The synchronous process package stays beside it.

Each has an In form taking IoLimits (resolveIn, statIn, runIn, runLineIn). A job still queued for a thread, which a cancel group's cancel or a deadline takes out of its queue, is answered Cancelled or TimedOut without having run. A job a thread has taken cannot be stopped: a cancel waits for it to end, and a deadline answers TimedOut at the deadline while the work goes on, its answer dropped. So a child process is not stopped by its limits: give its Options a timeout, which stops it and everything it started. At most four children run at once (the general lane's threads); more wait their turn.

actor Builder {
  pub async fn build(self) u64 {
    var args = List[String].empty();
    args.push(String.from("conec"));
    args.push(String.from("app.cone"));
    // The compile runs on a pool thread; this actor handles its other messages meanwhile
    let r = await aio.run(args.view(), process.Options(timeout: Duration.fromSeconds(60i64)));
    match r {
      case let Ok(ok) {u64.from(ok.exitCode)}
      case let Err(e) {if e.kind() == IoErrorKind.NotFound {say("no conec", 0u64);} 0u64}
    }
  }
}

What is left out: a child's standard input and output as streams while it runs, a spawn apart from the wait (the process package offers neither), and a file's metadata by its open File.

HTTP an actor awaits

The actorhttp package (a working name, as netmsg is; the final name is yet to be chosen) makes HTTP and HTTPS fetches awaitable the same way: an actor writes await client.get(url) and the behaviour pauses until the whole response is in. The fetch is httpclient's (its pools of connections per server, its retries and redirects, TLS under https://), run on a thread of actorhttp's own, and the answer comes back as a message, as an aio operation's does:

actor Weather {
  client: Client;

  pub async fn show(self, url: String, done: OneshotSender[u64]) {
    // The whole response, awaited: this actor handles its other messages
    // meanwhile. It is given ten seconds, and the answer says how it ended
    let r = await client.getIn(url.view(), IoLimits.until(Instant.now() + Duration.fromSeconds(10i64)));
    match r {
      case let Ok(ok) {
        say("status", u64.from(ok.status));
        printStr(ok.body.view());
        printStr("\n");
      }
      case let Err(e) {
        if e.isTimedOut() {printStr("too slow\n");}
        else if e.isCancelled() {printStr("cancelled\n");}
        else {printStr(e.message().view()); printStr("\n");}
      }
    }
    var d = done;
    d.send(1u64);
  }
}

Fetching from a small server on this machine that answers with the weather, it prints status 200 and the body, sunny, 21 C. The done it is handed is the sending end of a one-shot channel, on which main waits, as the kitchen's waited on its channel.

A Client (Client.standard(), or Client.make(config, maxBody) with an httpclient.Config and the most body bytes a response may have) is a handle that moves: it may be sent in a message, and clone() makes another handle to the same client, so any number of actors fetch through one set of connection pools at once. The last handle's going ends the client, and every fetch of it in flight is answered cancelled. get(url) and send(request) (an httpclient.Request, with its method, header fields, body, intent and redirect limit) answer a Result: the success is httpclient's Response, with the status, the header fields, the whole body as bytes, the URL that answered after any redirects, and its timing. An HTTP error status such as 404 is an answer, not an Err. The Err is a FetchError: the network or the client refusing (a name not found, a refused connection, a certificate refused, a body longer than the limit, a URL that does not parse), with httpclient's Failure in its failure saying at which stage and why, or the fetch cancelled or past its deadline, which e.isCancelled() and e.isTimedOut() read; never a panic. getIn(url, lim) and sendIn(request, lim) take the same IoLimits as aio's operations (a cancel group and an absolute deadline), and a request's own deadline is kept beside it, the tighter winning.

A program that wants one connection itself has actorhttp.connect(host, port) and actorhttp.connectSecure(host, port, tlsConfig), which answer a Conn that moves like a Socket: conn.request(head, body) writes a request head (RequestHead.make("GET", "/", "example.com")) and a body and answers the whole response; conn.requestIn(head, body, lim) adds limits. The connection carries one exchange at a time; a request cancelled or timed out on the wire resets it (HTTP/1.1's only way to stop one), and later requests on it fail as closed. A connectSecure connection is made when the TCP connection is: the TLS handshake runs under the first request, and a certificate the client's configuration refuses ends that request failed at the TLS stage (or at the read or closed stage, if the connection broke before the request was asked for). Dropping a Conn closes the connection.

A response can instead be read as it arrives. client.stream(request) is answered when the response's head is in, with a BodyStream (the status and header fields are fields of it) whose read() awaits the next piece of the body: Some(piece), then None when the body is whole, or an Err as above. client.events(request) is the same for server-sent events (the sse package's, HTTP, TLS and URLs): an EventStream whose next() awaits the next sse.Event. A reader that awaits slowly slows the sender (the connection is told to send more only as the actor takes what is there), and dropping the stream cancels the rest of the fetch.

The other way round, actorhttp.listen(addr, config) answers a Server (a handle that moves and clone()s; its last handle's going closes it), and await server.next() answers the next request, whole, as an Exchange: the Request (method, target, header fields, body, the client's address) and the way to answer it. A server usually has one actor looping on next() and giving each Exchange, which moves, to an actor of its own. The actor answers once: ex.respond(head, body), or ex.start(head, length) then await ex.write(bytes) as often as it likes and await ex.finish() (a body of unknown length goes chunked), or ex.startEvents() then await ex.sendEvent(&event) for a stream of server-sent events. A write is answered when the connection has taken the bytes, so an actor that awaits each is slowed to its peer's speed; a peer that has left answers the write Closed. ServerConfig.secure(tlsConfig) makes the connections TLS; its other fields bound the request body a server takes (past it, 413) and the requests that may wait for an actor (past it, 503). An Exchange dropped without an answer is answered 500. The package's header lists each choice; tests/server.cone, events.cone and tlsserver.cone are these, run.

A cancel and a completion that race, and a fetch dropped with its client, are settled as an aio operation's are: exactly one answer. At the program's end, a behaviour still paused on a fetch is abandoned, as one paused on a socket is (The I/O thread, and the program's end).
