Errors: the Error trait and AnyError

Note: Not built yet: .context on a Result or an Option (addContext is on an AnyError only; the rest waits for methods added to a type from outside it); getting the original error back out of an AnyError (it needs a type's identity through a trait value); and the final text of report(), which stands until the design of display lands.

A function that can fail returns a Result, and what its failure holds is an error value. The collections package defines what makes a value an error, the Error trait, and a catch-all that holds any of them, AnyError. A library returns its own typed errors, which meet Error; an application, where its functions fail in different ways, returns AnyError and lets ? convert. Both come with import collections use *;.

The Error trait

pub trait Error {
  pub fn message(self: &) String;                       // one line for a person, this error alone
  pub fn source(self: &) Option[&<Error] { None }      // the error that caused this one
  pub fn report(self: &) String { ... }                 // the message, then each cause under it
}

A type meets it by declaring is Error and having a message(self: &) String; source is given only by a type that has a cause. source answers a virtual reference, &<Error (a plain & to a trait cannot be called through), which a type with a cause builds with the type argument, Some[&<Error](&cause):

struct ConfigError is Error {
  pub path: String;
  pub cause: FsError;

  pub fn message(self: &) String { String.from("the config could not be read") }
  pub fn source(self: &) Option[&<Error] { Some[&<Error](&cause) }
}

report() is the trait's own, and gives the message and then the message of each cause, one to a line, as main prints a failure (below):

the config could not be read
  caused by: readFile app.cfg: No such file or directory

The wording of that report is provisional. The library's error types, FsError, HttpError, IoError, TlsError and the others, all meet Error with the message() they always had.

AnyError

An AnyError owns any error that is an Error and Sendable, so it may cross between actors. It has a generic from, so the ? operator converts any such error into it, with nothing written; an AnyError passes through ? as it is:

fn readConfig(path: &str) Result[Config, AnyError] {
  let text = fs.readFile(path)?;        // an FsError becomes an AnyError
  let config = parseConfig(text)?;      // so does a ConfigError, or an AnyError as it is
  Ok(config)
}

(The conversion is a plain generic method named from, not an overload from, which a generic bounded by a trait may not be.) AnyError.msg("text") makes one from a line of text alone. An AnyError is itself an Error: its message() is its outermost line, and source() and report() walk down the chain.

Putting a line of context over an error

addContext(line) adds a line over what an AnyError holds: the line becomes its message() and the error it was is under it. withContext(f) takes a closure that makes the line, called when the method is. Each gives the AnyError back, so they chain:

let e = AnyError.from(failure).addContext("reading the config").addContext("starting up");
// e.message():  "starting up"
// e.report():   "starting up
//                  caused by: reading the config
//                  caused by: the failure's own message ..."

The name is not context, which is a reserved word: it is held for a language feature not built yet (Held for unimplemented features).

A main that fails

A main returning a Result prints its error to its error output as Error: and the error's report(), and exits with status 1. With an AnyError or any type meeting Error that prints the whole chain; a type with only a message() prints that.

fn main() Result[void, AnyError] {
  let config = readConfig("app.cfg").addContext("starting up")?;
  ...
}

Error: starting up
  caused by: the config could not be read
  caused by: readFile app.cfg: No such file or directory
