Modularity and Reuse

This part is for a programmer who has written programs with The Guide, and now wants to divide a larger one into parts, or to write a library that others will use. It covers modules and packages, and also everything underneath them that lets a part be written once and used again: names and name folding, what a part shows and hides, traits and dispatch, generics and macros, and the ways a part is extended without being changed. It opens with why, because each of these mechanisms is an answer to the same few requirements.

Why modularity

A program that lives long enough changes. Modularity is the way a program is decomposed into parts so that a future change stays inside the part it concerns, and so that a part written once can be used again somewhere else. Those are its two requirements: insulation from change, and reuse. A third runs underneath both: isolation, a part keeping its state and its workings to itself, so that nothing outside it comes to depend on them.

How well this works depends on where the boundaries between parts are drawn. Count the dependencies among the pieces inside a part, its cohesion, and the dependencies that cross from one part to another, its coupling: a good decomposition has a great deal of the first and little of the second. Separating concerns, one responsibility to a part, is the everyday way to get there. It can be overdone: a program cut into too many small parts pays more in coupling between them than it saves in complexity inside each.

A language that supports modularity well is a larger language than one that does not. What it gives back is reuse and versatility, and programs that are easier to reason about and to debug.

Six strategies, each building on the last

The mechanisms a language offers for modularity cluster around six strategies. Each one builds on those before it, and this part takes them in that order:

  1. Composition: a component is assembled from parts, in some arrangement. A struct's fields, an enum's variants, a block's statements and a module's files are all parts.
  2. Namespaces: each part is given a name, unique within its component, by which it is reached from outside: geometry.Point, point.x. A name may also be folded in, so that it is reached bare.
  3. Encapsulation: a component publishes its interface and hides how it is implemented, which shrinks the surface that others can couple to. In Cone a name is private to its module unless it is pub.
  4. Substitution: one part may be swapped for another that meets the same interface, the way any bulb of the right fitting goes into a light socket. Traits, virtual references, function and closure references, and module traits are the interfaces.
  5. Generativity: many concrete components are generated from one template, by substituting parameters into it. Generics, macros and metaprogramming do this.
  6. Extensibility: usable parts are added to a component without changing it. Folding a part's names in, enriching a concrete type, and extending an enum or a module do this.

Two more pages finish the part: packages and the build, where modules are compiled apart and shared, and global state and initialization, a module's own variables and the order in which they are set up.

One mechanism, several sizes

A program is modular at several layers, from small to large: a block, a function, a type, an actor, a module, a package. The same strategies come back at each layer. In the small, languages largely agree on how to offer them; the larger the layer, the less they agree. Cone gives a strategy the same shape at every layer where it has it, so what is learned for a type carries over to a module. The table shows where each strategy is found:

The clearest case is name folding, which the manual describes as one operation wherever it appears: "the names in there are now names in here." A type folds in a part's names, a module folds in a global's or another module's, and a type or a module is built out of another of its own kind, with the same words in each place:

struct Car {
  pub engine Engine use fuel, thrust;     // a type folds in a part's names
  pub body   SportyLook;
  pub wheels RimWheels;
}

imm config Config = new Config(80i64, 24i64) use *;   // a module folds in a global's
import math3d use Point3, Mat3;                         // and another module's

struct Gauge extends Meter { ... }      // a type built out of a type
mod solids extends shapes;              // a module built out of a module

struct Node is Id { ... }               // a type says which abstraction it meets
mod plain is Runner;                    // and so does a module

fn max[T](a T, b T) T { ... }           // a function generic over a type
struct Box[T] { ... }                   // a type
mod stack[T];                           // and a module
