Weak References

Note: Cached weak references are not implemented. Nor is a pattern match on a weak reference that produces a borrowed reference: a weak reference gives a new counted owner instead.

Owning and borrowed references always point to live objects, and may always be directly used to manipulate the objects they point to. This is not true for weak references. Although there are many varieties of weak references, what they share in common is the idea that they do not keep alive the object they point to. Therefore, we have to confirm whether the weak reference still points to a live object before accessing it.

Weak references may sound like a bit like a nullable references, however there is additional intelligent logic that runs alongside the liveness check. Let's examine different kinds of weak references and explain the value they add to various region strategies.

Cycle-breaking Weak References

As mentioned earlier, one of the disadvantages of the reference counting region strategy is that they can leak memory whenever a data structure has cyclic references. Essentially, cyclic references prevent reference counts from ever decrementing to zero. This can cause useless islands of data, no longer accessible by the program, to persist in memory forever.

There are several good solutions for preventing cycle-based leaks. The most common involves the injection of at least one weak reference in every data structure cycle. Unlike normal references, weak references won't keep the object it points to alive. It accomplishes this using a separate weak reference counter which behaves a bit differently than the "strong" reference count

The downside of a weak reference is that you need to pattern match on it before you can use it, to ensure the object is still there. As with many weak references, a successful pattern match produces a lifetime-constrained borrowed reference which can be then be used to work with the object it points to.

Rcw and Weak

Today, cycle-breaking weak references are library code, not a kind of reference, and a weak reference is asked for a new counted owner rather than pattern matched into a borrow. The rcweak package's region Rcw counts both strong owners and weak references. A strong owner is allocated as any other, new Rcw[mut, T](...). The weak reference is an ordinary struct, Weak[T].

  • Weak[T].of(owner) makes one from an Rcw[mut, T] owner. A Weak[T] moves when assigned or passed, and is copied only by w.clone().
  • w.upgrade() gives an Option of a new counted owner: Some while the object is alive, and None once it has died. The owner in a Some goes when the Option does.
  • w.alive() and w.strong() do the same in two steps. w.strong() of a dead object is a panic at the line calling it.

The object is finalized when its last strong owner goes, and its memory is freed when its last weak reference goes too. In this family, the child holds a weak reference to its parent, so the parent's counted owners are the only thing that keep it alive:

import stdio use *;
import rcweak use *;
import collections use *;

struct ChildValue {
  pub name i64;
  pub parent Weak[ParentValue];          // the weak half of the cycle
  fn final(self &uni) { printStr("child gone\n"); }
}
alias Child = Rcw[mut, ChildValue];

struct ParentValue {
  pub name i64;
  pub kids List[Child];
  fn final(self &uni) { printStr("parent gone\n"); }
}
alias Parent = Rcw[mut, ParentValue];

fn main() i32 {
  imm p = new Parent(1, List[Child].empty());
  imm w = Weak[ParentValue].of(p);
  p.kids.push(new Child(2, w.clone()));
  match p.kids[0usize].parent.upgrade() {  // an Option of a new counted owner
    case imm owner Some { printInt(owner.name); printStr("\n"); }
    case is None { printStr("dead\n"); }
  }
  printStr(if w.alive() { "alive\n"; } else { "dead\n"; });
  0i32;
}

This prints 1 and alive. When main ends, p's last owner goes, so parent gone and child gone follow; the child's weak reference did not hold the parent up.

Once the last owner is gone, a weak reference finds nothing:

import stdio use *;
import rcweak use *;

struct Thing {
  pub n i64;
  fn final(self &uni) { printStr("thing gone\n"); }
}

fn main() i32 {
  mut w = Weak[Thing].none();
  {
    imm owner = new Rcw[mut, Thing](7);
    w = Weak[Thing].of(owner);
    printStr(if w.alive() { "alive\n"; } else { "dead\n"; });
  }                                        // the last owner goes: the Thing is finalized
  printStr(if w.alive() { "alive\n"; } else { "dead\n"; });
  match w.upgrade() {
    case imm o Some { printInt(o.n); }
    case is None { printStr("none\n"); }
  }
  imm s = w.strong();                      // a dead object: a panic
  printStr("not reached\n");
  0i32;
}

This prints alive, thing gone, dead and none, and then the w.strong() panics.

Cached or memo-ized Weak References

Imagine we want memory access to a large number of sizable objects. Due to memory constraints, we may not be able to fit all of them in memory at the same time, but we can readily reload or reconstruct them on demand. In this situation, we can use weak references to point to such cached objects, knowing that the underlying system store may automatically unload some objects at any time to reclaim space for other objects.

Pattern-matching on such a weak reference reloads the object, if it has been purged, before producing a usable borrowed reference to the now-live object.
