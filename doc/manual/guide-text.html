Cone
Text

Nearly every program reads, builds or prints some text. This page prints a receipt for a café, which takes both kinds of text Cone has: the text written into the program, and text the program builds as it runs.

// Text
//
// A café receipt: string literals, the methods of str,
// and String, text that grows, built the way print is fed.

mod text;

import stdio use *;
import collections use *;

fn main() {
  // A string literal is UTF-8 text, so any language prints as written
  imm shop = "Café Zürich";
  print <- shop, "\n";
  // Lengths and positions count bytes: é and ü take two bytes each
  print <- shop.len, " bytes, ", shop.charCount(), " characters\n\n";

  // Each line of the receipt is a String, built by 'item' below
  imm coffee = item("coffee", 450);
  imm cake = item("Sachertorte", 675);
  imm total = item("total", 450 + 675);
  print <- coffee.view(), "\n";
  print <- cake.view(), "\n";
  print <- total.view(), "\n\n";

  // Some methods change a String where it is
  mut thanks = String.from("thank you, come again");
  thanks.replace("come again", "à bientôt");
  thanks.upperAscii();      // ASCII letters only: à and ô stay as they are
  print <- thanks.view(), "\n";
}

// One line of the receipt: the name, dots out to a column, then the price.
// A literal passed for 'name' is copied into a new String, which moves in
fn item(name String, cents i64) String {
  imm price = money(cents);
  mut line = name;          // the String moves on, into 'line'
  line.padEnd(20usize - price.len(), '.');
  line <- price.view();
  line;
}

// 1125 cents is "CHF 11.25"; the cents are always two digits
fn money(cents i64) String {
  mut s = String.from("CHF ");
  s <- cents / 100;
  s <- ".";
  mut c = String.empty();
  c <- cents % 100;
  c.padStart(2usize, '0');
  s <- c.view();
  s;
}

It prints:

Café Zürich
13 bytes, 11 characters

coffee......CHF 4.50
Sachertorte.CHF 6.75
total......CHF 11.25

THANK YOU, à BIENTôT

What to notice

  • A string literal, "Café Zürich", is a str, Cone's type for text: it can be named, printed, and asked questions with its methods.
  • len counts bytes and charCount() counts characters. Text is UTF-8, where a letter like é takes more than one byte.
  • A String, from the collections package, is text that grows. s <- x adds text or a number to its end, just as print <- x prints it.
  • Methods such as replace, upperAscii and padEnd change a mut String where it is, and view() gives its text to print to read.
  • item takes a String and gives one back. The String moves in, and moves out again to its caller; a literal passed where a String is wanted is copied into a new one.

Two kinds of text

Cone has two kinds of text, for two jobs. Text written into the program, a string literal, never changes and lasts as long as the program runs, so it costs nothing to name or to hand around: shop is just another name for the literal. Its text is a str, Cone's type for text, and str has the methods one expects of text: its length, whether it starts or ends with something, where something else is found in it, the text without the spaces at its ends.

Text the program builds as it runs is a String, from the collections package. A String owns the memory its text is kept in, and grows that memory as text is added. It has every method of str as its own, so anything you can ask of a literal you can ask of a String, and more besides: methods that change it, such as replace, insert, padStart and upperAscii. Wherever a String is wanted and a literal is given, the literal's text is copied into a new String for you:

imm word String = "copied";       // a literal becomes a String where one is wanted
imm part = String.from("hello world").sub(6usize, 11usize);   // "world", a new String

Counting in bytes

Text in Cone is UTF-8, so text in any language is stored and printed just as it is written. In UTF-8, an English letter takes one byte, but é and ü take two each, and a Japanese character three. So "Café Zürich" has 11 characters in 13 bytes.

Every length and every position in Cone's text is a number of bytes, as it is in Rust and Go. A position measured in bytes costs nothing to find: the text need not be read from the start to reach it. When you do want characters, charCount() counts them by walking the text, and chars() gives you each one in turn. It also explains the last line of the receipt: upperAscii changes only the 26 ASCII letters, which are one byte each, so à and ô come through as they were.

Building text the way you print it

A String is built with the same arrow that prints. print <- x sends x to the output; s <- x adds it to the end of s. Text is added as it is, and a number as its digits, so money builds "CHF 11.25" in a few short lines, with no format string to get wrong. Building in a String and then printing it is also how the receipt lines up its prices: padEnd fills a String out to a given length, and padStart fills from the front, which is how the cents are always two digits.

To print a String, print is handed its view(): the String's text as a str, read where it is, without copying it.

Copy or move

Assigning a number, or handing one to a function, copies it. Changing the copy leaves the original as it was. Most values in Cone behave like this.

imm a = 3;
mut b = a;  // b holds a copy of a's value
b += 1;     // b's value is changed to 4
a;          // is still 3

Some values should never exist twice, because they own something: a String owns the memory its text is kept in. Two copies would each believe the memory was theirs to change and to free. So a value like this moves instead. imm today = plan; hands the text to today, and plan has nothing left: the compiler refuses any later use of it, with "This variable's value has been moved out." There is only ever one owner, so Cone knows exactly when the text is no longer needed, and frees it then, with no garbage collector and nothing for you to free by hand.

imm plan = String.from("day two: the coast road");
imm today = plan;         // plan's text moves to today
print <- today.view(), "\n";
// print <- plan.view();  // Error: plan's value has moved to today

Whether a value copies or moves is decided by its type, not by how it is used. Numbers copy. A type moves if it says so, if it has a finalizer, or if anything it holds moves; you will meet such types again with structs and collections. That is all a program needs to know about moving for now. Move vs. copy, in brief, below, has a little more, and Moves in depth has the rest.

A String has one owner

A String owns its text, so, as above, it moves rather than copies. Follow the text of "coffee" through the program. The literal is copied once, into a new String, because item asks for a String. That String moves into the parameter name, then into the variable line, which may change, and finally back out to main as item's result. At each step the text stays where it is in memory, and only its ownership passes on. When main ends, coffee is the owner, and its text is freed then, once.

A function that takes a String and hands back a String, as item does, is a natural shape in Cone: the caller gives the text away, and gets the finished text back.

Move vs. Copy, in brief

Values are copied as they flow from variable-to-variable or function-to-function. Changes made to a copy don't affect the original value.

Sometimes, however, we have values for which we don't want multiple copies to exist at the same time: for example, a handle to a just-opened file, where closing the file using one copy would make it unsafe to use the other. To provide safe support for such "non-copyable" values, Cone supports move semantics. Move semantics enable non-copyable values to be moved from one place to another in a code's logic. However, once the value moves, it may no longer be accessed from its old location. This restriction ensures there is only ever one copy of the value in existence.

Whether a value is handled by move vs. copy semantics is determined by its type. Most types copy. A type moves if it declares so, by naming Move in its is list, if it has a finalizer, or if any of its fields moves:

struct Handle is Move {
   pub id i32;
}

fn take(h Handle) {
  print <- h.id, "\n";
}

imm h = new Handle(1);
take(h);            // h moves into take
print <- h.id;      // **ERROR** h was moved out

A clone method takes no part in copying: a type may declare one and call it by name, but no copy calls it. Moves in depth has every rule, what a move leaves behind, moves on only some paths, and swapping.

Note: Making text from bytes, bytes as &str, does not yet check that the bytes are UTF-8, nor that nothing still writes them while the text is used.

Text comes in a few forms in Cone, each for a job. A string literal is a &str, a borrow of text that lasts as long as the program; a String is text that grows; an owner of text, So[str], owns it; and a cstr is text on its way to a C function. They share one set of methods, written once on str, and they share one convention: text is UTF-8, and every position in it is a number of bytes.

Text: str and String, briefly

A string literal, "Hello", is text: a sequence of bytes holding UTF-8 code points, of the type &str. It may be held in a variable, handed to a function and printed as it is, and it has the methods one expects of text:

imm greeting = "Hello world";
print <- greeting, "\n";
greeting.len                    // 11: bytes, not characters
greeting.startsWith("Hello")    // true
greeting.find("world")          // the byte index where it first starts, as an Option

Every position in text is a number of bytes, so it costs nothing to find; a text is UTF-8 by convention, and where a position must fall between characters the method says so. chars() gives each code point in turn as a char.

Text that grows is a String, from the collections package: built from text, appended to with <-, and lent as text with view().

String, the growable string

String is the growable string: a list of bytes and one spare byte, so its block always has a NUL after the text (which the length leaves out, rewritten by each change) for C, and a String that holds nothing has no block at all. s.view() lends it as a &str (the static empty literal when it holds nothing), and the String folds the methods of str in as its own (trimStart, isCharBoundary, slice and the ranges &s[a..<b], the orderings < ...: The Methods of str), and == and the orderings compare its bytes with any other text, a literal, a &str, a So[str] or another String. A literal is copied into a String wherever one is wanted (imm s String = "core", names.push("core")).

import stdio use *;
import collections use *;

fn main() i32 {
  mut s = String.from("hello");
  s <- ", ";                               // append text
  s <- "world", 33i64;                     // and a number
  s.appendByte('!');
  print <- s.view();
  print <- "\n";
  print <- s.len();
  print <- "\n";
  if s.view().startsWith("hello") { print <- "starts with hello\n"; }
  s.insert(5usize, "!!");
  s.replace("l", "L");
  s.upperAscii();
  print <- s.view();
  print <- "\n";
  imm parts = String.from("a,b,c").split(',');   // copies, which are Strings
  print <- parts.len();
  print <- "\n";
  print <- parts[1usize].view();
  print <- "\n";
  imm frozen = s.freeze();                 // the bytes move into a So[str]
  print <- frozen.len;
  print <- "\n";
  0i32;
}

This prints hello, world33!, 15, starts with hello, HELLO!!, WORLD33!, 3, b and 17, one to a line.

Text and bytes

Text is a &str throughout: a &Array[u8] is bytes, and is not text until it says so (bytes as &str), though any &str is a &Array[u8] where bytes are wanted.

Building, changing and reading a String

Building: String.from(text), String.fromBytes(bytes) (a copy of bytes that are text, such as a buffer read from a file or a socket; nothing checks they are UTF-8, as bytes as &str does not), String.withCapacity(n), String.fromCStr(c) (a copy of a cstr's bytes, or of a raw pointer's, which is a panic if null) and String.join(parts, sep); appending: append(text) (also s <- text; Rust's push_str), appendBytes(bytes) (bytes that are text, unchecked like fromBytes), appendByte, appendInt, appendUInt and appendHex; editing: insert(i, text) (i between characters), remove(start, end) (the bytes from start up to end, both between characters), truncate(n), clear, replace(from, to), replaceByte, padStart, padEnd, lowerAscii and upperAscii; reading, in bytes, with &str text: equals, equalsIgnoreAsciiCase, and (folded in from str) compare, startsWith, endsWith, find, findFrom and contains; and copies of parts, which are Strings: sub, trim, lines and split.

A String for C, and freezing it

s.cstr() is its C string, the NUL already there, so nothing is copied; it is good until the String next changes, and a NUL inside the text is a panic, at the caller's line, since C would stop reading there. s.freeze() consumes the String and moves its block, shrunk to the text and its NUL, into a So[str]: the bytes are not copied.

The Methods of str

str has the methods one expects of text, written once on str itself; a literal, a &str, a So[str] or Rc[str], and any type that lends one, a String, reaches them all. Every position is a number of bytes, so they cost nothing to find; a text is UTF-8 by convention, and where a position must fall between characters the method says so.

  • len (bytes, not characters), isEmpty, bytes() (the &Array[u8] of the text), s[i] (the byte, a u8; an index past the end is a program error as for a slice) and isCharBoundary(i) (a character starts at i, or the text ends there).
  • A part of the text: &s[a..<b], &s[a..] and &s[a..b] (the last byte included), each a &str borrowed from s, as a slice's range is a slice; they are the calls slice(a, b), sliceFrom(a) and sliceThrough(a, b). A bound that is out of order, past the end, or inside a character is a program error (a panic at the line of the slice), as in Rust: a &str is always whole characters. The range makes a part only when borrowed; the text itself has no size to hold.
  • Code points: chars(), charIndices() and charCount(). chars() is a cursor whose next() gives each code point in turn as a char, an Option[char], None past the last; charIndices() gives each with the byte index it starts at, a StrCharIndex with the fields offset and ch (what a lexer needs, and every offset is a place a slice may begin). charCount() counts them by walking the text, O(n), where len is the bytes. A byte that is not part of well-formed UTF-8 reads as U+FFFD, one for each such byte, so every char given is valid. These are code points and not graphemes: a letter and its combining accent are two. The bytes themselves are bytes(), above.
  • startsWith(p), endsWith(p), find(p) (an Option of the byte index where p first starts, 0 for an empty p), findFrom(p, i) (at or after i) and contains(p).
  • trim(), trimStart() and trimEnd(): a &str without the ASCII whitespace (space, tab, line feed, form feed, carriage return) at the ends.
  • ==, !=, <, <=, >, >= and compare(o) (-1, 0 or 1): the bytes compared, and UTF-8's byte order is the order of the code points. Between &str, So[str], Rc[str], a literal and a String, in any pair (Rust's cross-type PartialEq). === asks whether two references are the same place.
  • hash(h): feeds a hasher the bytes, then the terminator (h.writeStr), as a String does, so any kind of text hashes as the others of the same bytes do. A Dict[String, V] is asked by a &str for that reason.

How an owner of text (So[str], Rc[str]) is counted and freed is described with owning references.

A String as a Slice of Bytes

A string literal on its own is not an array but a &str, a borrow of its text that lasts as long as the program (managed references). Any &str converts to a slice of bytes, &Array[u8], wherever one is wanted, so a literal goes where a slice of bytes is taken. The way back is written, bytes as &str, since bytes need not be UTF-8:

fn say(bytes &Array[u8]) { printStr(bytes as &str); }

say("Padma");                       // the literal, as a slice of bytes

Fine-tuning

Needed only where text meets C.

C Strings: cstr

A C function that takes text takes a const char *: one pointer to bytes that end in a zero, whose length it finds by scanning for the zero. Cone's name for that is cstr, a borrowed C string, and a C binding declares its strings with it: extern fn puts(s cstr) i32;. It is a pointer and no more (a one-field struct that crosses to C as one), and it promises the zero. Nothing else does: a &str may be part of a longer text and a slice never has one, so neither converts to a cstr, nor does a raw pointer. What does:

  • A literal, wherever a cstr is wanted: puts("hi"). A literal with a zero inside ("ab\x00cd") is refused there, since C would read only ab; the same text is fine as a &str, a String or an owner.
  • A String, s.cstr(), with no copy: its block always keeps a zero after its bytes, rewritten by each change, and a String that holds nothing has a static empty literal for one. A zero inside the text would end the string early for C, so cstr() scans for one (at memchr's speed) and panics, at the caller's line, if it finds it. It is good until the String next changes or dies.
  • An owner of text keeps the zero after its bytes too, however it was made (copied from a literal or a view, or by s.freeze()): owner.cstr() on a So[str] is its C string, with no copy, checking the text for a zero inside as a String's cstr() does (cstr.fromOwned(&owner) is the same call). A plain &str has no cstr(): it promises no zero.
  • A general &str, which promises nothing after its bytes, reaches C by a copy: String.from(s).cstr(). There is no owned C-string type; a String is one.
  • A raw pointer the caller knows ends in a zero, cstr.fromPtr(p): an argv entry, what getenv answers when it is not null. A C function that may take or answer a null string stays a *u8 in its binding.

From C, c.view() is the &str of a cstr, found by scanning for the zero and not checked to be UTF-8 (text is UTF-8 by convention), c.len() the count of bytes before it, and c.ptr() the pointer, for a function that takes a buffer. Copy the view into a String to keep it (String.fromCStr(c)); whether C or Cone frees what a C function answered is the binding's knowledge, which copies and then calls C's free.

imm name String = "core";
libc.remove(name.cstr());                    // a pointer to its bytes and the zero, no copy
libc.remove("old.tmp");                      // a literal is a cstr where one is wanted
imm owner So[str] = "scratch.tmp";
libc.remove(owner.cstr());                   // an owner of text is one too, no copy
imm text = libc.strerror(2i32).view();       // a &str of C's answer, scanned
libc.fwrite(bytes as *u8, 1usize, bytes.len, f);  // a buffer and a count: a pointer, asked for

A slice is an address and a count, so it is not a pointer: the implicit conversion of a slice to a raw pointer is gone, and xs as *T takes the address of a slice's first element, for a C function that takes a buffer and a length (a slice coerces to no pointer). A buffer and its length are two parameters in C, so they stay a *u8 and a count.
