Enums, and match on variants

Some things come in kinds. A drink is an espresso, a latte or a tea. A size is small, medium or large. An order either goes through or fails, for one of a few reasons. An enum says so: it names every kind a value may be, and each value is exactly one of them. This page shows how to declare one, build its values, and find out which kind you have with match, the same match that chose among numbers in Conditionals.

A small cafe takes orders by code number:

// A cafe's menu: enums, and match on their variants
mod cafe;

import stdio use *;

// A plain enum: a closed set of names
enum Size {
  Small, Medium, Large;

  // One function over the whole enum, taking the value
  pub fn ml(self Size) i32 {
    match self {
      case Small {240;}
      case Medium {350;}
      case Large {470;}
    }
  }
}

// Variants that carry values of their own, and a field they all share
enum Drink {
  pub size Size;

  Espresso;
  struct Latte {
    pub shots i32;
    pub oat bool;
  }
  struct Tea {
    pub minutes i32;
  }
}

// Why an order can fail
enum Fault {
  SoldOut;
  NoSuchCode(i32);
}

// A price in cents. Every variant has a case, so no 'else' is needed.
fn price(d Drink) i32 {
  imm base = match d {
    case Espresso {250;}
    case imm l Latte if l.oat {350 + 60 * l.shots;}
    case imm l Latte {320 + 60 * l.shots;}
    case imm t Tea {200 + 10 * t.minutes;}
  };
  if d.size == Size.Large {base + 80;} else {base;}
}

// A drink for a code on the menu, or the reason there is none
fn order(code i32) Result[Drink, Fault] {
  if code == 4 {
    imm why Fault = Fault.SoldOut;
    return Error(why);
  }
  if code < 1 or code > 4 {
    imm why Fault = Fault.NoSuchCode(code);
    return Error(why);
  }
  imm drink Drink = match code {
    case 1 {Drink.Espresso(Size.Small);}
    case 2 {Drink.Latte(Size.Large, 2, true);}
    else {Drink.Tea(Size.Medium, 4);}
  };
  Ok(drink);
}

fn main() {
  each code in 1 .. 5 {
    print <- "#", code, ": ";
    match order(code) {               // a Result is an enum too
      case imm d Ok {
        print <- d.size.ml(), " ml for ", price(d), " cents";
        if d is Tea {print <- " (let it steep)";}
        print <- "\n";
      }
      case imm f Error {
        match f {
          case SoldOut {print <- "sold out, sorry\n";}
          case imm n NoSuchCode {print <- "there is no drink ", n, "\n";}
        }
      }
    }
  }
}

It prints:

#1: 240 ml for 250 cents
#2: 470 ml for 550 cents
#3: 350 ml for 240 cents (let it steep)
#4: sold out, sorry
#5: there is no drink 5

What to notice

  • Size is a plain set of names. Drink's variants carry values of their own, and every Drink, whichever kind it is, has a size.
  • A match names the variants. case imm l Latte hands over the latte as l, so its fields can be read, and an if after a pattern is a guard. Every variant has a case, so no else is needed.
  • NoSuchCode(i32) holds one number with no field name; case imm n NoSuchCode gives the number itself.
  • order answers a Result, and main matches its Ok and Error exactly as it matches a Drink: a Result is an enum too.
  • ml takes the whole Size as its value and answers a number. Nothing in the program is changed in place: functions take values and give back new ones.

One of several kinds

An enum declares a closed set of variants. The whole set is written in one place, inside the enum's braces, so the compiler knows every kind a value can be, and nothing elsewhere can add another. That is what lets it check a match for you. Leave the tea out of price and the program does not compile:

Error 1417: This match does not cover Tea: add a case for each, or end the match with 'else {}'.

So when the menu gains a hot chocolate next month, the compiler walks you to every match that names each variant and now has one more to learn. A match that ends in else has said what to do with anything it did not name, and is left alone.

Every value of an enum takes the same room in memory: the size of its largest variant, plus a small hidden tag that says which variant it is. That is why a Drink can be held in a variable, passed to a function and handed back, as easily as a number, whichever kind of drink it is.

Three ways to write a variant

One enum may mix all three:

  • A bare name, Espresso or Small, carries nothing of its own.
  • A struct, struct Latte {...}, carries named fields, as any struct does (Structs and methods).
  • A name and a type in parentheses, NoSuchCode(i32), carries one value of that type, with no field name.

A field written outside the variants, as size is in Drink, belongs to every variant, so it can be read from any Drink without asking which one it is: d.size. A variant's own fields wait for the match: d.shots is refused, since only a latte has shots.

A value is built by naming its variant through the enum, with its values in parentheses, the shared ones first: Drink.Latte(Size.Large, 2, true). A bare name is a value all by itself: Size.Large. Each variant's value is of its own kind, a Drink.Latte, and it is taken wherever a Drink is wanted: by a function whose parameter is a Drink, and by a variable declared as one, as drink in order is, which takes whichever variant the match gives it.

Note: Error(Fault.SoldOut), written straight into a function that answers a Result[Drink, Fault], is refused today, as is a variant handed straight to Ok or Some. That is why order first declares why as a Fault.

match, again

In Conditionals, match chose among numbers: values, ranges, or and guards. Here it chooses among variants, and it is the same match: the cases are tried from the top, the first that fits runs, and the value of the block that runs is the value of the match, as imm base = match d {...} shows. What is new is the pattern, which is a variant's name:

  • case Espresso asks only whether the value is that variant (case is Espresso says the same).
  • case imm l Latte asks the same, and when it is, gives you the latte as l, with its own fields to read.
  • A guard narrows a case further, just as it does on a number. The oat-milk latte comes first; a latte without oat milk fails its guard and falls to the next case.
  • For a variant written with a type in parentheses, the name you bind is what it holds: case imm n NoSuchCode makes n the number.

Inside a match the variants are named bare. The match knows which enum it is looking at, so Latte means Drink.Latte without being told.

When only one variant matters, an if can ask without a whole match. d is Tea is true or false, as the program uses it, and a binding in an if tests and hands over the variant at once:

fn shots(d Drink) i32 {
  if imm l Latte = d {
    l.shots;
  } else {
    0;
  }
}

shots(Drink.Latte(Size.Medium, 3, false)) is 3, and shots(Drink.Espresso(Size.Small)) is 0.

An enum whose variants are all bare names compares with ==, as d.size == Size.Large does: such a value is nothing but its tag.

When work can fail: Result

Some work can fail for reasons that are not a bug: a file that is not there, text that is not a number, an average of nothing at all. A function like that says so in its return type, with a Result: Ok holding the answer, or Error holding what went wrong. The caller cannot use a Result as though it were the answer; it checks which one it got, with a match that must cover both, so a failure cannot be overlooked by accident:

fn average(total i32, count i32) Result[i32, String] {
  if count == 0 {
    return Error(String.from("there are no values to average"));
  }
  Ok(total / count);
}

match average(30, 0) {
  case imm avg Ok { print <- "average: ", avg, "\n"; }
  case imm why Error { print <- "no average: ", why.view(), "\n"; }
}

Result is nothing new: it is an enum. The core library declares it in one line, with two variants written as types:

enum Result[T, E] {Ok(T); Error(E);}

Shorter ways to pass an error on are planned (below).

The [T, E] leave the two types open until a Result is used: a Result[Drink, Fault] holds a Drink when it is Ok and a Fault when it is an Error. Nothing else about it is special. Ok and Error are its variants, bare in every program because the core library makes them so, and match order(code) is the match you would write for any enum. So the error can be anything at all, an enum of your own included: Fault lists the ways an order can fail, and the inner match tells them apart.

Methods that take the whole value

pub fn ml(self Size) i32 names the enum as what it takes, so it is one function over the whole enum: inside it self is a Size, and match self asks which. A state that moves on is written the same way, as a function that takes a value and answers the next:

enum Light {
  Red, Green, Amber;

  pub fn next(self Light) Light {
    match self {
      case Red {Light.Green;}
      case Green {Light.Amber;}
      case Amber {Light.Red;}
    }
  }
}

mut light Light = Light.Red;
light = light.next();          // Green
light = light.next();          // Amber

Nothing is changed in place: next hands back a new value, and the variable takes it.

Enums: one of several variants

Note: All of this capability is implemented except calling a method that takes self by value on a value typed as the enum itself.

An enum declares a closed set of variants: a value of the enum is exactly one of them, and the whole set is written inside the declaration, so nothing elsewhere can add to it. That closedness is what buys an exhaustive match.

The variants may carry values of their own, or carry nothing at all (three forms below):

enum PhoneType {
	Home, Work, Mobile;
}

enum Point {
	pub struct XyPoint {
		pub x f32;
		pub y f32;
	}
	pub struct AngPoint {
		pub dist f32;
		pub angle f32;
	}
}

A bare name is an empty struct variant. That one sentence is what makes a plain set of named symbols and a set of variant structs the same thing, and it is why there is no second construct to learn: Home above declares exactly what struct Home; would.

Two properties hold of every enum:

  • An enum is discriminated: there is a hidden "tag" field at the beginning of the value, holding a number the compiler assigns to each variant, which is what tells at runtime which variant a value is.
  • Every variant occupies the same size of memory — the size of the largest, plus the tag — so smaller variants are padded to fit. A value of the enum can therefore be held in a variable, copied, passed by value, and replaced in place by a different variant. Write @unsized to decline the padding.

Where you want a set of variants that other modules can add to, an enum is the wrong construct: use a trait and structs that declare is against it. That versatility costs something, and the cost is worth knowing: an open trait has no tag, so a value of it carries a pointer to type metadata and a match has to check the possibilities one at a time. A closed set is not only exhaustive, it is faster, because a tag is an index.

Declaration

The simplest form is a name and its variants. A variant written as a struct carries fields of its own; one written as a bare name carries none. It is permissible for a struct variant to be empty of fields too, as the presence of the tag ensures the overall value is not empty.

An enum may also declare members in common: fields every variant has, and methods every variant answers. Neither is something Rust's enums offer, and both are what let a caller do useful work with a value whose variant it has not yet recovered.

enum Event {
	pub time datetime;                             // a field every variant has

	pub fn stamp(self &) datetime {time;}          // a method with a body: a default
	pub fn describe(self &) String;                // a method without one: a requirement

	pub struct ButtonEvent {
		pub button u8;
		pub pushed bool;
	}
	pub struct KeyEvent {
		pub key Unicode;
	}
	pub struct QuitEvent;
}

All three variants above begin with the time field, ahead of any fields they declare themselves. A method with a body is a default, which each variant gets unless it declares that name itself; a method without one is a requirement, which every variant must implement, and calling it through a reference to the enum dispatches on the variant — see Method dispatch.

Either way, what a variant has is its own copy of the method. It is called on a value, event.stamp(), or named through the variant, Event.KeyEvent.stamp. Naming it through the enum, Event.stamp, is an error: the enum keeps no copy of its methods, only of its static functions.

A common member may be written anywhere in the body. What makes a member common is its kind, not its position: a struct is a variant, and anything else is common. The layout still puts common fields first in every variant.

Variant forms

A variant is declared in one of three forms, and one enum may mix them freely:

enum Token {
	Number(f64);                                   // declared as a type
	Word(&str);
	struct Op {pub prec i32; pub right bool;}       // declared as a struct
	End;                                           // empty
}
  • As a type: a name and a type in parentheses, Number(f64);. The variant holds that type itself. It has no field name, so there is no .value, or any name at all, to reach what it holds by: a pattern that binds it gives the contents, as case imm n Number binds an f64 (a copy, or a move of what moves, as the matched value allows; through a reference, a reference to it). The variant stays a type of its own, distinct from the type it holds: a Number is not an f64. It is built as any variant is, Number[1.5], and may pin its tag value after its type, Data(i64) = 7;. Core's Option and Result are declared this way: None; Some(T); and Ok(T); Error(E);.
  • As a struct: struct Op {...} names its fields and may have methods. A binding gives the struct, whose tag is never a visible field.
  • Empty: a bare name holds nothing, End;, and declares what struct End; would.

A variant declared as a type is told from a common field by its parentheses: Number(f64); declares a variant, and time datetime; a field every variant has, whatever either is called. An enum with fields in common names everything it holds, so none of its variants is declared as a type, and is refused where one is written (ErrorTypeVariant); declare it as a struct, whose field has a name. (A name and a tuple type, t (i32, i32);, is a field too.)

Each variant's tag value is assigned for you, ascending from zero, or written (Red = 0xFF0000): Tag values.

Initialization

A value is built using a constructor for one of the variants: its name with its values in parentheses, with no new, and an empty variant's name alone:

mut event = Event.QuitEvent(timestamp);
oddval = Event.KeyEvent(timestamp, 's');
imm phone = PhoneType.Work;

Notice that the constructor supplies a value for every common field, and never for the tag: that one is settled by which variant was named.

A generic variant takes its type arguments from where its value goes, as every generic does (Generics): imm none Option[i32] = None;. Where nothing says, they are written in brackets after the name, and the values after them: None[i32], Some[i32](5). Square brackets after a variant give type arguments and never values, so Some[5] and None[] are refused, naming the spelling that replaces them. In a pattern or after is a name stays a type: case is None[IoBuf].

An empty variant's name is a value, so a method can be called on it directly: with pub fn get(self &) i32 in Lamp, Lamp.Red.get() constructs Red and calls get on it, as (Lamp.Red).get() does. Only a method reads this way (one that takes self); a variant that holds values is not a value by its name alone, so Shape.Circle.area() is still refused for the self it lacks. A generic enum's empty variant has nothing to take its type arguments from as a receiver, so they are written: Pending.Waiting[i64].key().

Naming a variant

A variant is a name of its enum, not of the module around it, so it is reached through the enum: Event.KeyEvent, PhoneType.Work. Two enums may therefore each declare a Quit without either crowding a namespace neither of them was asked to share.

Inside the enum's braces, every name the enum declares is bare: its variants, and its fields, methods and functions. That holds for a variant's own body too, since it is written there, so a method of one variant names another without the enum in front:

enum Traffic {
	struct Stop {
		fn next(self &) Traffic {Go(5);}   // Traffic.Go
	}
	struct Go {
		pub delay i32;
	}
}

A name the variant declares itself comes first: a field of Go spelled like a sibling variant is, inside Go's methods, the field. One exception to the rule: a variant of a generic enum reaches the enum's methods through self, as self.name(), since it receives them only when the enum is instantiated. In a generic enum the enum's bare name, and each variant's, is the instance being defined, at the enum's current type arguments: inside enum Maybe[T], Maybe is Maybe[T] and a variant's No builds Maybe.No[T] (see Generics). A variant that an extension copies from its base (Extending an enum) keeps what its names meant where it was written, so it still means the base's variants.

An enum's private members are its module's. A member not declared pub is private to the module that declares the enum, as a struct's is. So code written anywhere inside the enum's braces — the enum's methods, its static functions, and every variant's methods — reads and writes the private fields of the enum and of every variant, calls their private methods, and gives private fields their values when it builds a variant, through any value and not only through self, and so does every other function and type of the module. Outside the module they stay private. So pub means what it means everywhere: part of the enum's interface to the rest of the program, and not a way for one variant to reach another.

enum Gauge {
	struct Low {
		lo i32;
		pub fn above(self &, h &High) bool {h.hi > lo;}   // High's private field
	}
	struct High {
		hi i32;
	}
	pub fn level(g &imm Gauge) i32 {                      // a static function
		match g {
			case imm l Low {l.lo;}
			case imm h High {h.hi;}
		}
	}
}

(This sentence is the compiler's current reading and is still to be reviewed.) An anonymous function written inside the braces is not part of this: like one written in a struct's method, it belongs to the module.

A module that wants an enum's variants as names of its own says so with use, which names the enum and then, optionally, which variants:

use PhoneType;                         // Home, Work and Mobile, bare
use Event KeyEvent as Key, QuitEvent;  // only these, one of them renamed
use Point {XyPoint, AngPoint};         // a list may be spread over lines in braces
use Colors but Blue;                   // every variant but one

After use PhoneType;, Work means PhoneType.Work. The module that declares the enum is no exception: it writes use like any other module to have the variants bare. A use folds variants and nothing else of the enum, and a variant it leaves out is still reached through the enum. The enum may be named through a module, use shapes.Colors;. A folded name must not be one the module already has for something else, whatever brought that one in; two enums that each have a Quit are both folded by renaming one or leaving it out. Nor may a module fold the same variant in twice itself: writing use Colors; twice is an error. The same variant arriving by a wildcard import is the name the module already has, so use Option; is fine beside the Some and None every module already has.

The names a use makes belong to the module that wrote it and are private to it. Written pub use, they are public names of the module: another module reaches them through it, shapes.Red, and an import of the module with .* brings them in bare. That is how Some, None, Ok and Error are bare in every program: the core library writes pub use Option; and pub use Result;, and every module imports it with .*.

A pattern needs no use: below.

Copying

A value may be passed around, by copy, just like any other value. This is possible because every variant is the same size — the size of the largest, plus the tag.

Because they are all one size, allocated memory holding one variant can be given a value of a different variant instead, and a pool allocator can hand out and reclaim variants of one enum interchangeably.

If any variant is a move type — it declares Move, has a finalizer, or holds a value that moves — the enum is a move type too, since a value of the enum may be that variant: it is moved rather than copied.

Finalizing

A value typed as the enum is finalized at the end of its life as the variant it holds would be: the tag says which variant it is. An enum may declare its own finalizer, which runs for every variant, after the variant's own if it has one, and before the finalizers of the variant's fields:

enum Resource {
	fn final(self &uni) {
		log("released");     // runs for every variant, after its own
	}
	struct File {
		pub handle Handle;
		fn final(self &uni) {
			close(handle);    // runs first, for a File
		}
	}
	struct Nothing {}
}

An enum with nothing to finalize in any variant costs nothing: dropping an Option[i32] does no work, while dropping an Option[String] finalizes the string when it holds one. An owning reference a variant holds is released as the enum value dies, so the owner held in a Some is let go with its Option.

Value Access

A common field is readable from a value whose variant is not yet known, because every variant holds it at the same offset. To reach a variant's own fields, use pattern matching to establish which variant the value holds. Once it has been narrowed it is used like any other struct value. A name tested for a variant, if s is Circle, is that variant where the test holds, so s.radius reads the field there, until the name may hold another variant (Flow typing); a pattern that binds (if imm c Circle = s, or imm c Circle = s else {...}; past an early exit) gives the variant as a value of its own. A variant declared as a type has no field to read: its pattern binds what it holds.

match on variants

A match on an enum names its variants in its cases: case is and a variant tests for it, and a variable before the variant binds it, so that its own fields can be read. A match that names every variant needs no else (Covering every value).

A pattern needs no use. A pattern knows the enum of the value it is matched against, so it names that enum's variants bare, and looks there before it looks at the names in scope:

fn pushed(e &imm Event) bool {
	match e {
		case imm b ButtonEvent {b.pushed;}   // Event.ButtonEvent, with no 'use Event;'
		case is QuitEvent {false;}
		else {false;}
	}
}

The same holds in a bound if and in an is test. Because the matched enum is asked first, a use of another enum with a variant of the same name does not change what a pattern means. Variant type partial matches has the details, including how a generic enum's variant takes its type arguments from the value. Option is matched the same way: case imm x Some and case is None (Option).

More about enums

Tag values

Each variant's tag value is assigned for you, ascending from zero in declaration order. You may write a value instead, which is what lines an enum up with the constants of a library written in another language. Numbering resumes from the last value written, so only the variants that need a particular value have to say so.

An enum may also name the integer type its tag values are laid out in. That fixes the tag's width, so a value too large for it is an error rather than a silent widening away from the layout you asked for. Without it the tag is as wide as the largest value needs — note that this follows the largest value, not the number of variants.

enum Colors u32 {
	Red   = 0xFF0000,
	Green = 0x00FF00,
	Blue  = 0x0000FF;
}

A tag value may be negative, as some libraries' constants are. Each value must fit the named integer type the way any integer literal must fit its type, and a negative sign counts: -4 fits i32, while its bit pattern 0xFFFFFFFC does not, and a negative value fits no unsigned type. Numbering resumes from a negative value too, counting up. An enum that names no type and holds a negative value gets the narrowest signed tag that holds every value.

enum VkResult i32 {
	Success = 0,
	NotReady,                  // 1
	ErrorOutOfHostMemory = -1,
	ErrorOutOfDeviceMemory = -2,
	ErrorDeviceLost = -4;
}

The tag field cannot be accessed, referenced or mutated: which variant a value holds is reached by pattern matching, and compared with ==.

For alignment reasons it may be desirable to place the tag somewhere other than first. To do this, write an anonymous field of type tag where it should go. tag means this only where a field's type is written, so it is not a reserved word and a field may still be named tag.

enum Aligned {
	pub wide i64;
	_ tag;

	pub struct Small {pub n i32;}
	pub struct Large {pub a i64; pub b i64;}
}

Method dispatch

Sometimes every variant should answer the same method with its own implementation. Declare the method on the enum without a body, and let each variant implement it:

enum Number {
	pub fn double(self &mut Self);

	pub struct Real {
		pub n f32;
		pub fn double(self &mut Self) {
			n *= 2;
		}
	}

	pub struct Complex {
		pub r f32;
		pub i f32;
		pub fn double(self &mut Self) {
			r *= 2;
			i *= 2;
		}
	}
}

Calling number.double() on a reference to a Number invokes the implementation belonging to whichever variant the reference points at. The tag says which variant it is, that selects the variant's vtable, and the vtable holds the method.

The same goes for any other trait the enum complies with. A reference to a Number may be passed where a virtual reference to such a trait is expected, and the virtual reference it becomes carries the vtable of whichever variant it points at, chosen by the tag, exactly as a reference to that variant would. Narrowing it with is or match therefore names a variant, never the enum.

The enum need not comply as a whole for a match to use a trait. A match on an enum may name a trait, case imm m Measured, which matches every variant that complies with it and binds a virtual reference to the trait built from the variant, whose vtable the tag chooses (Trait patterns).

A method may also take self by value, and a variant's value calls its own copy:

enum Reading {
	pub id i32;
	pub fn get(self) i32 {id;}
	pub struct Low {}
	pub struct High {pub n i32;}
}

Reading.High(1, 4).get()      // 1: High's own copy of get

Note: on a value typed as the enum itself, which variant's copy runs would have to be read from the tag the same way, and that is not built for a value. Calling such a method on a value of the enum is an error today; match to recover the variant, or declare the method with a reference receiver, which dispatches as above, or name the enum as the receiver.

One function over the whole enum

The receiver a method names decides which it is. A method written with self & or self &Self belongs to the variants: it is copied into each, and inside a copy self is that variant. A method whose receiver names the enum — self &Lamp, self &mut Lamp, any other kind of reference, or by value self Lamp — is one function over the whole enum. It is not copied, nothing is dispatched on the tag, and inside it self is the enum, so match self, case is and self is Red work as they do anywhere else:

enum Lamp {
	pub n i32 = 7;
	Red;
	Green;
	Off;

	pub fn describe(self &Lamp) i32 {      // one function over the whole enum
		match self {
			case Red   {10;}
			case Green {20;}
			case Off   {30;}
		}
	}
	pub fn next(self &mut Lamp) {          // may store any variant through self
		match self {
			case Red   {*self = Lamp.Green;}
			case Green {*self = Lamp.Off;}
			case Off   {*self = Lamp.Red;}
		}
	}
	pub fn get(self &) i32 {n;}            // copied into each variant, as above
}

imm l Lamp = Lamp.Green;
l.describe()               // 20
Lamp.Red.describe()        // 10: a variant's value calls it, widened to Lamp

A method over the whole enum is called on a value of the enum or on a value of one of its variants, which is widened to the enum for the call, and by value it takes a copy. A variant's value cannot lend &mut Lamp, since the method could store another variant in it: declare the value as the enum, mut l Lamp = Lamp.Red. If a variant declares a method of the same name, a value typed as that variant calls the variant's own, and a value typed as the enum calls the enum's. Within one enum a name is declared once, so the two kinds cannot share a name there. A package that declares such a method defines it once, and an importer calls it. An enum that extends another does not inherit its base's methods over the base, since a value of the extension is not a value of the base. A generic enum's method over the whole enum, self &Option[T], is not available yet.

Inside a variant, Self names the variant, so a variant holding the enum writes the enum's name: Branch(List[Tree]), not List[Self].

Complying with a trait

An enum may say in its declaration that it complies with one or more open traits, exactly as a struct does, with is after its name. What the trait requires and what it gives then reach every variant: a default the variant does not declare becomes its own copy, and a requirement is met by the variant's own method or by one with a body the enum gives every variant.

trait Named {
	pub fn label(self &) i32;
	pub fn loud(self &) i32 {label() * 100;}
}

trait Measured {
	fn size(self &) i32 {7;}
}

enum Shape is Named {
	pub k i32;
	pub fn label(self &) i32 {k;}    // meets Named's requirement for every variant

	pub struct Circle {
		pub r i32;
		pub fn label(self &) i32 {r * 10;}
	}
	pub struct Square is Measured {        // a variant may name traits of its own
		pub s i32;
	}
}

fn loudOf(n &<Named) i32 {n.loud();}
fn shapeLoud(s &Shape) i32 {loudOf(s);}   // passes the variant's vtable, chosen by the tag

loudOf(&Shape.Circle(1, 7))     // 7000: Circle's own label, Named's loud
loudOf(&Shape.Square(2, 3))     // 200: the enum's label, Named's loud

A variant may name traits of its own in the same way, beyond its enum: struct Square is Measured above. Its enum is its base without being written, and naming the enum in the list is an error, since a variant is already a member of the enum it is written inside.

An enum's list and a variant's name only open traits, and none of them is a base in the sense a struct's first one is: the enum lays out itself and every variant, discriminant first, so a trait either one names may not require fields. Nor may any is list name an enum, whether first or later: an enum's variants are all declared inside it, and nothing outside may join the set. An enum that extends another takes its base's traits with the variants it copies and names none of its own.

Comparing enum values

A value may be compared for equivalence, and not for order: which variant a value holds is what a comparison can answer, and declaration order is not a magnitude.

Where every variant is empty, the value is the tag, so the comparison is exactly a tag comparison:

if phone == PhoneType.Mobile { ... }

Where a variant carries fields, two values are equal when they hold the same variant and that variant's own == says their payloads are equal: the tags are compared first, and only if they match is the variant's == called. A variant that carries nothing is equal to another of its kind by its tag alone. != is the negation. A variant's == is written as any struct's is, taking another of the variant, by value or by reference:

enum Shape {
	struct Circle {
		pub radius f32;
		pub fn `==`(self, other Circle) bool {radius == other.radius;}
	}
	struct Rect {
		pub w f32;
		pub h f32;
		pub fn `==`(self &, other &Rect) bool {w == other.w and h == other.h;}
	}
	struct Dot;                       // equal to any other Dot
}

imm unit Shape = Shape.Circle(1.0);
unit == Shape.Circle(1.0)             // true: the same variant, equal payloads
unit == Shape.Circle(2.0)             // false: the same variant, a payload that differs
unit == Shape.Rect(1.0, 1.0)          // false: a different variant
unit != Shape.Dot                     // true

The comparison is the enum's: it is written on a value of the enum, and a variant on its left is compared with the variant's own ==, which takes another of that variant.

Comparing with an empty variant asks the tag alone. When either operand is an empty variant, unit == Shape.Dot, unit != Shape.Dot, or the variant on the left, the other value either holds that variant or does not, and the comparison says which, whatever the enum's other variants carry and whether they declare a ==. It is the test unit is Dot in the form of a comparison. This holds for every enum, core's Option included: maybeInt == None and maybeInt != None need no == on Some. The empty variant takes the type of the other operand where it needs one, as it does wherever its enum is expected. Two values that both carry fields still compare as above, and are refused where a variant declares no ==.

A variant carries fields when it holds anything beyond the tag, and that includes the fields every variant of the enum has in common: an enum with pub time i32; compares the time through each variant's own ==, an empty variant's included, since the time is part of what it is.

Every variant that carries fields must declare a == of its own for the enum to be compared: an enum compares by what its variants say, and there is no comparison of a struct's contents to fall back on (deriving one is still to come). If one does not, comparing the enum is an error, and the message names the first variant without one and the fields it carries. Writing that variant's ==, or matching to recover the variant, is the remedy. That includes core's Option and Result, whose Some, Ok and Error declare none: two options holding values are matched, not compared, for now (an option against None is compared, as above).

The operands are only read, wherever they lie: comparing two values of an enum that moves moves neither, and both can be used afterwards.

Rarely needed:

Declining the padding

Padding every variant to the largest costs memory, and whether to pay it for the convenience of a value is a choice only you can make. Write @unsized to decline it:

enum @unsized Shape {
	pub kind i32;

	pub struct Dot;
	pub struct Polygon {pub points Array[Point, 64];}
}

Each variant then occupies only what it needs, and the enum has no single size. So no value of it may be held — not in a variable, not in a parameter, not in a field — and it is reached only by reference:

imm shape &Shape = &someDot;

Notice how a reference to a variant coerced automatically into a reference to the enum. Everything else is unchanged: the tag is still in the value, a common field is still readable through the reference, matching still recovers the variant, and dispatch still works. What is given up is the value semantics — holding one in a variable, copying it, passing it by value, and swapping a variant in place.

Most types that want this are graphs and trees, and those are usually better served by an open trait and structs that are-a it: once a type is reached by reference anyway, there is little left for a closed set to buy. So @unsized is for the case that is genuinely closed, wants exhaustive matching, and has variants whose sizes differ enough to matter.

Patterns on variants

Binding past an early exit

A binding made by if imm n Ok = r lives in the block of the if. To use it after the test and leave otherwise, write the binding as a declaration with an else that must not fall through (return, break, continue, or a call that does not return, such as panic):

fn bump(r Result[i32, Fin]) i32 {
  imm n Ok = r else { return 0; };
  n + 1;
}

It binds what a binding does (What a match takes): a copy of plain data, a move of an owner, a reference into a borrowed value (imm n Ok = &mut r else ... gives an &mut i32); it may be mut; and the pattern names only the variant, taking its type arguments from the value. An else that falls through is an error. Since the else leaves, r is known to be the variant after the declaration, as after any branch that leaves.

Trait patterns

In a match on an enum, a pattern may name a trait instead of a variant. It matches every variant that complies with the trait: one that declares it with is, or has what it requires (Traits), including what the enum gives every variant. A variant that does not comply, Third below, is left to the cases after it. The match compiles to tests of the tags of the variants that comply, so it costs nothing beyond them, and it counts toward covering every value as the variants it names, so the match below needs no else:

trait Measured {
  pub fn size(self &) i32;
}

enum Shape {
  struct Circle is Measured { pub r i32; pub fn size(self &) i32 {r * 10;} }
  struct Square is Measured { pub s i32; pub fn size(self &) i32 {s * 100;} }
  struct Third { pub t i32; }
}

fn measure(s &Shape) i32 {
  match s {
    case imm m Measured { m.size(); }   // Circle's or Square's own size, by their vtables
    case is Third { 7; }
  }
}

The binding is a virtual reference to the trait, built from the variant the matched reference points at, so a call through it goes through that variant's vtable. As for a variant (Variant type partial matches), the matched value supplies the kind and the permission: on a &mut Shape, m is a &<mut Measured and may call what needs self &mut; on a &Shape it is read-only. It is a reference into the variant, so it follows the collection rule as a binding to a variant does, and it may not outlive the value it borrows. Because only a borrowed reference can lend a virtual reference, a pattern that binds a trait needs the matched value to be one (match &s, match &mut s); a value or an owner such as an Rc can be asked, case is Measured, and not bound. A pattern may not be written as a plain reference to the trait (&Measured), which has no vtable to carry. The patterns work in a bound if, imm m Measured = s, in let-else, and joined by or and guarded like any other.

Which variants comply is decided as a generic's where T is Measured decides it: by declaring the trait, or structurally for a trait that requires something. A marker trait, which requires nothing, is complied with by declaring it alone. A method written over the whole enum (fn size(self &Shape)) is one function that no variant has a copy of, so it makes no variant comply; a trait that no variant complies with is an error, since the pattern could never match. Only a closed family can say which of its values comply, so an open trait has no trait patterns: a &<Measured can be narrowed to the concrete type it was made from, and only to that (Virtual references).

Note: Not implemented: partial matches that test the values inside an array, a struct or a variant (case is [1, _], case is Point[0., _], SomeInt[<0]). The square brackets those partial patterns are written with here are provisional: how a pattern spells a type or a construction is an open design question, as is how a variant is constructed.

Partial matches

When dealing with a composite data structure, partial matching supports value or type matching on selected parts of that data. A partial match pattern mimics the type structure of the data we are matching against, specifying match patterns for the value or type of particular substructural elements. It also supports "destructuring", binding variables to these or other substructural elements.

Partial match patterns begin with the is operator. Additional specifics of the pattern vary by type.

Collection partial matches

A partial match can check whether an array (or array reference) begins with elements that match patterns:

match numbers {
  case is [1, _] { 1; }
  case is [_, 1] { 2; }
  case is [<=0, <=0] { 3; }
  else { 4; }
}
Struct partial matches

A matching pattern may be created for specific named fields:

match points {
  case is Point[0., _] { 1; }
  case is Point[_, 0.] { 2; }
  case is Point[<0., &lt=0.] { 3; }
  else { 4; }
}

Any unspecified fields in a struct pattern are assumed to match.

Variant type partial matches

An variant pattern typically just matches against each option's variant type, binding to a variable:

match oddval {
  case imm intval SomeInt { intval; }
  case imm point PointStruct { i32.from(point.x * point.y); }
  case is None { 0; }
}

A binding gets what the variant holds. A variant declared as a type (SomeInt(i32);, see Variant forms) holds that type itself, so intval above is the i32, with no field to name: Some, Ok and Error are declared this way. Bound by value, it is a copy of the i32, or, when what it holds moves, a move of it out of the matched value, which is then finalized without it; a mut binding changes the copy and not the matched value. Bound through a reference (case imm n SomeInt on a reference to the enum), it is a reference of the same permission to what the variant holds, an &i32 here. A variant declared as a struct binds the struct, whose tag is never a visible field.

A variant is a name of its enum (see Naming a variant), and a pattern names it bare with no use: the match already knows which enum the value belongs to. This is true of every pattern on a value — a case, a bound if or elif, and an is test — and it looks through a reference, so case imm c Circle on a &Shape names Shape.Circle.

A pattern names only the variant. The matched value supplies the rest: the type arguments, and, where it is a reference, the kind of reference, its region and its permission. On a &imm Shape, case imm c Circle binds an &imm Circle; on a &mut Shape (a borrow made at the match), an &mut Circle; on an Rc[imm, Shape], an Rc[imm, Circle]; on a Shape, a Circle. A test with no binding, case Circle or s is Circle, asks only whether the value is that variant. A pattern may still be written as the reference, case imm c &Circle, which then checks that the matched value is one: it is an error where the value is no reference, or is in another region, or has a weaker permission than the pattern asks for. A managed reference is never spelled in a pattern, and the older +Rc-mut Circle is refused.

A binding through a reference points into the variant, and follows the collection rule. Through a reference, c is a reference into the value's payload, and a change of variant would have it read the payload as the wrong type. It is a borrow into the enum, as an element is a borrow into a list (Borrowed references), so it is allowed through any reference, and refused only if something could change which variant the enum holds while c is still to be used:

  • the enum stored over whole (*s = Shape.Rect(1, 2, 3)) or swapped, through the same name or another;
  • a call handed the enum, or anything that could reach it, whose body (or what it calls) does either, or whose body the compiler cannot read.

Writing a field within the variant is not a change, whether through c or through the enum's name, and neither is a field every variant has (s.kind = 9), nor reading the enum, nor a call that only reads it. The refusal is reported where c is used again, and names the change; a change after its last use is fine, which is how a state machine moves to its next state. A &mut borrow of a local made where it is matched is asked the same (match &mut s: the local is one more alias while the binding is used, Freezing access to the source of a borrow); a & one needs no question: the borrow freezes the local until the binding's last use, and a uni, imm or mut1 reference has no other name to change it. A value owned by an Rc is another owner of the same value: where no writer can store another variant through any owner (Rc[imm, Shape]), the binding is a copy of the owner, counted one more and let go as the arm ends, typed as the variant (Rc[imm, Circle]), and the variant is at its enum's address, so nothing moves. Where another owner could change which variant the value holds (Rc[mut, Shape], Rc[ro, Shape]), no loan stands for it and the narrowing is refused: bind the payload by copy, or match through a borrow of the value, which is followed. An is test binds nothing.

fn grow(s &mut Shape) {
  match s {
    case mut c Circle {c.radius = 2;}   // Ok: nothing changes the variant while c is used
    else {}
  }
}
fn restart(s &mut Shape, t &mut Shape) i32 {
  match s {
    case mut c Circle {
      c.radius = 2;       // Ok: writing a field within the variant
      *t = Shape.Rect(1, 2, 3);   // Error: t may be another name for s, and c is used again
      c.radius;
    }
    else {0;}
  }
}
fn step(m &mut Machine) {
  match &mut m.state {
    case mut c Circle {
      c.radius = c.radius + 1;
      m.state = Shape.Rect(1, 2, 3);  // Ok: c is not used again
    }
    else {}
  }
}

The matched value's enum is asked first. A bare name in a pattern means that enum's variant whenever the enum has one of that name, whatever the name means elsewhere in the module, so a use of another enum with a Red does not change what case is Red means on a Lamp. Only a name the enum has no variant of is looked up as any other name is. A qualified pattern, case is Colors.Red, is taken as written; and a variant named through its enum alone, case Colors.Red, means case is Colors.Red, as the variant bare does.

The value supplies a generic variant's type arguments. On an Option[i32], case imm s Some means Some[i32]. Arguments may still be written where the name is in scope, as Some[i32] always is. Written on a variant that is in scope only because the matched enum has it, they are an error that says to drop them or to name the variant through its enum.

A struct variant bound by value is the value the arm took, under its variant's name, not a second copy of it. The arm takes the matched value into a variable of its own (a move of one that owns, which consumes a matched place on the paths to that arm), and when the arm ends it is finalized once, as the variant it is. Moving the bound variable, or handing it back as the case's value, moves that value. A bound variable declared mut changes that value, not a matched place: assigning over it, or over one of its fields, finalizes what is replaced, and a value swapped out of it with <=> leaves what was swapped in to be finalized with it. As with a plain mut local, one moved out (on every path or only on some) and then assigned over holds the new value, which is finalized with the matched value. A match on a call holds the matched value itself for the whole match and finalizes it as the match ends, whichever case ran.

If desired, pattern matching and binding can also be applied to the internal value(s):

match oddval {
  case imm intval = SomeInt[<0] { -intval; }
  case imm intval = SomeInt { intval; }
  case is PointStruct[x=_, y=_] { i32.from(x * y); }
  case is None { 0; }
}

Option: a value that may be missing

Note: Option is built as core's enum. Not built, for an Option: a plain value where an Option is wanted (mut maybeInt ?i32 = 5;: write Some(5)), the ? and or operators, ?., catch None, and an Option as an if condition. The forms that are not built are gathered at the end of this section.

The Option type is an enum that core declares, enum Option[T] {None; Some(T);}: Some is a variant declared as a type, so it holds its T with no field name, and a pattern that binds it, case imm n Some, gives the T itself. It is useful when we want to express the idea that we may or may not have a value of a certain type. In some languages, these are sometimes called nullable types, since null represents the absence of a value. Optional values are so useful that many kinds of syntactic sugar exist to make them easy to work with.

Creating Option Values

Let's declare and initialize a variable that might hold an integer:

mut maybeInt ?i32 = 5;

Notice that the type specifies a question mark before the integer type. The question mark signifies this is an Option type. It is a syntactic abbreviation for Option[i32].

The value of 5 is automatically coerced into its optional integer equivalent (not built yet, as the note above says: write Some(5) today). It would also be possible to specify this explicitly using Some[i32](5) or its shorter inferred version: Some(5).

To initialize this variable as having no value, use None:

mut maybeInt ?i32 = None;

Again, None is an inferred abbreviation for None[i32]. The abbreviation is only possible when the context makes it clear what sort of Option type we are working with: a declared variable, a return type, an assigned variable, a parameter, a field, the branches of an if and the other operand of == each say, by the general rule that a generic's type arguments are inferred wherever they can be (Generics). Nothing about it is particular to Option: Ok(5) takes its error type from the Result it is wanted as, and Some(5) is an i64 where an Option[i64] is wanted. Thus, this is ambiguous and therefore an error, and the message says to write None[T]:

mut maybeInt = None;   // **ERROR**: What type does the Option wrap?

An option is compared with None by its tag alone: maybeInt == None is true when it holds no value, and maybeInt != None when it does, though Some declares no == of its own (Comparing).

Unwrapping Option Values

We cannot work with an Option value in the same way we would a value of its enclosed type. Imagine trying to add some number to a optional integer (for example: maybeInt + 4). How should it perform the addition when maybeInt is None? In the face of this uncertainty, the compiler views it as unsafe and will emit an error.

To safely work with a optional value, it must first be unwrapped. This means performing pattern matching on the optional value to determine whether it holds a value or None. Based on which it is, we can then act one way in one case and another way otherwise.

Explicit pattern matching is versatile enough to handle any unwrap-and-act scenario, but the resulting code may be undesirably verbose. Several operators offer succinct ways to work with optional values; they are not built yet, and are described with the planned forms at the end of this page.

Testing for a value

Note: Not built. Core's Option declares no isTrue, so an Option used as a condition is refused (Error 1013: the condition requires a true/false value); test the variant, maybePoint is None, or compare, maybePoint == None, as below.

An Option used as a condition, if maybePoint { ... }, is a plain truth test: it asks the Option's isTrue, which is true when it holds a value, and nothing more. It does not unwrap anything, and maybePoint is the same optional value inside the block. Narrowing comes only from the language's own tests, is and a binding, never from what a method returns: isTrue is one method among others, and a three-variant enum whose false covers two of them has no one variant to narrow to. To ask whether a value is there and say so, test the variant:

if maybeRef is None {
  // do some error recovery actions
}

Inside the block maybeRef is known to be None, and after a block that leaves it is known not to be (Flow typing). It is still the whole Option: Some holds its integer as a type, with no field to name, so to work with the value inside, bind it.

Unwrapping with a binding

Every enum unwraps with the same two forms, and an Option is no exception. A binding in an if is the value inside, for the block:

if imm p Some = maybePoint {
  imm x = p.x;
  imm y = p.y;
  imm dist = p.dist();
}

A second condition is a nested if, since the binding is made by the first:

if imm n Some = maybeInt {
  if n < 10 {
    scale *= n;
  }
}

To use the value after the test and leave when there is none, bind it in a declaration whose else leaves (Binding past an early exit):

imm p Some = maybePoint else { return; };
imm dist = p.dist();

Pattern Matching

A bound if may carry an else for when there is no value, and a match handles every case at once:

if imm integer Some = maybeInt {
	scale *= integer;
} else {
	// Some recovery stuff
}

When maybeInt is not None, its value is unwrapped and copied into the variable named integer, where it can then be used inside that block. If it is None, then the alternative block is performed.

The form of the value after = decides what the binding is (What a match takes). A variable, as above, is tested where it stands and only the block that binds takes from it: the integer is a copy, and an Option that holds something that moves (an Option[String]) is moved from, which consumes the variable on that path, while the else block still has it. A borrow, if imm integer Some = &maybeInt, binds an &i32 into the Option instead and takes nothing, and a call is a temporary the statement owns. The pattern names only the variant: it takes the type argument, and the reference kind of a borrow, from the value.

Option References

Option references are optimized so they take no more space than regular references. The None reference value is just a non-addressable address (typically, 0). (Memory describes references.)

The Option operators

Note: Nothing in this section is built. It is the design these pages first described, kept as it was written. The design of error handling is under way, and will rewrite this section, and with it the operators an Option and a Result are meant to have.

Force unwrap, treat None as an exception

Note: Not built. A ? after a value is refused as an invalid term; unwrap with match until it is built.

One approach is to expect the value to not be None, and treat it as an exception if it is. To handle a optional value this way, follow the optional value with the ? operator.

imm val = maybeInt?;

If maybeInt is not None, then val will be the unwrapped integer value inside.

An exception will be thrown if maybeInt is None. This exception can be caught and handled if a catch None handler is provided. If one is not specified, the exception will panic.

Give None a default value

Note: Not built. or with an optional value on its left is not this operator yet, so the example below does not compile; unwrap with match until it is built.

An alternative approach to unwrapping involves specifying a default value use when the optional value is None. This form of unwrapping uses the or operator:

imm val = (maybeInt or 0) * scale;

val will use the value of maybeInt if it is not None. Otherwise it will use 0.

The value to the right of the operator cannot be a optional type, and its type must match that of the wrapped type for the optional value on the left. The expression for the default value will only be evaluated when the optional value is None.

None propagation on safe method calls

Note: Not built. The compiler reports ?. as reserved wherever it is written.

A third operator applies when we want to perform some operation on a optional value when it is not None, but evaluate to None when it is. This approach uses the ?. operator, a variation of the dot operator used to perform methods or access fields:

imm x = maybePoint?.dist();

If maybePoint is not None, then x is a optional value that wraps the calculated distance of that point. However, if maybePoint is None, then x will also be None. In effect, we are performing a method or accessing a field if it is safe to do so, and propagating None otherwise. Unlike the previous two operators, the result of using ?. is always a optional value.

This operator may also appear on the left hand side of an assignment statement, and will bypass the assignment altogether if the optional value is None.

Result: success or an error

In many cases it is possible and desirable to recover from an exception, when a program tries to do something and fails. Today a program does it with core's enums: a Result, for a success or an error (and an Option, for a value that may be missing). What must not happen at all is a panic.

Result is an enum

Core declares enum Result[T, E] {Ok(T); Error(E);}: each is a variant declared as a type, holding its value with no field name, and a pattern that binds one, case imm n Ok, gives that value itself. A Result is built, passed, returned and matched like any enum, and its variants, Ok and Error, are names in every module.

The standard library's functions that can fail answer one: the fs package's (Failure: Result and FsError), and an I/O operation an actor awaits (Awaiting I/O).

Planned, not built: exceptions, and the operators

Note: Nothing in this section is built. It is the design these pages first described, kept as it was written. The design of error handling is under way, and will rewrite this section, and with it the operators a Result is meant to have; the ? operator and its companions are coming soon. Today a Result is handled with match, as above. The operators planned for an Option are with Option.

Throwing Exceptions

Recoverable exceptions are always directly communicated from one function back to the function that called it. Instead of returning the expected value, it throws an exception value.

fn factorial(mut n i32) i32 throws bool {
  if n <= 0 { throw false; }
  mut result = 1;
  while n {
    result *= n--;
  }
  result;
}

This function specifies throws as part of its signature to indicate that if it cannot successfully return an integer value, it will throw a boolean exception instead. The first line does exactly that: If the parameter is a negative number, it throws an exception value of false.

Exception Handling

Now that we have a function that can throw an exception, let's show different ways to handle it.

Give exception a default value

Use the || operator to establish a default value in the event of a thrown exception.

fn calc(n i32) i32 {
  factorial(n) || 0;
}

If factorial throws an exception, it is treated as if it had returned 0 instead. The value to the right of the operator must be a plain value, and its type must match that of the success value on the left.

Panic on exception

Use the ? operator following any call to an exception-throwing function.

fn calc(n i32) i32 {
  factorial(n)? + 10;
}

This checks whether the function call succeeds and returns a value. If so, it adds 10 to that result and returns it. Since this function gives no clue on how to handle an exception, the default behavior on a thrown exception will be that the program panics and shuts down.

Exception propagation

Another approach involves re-throwing the exception to the next caller up the call stack.

fn calc(n i32) i32 throws bool {
  factorial(n)? + 10;
}

Even though this function still does not specify an exception handler, its signature shows that it also throws exceptions. As a result, if the call to factorial throws an exception, that exception will be re-thrown to the function which called calc. Importantly, there must be a type match between the exception value received and the one the function re-throws.

catch exception handlers

If we want some other behavior than panic or re-throw, one or more exception handlers must be specified in the form of a catch blocks. This block appears at some point after the try, but need not be immediately afterwards.

fn calc(n i32) i32 {
  factorial(n)? + 10;

  catch {
    0;
  }
}

Should the call to factorial throw an exception, the catch block handler will be run. In this case, it returns the number 0. In effect, we have completely recovered from the thrown exception, as this calc itself throws no exception.

Alternatively, we could handle it by throwing an exception of a different type or value.

fn calc(n i32) i32 throws i32 {
  factorial(n)? + 10;

  catch {
    throw 0;
  }
}

If we need more information about the exception, a variable name (and optionally a type) may also be specified on the catch statement. This binds to the exception value, so that it may be interrogated: 

fn calc(n i32) i32 throws i32 {
  factorial(n)? + 10;

  catch err {
    if err {
      panic("factorial failed");
    } else {
      throw 0;
    }
  }
}

This handler will trigger a panic if the thrown exception value is false. Otherwise, it will throw a new exception value of 0.

Results and throws

In the discussion of exception handling above, we introduced the idea that some functions can choose to throw an exception value on failure and a regular value on success. This is actually just a Result value being returned. Built-in language syntax just makes it clearer and simpler to work with such values:

  • A function whose return signature is i32 throws bool is another way to write a Result type: Result[i32, bool]
  • return 3 is equivalent to return Ok(3).
  • throw false is equivalent to return Error(false).

The ? and || operators

The ? operator (try) and || operator (or else) offer more concise and readable ways to perform various common patterns for applying pattern matching blocks against a Result value.

Comes back in …

  • Conditionals: match on numbers, ranges, or and guards, and covering every value.
  • Functions: writing the functions that return a Result.
  • Collections: Option, the enum a collection hands you when it may have nothing to give.
  • Moves in depth: an enum with a variant that moves is moved, not copied.
  • Substitution and Extensibility: traits, open sets of variants, and extending an enum.
  • Namespaces: folding an enum's variants into a module.
  • Generativity: generic enums such as Option[T] and Result[T, E].
  • Talking to C: enums that line up with a C library's constants.
