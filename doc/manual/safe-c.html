Cone
Talking to C

Note: A C-named function passes a struct by value as C does on x86-64 (Windows, Linux and macOS) only, not yet on WebAssembly.

Much of the world's useful code is written in C, and a Cone program often needs to call it: a graphics library, an operating-system service, a compression routine. Code in C may in turn need to call back into Cone. This page covers the mechanisms that reach beyond Cone itself: extern, for what is defined in another compiled unit — a separately built Cone package, or code written in another language such as C — the @c attribute that spells names as C spells them, and the C-named module that holds a binding to a C library. (Reaching another Cone module is the business of import, covered in Namespaces.) Because Cone has no way to assure that another language has been as rigorous as Cone is about safety, a call to an extern function is one of the things trust exists for.

extern

extern says one thing: this function, method or global variable is defined elsewhere, in another compiled unit, so it is declared here without a body or a value, and the linker finds its definition. It says nothing about how the symbol is spelled. That is the module's to say: in an ordinary module a declaration has a Cone name, and in a module marked @c it has a C name.

It is written in front of a declaration, or of a block of them:

pub extern fn addOne(n i64) i64;
extern imm hits Atomic[u64];

pub extern {
  fn printStr(str &str);
  fn printInt(nbr i64);
}

A pub before a block reaches every declaration in it. A declaration may be private: an include file declares the private names a public inline body reaches, since that body is compiled into the importer, which then needs them. A function with a body, or a global with a value, is an error in an extern declaration. A thread-local global is declared with its attribute, extern mut @threadlocal depth i64;, and may name a C thread-local in a @c module as well as a Cone one.

Methods and operators

Inside a type, extern fn declares a method, a static function or an operator that is defined elsewhere:

pub struct Acc {
  pub total i64;

  pub extern fn plus(self, n i64) i64;
  pub extern fn `+`(self, other Acc) Acc;
  pub extern fn zero() Acc;
}

Such a method meets a trait's requirement like any other. What a user needs the body of cannot be extern, and is an error: an inline or generic function, a trait's methods, a generic type's methods. They are written whole, and compiled where they are used. A type's fields are part of its value, and are declared as they are.

Associated types

Not uncommonly, external functions and variables depend on custom types and constants defined by the external library. If so, these types are declared beside the extern declarations, in the same module: an extern block holds functions and variables only. Constants can be defined using an enum. If the internal field structure of a type is unknown, an opaque struct may be used. Marking an external function trustable, so that a call to it that passes a pointer needs no trust block, is not built yet.

extern in a file of its own

It can be helpful to put the extern declarations for some C-compatible library (e.g., libcurl or sdl2) into a file of its own. Placed in a module's folder, that file is one of the module's files like any other, so every file of the module can use its declarations. A C-named binding is a module of its own, since @c is on its mod line.

C names: @c

Code written in C is reached the same way, with its names spelled as C spells them. @c says so, and is written after the keyword of a mod line or a fn, in one of four forms: @c, @c("text"), @c(system) and @c("text", system).

On a mod line it makes the whole module C-named: its functions and global variables take their names unchanged, after the prefix the string gives. A C library's binding is such a module, and everyone else imports it and sees Cone:

mod @c("SDL_") sdl;

pub extern {
  fn Init(flags u32) i32;                    // the C function SDL_Init
  fn Quit();                                 // SDL_Quit
  fn @c("IMG_Load") LoadImage(file cstr) *u8; // a name outside the prefix
}

On a fn it gives that one function a C name: bare, its own name; with a string, the string is its whole symbol and no prefix is added. That is how a name outside a module's prefix is reached, and how a C function is declared in an ordinary module:

pub extern fn @c abs(n i32) i32;

A bare @c on a function its module already gives a C name says nothing, and is an error; the string form is fine there. system selects the platform's system calling convention (stdcall on 32-bit Windows), for the function or for every function of the module; an extern one is also imported from a DLL:

extern fn @c(system) GetTickCount() u32;

@c goes only where there is one symbol to name. It is an error on a type, on an anonymous, generic or inline function, and on a trait's or a generic type's method. In a C-named module a type's methods, and a generic function, keep Cone names. extern system, the older spelling of the system convention, is an error that names @c(system).

C-named modules

A module's declarations are spelled with Cone names by default: the name the linker sees carries the module, and the type, it is declared in. A module is C-named by writing @c after mod: its functions and global variables then take their names unchanged, as C spells them, after the prefix a string gives, and @c(system) gives its functions the platform's system calling convention.

mod @c("SDL_") sdl;

pub extern fn Init(flags u32) i32;      // SDL_Init

This is what a binding to a C library is: a module whose names bind to the library's symbols, imported like any other and reached as sdl.Init. Naming, and the C calling convention that comes with a C name, are the only things it changes about its declarations (and it has no prelude, below): whether each declaration is defined elsewhere is its own extern, and a C-named module may hold bodies too, which it compiles and publishes under C names when they are pub. A type's methods and a generic function keep Cone names, since a C name has no room for an owner or type arguments. Such a module, alone in its package, is a C package, whose manifest names the C library to link.

A C-named module does not import core automatically, as every other module does: it declares what a C library defines, in C's types, and core itself imports one, libc. So core's names, such as Option and malloc, are not in reach in it unless it imports core itself, and declaring one of them there is no clash.

Exporting to C

A Cone function with a body is published to C under a C name by writing pub and @c: the symbol is then external, so C code links against it. Without pub it is still spelled as C spells it, but stays private to its object. The same holds for the bodies of a C-named module.

pub fn @c("cone_square") square(x i64) i64 { x * x; }

fn @c("main") start() i32 {    // the program's entry, under another Cone name
  0i32;
}

Structs by value: C's calling convention

A function a module gives a C name is called as C calls it, and calls C as C expects. Where it takes or returns a struct by value, the struct is passed the way the platform's C compiler passes the same C struct, so a Cone struct laid out as C lays out the struct crosses either way unchanged: to an extern function C defines, and into a Cone function C calls, directly or through a pointer to it that Cone handed C.

struct Vec4 { pub x f32; pub y f32; pub z f32; pub w f32; }

extern fn @c v4_sum(v Vec4) f32;       // float v4_sum(Vec4 v);
pub fn @c scaled(v Vec4, k f32) Vec4 { // C calls it: Vec4 scaled(Vec4 v, float k);
  new Vec4(v.x * k, v.y * k, v.z * k, v.w * k);
}

How a struct crosses is the platform's C ABI. On 64-bit Windows a struct of 1, 2, 4 or 8 bytes crosses as one integer of its size, whatever its fields (floats too). Any other size is passed as a pointer to a copy the caller made, and is returned through a pointer to the caller's result slot, which C passes as a hidden first parameter. The Vec4 above is 16 bytes, so it crosses by pointer both ways; a struct of two i32s is one 64-bit integer. On x86-64 Linux and macOS (System V) a struct of up to 16 bytes is passed in registers, each eightbyte of it in an integer register if any integer or pointer is in it and in a floating-point register if it holds only floats: the Vec4 above travels in two floating-point registers, a struct of an i32 and an f64 in one of each, and a result likewise comes back in registers. A larger struct is copied to the stack, as is one that finds too few registers left, and a larger result comes back through the caller's result slot. The C library's own div and lldiv return a struct each way:

struct DivT { pub quot i32; pub rem i32; }      // C's div_t: 8 bytes, returned as one integer
struct LldivT { pub quot i64; pub rem i64; }    // C's lldiv_t: 16 bytes, returned through a result pointer

extern fn @c div(numer i32, denom i32) DivT;
extern fn @c lldiv(numer i64, denom i64) LldivT;

fn main() {
  imm d = div(17, 5);          // d.quot is 3 and d.rem is 2
  imm l = lldiv(17i64, 5i64);  // so are l.quot and l.rem
}

The same holds for bool, which is C's bool: an argument or a result crosses as one byte holding 0 or 1, widened in its register as the platform's C compiler widens it, and a bool field of a struct is one byte holding 0 or 1, as a C bool field is. An integer narrower than C's int is widened by its sign as C widens it on that platform. A bool, and an 8- or 16-bit integer, cross as C's do on 64-bit Windows, x86-64 Linux and macOS, and WebAssembly.

extern fn @c SetWindowFullscreen(window *Window, fullscreen bool) bool;  // bool f(Window *, bool);

A slice, a tuple or an array is not a C type, and passes as Cone passes it: a slice's pointer and length arrive as two arguments, as a C function's (char *, size_t) takes them.

A reference to a C-named function, and a pointer C hands Cone, are called as C calls them: their type is &fn @c (sig), which a Cone function's &fn(sig) is never taken for (A reference to a C-named function). A callback parameter C calls is typed so, and the Cone function handed to it is fn @c. A type's method named with @c keeps Cone's convention, since a vtable calls it by its Cone signature.

Fine-tuning

These parts are rarely needed: the first by those who publish a Cone package for others to link against, the second by those who declare the same C function in several places.

Declaring a Cone package

A package compiled on its own is reached through an include file: the package's root module, with everything its object defines declared extern, and its types, macros, inline bodies and generics written in full. The include file's module is an ordinary, Cone-named module of the package's name, so each extern declaration is spelled exactly as the package defines it, and the two objects link. It is Cone source, named for the package: stdio's is build/debug/stdio.cone in a program Congo builds, generated by compiling stdio, which declares the globals print and eprint and the methods of their type IOStream, all defined in stdio's own object.

Compiling a package as a library writes its include file, name.cone, beside the object. It is the package's own source with what a program does not need taken out: each body the package's object holds is left out and its declaration marked extern, each private declaration nothing a program expands reaches is left out, and everything else, comments included, is kept as written, under a comment saying the file is generated and is not to be edited. A global whose type the source leaves to be inferred has its type written in. Where the include file's lines stop being the source's, a comment such as //#line 24 "loc.cone" says the line after it is line 24 of the package's loc.cone, so an error or a panic in code a program compiles from the include file names the package's source file and line. Congo compiles each package before what imports it, and every importer against the include file that compile wrote, the packages that come with Cone included; an include file may still be written by hand where a build description names one.

What the package's root reaches in one of its submodules — a type a public function names, a function an inline body calls, the names a pub use re-exports — is declared in a nested module block inside the include file, holding only what is reached, edited the same way:

mod coll;

mod vec {
pub struct Stack {
  pub len i64;
  a i64;

  pub extern fn push(self, v i64) Stack;
}

pub extern fn stackOf(x i64, y i64) Stack;
}

pub use vec Stack, stackOf;

pub extern fn countOf(s &vec.Stack) i64;

Each name in a block is spelled after the submodule that declares it, as the package's object spells it. A block is private to the package: a program reaches Stack as coll.Stack, through the root's pub use, and cannot name coll.vec. A submodule nothing reaches has no block, and a generic submodule's block holds its whole text. Only a generated include file — one an import line names that opens with the generator's comment — may hold a module block; in source, and in an include file written by hand, a module is never declared inside a file.

An include file opens with its mod line and its imports follow, as in any module file. A package whose public functions take or return another package's types imports that package in its include file, as it does in its source. A program importing the first package can then use those values, their fields and their methods; it names the second package only if it imports it too, or if the include file's import says pub.

A global the package folds through is declared extern with the source's fold clause, as in pub extern mut config Config pub use *;, so the names the fold puts into the package are names of the include file too.

A generic function or type is written whole because each program makes the instances it uses, from that body: the package cannot know which type arguments its users will give. The package's object holds the instances the package itself uses, and the program's object holds the ones it uses; where both use the same one, say larger[i64], both objects define it, and the linker keeps one copy. Any private function the generic's body calls is declared extern in the include file, as for an inline body.

pub fn larger[T](a T, b T) T {
  if a > b {a;} else {b;}
}

pub struct Pair[T] {
  pub a T;
  pub b T;

  pub fn sum(self) T {a + b;}
}

A package whose root module is a generic module, mod g[T];, is reached the same way: its include file is the generic module's whole source, and each package or program that uses an instance, say g[i64], compiles it. The copies merge at link, globals included, so the instance has one set of globals however many objects use it. A package's include file shows its root module alone, so a generic module inside a package is not yet reachable from outside it.

One C name, one symbol

C has one namespace for its symbols, so a C name means the same thing wherever it is declared. Several modules of one program may each declare the same C function, and they all call the one function:

mod geometry;

extern {
  fn @c abs(n i32) i32;     // also declared by the module that contains this one
}

Every declaration of one C name must agree: a function in its parameter and return types and its calling convention, a global in its type and its permission. Two that do not are an error, as C's "conflicting types" is, and the error names both. One of them may have a body, which is then the C name's definition, and the others are declarations of it; two bodies under one C name are an error too. A private C-named function is not among them: it stays private to its module, and a C function of the same name declared elsewhere is still reached. The compiler checks the modules it compiles together; between packages compiled separately, the linker does.
