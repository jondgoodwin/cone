Cone
Platforms and Targets

Note: This page gathers what the manual already says, in status notes and in the library pages, about where Cone code runs. It adds nothing of its own: each entry names the page it comes from, and that page is the authority. Where this page and one of those disagree, the other page is right.

Cone's compiler, conec, compiles for a target, named by a target triple: the host's own, or the one --triple or --wasm names. Most of the language is the same on every target; this page lists the places the manual says it is not, so that a program (or a package) knows which targets to expect it to build for.

Windows and Linux

These two, on x86-64, are where the manual says things run. Each of these is stated as running on both:

  • Threads, locks, channels and actors. The thread and sync packages, and so the locks, the channels and the actors built on them, run on Windows and Linux (x86-64). The actors package likewise. Source: the status notes of Roll your own: threads, atomics and locks and Actors in depth.
  • I/O. iocore (sockets, timers, files, cancel groups and the blocking pool), iobuf, aio, actorhttp and the HTTP and TLS packages over them run on Windows and on Linux. The loop is an I/O completion port and Winsock on Windows, epoll on Linux. Source: I/O in depth, Time, HTTP.
  • Files, paths, environment, processes. path reads the paths of the system the program is built for (Windows' drive letters, shares and both separators; or POSIX's one separator and root); fs and env are written over ISO C and the posix package, which is the C library's own POSIX functions on Linux and maps the POSIX names onto the Windows C runtime on Windows; process is written directly over kernel32 on Windows and over posix_spawn, pipes and poll on Linux. Where the two behave differently it is said where the function is described. Source: Files, paths and processes.
  • Time. time calls the operating system for one thing, Instant.now(): QueryPerformanceCounter on Windows, clock_gettime on Linux, chosen when the program is compiled. Source: Time.
  • TLS. tls asks the operating system whether a server is who it says it is: on Windows its certificate verifier (crypt32), on Linux OpenSSL's own check against the system's roots. On Windows, Congo copies OpenSSL's two libraries beside any program that imports tls or httpclient; on Linux those programs link the system's OpenSSL 3 (libssl-dev on Ubuntu). Source: HTTP.
  • C structs by value. On 64-bit Windows a struct crosses as one integer if it is 1, 2, 4 or 8 bytes and otherwise by pointer; on x86-64 Linux (System V) a struct of up to 16 bytes is passed in registers. Source: Structs by value.
  • The standard library's packages. The library catalogue has a section, "Where they run", saying which packages run on Windows and on Linux, which call nothing of the system's, and which have been run on Linux so far. Source: The Standard Library.
  • Linking. What differs by system in a package's link libraries goes in a section of the manifest's [link] table: [link.windows], [link.linux] and [link.macos]. Source: Packages and the build.

macOS

The thread and sync packages, and so the locks, the channels and the actors built on them, and the actors package, run on Windows and Linux (x86-64), not yet on macOS (Roll your own: threads, atomics and locks, Actors in depth). A version of path, fs, env and process for macOS would change their insides, not what a program calls (Files, paths and processes). What the manual does say about macOS is that a C-named function passes a struct by value as C does on x86-64 macOS, as it does on x86-64 Linux (Structs by value), that a target triple naming darwin or macos makes isMacOS() true (below), and that [link.macos] is a link section.

WebAssembly

A WebAssembly target is named with --wasm (or a WebAssembly triple). What the manual says about it:

  • No C struct by value yet. A struct crosses as C passes it on x86-64 (Windows, Linux and macOS) only, not yet on WebAssembly. A bool, and an 8- or 16-bit integer, cross as C's do on WebAssembly too. Source: Structs by value.
  • Pointer-sized numbers are 32 bits. usize and isize are 64 bits on some targets and 32 on others, such as WebAssembly, so neither may be reinterpreted as a fixed-width number type; convert the value instead. Source: Type Reinterpretation.
  • Barriers are nothing. A GPU workgroup's barriers do nothing on WebAssembly. Source: Intrinsics, The GPU.
  • No entry from the compiler. A WebAssembly or GPU module gets no entry (runner of every module's initializer and finalizer) from the compiler. Source: Global state and initialisation.

SPIR-V and the GPU

Compiled for a GPU, the entry points of a module are written as SPIR-V's Vulkan form: conec --triple=spirv1.6-unknown-vulkan1.3 writes <name>.spv. SPIR-V's OpenCL form (--triple=spirv64-unknown-unknown) has kernels of another kind, and a compute entry point compiled for it is refused. Not implemented: any GPU target but SPIR-V's Vulkan form. A SPIR-V triple makes none of the OS tests below true. Source: The GPU (its status note and its first section on compiling for a GPU).

Choosing by target in your own code

Core has constants of the compile that say which OS the compile targets, read from its target triple with no flag: isWindows() (a triple naming windows, such as x86_64-pc-windows-msvc), isLinux(), isMacOS() (one naming darwin or macos) and isWasm(); at most one holds, and none for a SPIR-V triple. An if on one of them has only the side the build takes generated, so a program links without the other platform's functions. This is a provisional mechanism: its final design is open. The full description, with its caveats, is under Constants of the build.
