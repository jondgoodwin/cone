parallel each

Some work is one big job made of many small ones that do not depend on each other: the same test for every number in a range, the same change to every order in a list. Put the word parallel in front of an each, and every core of the machine works on the loop at once. There are no threads to start and no work to share out by hand: it is the loop you would have written anyway. Here it finds the primes below a million:

mod primes;

import stdio use *;
import collections use *;
// parallel each runs on the same worker threads as actors
import actors;

// Is n a prime? Try every divisor up to its square root
fn isPrime(n u64) bool {
  mut d = 2u64;
  while d * d <= n {
    if n % d == 0 { return false; }
    d += 1;
  }
  true;
}

fn main() {
  // Every core tests numbers at once, and the list keeps
  // the primes in order, as a plain each would
  imm primes = new List[u64] <- parallel each n in 2u64 ..< 1000000u64 if isPrime(n) yield n;
  print <- "There are ", primes.len(), " primes below a million\n";
  print <- "The largest is ", primes[primes.len() - 1], "\n";

  // Adding them all up, on every core too
  print <- "They add up to ", primes.parallel().sum(), "\n";
}

It prints:

There are 78498 primes below a million
The largest is 999983
They add up to 37550402023

Try this: take the word parallel out of the loop, and the answers stay the same, with one core doing all the work. Then search below ten million, with and without it. On a 16-core laptop, the parallel loop takes about half a second, and the plain one about five.

One loop, every core

A parallel each suits work where each pass stands on its own. Whether 7919 is a prime has nothing to do with whether 7920 is, so the numbers can be tested in any order, on any core, all at once.

You do not say how to split the work. The loop starts as one piece covering the whole range, and a worker with a big piece cuts it in half and leaves one half for an idle worker to take. So the work spreads evenly even when some passes take longer than others, as testing a big number takes longer than a small one. When the program reaches the statement after the loop, every pass has finished.

The if after the range keeps only the numbers it holds for, as it does in a plain each. And the list is built just as Collections built one, with parallel in front of the each: each piece of the loop collects its own primes, and the pieces are joined in order at the end, so the list is the one a plain loop would have made, whichever pass finished first.

Getting the results out

Because the passes really do run at the same time, a pass may not change a variable declared outside the loop: if two passes added to one total at the same moment, one of the additions could be lost. The compiler refuses it, and says what to do instead:

mut total = 0;
parallel each n in 0 ..< 1000 {
  total = total + n;                 // refused
}

A 'parallel each' body may not write total, which is declared outside the loop: the passes run at the same time. Outside variables are read-only for the loop. Hand results back with the parallel builder, or 'mutItems()' on the items, or count with an Atomic.

The program above uses the parallel builder. A total such as the sum of the primes is a reduction, which boils a whole list down to one value: primes.parallel().sum() has each core add up a stretch of the list, and then adds the stretches' totals together. The stretches are cut by the list's length alone, so the answer is the same on every run, on any machine. An Atomic is a number that every pass may add to safely, and Concurrency has it.

Changing every item at once

Sometimes the job is not to find anything, just to update everything. Back at the bakery, the year ends with ten percent off every order of $50 or more:

// A made-up year of the bakery's orders: what each customer spent, in dollars
mut orders = new List[i32] <- each i in 1 .. 100000 yield i % 90 + 3;
print <- "Takings: $", orders.parallel().sum(), "\n";      // Takings: $4749610

// Ten percent off every order of $50 or more, all at once
parallel each o in orders.mutItems() {
  if *o >= 50 { *o -= *o / 10; }
}
print <- "After the discount: $", orders.parallel().sum(), "\n";   // $4430753

mutItems() gives each pass one order of its own to change, and no two passes are ever given the same one, so they can all change their orders at once. o stands for the order where it sits in the list, not a copy of it, and *o reaches through to the order itself; references like this one come later, in Memory.

Actors or a parallel each?

Both put every core to work, and they suit different shapes of work. When the job is the same thing done to many items, with nothing to remember between them, a parallel each is the simplest thing to write. When the work falls into parts that each keep their own state and have an ongoing job, like the stock room, give each part to an actor. The two mix: a behaviour may run a parallel each over its actor's own data (below), and a pass may send a message to an actor.

One loop on every core

import actors;

fn total(xs &Array[u64]) u64 {
  imm sum = Atomic[u64].of(0u64);
  parallel each x in xs {
    sum.add(weigh(*x));
  }
  sum.load();               // every pass has finished
}

The loop has finished when control reaches the statement after it. The work is split as it runs: whoever runs a piece splits it in half while it is big, queues one half and works the other, and an idle worker takes the oldest, largest half. So uneven passes spread themselves, and the code that wrote the loop works on pieces of its own loop while it waits. A module that writes one imports actors.

The filter, parallel each x in xs if cond { … }, skips the items for which the condition is false, as it does for each. A parallel each takes no else and is a statement. (Writing a parallel each.)

From Writing a parallel each: parallel is a word only directly before each: anywhere else it is a name like any other (a variable, a function, a field).

What it can walk

The source must be something that can be cut into independent pieces and says how big it is: a number range counting up by one (parallel each i in 0 ..< n), an array, a slice, a list, and the runs chunks(n) and mutChunks(n) give. A cursor, a generator, a file or a channel hands out its items one after another and cannot be split: collect it into a list first, and walk the list. As in an ordinary each, the variable is a new one on every pass. (What it can walk.)

What the body may do

The passes run at the same time, so the body keeps rules an ordinary each does not:

  • What is declared outside the loop is read-only in it. Writing it is refused. What the pass declares itself is its own to change.
  • A pass may change its own item: parallel each x in list.mutItems() gives each pass its own item to change, and the items are disjoint.
  • Results come back through something that is changed by its methods, an Atomic, as above, or as a list the loop builds (below).
  • A value from outside that holds an Rc may not be named in the body: copy what the loop needs into a local before it. An Arc, an Atomic and a number are free. (This is the marker Shareable, Sendable and Shareable.)
  • continue skips the rest of a pass. A break, a return and an await are refused.
  • A message sent to an actor is allowed, and is sent after the loop, in iteration order, so an actor sees the same order every run.

Each rule, and how a loop fills a buffer a row at a time with mutChunks, is in What the body may do and Filling a buffer.

Building a list, and adding up

A list is built by a parallel each as it is by an each inside <-: put parallel in front of the each, and give the value each pass appends with yield. The list holds the values in the order a plain each would give them:

imm weights = new List[u64] <- parallel each x in xs yield weigh(*x);

A result such as a total is a reduction, a method called on parallel():

imm total = xs.parallel().sum();                 // the total of the numbers (0 for none)

(The parallel builder, Reductions, which also fold and find.)

From The parallel builder: The list holds the values in the order of the passes, the order a plain each would give them, however the passes were spread over the workers; with a filter, the values of the passes that kept their items, in order. The loop has finished, and the list is whole, when control reaches the statement after it. Only a List is built this way. A dictionary or any other collection is built from a list of pairs after the loop.

From Reductions: The result is the same on every run, with any number of workers, a float sum included: the items are cut into runs by their count alone (at least 128 items to a run, and at most 256 runs; a view of 128 or fewer is one run, folded at once on the caller's thread), each run is folded front to back, and the runs are joined by halving. So a float sum is not the plain loop's last bits, and is identical from one run, and one machine, to the next.

In an actor's method

From In an actor's method: A parallel each written directly in a behaviour (a method declared async do) cuts the behaviour where the loop ends, as an await does. The behaviour returns to the actor's dispatcher while the passes run on the workers, and the rest of it runs when the last pass has finished:

actor Scaler {
  vals List[u64];
  scale u64;

  pub async do run(self, add u64) {
    imm k = add * 2u64;
    parallel each v in vals.mutItems() {
      *v = *v * scale + k;      // the actor's fields are read through self; k and add are carried
    }
    // here the loop has finished, and this is the same behaviour, the same call
  }
}

The actor is not run again until the loop has finished, the rest of the behaviour included. Its mailbox goes on accepting messages, and they are handled after the behaviour, in order. (The rest: In an actor's method.)

Testing your code: congo test

A program you can change with confidence is one whose behaviour is pinned down by tests, and a Cone test is just another small program. It lives in the tests folder of the package it tests, imports that package, makes some checks with the testing package, and returns what done gives:

mod arith;

import testing use *;
import mylib;

fn main() i32 {
  expectInt(mylib.sum(2, 3), 5, "sum of 2 and 3");
  expectFloat(mylib.mean(1., 2.), 1.5, 0.000001, "mean of 1 and 2");
  expect(mylib.isEven(4), "4 is even");
  done();
}

Beside it, tests/arith.out says what it must print, here 3 checks passed. Run congo test in the package's folder, and it builds the package, runs every test, and compares what each printed with its .out file:

        test arith ... ok
      Result mylib: 1 test: 1 passed, 0 failed; 0 examples: 0 built, 0 failed to build

Every check, what a failing one prints, and the files beside a test are in Testing.
