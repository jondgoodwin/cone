Cone
Values, variables and expressions

Every program works with values: it names them, computes new ones from old ones, and hands them around. This page shows how Cone does each of those, by working out the numbers for a day's drive.

// Values, variables and expressions
//
// A day's drive, worked out: numbers and their types, imm and mut,
// a named constant, operators, a block that gives a value,
// and which values copy and which move.

mod values;

import stdio use *;
import collections use *;

const kmPerMile = 1.609344d;

fn main() {
  // imm: a variable that never changes. Its type, f64, comes from the literal
  imm miles = 420d;
  imm km = miles * kmPerMile;
  print <- miles, " miles is ", km, " km\n";

  // mut: a variable that may change. Its type may be written out
  mut minutes i32 = 0;
  minutes += 7 * 60;        // seven hours of driving
  minutes += 3 * 25;        // three stops of 25 minutes
  ++minutes;                // and one to find the car keys
  print <- "on the road: ", minutes / 60, " h ", minutes % 60, " min\n";

  // One number type becomes another only when asked
  imm hours = f64.from(minutes) / 60d;
  print <- "average speed: ", miles / hours, " mph\n";

  // A block is a value: the value of its last statement
  imm fuel = {
    imm gallons = miles / 32d;
    gallons * 3.45d;
  };
  print <- "fuel: about $", fuel, "\n";

  // Two drivers trade places in one statement
  mut driving = 1;
  mut resting = 2;
  driving, resting = resting, driving;
  print <- "driver ", driving, " takes over from driver ", resting, "\n";

  // Numbers copy: changing the copy leaves the original as it was
  mut odometer = 12000;
  imm start = odometer;
  odometer += 420;
  print <- "odometer: ", start, " to ", odometer, "\n";

  // A String, text that grows, moves instead: it has one owner at a time
  imm plan = String.from("day two: the coast road");
  imm today = plan;         // plan's text moves to today
  print <- today.view(), "\n";
  // print <- plan.view();  // Error: plan's value has moved to today
}

It prints:

420 miles is 675.924 km
on the road: 8 h 16 min
average speed: 50.8065 mph
fuel: about $45.2812
driver 2 takes over from driver 1
odometer: 12000 to 12420
day two: the coast road

What to notice

  • Each variable is declared imm (it never changes) or mut (it may). The type may be written after the name, as minutes i32, or left for the compiler to infer from the value.
  • A suffix on a literal says its type: 420d is a 64-bit float, an f64. A whole number with no suffix is an i32.
  • minutes / 60 divides two integers, so the answer is a whole number; % gives the remainder. To divide an integer by a float, it is first converted: f64.from(minutes).
  • A block in braces has a value, that of its last statement, and its own variables, such as gallons, end with it.
  • driving, resting = resting, driving; assigns both at once, so the two values swap.
  • A number copies; a String moves. Remove the // from the last line to see the compiler refuse to use plan after its text moved.

Naming a value: imm and mut

A variable is a name for a value. Cone asks you to say, each time you declare one, whether the value may change. imm (immutable) says it never will: miles is 420 for as long as it exists, and an attempt to assign it again is refused before the program ever runs. mut (mutable) says it may: minutes starts at zero and is added to as the day goes on.

A variable's declaration always begins with one of the two words, so a reader can always see, at the declaration, which values hold still. Most of a program's values turn out not to need changing, and writing imm for them makes the ones that do stand out. If you know JavaScript, imm and mut play the parts of const and let. Cone has a const too, for something different: a name for a value that is fixed when the program is compiled, such as kmPerMile, declared at the top of the file.

Every value has a type

Every value in Cone has a type, known when the program is compiled. Usually you need not write it, because the compiler infers it from the value: miles is an f64 because 420d is. Where you want a particular type, you can write it after the name, as minutes i32 does, or on the literal, as a suffix.

The number types say their size in their name: i8 to i64 are signed integers, u8 to u64 unsigned ones, and f32 and f64 floating point. A whole-number literal with no suffix is an i32, and one with a decimal point or an exponent is an f32; d makes it an f64, and u8, i64 and the rest may be written after a number too.

imm small = 65u8;      // u8
imm count = 1_000_000; // i32: underscores are ignored
imm ratio = 3.14159;   // f32
imm precise = 1d;      // f64

Types are strict. Where a value of one number type goes into a larger type of the same kind, an i32 into an i64 or an f32 into an f64, nothing can be lost and Cone widens it for you. Anything else must be asked for. An integer is not a float, so minutes / 60d is refused: the program asks for the conversion by name, f64.from(minutes). Every number type has a from that takes any other number, and the name says plainly where a value changes type. Even assigning 24.0 to minutes is refused, because minutes holds integers.

Computing new values

An expression combines values with operators to make a new one, and the operators are the ones you know: + - * / %, with the usual precedence, and parentheses to change it. Division of two integers gives a whole number, rounding toward zero, which is why minutes / 60 is 8 and minutes % 60 the 16 minutes left over.

A mut variable can be updated in place: minutes += 75 is minutes = minutes + 75, and -=, *= and /= work the same way. ++minutes adds one. And several variables can be assigned in one statement, each taking the value in the same position on the right. Because every value on the right is worked out before any variable changes, driving, resting = resting, driving swaps the two, with no temporary variable to hold one of them on the way.

A block is a value

Braces group statements into a block, and in Cone a block is itself an expression: its value is the value of its last statement. That lets a calculation that needs a few steps, and a scratch variable or two, be written right where its answer is wanted. gallons exists only inside the block that computes fuel; when the block ends, so does it, and nothing outside can use it by mistake.

The same rule gives a function its result. A function's body is a block, so its last expression is what it returns, with no return needed: the pi program on the first page ends with result * 6d;. if and match are values the same way, on the next pages.

Copy or move

Assigning a number, or handing one to a function, copies it. start is a copy of odometer, so adding to odometer afterwards leaves start at 12000. Most values in Cone behave like this.

Some values should never exist twice, because they own something: a String owns the memory its text is kept in. Two copies would each believe the memory was theirs to change and to free. So a value like this moves instead. imm today = plan; hands the text to today, and plan has nothing left: the compiler refuses any later use of it, with "This variable's value has been moved out." There is only ever one owner, so Cone knows exactly when the text is no longer needed, and frees it then, with no garbage collector and nothing for you to free by hand.

Whether a value copies or moves is decided by its type, not by how it is used. Numbers copy. A type moves if it says so, if it has a finalizer, or if anything it holds moves; you will meet such types again with text, structs and collections. That is all a program needs to know about moving for now. Moves in depth has the rest.

In detail

The rest of this page is the complete reference for values, variables, numbers, expressions, blocks and conversions; skip to the next page if the program above was enough.

We begin with literals and variables, two basic building blocks for any expression. Along the way, additional concepts will be introduced, such as types, variable declarations, assignment, and scope.

imm height = 1.86;     // a variable that never changes: f32 is inferred
mut age = 23;          // a variable that may change: i32
age = 24;
const pi = 3.141592;   // a named constant

Literals

A literal is a specific, unchangeable value. Each of these numbers is a literal:

123
3.14159
1e6          // 1000000.0
-1_000_000   // underscores are ignored
0x1000       // Hexadecimal

Beyond numbers, other forms of literals will be introduced later, including:

  • string and character literals (e.g., "Hello" and 'a')
  • boolean true and false
  • struct, array, and other compound values

imm and mut

A variable is like a named container which holds a value of some specific type.

Variable declarations

Before a variable can be used, it must first be declared and initialized. This example explicitly does both:

imm height f32 = 1.86;

Let's examine each part of this variable declaration statement:

  • imm at the beginning announces that this statement is a variable declaration. It also indicates that the variable is immutable: once given its initial value, it can never be given a different value.
  • height is the name of the variable. A variable name is an identifier which typically begins with an alphabetic letter, followed by letters or numbers. Underscores are also permissible.
  • f32 is the variable's declared type. The variable can only hold values of this type.
  • Following the = is an expression that establishes the initial value for the variable. In this example, height's value is 1.86.

When an initial value is specified, the type can usually be omitted. It will be inferred, as this example shows:

imm height = 1.86;     // f32 type is inferred
imm width  = height;   // its value is 1.86 and type is f32

Notice that the second statement makes use of the variable 'height' after it has been declared and initialized.

Mutable Variables

What if we need to change a variable's value after initialization? To allow that, use mut (instead of imm) on the declaration statement: 

mut age = 23;      // type is i32
// ... some statements here ...
age = 24;          // alters age to hold 24 instead

Just enough: mut and imm are called permissions. Cone supports a number of other permissions. These are discussed more fully on the Permissions page.

Note: If we had tried to re-assign age to 24.0, we would have gotten an error message. This is because age is declared to only hold integer values, and 24.0 is a floating point number. Type safety of variables requires that the expression's type be the same or coerceable.

Types you can name

Every value has a type it belongs to. A type is a pattern that:

  • Establishes all permissible values. Thus, the bool type only supports true and false as values. Integer types only support integer number values. Floating point types support floating point number values, and so on.
  • Determines how values are digitally encoded, including how many binary bits are needed to encode them.
  • Specifies what operations can be performed on values of that type. For example, an integer type permits two integers to be added together, the result of which is another integer value. These type operations are called methods.
  • Enforces constraints that ensure the type's values are handled consistently and safely.

Every value in a program has a type, known at compile-time due to an explicit declaration or because the type can be easily inferred based on the context. By knowing the types of all values, the compiler can optimize a program's performance and memory use. Clear typing facilitates precise, flexible data manipulation and improves the safe and correct use of data.

The names of specific types are capitalized by convention. This helps cleanly distinguish variable names from type names, reducing unexpected naming conflicts and improving code clarity. One notable exception to this naming convention is the type names for the primitive numeric types.

Besides the numbers below, two more types are built in. bool holds true or false. Text is built of char, a Unicode code point (character literals), which is compared but is no quantity. And void is the type of no value at all: the return type of a function that returns nothing. The whole repertoire of types is listed at the end of this page.

Integers and floats

The built-in number types specify their bit-size as part of the type's name. Here they are:

  • Signed integer types: i8, i16, i32 and i64
  • Unsigned integer types: u8, u16, u32 and u64
  • Floating point types: f32 and f64

Later, a number of other types will be introduced.

Typed Number Literals

To explicitly specify the type for a numeric literal, append the type name right after the number:

65u8       // 8-bit unsigned integer
1f64       // 64-bit floating point number

If the type is omitted, the number is understood to be 32-bits. When the number explicitly includes a decimal point or exponent, it is treated as a floating point number (f32). Otherwise, it is considered to be a signed integer (i32).

3.14159    // f32 (because of the decimal point)
1e6        // f32 (because of the exponent)
1_000_000  // i32 (no decimal point or exponent)

Type name shortcuts are also supported:

1000u      // u32
1f         // f32
1d         // f64

An integer's bits

Every integer type (u8 to u64, i8 to i64, usize and isize) has methods that count and move its bits. Each count is a u32, and each is defined for 0, as the width:

x.countOnes()
How many of its bits are 1.
x.leadingZeros()
How many bits are 0 above its highest 1: the width, for 0.
x.trailingZeros()
How many bits are 0 below its lowest 1: the width, for 0.
0x2Cu8.countOnes()        // 3
1u64.leadingZeros()       // 63
0u32.trailingZeros()      // 32
(-1i16).countOnes()       // 16: a signed integer's bits, the sign's among them

The rest take an amount n, a u32, and use it modulo the width, so every amount has an answer and 0, the width and twice the width give the same one:

x.rotateLeft(n), x.rotateRight(n)
The bits moved by n, those shifted out of one end coming in at the other.
x.shlMasked(n), x.shrMasked(n)
A shift by n modulo the width: the shift most processors do in one instruction. shrMasked fills with the sign bit on a signed integer and with zeros on an unsigned one. The operators << and >> differ only past the width, where they shift every bit out (Shift operators).
0x81u8.rotateLeft(1)      // 0x03
1u32.shlMasked(33)        // 2, a shift by 1
1u32 << 33u32            // 0
(-16i8).shrMasked(10)     // -4, a shift by 2

The same operations are core's intrinsics, mem.countOnes(x) and the rest (Intrinsics), whose type parameter is any of these integer types.

Named constants

Constant literals can be given a name. For example: 

const pi = 3.141592;

With this declaration in place, any program reference to the name pi will substitute in the the corresponding floating-point constant literal value.

A constant's value may be an expression computed from constants alone: number literals, true and false, and other named constants, declared before it or after, combined by the arithmetic, bitwise and shift operators (+ - * / % | & ^ ~ << >>, and a prefix -), the comparisons, not, and and or, a number's conversion T.from(x), a reinterpretation with as, and parentheses. The constant is the literal the expression computes:

const Red = 0x1u32;
const Green = 0x2u32;
const All = Red | Green | Blue;    // 0x7u32
const Blue = 0x4u32;
const Half = 1.0f32 / 2.0f32;      // 0.5f32

Each operator gives the value it gives when the program runs, on the same type: an f32 is computed as an f32, integer division truncates toward zero, and << drops the bits shifted out. What has no value when the program runs is an error: a result its type cannot hold (255u8 + 1u8), a division or remainder by zero, and a float converted to an integer that cannot hold it. So is a shift by the type's width or more, or by a negative amount, although the running program gives one a value (Shift operators). So is a constant whose value names itself, directly or through other constants. A function call, a variable or a method like sqrt is not a constant, so neither is an expression using one. The same expressions may be written wherever a constant is required: a global variable's or a static's value, a parameter's or a field's default, and the elements of an array, struct or tuple literal in any of these.

A variant of an enum that holds no value is a constant: Kind.Os for enum Kind {Os, Cancelled, TimedOut;}, and None for an Option, whose other variant does hold one. It is its tag, and the rest of the enum's value, where it is wider than the tag, is zero. It may be a named constant's value, a global's, a parameter's or a field's default, or an element of an array, struct or tuple literal in any of these. A variant that holds a value is not, nor is a variant of an enum that has fields in common, whose value is no part of the tag.

enum Kind {Os, Cancelled, TimedOut;}

const Fallback Kind = Kind.TimedOut;
struct Failure {
	pub code u32;
	pub kind Kind = Kind.Os;       // left out of new Failure(5u32), it is Os
	pub next Option[i32] = None;   // and none; Some(5) is not a constant
}

A constant may name a compound literal too, such as an array, a struct or a tuple. Each use of it is that literal, so it may be used however the literal could be:

const primes Array[u32, 4] = [2u32, 3u32, 5u32, 7u32];

primes[n]          // an element, by a constant or run-time index
&primes            // a reference to the array, as &[2u32, 3u32, 5u32, 7u32] is

Note: Named constants of numbers, strings, arrays, structs and tuples are implemented, and so are the constant expressions above. A constant's elements and fields may be read, and a constant array or string, which is kept in read-only memory as its literal is, may be borrowed: as a reference or a slice, never mut, living as long as the program. No other constant may be borrowed, nor may a field of one or of one of its elements, since each use of it is a fresh copy with no place in memory, as its literal would be; that includes calling a method that takes a borrowed self on one. (Borrowed references explains borrowing.)

Delayed initialization and scope

Delayed initialization

It is often preferable to initialize a variable as part of declaration. When that is not realistic, initialization may be performed later using an assignment:

imm height f32;
// ... some statements here ...
height = 1.86;         // Initialize height now

An assignment essentially copies the evaluated value of the expression to the right of the = into the variable specified to the left. (Later, we will show that assignment can also be used to place values into structures that lie "within" a variable's value.) Any assignment is itself an expression, and may be used wherever expressions are allowed.

It is worth pointing out that any attempt to re-assign 'height' later to another value will trigger an error message:

height = 2.12;         // **ERROR** since height is immutable and initialized

Scope and Visibility

As we have seen, variables have a name, permission, type and value. They also have a scope and visibility. Scope and visibility restrict where a variable may be referenced and used in a program.

  • Scope is established by where the variable's declaration is found. Based on this position, the scope can be global, local to a function, local to a block, or a field in a type.
  • Visibility is declared, not spelled: a global variable or type field is private unless its declaration begins with pub. Visibility determines whether a global variable or type field is visible outside its owning namespace.

Operators and precedence

Note: All of this capability is implemented except the special my name and max and abs on numbers, which are not built.

Now that we have literals and variables, we can construct more complex expressions that use operators, methods and functions calls to calculate new values. Although the expression examples on this page work with integer and floating point values, similar expressions can be formulated that manipulate values of other types.

Expressions are gathered into blocks. A block is the basic unit for structured control flow. It holds a ordered collection of statements that are executed in order, starting with the first statement. It may also accumulate its own temporary, local state. Blocks that evaluate to some value may also be used in expressions.

Arithmetic Operators

Integer and floating point numbers may be computed using arithmetic operators:

'+'
Add
'-'
Subtract (or negate when used as a prefix operator)
'*'
Multiply
'/'
Divide
'%'
Modulo (remainder)

Thus:

-12 + 14    // 2
6 / 5       // 1
-4 % 3      // -1 (where -4/3 --> -1, truncating towards zero)
2*2 + 2*3   // 10 (standard algebraic operator precedence)
2 * (4 + 1) // 10 (parentheses override operator precedence)

Bitwise expressions

The bitwise operators operate on true/false values:

'|'
Or
'&'
And
'^'
Xor
'~'
Not

For example:

true | (false & true) // true
true ^ ~true          // true

These bitwise operators may also be used on unsigned integers, as they are viewed as a collection of true/false bits.

0xE0u | 0xB8u  // 0xF8u

Shift operators

The shifting of an integer's bits is accomplished using the << and >> operators:

0x0Cu << 1    // 0x18, after shifting bits left once

The amount to shift by is a value of the same integer type. << fills the bits it vacates with zeros, and the bits shifted past the top are gone. >> on an unsigned integer fills with zeros; on a signed integer it fills with copies of the sign bit, so a negative value stays negative.

Every amount gives an answer, the same in every build. An amount of the integer's width or more shifts every bit out: << gives 0, as does >> on an unsigned integer, and >> on a signed integer gives the sign in every bit, 0 or -1. The amount is read as an unsigned number of its own width, so a negative amount of a signed type is past the width too:

imm n = 64u64;
255u64 >> n         // 0
(1u64 << n) - 1u64  // all ones: 1 << 64 is 0
-8i32 >> 40i32      // -1, at run time

In a constant expression, such as a const's value, a shift by the width or more, or by a negative amount, is an error.

An amount taken modulo the width is asked for by name: the integer methods shlMasked and shrMasked, the processor's one-instruction shift, and rotateLeft and rotateRight (An integer's bits).

Other Expression Operators

Cone supports several more expression operators. Descriptions may be found in the chapters relevant to their common use:

  • conditional expression operators
  • 'with' block operators
  • construction, new Point(1, 2), which builds a struct's value by one of its initializers

The precedence of every operator is listed in Lexical Elements.

Assignment forms: +=, ++, parallel assignment

An 'lval'-based expression is one where the expression to the "left" represents a memory "container" which holds a value. Lval-based expressions will change the stored value. The assignment expression introduced above is lval-based, as examples specified a variable to the left of the =.

Parallel Assignment

Parallel assignment makes it possible to simultaneously assign multiple values to multiple variables. This can be convenient when swapping the values held by two variables:

// Swap the variable values for a and b
a,b = b,a;

This is also useful for capturing multiple values returned by a function or method call:

min, max = minmax(5, 4);

Increment/decrement Operators

When used to the left of an lval, ++ will increment the number and -- will decrement it.

mut cnt = 10;
++cnt;          // 11
--cnt;          // 10

When used to the right of an lval, it will still increment and decrement, but the expression will return the original value.

mut cnt = 10;
imm x = cnt++;  // x is 10, cnt is 11

Arithmetic Assignment

The arithmetic assignment operators (e.g., '+=', '-=', '*=', '/=') offer a convenient way to update an existing stored value:

counter = 3;
counter += 1;  // 4. Equivalent to: counter = counter + 1

Logical assignment operators

These work similarly to the arithmetic assignment operators:

mut flags = 0xC0u;
flags |= 0x01u;   // 0xC1u
flags >>= 1;      // 0x60u

Calling a method

Additional calculations can be performed using method calls. The name of the desired method follows the object value, separated by the dot operator ('.'): 

(-1).abs    // 1 (the absolute value, making a number positive)
(pi/2).sin  // 1.0 (trigonometric sine function)

Sometimes, a method may require additional values. These argument values are specified within parentheses following the method's name.

4.max(5)    // 5 (returns the larger of the two numbers)

Method calls are very common and convenient. It is helpful to know that:

  • The logic a method performs depends on the type of the value it is applied to. Thus, a method named 'max' applied to an integer is actually a different method than when 'max' is applied to a floating point number. Every type defines the names and logic for all methods it supports. An error results when trying to use a method not implemented by the value's type.
  • The arithmetic operators introduced earlier (e.g., + for add) are implemented under the covers using number type methods: 
    // The method name equivalent for the + operator is `+`
// The method name is enclosed in backticks since it includes punctuation
3+4 // is actually the same as: 3 .`+`(4)
// The space between 3 and . is needed here, otherwise 3. would be parsed as the float 3.0
// When using a variable this space is not needed: n.`+`(4)

Note: The arguments to a function or method call are evaluated in left-to-right order. This is also true for tuples.

Note: Inside any argument on a method call, the special name my may be used. Its value is the same as the object of the method call. This can be helpful to call helper methods on the object to prepare other argument values.

Function calls

Function calls are very much like method calls, except they are not applied to a value in the same way. Instead of specifying a value, dot operator, and a method name, one simply specifies the function name followed by any comma-separated arguments in parentheses. 

pow(10f, 2f)

Functions shows how to declare one.

Blocks are values

Statements

A statement is typically some expression to be performed. If the expression evaluates to some value, it is then usually discarded by the statement. In addition to expression statements, there are other kinds of statements, such as variable declarations, a block treated as a statement, or various statements used to control execution flow (Conditionals, Loops).

Every statement that does not finish with a block is terminated by a semicolon. The semicolon is never optional: not at the end of a line, and not on the last statement before a block's closing brace. This example shows two expression statements:

mut a = 12;
mut b = 5;

A single line may hold more than one statement, each ended by its own semicolon:

a = 24; b = 6;

A statement may span as many lines as it needs, since nothing but the semicolon ends it. Indenting the continuation lines helps a reader see that they belong to one statement, but the compiler pays no attention to indentation or to where a line ends:

a = b + c + d
    - e + f;     // One statement: a = b + c + d - e + f;

So a missing semicolon is never silently inferred. Leave one out and the compiler reports it, at the end of the statement the semicolon belongs to:

a = b + c + d     // Error: expected ';' to end the statement
e = f;

Blocks

Blocks offer a versatile, easy-to-apprehend way to structure logic. A block's well-defined single point of entry and exit establishes clear boundaries around control flow as well as the local context it manages.

Versatility comes from being able to nest different kinds of block easily within each other. This inherent modularity is useful when used in conjunction with control flow statements or to establish a context for compiler operations (e.g., safety constraints).

Blocks support these roles:

  • Holding an ordered collection of statements
  • Establishing a lexical scope for a local context
  • Building and/or returning a value
Ordered Collection of Statements

At its simplest, a block is merely a ordered set of statements which are executed one after another, in order. The block's statements are wrapped inside curly braces, which is the only way to mark that several statements belong to one block:

{
	a = 12;
	b = 5;
}

Indentation is for the reader. Where a block begins and ends is decided by the braces alone:

if a == 0 {
	a = 12;
}
b = 5;        // Not part of if's inner block: it follows the closing brace.

Blocks may be specified within blocks:

{
  ++a;
  {
    ++b;
    --a;
  }
  a + b;
}

The statements incrementing b and decrementing a comprise an interior block within an outer block. This particular example is a bit contrived, as there is no good reason for us to use an interior block here, since the logic would work the same if all statements belong to a single block. However, later we will see useful examples of blocks embedded within other blocks.

Lexical Context

Execution of a block's statements always begins with the first statement, as one cannot jump into the middle of a block. Likewise, execution of the block always finishes at the end of the block. This single-entrance and single-exit nature makes it possible for a block to create a temporary execution context that persists for the lifetime of the block and then is automatically cleaned up at the end of the block.

Local Variables. Any variable declared wihin a block provides a temporary working state for that block. Such variables are local to their block. They cannot be referenced or used outside of that scope. This silly example illustrates the block scope of declared variables:

{
	mut result = 0;
	{
		mut sum = a + b;
		result = sum;
	}
	++result;    // sum cannot be referenced in outer block
}

The block where a variable is defined is considered to be its lexical scope. Scopes are nested from outer to inner, with global variables having the outer-most scope. Variables declared in outer scopes are accessible in any inner scope. However, the reverse is not true. Thus, the outer block may not refer to sum.

If an inner block declares a local variable of the same name as an outer scope (including global variables), the outer-scoped variable is effectively inaccessible throughout the lexical scope of that inner block. To avoid potential confusion, this should be avoided.

Resource Disposal. The execution lifetime of a local variable does not last beyond its lexical scope. At the end of the block, any resources acquired by local variables are automatically reclaimed. Reclamation might encompass a wide variety of possible activities, including: freeing heap-allocated memory, decrementing counters, releasing locks, joining threads, or other type-based finalization activity that closes acquired resources or removes dependencies to other objects.

Blocks as expressions

Blocks that evaluate to a value may be used as an expression, embedded within a larger expression. When a block is used as an expression, its value is that of the last statement in the block.

// Using a block as an expression
a = {
	3.14;
	6;      // a's value will become 6
}

A with block is a block that focuses its logic around one value, named this, whose fields and methods it reaches with a bare dot:

with &mut point {
	.x /= len;      // the same as point.x /= len
	.y /= len;
}

with blocks and this has the form in full, with the prefix operators that act on this.

Conversion, coercion and subtypes

Note: Most of this is implemented to some degree.

Features that enrich types

We have introduced many different flavors of types. Let's now talk about some type-based features that enrich our use of types and typed values.

  • A type's from method, f32.from(x), for explicit conversion of values from one type to another, and as for reinterpretation. Where subtyping is in play, values will implicitly coerce to their supertype.
  • alias, which gives some type a second name (Namespaces).
  • extend, which allows an existing type to be extended to support additional methods (Extensibility).

Typing is strict: You cannot put a round peg in a square hole.

Since all values, expressions and variables have a type, the compiler can (and will) check whether the use of types is consistent. In most cases, an error will be reported wherever a program:

  • Stores a value of one type into a variable or collection declared for a different type.
  • Passes an argument of one type to a function that expects a value of another type in that position.
  • Returns a value of one type when the function's signature declares a different type for the return value.
  • Creates a reference (or pointer) to an object whose type does not match the reference's type declaration.

These constraints protect against a program manipulating a value in ways that make no sense or could be harmful, due to acting as if the value has a different meaning than it actually does.

However, sometimes we do want to transform a value of one type to another type. Cone supports three such capabilities:

  • Coercion, which implicitly and safely converts a value to some other expected type (usually a supertype).
  • Conversion, which explicitly asks a method of another type for the closest "equivalent" value in that type. This mapping is imperfect, as some (or all) of the meaning of the original value could be lost.
  • Reinterpretation, which explicitly preserves the original value but re-interprets it as if it has a different type. This potentially unsafe capability will be described on another page.

To distinguish between coercion and conversion, it is first necessary to understand how subtyping works in Cone.

Numeric conversions

To convert a number from one type to another, call the intended type's method from with the number:

imm six = i32.from(6u8);    // Converts 8-bit unsigned integer to 32-bit signed integer
imm sixf = f64.from(six);   // Converts 32-bit signed integer to 64-bit floating point number

If the receiving number type is a smaller size, numeric information may be lost. Explicit Conversion gives what each conversion does.

Subtypes

Subtyping captures a simple but powerful idea: if we have two types named Base and Subtype, how do we determine when it is safe to substitute in a value of type Subtype whenever our program logic is looking for a value of type Base?

Here are two essential criteria (there are others):

  • Every possible value in Subtype can be mapped uniquely to its semantically identical value in Base.
  • The behavior of values in Subtype must correspond in every way to the behavior of equivalent values in Base. In our case, that means at minimum that for every method in Base, there exists an equivalent method in Subtype with the same type signature and constraints.

Many type pairs in Cone comply with these criteria and support a safe subtyping relationship:

  • Any variant type is a subtype of any trait or struct type that it complies with, even if it does not inherit from it.
  • Any non-nullable type is a subtype of its nullable equivalent (e.g., &Foo is a subtype of ?&Foo).
  • An owning reference is a subtype of the borrowed reference to the same value type (e.g., So[Foo] is a subtype of &Foo)
  • A pointer is a subtype of any reference whose object type is the same.
  • Some reference permissions are subtypes of others (e.g., ro is a subtype of imm or mut). Similarly, most permissions are a subtype of uni.
  • A smaller number type is a subtype of a larger version of the same type (e.g., u8 is a subtype of u32).
  • A struct is a subtype of any trait it conforms to.

An important characteristic of subtyping relationships is that it is trivially safe to transform a Subtype value into its equivalent Base value. However, the journey of a value back from Base to Subtype often requires some sort of pattern-matched guard, as there are likely to be values in Base that do not have a valid mapping from Subtype to Base. A successful pattern match guarantees we will get back a valid Subtype value when the reverse transformation is applied.

Implicit Coercion

We call it coercion when implicitly converting a value into an expected type (usually a supertype). Coercion is the one safe exception to the strict typing rule described earlier, given that the type of a value and its receiver are not strictly the same.

Since coercion is always safe, Cone performs it implicitly when copying or moving a subtype value to any container (variable, parameter, return value, field, reference) expecting a base value. This happens during assignments, function calls and returns. For example:

fn doStuff () {
  imm bigint u32 = 101u8;        // Coerce a u8 to u32
  mut matrix = new So[Mat4];     // Allocate a matrix
  imm float = mat4det(matrix)?;  // Coerce So[Mat4] to &Mat4
}

fn mat4det(mat &Mat4) f32 throws DivByZero {
  // ...
  return 1.0;                     // Coerce f32 to Result<>
}

Coercion is more than just changing the type of some value. It usually means creating a new value whose encoding is different than its source value.

Coercion can also trigger compiler mechanics: In the case of coercing an owning reference to a borrowed reference, it triggers appropriate borrowing mechanics on the source variable. Similarly, when coercing a non-copy value, move semantics apply.

If an expression requires, it is possible to explicitly request coercion. For non-reference types, use the appropriate constructor (as described below for conversion). For references, use the as operator:

imm newref = oldref as &Point;  // Explicitly coerce to a borrowed reference

Between references, as may only be a coercion: it never gives a reference a permission its source could not be coerced to (& to &mut, or &mut to &uni), which would need trust. For now there is one exception: the imm a type declaring Immutable gives a reference written with no permission may come from a & (bytes as &str); a permission written out may not.

Implicit Coercion to bool

In addition to supertype coercions, Cone supports the automatic coercion of some value to bool, so long as the value's type implements the isTrue method. This is implemented by the number and pointer types. A number is true if it is not zero. A pointer is true if it is not null.

The other direction is never implicit. A bool is not a number, so it does not coerce to one anywhere a number is wanted: an initializer, an assignment, an argument, an index or an operand of arithmetic. It is converted explicitly, usize.from(b) (see Explicit Conversion), which gives 0 for false and 1 for true:

imm count usize = flag;              // **ERROR** a bool is not a number
imm count usize = usize.from(flag);  // 0 or 1
A char Coerces to No Number

A char is a Unicode code point held in 32 bits, and it is no number. It coerces to none, a wider unsigned type included, and no number coerces to it, neither a u8, whose values above 127 would be Latin-1 characters, nor a u32, which may be no code point at all. Each direction is a conversion, asked for (see Explicit Conversion); the one exception is the character literal that is ASCII, which is a u8 where a u8 is wanted:

imm code u32 = c;                    // **ERROR** a char is not a number
imm code u32 = u32.from(c);          // the code point
imm low u8 = u8.from(c);             // the low 8 bits: a code point past ASCII is not a byte
imm c char = b;                      // **ERROR** a u8 is not a char
imm c char = char.from(b);           // U+00xx: a Latin-1 character when b is 128 or more
imm b u8 = 'a';                      // fine: the literal is the byte 97
A Slice Coerces to No Pointer

A slice is an address and a count, so it is not a raw pointer, and it converts to none implicitly: the count would be dropped without a word. A pointer to its elements is asked for with as, which takes the address of the first element. Only a pointer to the slice's own element type is made this way (it retypes nothing). Text is neither: a &str is no pointer, and reaches C as a cstr, which a raw pointer is not either, except by cstr.fromPtr(p), whose caller promises the zero that ends it:

imm p *u8 = bytes;                   // **ERROR** a slice is not a pointer
imm p *u8 = bytes as *u8;            // the address of bytes[0]
fwrite(bytes as *u8, 1usize, bytes.len, f);
puts(text);                          // **ERROR** a &str promises no zero after it: a literal or s.cstr() does
imm c cstr = p;                      // **ERROR** a pointer promises no zero either
imm c cstr = cstr.fromPtr(p);        // the caller promises it
Implicit Coercion of 'self'

Cone offers a very different form of coercion when dealing with method calls (or field access) and the 'self' value. This convenience sugar automatically coerces self from a value to a reference (or the other way).

Cone will automatically transform 'self' to a mutable borrowed reference for operators that expect an lval, such as ++, +=, or a 'set' method.

++a;    // equivalent to:  Type.`++`(&mut a)

The same is true of a method called by name on a value held in a variable (or a field of one): when no method accepts the value itself, but one declares self as a borrowed reference, the value is borrowed for it. A method that only reads is handed a read-only borrow; one declaring self &mut is handed a mutable one, which the variable must permit; one declaring self &uni is handed a unique one, which only a place that lends &uni can give (a mut variable, or a part of one held by value: From 'uni'), and the call is held to what (&uni v).bump() would be. A temporary value has nowhere to be borrowed from, so such a call on one is an error, and a pointer is never borrowed from.

list.push(x);   // equivalent to:  (&mut list).push(x)
list.len();     // equivalent to:  (&list).len()

Automatic de-reference of 'self' may happen when 'self' is a reference, but no method matches with a reference-based self. 'self' is then automatically dereferenced in hopes of finding a matching method that uses a value rather than a reference.

&a + 5;  // may coerce to:  a + 5

A method called by name on a reference to a reference (&&T, &mut &T, a borrow of an owner) reaches through every level the same way, the outermost level winning a name, and with the access the dereferences written out would give: an owner reached through a & lends only &, so a self &mut method is not reached through it (Implicit De-referencing).

Explicit Conversion

Type conversion involves transforming a value of one type to the closest possible value in another type. For example, converting the integer 1 to the floating point number 1.0, or serializing it to text: "1". Unlike coercion, conversion may not map perfectly: A valid mapping may not exist or some precision may be lost.

A conversion is not a construction but a method of the new type, from, called on the type with the value to convert. It is the type's default conversion from another type; any other way of converting, such as one that saturates at the type's limits or one that checks that the value fits, is an ordinary method with a name of its own.

imm float = f32.from(1);
imm count = u32.from(list.len());
imm name = String.from("node");    // collections' String, from a slice of bytes

Every number type has from, which takes a value of any number type. It may be called on the type named directly, through an alias of it, or on a generic's type parameter: T.from(x) converts to whichever type T is. The into operator is retired: from is the conversion. Between numbers it does what the machine does:

  • To a narrower integer, the low bits are kept: u8.from(300) is 44.
  • To a wider integer, a signed value converting to a signed type is sign-extended; every other value is zero-extended from its own width, so u64.from(-1i8) is 255. Between a signed and an unsigned type of one width, the bits are kept: i8.from(200u8) is -56.
  • A float converts to an integer by truncating toward zero: i32.from(-2.75) is -2. A float whose truncated value the integer type cannot hold, a negative one to an unsigned type among them, has no defined result.
  • An integer converts to the nearest float, and a float to the nearest float of the other width.
  • An integer literal with no suffix is an i32 and converts as one: u64.from(-1) is 4294967295. Converting a literal gives a literal, so it may be a global's value.

Converting a number, reference or pointer to bool, written bool.from(n), gives the answer its isTrue method gives a condition (see Implicit Coercion to bool): bool.from(2) is true, as are bool.from(0.5) and NaN; only 0, -0 and a null pointer are false. A bool converts to a number as 0 or 1.

A number type takes no square brackets: u64[count] is an error naming u64.from(count).

In some cases, it may be more convenient to request conversion by using some method in the old type:

imm text = 1.text;

Move vs. Copy, in brief

Values are copied as they flow from variable-to-variable or function-to-function. Changes made to a copy don't affect the original value.

imm a = 3;
mut b = a;  // b holds a copy of a's value
b += 1;     // b's value is changed to 4
a;          // is still 3

Sometimes, however, we have values for which we don't want multiple copies to exist at the same time: for example, a handle to a just-opened file, where closing the file using one copy would make it unsafe to use the other. To provide safe support for such "non-copyable" values, Cone supports move semantics. Move semantics enable non-copyable values to be moved from one place to another in a code's logic. However, once the value moves, it may no longer be accessed from its old location. This restriction ensures there is only ever one copy of the value in existence.

Whether a value is handled by move vs. copy semantics is determined by its type. Most types copy. A type moves if it declares so, by naming Move in its is list, if it has a finalizer, or if any of its fields moves:

struct Handle is Move {
   pub id i32;
}

fn take(h Handle) {
  print <- h.id, "\n";
}

imm h = new Handle(1);
take(h);            // h moves into take
print <- h.id;      // **ERROR** h was moved out

A clone method takes no part in copying: a type may declare one and call it by name, but no copy calls it. Moves in depth has every rule, what a move leaves behind, moves on only some paths, and swapping.

Fine-tuning

Rarely needed on a first reading.

Static variables

A variable declared static inside a function is one copy shared by every call of the function, kept across calls (static mut calls = 0;). Static variables has the rules at every scale.

void, and Never

The language's pre-defined void type is used whenever we want to represent that no value is expected. This is useful in several circumstances:

  • As the return type for a function or method that accomplishes some effect, but returns no value.
  • As the value for a generic type for which it makes sense to substitute in the void type. For example, a function that returns no value on success, but returns an E type on failure would have a return type of Result[void, E].

There is only one possible value for a void type: nil. Any return or break statement that specifies no expression value is effectively returning a value of nil.

Zero-sized values may not be stored in memory. For this reason, one may not define a variable of type void nor allocate space for a new value of type void. However, it is fine for a struct to define a void-typed field, so long as at least one other field has a non-zero-sized type.

Never is the return type of a function that does not return at all: the core library's panic, or the C library's abort. It is void wherever a value is asked of it, and says one thing more: control does not come back from the call. So a call to one may end a block that must produce a value, which then has no value on that path, and a function declared to return Never must end in such a call. Panics has examples.

The primitive 'int' and 'float' number types

Note: The primitive int- and float- types are not implemented, and the standard number types (i32, f64 and the rest) are built into the compiler rather than defined in a library. A custom number type written as below, with a standard number type as its field in place of int-32, does work: a struct wrapping the number, methods on it, and its conversion from a number, Nbr32.from(somenbr), declared as below. The standard number types' from is built into the compiler with them, and so are an integer's bit methods, which are implemented.

int-32 specifies a 32-bit integer. Any integer value from 1 to 128 may be specified after the dash, to establish the number of bits.

Similarly, float-32 is a 32-bit floating point number. Floats only support 32 and 64-bit values.

Unlike i32, int-32 does not define any methods for manipulating its values (e.g., adding and subtracting). It is also agnostic on the semantic interpretation of its values ... it does not even signify whether the integer value should be interpreted as signed or unsigned. Its lack of built-in methods and interpretation is what makes it an ideal foundation for defining new types with very different interpretations and methods.

Custom Number Types

Rarely needed, and largely hypothetical for now (see the note above): defining a number type of your own.

There are several reasons why we might want to define distinctly different number types than those provided by the standard library:

  • One might want to use different types to distinguish between units of measure, thereby potentially avoiding problems like the loss of the $125 million Mars probe.
  • Different number types could make different promises for undefined behavior (e.g., protecting against undesired overflows), or could guarantee the number values are bounded by some range.
  • Integers that support intrinsic atomic operations can be separately typed, as the core package's Atomic[T] is.

Creating a new numeric integer type is nearly as simple as wrapping an primitive integer type as a field in a struct. For example:

struct Nbr32 {
    pub nbr int-32;
}

Methods may be added to this struct to define the operations that may be performed on values of this type. These methods can make use of fast internal integer primitive functions (TBD).

Although numbers of one type are never implicitly converted into the equivalent number of another type, a conversion may always be asked for explicitly. A conversion is a method of the type converted to, named from and called on the type, which takes the value to convert:

imm converted = Nbr32.from(somenbr);

Every standard number type has one, which takes a value of any number type (Explicit Conversion). A custom number type declares its own, an ordinary function of the type:

struct Nbr32 {
    pub nbr int-32;

    pub fn from(n i32) Nbr32 {
        new Nbr32(n);
    }
}

from is the type's default conversion from another type. A conversion that differs from it, such as one that saturates at the type's limits or one that checks that the value fits, is an ordinary method with a name of its own.

The repertoire of types

As mentioned earlier, every value has a type it belongs to. Each type establishes all its permissible data values, determines how those values are digitally encoded, and specifies what operations can be performed on values of that type.

Cone offers a comprehensive repertoire of types:

  • Primitive integer and floating-point number types. Several are built-in, such as i32, u8, f32 and bool, as illustrated in prior page examples. Text is built of char, a Unicode code point (character literals), which is compared but is no quantity. Additional distinct number types may be defined using the integer or float keywords.
  • struct types. Each named struct type is composed of some number of co-located, named, and typed fields.
  • array types. Statically-sized arrays are composed of a fixed, constant number of values, all of the same type.
  • enum types. Each named enum type declares a closed set of variants. Any value of the enum is exactly one of them, and a variant may carry values of its own or carry nothing but its name. Cone builds in support (and syntactic sugar) for two enum types: Option and Result.
  • reference types. These offer a safe way to point at some value stored in memory. There are three flavors: regular, array and virtual. References can additionally be region-managed or borrowed. Race safety is protected via permissions.
  • pointer types. Like references, pointer types also point at some memory-stored value. Unlike reference, pointers do not have compiler-enforced guard rails to ensure their use is safe.
  • traits types. Traits are supertypes that abstract the type signature (interface) that is common across several types. They are very useful when we want to work with values of many different types in the same way.
  • void type. This built-in type represents the absence of any value. It does have its uses.

What the type system offers

As you will see explored later, Cone's type system supports a rich and useful variety of semantics:

  • Most types are concrete, but some (particularly trait) are abstract. Only concrete-typed values can be passed around or stored in variables. Abstract values can only be pointed-at using a reference.
  • Most types are defined and used by name (nominal). Others are defined by their structure (e.g., arrays and references).
  • Some types enforce constraints on how its values may be used:
    • The values of most types may be freely copied. However, some types are defined with move semantics, which prevents the existence of multiple copies of the same object.
    • Most values may freely move around anywhere in a program. However, some types restrict its values to a particular scope, such as the lifetime of a block, a particular thread, or a region.
  • In certain cases, it is safe and possible to implicitly coerce a value of one type into its supertype's comparable value.
  • Named types can be genericized using type parameters.
