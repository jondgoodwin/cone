Cone
Each and Iteration

Note: Built: number ranges with <, ≤, >, ≥ and by; arrays, slices and lists; and anything with a next method (a cursor) or an iter method (something that gives one), a generator among them, with one variable or several that unpack a pair; a filter after the source (if); an else that makes the loop a value; the ways to walk a list, an array or a slice that change its items in place (mutItems), consume it (drain) or number them (indexed), and zip; each as an entry of the append operator's list (below); and parallel each over a number range, an array, a slice or a list, in a function or an actor's method, and the parallel builder that builds a list from it. Not built yet: closure iterators, the adapters (map, filter, fold) and a source that runs its own loop, all of which wait for closures. An enum's variant is constructed with its values in square brackets, as written here: that is the current spelling, and how a variant is constructed is an open design question (Enums).

each makes it easier than while to iterate over a sequence of values. For example, here's the factorial function using each:

fn fact(n i32) i32 {
  mut result = 1;
  each x in 2 <= n {
    result *= x;
  }
  result;
}

Effectively this each statement binds the variable x to each iterated value from 2 up to n inclusively, each time performing the loop's inner block.

As this example shows, the each statement has a simple structure:

  • One or more variables to be bound to values produced by the iterator. These variables are local to the each block and cannot be accessed outside that scope. Every pass binds new ones, and the block cannot change them: counting by hand is a while. A write to one is refused, and the message says how to change the items in place instead: walk src.mutItems().
  • An iterator that produces different value(s) on each iteration of the loop. The iterator follows in.
  • A block containing the logic to be performed on each iteration.

break and continue

break and continue statements may be used within an each block to stop or re-start the loop. Either may name a loop's label, to leave or re-start an outer one, and return leaves the function. Each of the three may end with an if and a condition, as continue if x % 2 == 0; does (While, Break and Continue).

Skipping items: if

An if and a condition after the source is a filter: the items for which the condition is false are skipped, as if the block began with if !cond { continue; }. It reads the loop's variables, and works for every kind of source below, ranges included:

each x in 0 < 10 if x % 2 == 0 {       // 0 2 4 6 8
}
each name in names if name.len > 3 {   // a List[String]
}
each key, value in ages if value > 18 {
}
each x in 100 >= 0 by 10 if x != 50 {
}

A loop that gives a value: else

A loop that is searching for something has two ways to end: it finds it and leaves with break, or it runs out of items. An else after the loop's block says what the loop is worth when it runs out, and with one the whole each is an expression whose value is the break's or the else's:

fn firstBig(list &List[i32], limit i32) i32 {
  each x in list {
    if x > limit { break *x; }
  } else {
    -1;              // nothing was big enough
  }
}

imm total = each x in 1 <= 100 {
  if x * x > 500 { break x; }
} else {
  0;
};

The value is of one type, whichever way the loop ends. The else block is an ordinary block (its last expression is the value, and it may do other work first), run only when the items run out; a break skips it. It stands outside the loop: the loop's variables are not in view, and a break or continue in it belongs to the loop around. It may end in a return instead, which gives the loop no value (else { return -1; }). An each with an else may also be a statement; a break that gives no value is then fine, and the else is run for what it does. An each without an else is a statement only. while with a condition does the same (While).

Building a collection: each inside <-

An each may stand in the list after the append operator (Operator Methods), beside values, of, fill and pairs. With only a source it drains it: every item is appended. With variables it is the loop's own header, including the if filter, and a yield in the place of a block says what each pass appends:

imm copy = new List[i32] <- each other;                     // every item of other
imm big = new List[i32] <- each x in other if x > 9 yield *x;
imm squares = new List[i32] <- each i in 1 <= 5 yield i * i;  // 1 4 9 16 25
imm index = new Dict[i32, str] <- each p in people yield p.id: p.name;
xs <- 0, each x in other yield x + 1, 99;               // in the middle of a list

This yield belongs to the entry: it is not a generator's, which is a statement of its own, so a generator may build a list this way and then hand values to its caller. Two or more variables unpack a tuple item as they do in a loop, and yield k: v appends a pair to a collection that takes a key and a value. The items an each gives of a collection are borrows, so a drain appends a copy of each (a type that moves is not copied: drain a source that hands its items over, each other.drain()), and a yield writes the * itself where it wants the value. The list being appended to cannot be the source: xs <- each xs is refused, as pushing to a list while a loop walks it is. An array's contents cannot hold an each, as its size is fixed.

Iterators

each supports several ways to iterate over a sequence of values:

  • Number range, for simple arithmetic progressions.
  • Array, slice or list, to work with individual elements.
  • Cursor, something with a next method, and anything that gives one. A generator is a cursor.
  • Closure, to deal with algorithmically-generated values (not built yet).

Number Range Iterator

As the above example shows, a range is written as a comparison, < or <=, and iterates successively over integers or floating point numbers. Iteration begins with the first number and then increments by 1 until it reaches (<) or passes (<=) the second number. Expressions may be used in place of literal numbers, if desired.

To iterate backwards (decrementing the iterated number), use the > or >= operators instead.

each x in 6 > 1 {  // iterates:  6 5 4 3 2
}

A step value may be specified after by. Instead of incrementing or decrementing by 1, the step value specifies how much to increase the iterated number each time:

mut sum = 0;
each x in 0 <= 10 by 2 { // iterates: 0, 2, 4, 6, 8, 10
  sum += x;
}

A range counting down takes a negative step value. Iteration stops as soon as a step moves the number away from the bound rather than toward it, which is also what a step past the largest (or smallest) value the number's type can hold amounts to:

each x in 10 >= 0 by -2 {      // iterates: 10, 8, 6, 4, 2, 0
}
each x in 250u8 <= 255 by 2 {  // iterates: 250, 252, 254
}

A range gives one variable. The loop steps a counter of its own and each pass's variable holds the number, so writing to the variable is refused. A loop that steers its count by hand is a while.

Array, Slice and List Iterators

each can be used to iterate through every element of an array, a slice or a list, one at a time. The variable is a borrow of the element (the elements themselves stay where they are, and the list is still whole afterwards). A borrowed number needs no * in an expression: it is read through on either side of an operator (x + total, total + x), on the right of a compound assignment (sum += x) and in a comparison (x > 1, or x == y for two borrows, which compares the values), and so is any value that copies freely: a bool, a char, a plain struct (Implicit De-referencing). The * is written where the value itself is wanted: a copy of the item (imm y = *x), a value handed to a function, a break or yield, or a store through a &mut:

mut sum = 0;
each x in [4, 3, 8, 2] {
  sum += x;
}

mut chars = 0usize;
each name in names {      // a List[String]: name is a &String
  chars += name.len;
}

An array or a slice is walked by a counted loop over its length, and so is a list, which lends its elements as a slice: none of them makes an iterator object, and the loop is the one a while over the indexes would be. While the loop runs the list may not be changed, since the borrows it hands out would not survive a change. For the same reason an await in the body is refused over an array or a list, whose borrow would have to last across it; over a number range it is fine (Concurrency).

Changing items in place: mutItems

A plain each only reads. To change the items of a list, an array or a slice where they are, walk mutItems(), which lends each item as a &mut:

each x in list.mutItems() {
  *x = *x * 2;       // x is a &mut of the item
}

It is the same counted loop as a plain each over a slice. The list stays borrowed mutably while the loop runs, so nothing else may read or change it until the loop is over. A list, an array or a slice that is only read has no mutItems to take (an imm list, or a &Array[T] parameter).

A borrow written as the source, each x in &mut list, is refused, in parallel each and in <- each too, with the message to write list.mutItems(): each reads what it walks, and the change in place is a method that lends the items. each x in &list is allowed and reads, as each x in list does.

Taking items out: drain

list.drain() gives the values up one at a time, moving each out of the list into the loop's variable, which then holds the value itself (not a borrow of it), so it works for items such as a String that cannot be copied:

each name in names.drain() {   // name is a String, moved out of names
  joined.append(name.view());
}
// names is now empty (its block is kept for reuse)

The list is left empty as soon as drain is called, and may not be used while the loop runs. Each pass's value is finalized as the pass ends. A loop left early, by break or return, finalizes the values it did not reach.

Positions: indexed

indexed() of a list, an array or a slice gives each position with a borrow of its item, a pair that two variables unpack. Walked directly by each, it is a counted loop, as a plain each is:

each i, name in names.indexed() {   // i is a usize, name a borrow of the item
  print(i, name);
}

Two together: zip

zip(&xs, &ys) walks two lists (or deques, sets, dictionaries, or anything else with an iter method) side by side, giving a pair of what each gives, and ends when the shorter does:

each x, y in zip(&xs, &ys) {
  ...
}

An array and a slice have an iter() too (each x in a.iter() is the loop each x in a is), and zip takes them, with the & a list takes: zip(&arr, &xs), or two slice parameters, zip(s, t).

Cursor Iterators

A cursor is anything with a next method that answers an optional value, Some with the next item or None when there are no more. A type needs no declaration to be one, only the method (it is met by shape, as Iterator in the core library names, which is what generic code asks for):

struct Countdown {
  n i32;

  pub fn next(self &mut) Option[i32] {
    if n <= 0 { return None[i32][]; }
    imm v = n;
    n = n - 1;
    Some[i32][v];
  }
}

mut countdown = new Countdown(3);
mut digits = 0;
each n in countdown {     // iterates: 3 2 1
  digits = digits * 10 + n;
}

The cursor is used as it is: a cursor in a variable is advanced there, so a loop left with break can be followed by another that carries on from where it stopped. A cursor that lends (a deque's items(), say) gives borrows of its items, as an array does; one that gives values gives the values themselves. An item that moves (a String the cursor hands out) is taken out of the optional value by the one variable, and is the variable's from then on; several variables, which would take the elements of a moving pair out one by one, are refused.

Something that gives a cursor

A value with no next but an iter method, which gives a cursor, is walked through the cursor it gives, as if the loop had called iter itself:

each x in collection {  // equivalent to: each x in collection.iter()
}

The collections give cursors in this way: a deque's, a set's and the dictionaries'. Calling iter only reads the collection: it is borrowed and not consumed, and may not be changed while the loop runs. Other views of a collection are ordinary methods that answer a cursor, walked the same way: each k in dict.keys(), dict.values(), deque.items(), text.chars() (Collection Types).

Two variables

Two or more variables unpack an item that is a tuple. A dictionary's cursor gives its pairs, a borrow of the key and a borrow of the value, so

mut both = 0;
each key, value in ages {   // a Dict[i64, i64]
  both += key * value;
}

and one variable would take the pair whole (pair.0 and pair.1). A number of variables that does not match the tuple, and any number but one for an array, a slice or a list, are refused.

Closure Iterator

Not built yet: this section waits for closures, none of which are built (Closures). The closure spelling below is a sketch. Look to closures for iterator versatility. Using closure iterators, one can scan through elements in a complex collection, retrieve values from a streaming resource, algorithmically calculate a sequence of values, etc. Because closures are stateful, they can generate a new value on every call.

In order for a closure to be suitable as an iterator, it must be able to signal when it is done producing values. It typically does this by returning an optional value, with the value of None signalling when it is done, just as a cursor's next does.

In the following example, imagine a closure that starts off holding the value 12, and halves (and returns) its value on each call. When the value gets to 0, it returns None instead:

mut sum = 0;
each x in |{cnt = 12}| if cnt > 0 {Some[cnt /= 2]} else {None} {
  sum += x;
}

The value of sum at the end will be 10, as each successive call to the closure returns 6, 3, and 1. After 1, it returns None, which stops iteration.

Because it is stateful, a closure is typically single use. It is created before it is needed, used to produce values lazily, and then discarded afterward. This is because, unless its state can be independently reset, it will only ever afterward say it is out of values.

Adapters and sources that run their own loop

Not built yet. Two more uses of closures with each are planned, both after closures:

  • Adapters. map, filter, fold and the like are to be methods every Iterator shares, generic over the closure's own type, so that a chain such as items.filter(...).map(...) is compiled into one loop with no call through a pointer for each item. Such a chain could then feed an each loop or the entries of a collection being built.
  • A source that runs its own loop. A source may offer an optional method that runs the loop itself, taking the body as a closure, for a source that cannot hand out its items one by one (a line reader that lends each line from its own buffer, say). each would use it when the source has it, and otherwise use next; break, continue and return in the body would reach the source as signals, and an await in such a body may be refused.

parallel each

Note: Built in a function and in an actor's methods (below): over a number range, an array, a slice or a list, with the header if and mutItems(), and, in a function that is not an actor's method, the parallel builder (new List[T] <- parallel each … yield). Not built yet: inside a generator; a source of your own that is a ParallelIterable; and the reductions that come with closures. A parallel each takes no else and is a statement.

Writing parallel in front of an each runs the loop's passes at the same time, on the actors package's workers, one for each CPU:

import actors;

fn total(xs &Array[u64]) u64 {
  imm sum = Atomic[u64].of(0u64);
  parallel each x in xs {
    sum.add(weigh(*x));
  }
  sum.load();               // every pass has finished
}

The loop has finished when control reaches the statement after it. It starts as one task for the whole range of passes; whoever runs a task splits it in half while it is bigger than a small share of the range, queues one half and works the other, and an idle worker takes the oldest, largest half. So uneven passes spread themselves, and the code that wrote the loop works on pieces of its own loop while it waits. A module that writes one imports actors.

parallel is a word only directly before each: anywhere else it is a name like any other (a variable, a function, a field).

The filter, parallel each x in xs if cond { … }, skips the items for which the condition is false, as it does for each.

What it can walk

The source must be something that can be split into independent pieces and says how big it is: a ParallelIterable, met by its methods alone, with no declaration, as Iterator is (len, and split(at) giving the items before at and the items from it on). Today the loop walks a number range counting up by one (parallel each i in 0 < n, or <=; a count down or a by step is refused, since which pass runs first is not defined in parallel), an array, a slice and a list, which it cuts into ranges of positions itself. A cursor, a generator, a file or a channel hands out its items one after another and cannot be split: collect it into a list first, and walk the list. As in the loops above, the variable is a new one on every pass, and is a borrow of the item for an array, a slice or a list.

What the body may do

The passes run at the same time, so the body keeps rules an ordinary each does not:

  • What is declared outside the loop is read-only in it, borrowed for as long as the loop runs. Writing it is refused: an assignment, an operator that assigns, a field, an element, a swap, a method that changes it, or a borrow that may write, and a write through a &mut reference declared outside. What the pass declares itself is its own to change. A write through a raw pointer is not checked: the loop trusts its writer.
  • A copy of a value from outside is a write when it counts: copying an Rc adds to its count, which passes running at the same time cannot do without atomic operations. So a body may not copy an Rc (or a struct, tuple, array, enum or list element that holds one, or a traced Gc reference, whose roots are the collector's one chain) that is not its own. Reading it is free: dereferenced, lent with &, a field that is a number. An Arc counts atomically and may be copied. What a function the body calls copies is that function's.
  • A Gc may not be made or held in the loop, for now: the collector's heap and its one chain of roots are not safe on the workers the passes run on. An allocation (new Gc[...]), a call that returns one, or a literal holding one (a struct, tuple, array or enum holding a traced reference counts) is refused in the body, and in a parallel builder's source, if and yield, with a message saying GC per actor is coming. The refusal lifts when the collector is per actor.
  • Results come back through something that is changed by its methods, an Atomic, or as the list the parallel builder builds.
  • A pass may change its own item: parallel each x in list.mutItems() (or an array's or a slice's, or a mutable slice as the source itself) gives x as a &mut of the pass's item, and the items are disjoint. Then the body may not name the list (or slice, or the struct holding it, or what is inside the place the items are lent from) as well: &mut is shared in Cone, so another pass may be changing the item it would read. Another field of the same struct is free.
  • continue skips the rest of a pass. A break or continue of a loop inside the body is the pass's own. A break and a return are refused (which items had run by then would vary from run to run), and so is an await (a pass runs to completion and has no mailbox).
  • A message sent to an actor is allowed, and is not sent where it is written: the passes' messages are kept and sent after the loop, by the code that wrote it, in iteration order — the first pass's, then the second's — so an actor sees the same order every run. A loop inside a pass's body is gathered into that pass in the same way.

In an actor's method

A parallel each written directly in a behaviour (a method declared async do) cuts the behaviour where the loop ends, as an await does. The behaviour returns to the actor's dispatcher while the passes run on the workers, and the rest of it runs when the last pass has finished:

actor Scaler {
  vals List[u64];
  scale u64;

  pub async do run(self, add u64) {
    imm k = add * 2u64;
    parallel each v in vals.mutItems() {
      *v = *v * scale + k;      // the actor's fields are read through self; k and add are carried
    }
    // here the loop has finished, and this is the same behaviour, the same call
  }
}
  • The actor is not run again until the loop has finished, the rest of the behaviour included. Its mailbox goes on accepting messages, and they are handled after the behaviour, in order. A message sent after the behaviour began is handled after all its parallel work.
  • The passes borrow the actor's fields directly, through self, for the loop: nothing is moved out or copied, and no update is lost. This is the one borrow a behaviour holds across the cut; nothing else runs the actor, and a pass can neither await nor receive, so the loop always finishes.
  • What the behaviour holds across the cut is carried as it is across an await: the parameters and locals it uses afterwards, and every droppable value, which dies where it would have died had the method not been cut. What the passes read of the behaviour's variables is copied as the behaviour returns, so a pass may not read a borrow held in a variable (imm t = &total; read total through self instead), and the array or slice the loop walks may not lie in the behaviour's own frame (an array in a local, or made for the loop; walk a list, or an array in a field).
  • The messages the passes send are sent when the last pass has finished, before the rest of the behaviour runs, in iteration order.
  • A behaviour that returns a value answers it from after the loop. A loop in a loop of the behaviour, and several loops, are a cut each. A loop inside a pass's body runs inside that pass.
  • A synchronous fn of an actor cannot be cut. A loop there runs where it stands, the worker running passes meanwhile, so its actor is not run again until the method that called it has returned.
  • The parallel builder is not built inside an actor's method yet.

The parallel builder

A list is built by a parallel each as it is by an each inside <-: put parallel in front of the each in the list of entries, and give the value each pass appends with yield:

imm weights = new List[u64] <- parallel each x in xs yield weigh(*x);
imm keep = new List[u64] <- parallel each x in xs if x > 9 yield weigh(*x);
imm squares = new List[i32] <- parallel each i in 0 < n yield i * i;     // n an i32
xs <- 0, parallel each x in other yield x + 1, 99;    // in the middle of a list

The list holds the values in the order of the passes, the order a plain each would give them, however the passes were spread over the workers; with a filter, the values of the passes that kept their items, in order. The loop has finished, and the list is whole, when control reaches the statement after it. The body's rules above hold for the header, the filter and the yield: nothing outside the loop is written, an Rc from outside is not copied, and there is no break, return or await. The items of a collection come as borrows, as in a loop, so the yield writes its own *; a value that moves (a String made in the body) is handed to the list. With only a source, new List[T] <- parallel each src, every item is appended as a copy.

Only a List is built this way. A dictionary or any other collection is built from a list of pairs after the loop: a receiver that is not a List is refused, and so is yield k: v into a list. A builder inside an actor's method or a generator is refused as a parallel each is, and the list being appended to cannot be the one the loop reads, as for each.

Underneath, each piece of the loop (a run of consecutive passes) appends to a list of its own, and when the loop has finished the pieces' lists are joined onto the end of the list being built in the order of where each piece began. List has four methods the compiler calls for this, pieceBag, emptyPiece, depositPiece and joinPieces: they are not for a program to call.
