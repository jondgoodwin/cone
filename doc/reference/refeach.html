Each and Iteration

Note: Built: number ranges with <, ≤, >, ≥ and by; arrays, slices and lists; and anything with a next method (a cursor) or an iter method (something that gives one), with one variable or several that unpack a pair; and parallel each over a number range, an array, a slice or a list, outside actors. Not built yet: closure iterators, and the ways to walk a list that change its items in place, consume it, or number them. An enum's variant is constructed with its values in square brackets, as written here: that is the current spelling, and how a variant is constructed is an open design question (Enums).

each makes it easier than while to iterate over a sequence of values. For example, here's the factorial function using each:

fn fact(n i32) i32 {
  mut result = 1;
  each x in 2 <= n {
    result *= x;
  }
  result;
}

Effectively this each statement binds the variable x to each iterated value from 2 up to n inclusively, each time performing the loop's inner block.

As this example shows, the each statement has a simple structure:

  • One or more variables to be bound to values produced by the iterator. These variables are local to the each block and cannot be accessed outside that scope. Every pass binds new ones, and the block cannot change them: counting by hand is a while.
  • An iterator that produces different value(s) on each iteration of the loop. The iterator follows in.
  • A block containing the logic to be performed on each iteration.

break and continue

break and continue statements may be used within an each block to stop or re-start the loop. Either may name a loop's label, to leave or re-start an outer one, and return leaves the function.

Iterators

each supports several ways to iterate over a sequence of values:

  • Number range, for simple arithmetic progressions.
  • Array, slice or list, to work with individual elements.
  • Cursor, something with a next method, and anything that gives one.
  • Closure, to deal with algorithmically-generated values (not built yet).

Number Range Iterator

As the above example shows, a range is written as a comparison, < or <=, and iterates successively over integers or floating point numbers. Iteration begins with the first number and then increments by 1 until it reaches (<) or passes (<=) the second number. Expressions may be used in place of literal numbers, if desired.

To iterate backwards (decrementing the iterated number), use the > or >= operators instead.

each x in 6 > 1 {  // iterates:  6 5 4 3 2
}

A step value may be specified after by. Instead of incrementing or decrementing by 1, the step value specifies how much to increase the iterated number each time:

mut sum = 0;
each x in 0 <= 10 by 2 { // iterates: 0, 2, 4, 6, 8, 10
  sum += x;
}

A range counting down takes a negative step value. Iteration stops as soon as a step moves the number away from the bound rather than toward it, which is also what a step past the largest (or smallest) value the number's type can hold amounts to:

each x in 10 >= 0 by -2 {      // iterates: 10, 8, 6, 4, 2, 0
}
each x in 250u8 <= 255 by 2 {  // iterates: 250, 252, 254
}

A range gives one variable. The loop steps a counter of its own and each pass's variable holds the number, so writing to the variable is refused. A loop that steers its count by hand is a while.

Array, Slice and List Iterators

each can be used to iterate through every element of an array, a slice or a list, one at a time. The variable is a borrow of the element, read through * (the elements themselves stay where they are, and the list is still whole afterwards):

mut sum = 0;
each x in [4, 3, 8, 2] {
  sum += *x;
}

mut chars = 0usize;
each name in names {      // a List[String]: name is a &String
  chars += name.len;
}

An array or a slice is walked by a counted loop over its length, and so is a list, which lends its elements as a slice: none of them makes an iterator object, and the loop is the one a while over the indexes would be. While the loop runs the list may not be changed, since the borrows it hands out would not survive a change.

Cursor Iterators

A cursor is anything with a next method that answers an optional value, Some with the next item or None when there are no more. A type needs no declaration to be one, only the method (it is met by shape, as Iterator in the core library names):

struct Countdown {
  n i32;

  pub fn next(self &mut) Option[i32] {
    if n <= 0 { return None[i32][]; }
    imm v = n;
    n = n - 1;
    Some[i32][v];
  }
}

mut countdown = new Countdown(3);
mut digits = 0;
each n in countdown {     // iterates: 3 2 1
  digits = digits * 10 + n;
}

The cursor is used as it is: a cursor in a variable is advanced there, so a loop left with break can be followed by another that carries on from where it stopped. A cursor that lends (a deque's items(), say) gives borrows of its items, as an array does; one that gives values gives the values themselves. The items must be values that copy, or borrows: an item that moves (a String the cursor hands out) cannot yet be taken out of the optional value, and is refused.

Something that gives a cursor

A value with no next but an iter method, which gives a cursor, is walked through the cursor it gives, as if the loop had called iter itself:

each x in collection {  // equivalent to: each x in collection.iter()
}

The collections give cursors in this way: a deque's, a set's and the dictionaries'. Calling iter only reads the collection: it is borrowed and not consumed, and may not be changed while the loop runs.

Two variables

Two or more variables unpack an item that is a tuple. A dictionary's cursor gives its pairs, a borrow of the key and a borrow of the value, so

mut both = 0;
each key, value in ages {   // a Dict[i64, i64]
  both += *key * *value;
}

and one variable would take the pair whole (pair.0 and pair.1). A number of variables that does not match the tuple, and any number but one for an array, a slice or a list, are refused.

Closure Iterator

Not built yet. Look to closures for iterator versatility. Using closure iterators, one can scan through elements in a complex collection, retrieve values from a streaming resource, algorithmically calculate a sequence of values, etc. Because closures are stateful, they can generate a new value on every call.

In order for a closure to be suitable as an iterator, it must be able to signal when it is done producing values. It typically does this by returning an optional value, with the value of None signalling when it is done, just as a cursor's next does.

In the following example, imagine a closure that starts off holding the value 12, and halves (and returns) its value on each call. When the value gets to 0, it returns None instead:

mut sum = 0;
each x in |{cnt = 12}| if cnt > 0 {Some[cnt /= 2]} else {None} {
  sum += x;
}

The value of sum at the end will be 10, as each successive call to the closure returns 6, 3, and 1. After 1, it returns None, which stops iteration.

Because it is stateful, a closure is typically single use. It is created before it is needed, used to produce values lazily, and then discarded afterward. This is because, unless its state can be independently reset, it will only ever afterward say it is out of values.

parallel each

Note: Built in a function that is not an actor's method: over a number range, an array, a slice or a list. Not built yet: inside an actor's method; a source of your own that is a ParallelIterable; the parallel builder (new List[T] <- parallel each … yield); a header if; changing the current item (mutItems()); and the reductions that come with closures.

Writing parallel in front of an each runs the loop's passes at the same time, on the actors package's workers, one for each CPU:

import actors;

fn total(xs &Array[u64]) u64 {
  imm sum = Atomic[u64].of(0u64);
  parallel each x in xs {
    sum.add(weigh(*x));
  }
  sum.load();               // every pass has finished
}

The loop has finished when control reaches the statement after it. It starts as one task for the whole range of passes; whoever runs a task splits it in half while it is bigger than a small share of the range, queues one half and works the other, and an idle worker takes the oldest, largest half. So uneven passes spread themselves, and the code that wrote the loop works on pieces of its own loop while it waits. A module that writes one imports actors.

parallel is a word only directly before each: anywhere else it is a name like any other (a variable, a function, a field).

What it can walk

The source must be something that can be split into independent pieces and says how big it is: a ParallelIterable, met by its methods alone, with no declaration, as Iterator is (len, and split(at) giving the items before at and the items from it on). Today the loop walks a number range counting up by one (parallel each i in 0 < n, or <=; a count down or a by step is refused, since which pass runs first is not defined in parallel), an array, a slice and a list, which it cuts into ranges of positions itself. A cursor, a generator, a file or a channel hands out its items one after another and cannot be split: collect it into a list first, and walk the list. As in the loops above, the variable is a new one on every pass, and is a borrow of the item for an array, a slice or a list.

What the body may do

The passes run at the same time, so the body keeps rules an ordinary each does not:

  • What is declared outside the loop is read-only in it, borrowed for as long as the loop runs. Writing it is refused: an assignment, an operator that assigns, a field, an element, a swap, a method that changes it, or a borrow that may write, and a write through a &mut reference declared outside. What the pass declares itself is its own to change. A write through a raw pointer is not checked: the loop trusts its writer.
  • Results come back through something that is changed by its methods, an Atomic, until the loop that builds a list (the parallel builder), and changing the items in place, are built.
  • continue skips the rest of a pass. A break or continue of a loop inside the body is the pass's own. A break and a return are refused (which items had run by then would vary from run to run), and so is an await (a pass runs to completion and has no mailbox).
  • A message sent to an actor is allowed, and is not sent where it is written: the passes' messages are kept and sent after the loop, by the code that wrote it, in iteration order — the first pass's, then the second's — so an actor sees the same order every run. A loop inside a pass's body is gathered into that pass in the same way.
