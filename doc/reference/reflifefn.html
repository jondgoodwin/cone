Lifetime Annotations

Note: Lifetime annotations on a function's signature, on a struct's fields and uses, and the where clause ordering lifetimes are implemented. A lifetime is written right after the reference's &, before its permission: &'a i32, &'a mut i32, &[]'a u8; and the global lifetime is 'static. Parameters are written name type, without the colon some examples below still show. A returned borrowed reference has the lifetime of the shortest borrowed reference passed to the call for a parameter whose lifetime it may hold, and keeps those arguments frozen while it is used, a method's receiver included (see borrowed references); where only a lifetime of what an argument points at may be held -- a struct's, held by the receiver of one of its methods -- it keeps frozen only what the argument holds in that lifetime, not the argument. A call is refused when a mutable or unique borrowed reference to a place that can hold a borrowed reference (a method's receiver included) could store there one, of a lifetime that place holds, that lives less long. A value passed by value that holds a borrowed reference counts as one of the lifetimes its type names, the unnamed one where it names none, for both rules. Inside the function, a borrowed reference the caller lent may be returned only as a lifetime it is written with, or one its where clause orders shorter, and stored only where what a parameter points at holds such a lifetime; no order between two names is inferred but what a where clause declares. A 'static parameter takes only a global borrow, and 'static may be written on a parameter's own reference or in the result, not inside a parameter's type. A value holding borrowed references has the lifetime of the shortest of them, as makewrap below shows. Not yet implemented: a + 'a bound on a type parameter or a virtual reference, and invariant lifetimes.

To ensure borrowed references are always safe to use, they carry a lifetime constraint that restricts them from living beyond the scope they were created in. This constraint prevents a borrowed reference from pointing to an object that no longer exists. Borrowed references may move freely around the program, so long as they never try to travel beyond this lifetime barrier. Attempts to violate this lifetime constraint result in a compiler error.

For a borrowed reference used within the same function where it was borrowed, the compiler knows exactly which scope created the borrowed reference, and thus knows exactly what scope represents its lifetime barrier. However, a function that receives a borrowed reference from another function has no visibility into which scope created the borrowed reference. There is effectively a thick brick wall separating a called function from the function that calls it. Each cannot see anything about what the other is doing with borrowed references.

Lifetime Annotations on Function Signatures

To bridge this knowledge gap, Cone looks for lifetime annotations on borrowed references in a function's signature.

fn dostuff(a: &'a i32, b: &'b i32) &'a i32, &'b i32;

'a and 'b are lifetime annotations representing two possibly-different lifetime scopes. Lifetime annotations are used to establish lifetime relationships between borrowed references. In this example, this means the first return value has the same lifetime as a, and the second has the same lifetime as b.

Although the called function treats them as having the "same" lifetime, they might in fact have different lifetimes in the calling function. When references with two different lifetimes are treated as having the same lifetime, their understood lifetime would be the shortest one, as that is the only lifetime these references have in common.

Lifetime annotations may be omitted on some or all borrowed references on a function signature. All borrowed references without annotations are understood to have the same lifetime, as if they had all been marked by the same lifetime annotation. The above example is thus identical to:

fn dostuff(a: &i32, b: &'b i32) &i32, &'b i32;

We can rule out the need for any lifetime annotations if the function does not receive at least two borrowed references in its parameters. We can also rule out them out if the borrowed references in parameters are all read-only (ro) and no borrowed reference is returned. Beyond this simple test, there are two specific situations where lifetime annotations might be required.

Returned borrowed references

When a function returns a borrowed reference and accepts at least two borrowed references as parameters, lifetime annotations might be needed. Let's illustrate with a simple example:

fn caller(nbr i32) i32 {
  mut ref &i32;
  imm outer = 5;
  {
    imm inner = 10;
    ref = refswitch(nbr, &outer, &inner);
  }
  *ref; // Is this safe???
}

That final de-reference will not be safe if the called function looks like this:

fn refswitch(nbr i32, ref1 &i32, ref2 &i32) &i32 {
  if nbr < 0 {
    ref1;
  } else {
    ref2;
  }
}

The problem is that caller has no idea whether refswitch will return a reference to inner or outer. Since it could possibly be a reference to inner, that final de-reference could be unsafe, as inner is gone by the time the de-reference happens.

However, if we call a function that clearly indicates the returned reference only originates from ref1 (by marking ref2 as having a different lifetime 'a), then caller's logic is safe:

fn refswitch(nbr i32, ref1 &i32, ref2 &'a i32) &i32 {
  ref1;
}

If the signature shows the returned reference originates from ref2, caller once again triggers a compiler error:

fn refswitch(nbr i32, ref1 &'a i32, ref2 &i32) &i32 {
  ref2;
}

The lesson here is pretty simple: If a function returns a borrowed reference, make sure its lifetime annotation matches the borrowed reference(s) it could be sourced from. Then make sure that any borrowed references that are not the source for it are marked with a different lifetime. When correctly marked in this way, lifetime constraints will be properly enforced on both the caller and called functions.

Mutable borrowed reference parameters

When a function passes at least two borrowed references as parameters, at least one being mutable, lifetime annotations might be needed. Consider:

fn tryit() {
  imm i = 5;
  mut a = &i;
  {
    imm b = 10;
		refstore(&mut a, &b); // is this ok?
	}
}

That's not going to work if it calls this function:

fn refstore(refmut &mut &i32, refval &i32) {
  *refmut = refval;  // Oh my!
}

What's the problem? refstore assumes that both borrowed references point to objects of the same (smallest) lifetime. tryit knows that smallest lifetime is the scope of b. However, it realizes that there is a risk that refstore might store refval in retmut (as it does!), which would effectively lengthen the reference's lifetime to the scope of a, which is longer than the known lifetime of the object (b) it points to. Because of this risk, tryit will trigger a compile error on that call.

The same risk arises whenever a call is handed a mutable (or unique) borrowed reference to anything that can hold a borrowed reference, not just to a borrowed reference itself: a struct with a borrowed-reference field, an Option or List of borrowed references, or a slice of them. A method's self &mut receiver counts the same way, so a setter that stores its argument into a field of its receiver, or a push onto a list of borrowed references, may not be handed a borrowed reference that lives less long than the receiver's value:

struct Holder {
  pub r &i32;
  pub fn set(self &mut, r &i32) { self.r = r; }
}

fn tryset() {
  imm i = 5;
  mut h = new Holder(&i);
  {
    imm b = 10;
    h.set(&b);  // error: h outlives b
  }
}

Handing over a borrowed reference that lives at least as long as the place it could be stored in is always allowed.

There are two ways to make this error go away. The first involves move b to the same scope as a, making the lifetimes truly equivalent. The other approach is to make the refstore function promise it won't store one reference inside the other, by marking their lifetimes as independent:

fn refstore(refmut &mut &i32, refval &'b i32) {
  **refmut = *refval;
}

The lesson here is once again simple: If you pass a mutable borrowed reference, mark every other borrowed reference with a different lifetime annotation if you don't intend for it to be stored in the mutable borrowed reference.

Lifetime Annotations on Fields

It is not enough to just constrain the lifetimes of borrowed references, we must also constrain the lifetimes of any data structures that contain borrowed references as fields. Consider:

struct Wrapper['a, 'b] {
  pub refa &'a u32;
  pub refb &'b u32;
}

Every Wrapper value contains two fields, both borrowed references, each with a different lifetime constraint. The lifetime of this value will be constrained by whichever ends up as the shorter of the two lifetimes:

fn process() {
  imm val = 5;
  makewrap(&val);
}

fn makewrap(valref &i32) Wrapper {
  imm val = 10;
  new Wrapper(valref, &val);  // oops
}

The Wrapper value is created in the makewrap function using a borrowed reference created in that function. Therefore, this value is lifetime-constrained to this function and may not be returned to process.

Declaring a struct's lifetimes

A struct (or an enum) declares the lifetimes its fields name in its square brackets, apart from its type parameters: struct Wrapper['a, 'b], struct Cursor['a, T]. Its fields name those lifetimes and no others. A struct whose fields name exactly one lifetime may leave its brackets without it, and that one is taken as declared; one whose fields name two or more declares them all, so that a misspelled name is caught rather than taken for one more lifetime. Every borrowed reference a struct declaring lifetimes holds names one of them: an unnamed borrow there would be of whatever lifetime each signature using the struct leaves unnamed.

A lifetime changes neither a struct's layout nor its code, so it is never instanced: Wrapper['a, 'b] and Wrapper are one type, and a generic struct has one instance per type argument, none per lifetime. A struct is constrained by a lifetime only by holding a borrow: one declaring lifetimes but holding no borrow travels anywhere, and a generic one is constrained per instance (List[&R] is, List[i32] is not).

Lifetime Annotations on Types

The same lifetime annotation principles we discussed earlier apply to functions that receive or return values which have borrowed references within them as fields.

fn process() {
  imm val = 5;
  makewrap(&val);
}

fn makewrap(valref &i32) &i32 {
  imm val = 10;
  getref(new Wrapper(valref, &val));
}

fn getref(wrap Wrapper['a, 'b]) &'a i32 {
  wrap.refa;
}

getref shows how lifetime annotations are specified on aggregate types: inside the struct's square brackets are two lifetimes, one for each lifetime the struct declares, in the order it declares them. Notice that the function returns the borrowed reference held by refa (the longer one), also signalled by the lifetime annotation on the return type. A use naming none, Wrapper, gives every lifetime the struct declares the signature's unnamed lifetime.

Were we to change getref to return refb instead, the makewrap function will be smacked with an error for trying to return a borrowed reference it created and which must not outlive its scope.

Lifetimes in a struct's methods

Inside a struct's methods, Self (and so an unwritten self type) is the struct with its own lifetimes, which act there as the caller's lifetimes do. A method may so promise that its result points where a field points, not into the struct:

struct Cursor['a] {
  pub items &[]'a R;
  pub at usize;
  pub fn next(self &mut) Option[&'a R] {
    if at < items.len() {
      imm r = &items[at];
      at = at + 1usize;
      return Some[&R][r];
    }
    None[&R][];
  }
}

fn firstOf(items &[]R) Option[&R] {
  mut c = new Cursor(items, 0usize);
  c.next();     // Ok: points where items points, not into c
}

Because next's result is of the cursor's 'a, not of the &mut borrow of self, a call keeps frozen only what the cursor holds in 'a, and the result may outlive the cursor. Written without lifetimes, the result would share the receiver's borrow, and could not be returned. The method in turn may return only what its fields of 'a point at: &self.at, a borrow of the cursor itself, is of self's own lifetime, not 'a.

Two lifetimes in one struct

A struct may hold borrows of two unrelated lifetimes. A value of it is usable wherever all its lifetimes hold, and what one of them holds is kept apart from the other's:

struct Parser['src, 'ar] {
  pub text &[]'src u8;
  pub ar &'ar mut Scratch;
  pub at usize;
  pub fn word(self &mut) &[]'src u8 { ... }
}

fn firstWord(text &[]u8) &[]u8 {
  mut scratch = new Scratch(0);
  mut p = new Parser(text, &mut scratch, 0usize);
  p.word();     // Ok: the word is of the text, not of the local scratch
}

With one lifetime for both fields, the word could hold anything the parser holds, the local scratch arena included, and could not be returned. A borrow of one of two unrelated lifetimes may not be stored where the other's are held: that needs a where clause ordering them (below). A call whose signature names the struct's lifetimes as one, or orders them beyond the struct's own order, may move a borrow from one field to another, so after it the caller no longer knows which field holds which borrow, and keeps them all as one.

Where clauses ordering lifetimes

Two lifetimes a signature names are unrelated unless its where clause orders them. 'a >= 'b says 'a lasts at least as long as 'b: a borrow of 'a may then be stored where 'b borrows are held, and returned where a 'b one is promised, but not the reverse. 'a == 'b orders each at least as long as the other. The order is transitive, and nothing beyond what the clauses say, and their transitive closure, is inferred.

fn put(d &mut &'b R, s &'a R) where 'a >= 'b {
  *d = s;       // Ok: 'a lasts at least as long as 'b
}
fn pick[T](x &'a T, y &'b T) &'b T where 'a >= 'b and T is Copy {
  x;
}

A caller reads the same order: it keeps put's second argument alive as long as the place its first points at is used. A where clause orders lifetimes on any function, generic or not, among the lifetimes its signature names; on a struct, struct Pair['a, 'b] where 'a >= 'b, among those it declares, in its methods and in every signature using it; and on a generic type's methods. Lifetime comparisons join each other and type clauses by and only: a lifetime is never instanced, so no instance settles which alternative of an or holds, and the body could rely on none of them. An or or a not over a lifetime comparison is refused.
