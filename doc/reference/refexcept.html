Exception Handling

Note: Panics are implemented, as described under Panics below: panic, assert (every build), assertDebug and assertDebugMsg (debug builds only), unreachable, todo, the panic hook and the Never return type. Throwing and catching exceptions, the ? and || operators on a throwing call, requires, and contract conditions are not. Overflow and divide by zero do not panic.

An exception occurs whenever a program tries to do something and fails. Sometimes, there is no graceful way to recover from certain exceptions. For example, maybe the program:

  • Needs more heap or stack memory and it is all used up.
  • Encounters a math error, such as an overflow or divide by zero.
  • Tries to access an out-of-bounds memory location.

When there is no obvious way to recover from an exception, the program "panics", shutting down as quickly and gracefully as possible. Part of the shutdown process involves reporting on the nature of the failure so the logic problem that failed to prevent this problem can be fixed.

In many cases, however, it is possible and desirable to recover from an exception. This page describes how.

Throwing Exceptions

Recoverable exceptions are always directly communicated from one function back to the function that called it. Instead of returning the expected value, it throws an exception value.

fn factorial(mut n i32) i32 throws bool {
  if n <= 0 { throw false; } 
  mut result = 1;
  while n {
    result *= n--;
  }
  result;
}

This function specifies throws as part of its signature to indicate that if it cannot successfully return an integer value, it will throw a boolean exception instead. The first line does exactly that: If the parameter is a negative number, it throws an exception value of false.

Exception Handling

Now that we have a function that can throw an exception, let's show different ways to handle it.

Give exception a default value

Use the || operator to establish a default value in the event of a thrown exception.

fn calc(n i32) i32 {
  factorial(n) || 0;
}

If factorial throws an exception, it is treated as if it had returned 0 instead. The value to the right of the operator must be a plain value, and its type must match that of the success value on the left.

Panic on exception

Use the ? operator following any call to an exception-throwing function.

fn calc(n i32) i32 {
  factorial(n)? + 10;
}

This checks whether the function call succeeds and returns a value. If so, it adds 10 to that result and returns it. Since this function gives no clue on how to handle an exception, the default behavior on a thrown exception will be that the program panics and shuts down.

Exception propagation

Another approach involves re-throwing the exception to the next caller up the call stack.

fn calc(n i32) i32 throws bool {
  factorial(n)? + 10;
}

Even though this function still does not specify an exception handler, its signature shows that it also throws exceptions. As a result, if the call to factorial throws an exception, that exception will be re-thrown to the function which called calc. Importantly, there must be a type match between the exception value received and the one the function re-throws.

catch exception handlers

If we want some other behavior than panic or re-throw, one or more exception handlers must be specified in the form of a catch blocks. This block appears at some point after the try, but need not be immediately afterwards.

fn calc(n i32) i32 {
  factorial(n)? + 10;
	
  catch {
    0;
  }
}

Should the call to factorial throw an exception, the catch block handler will be run. In this case, it returns the number 0. In effect, we have completely recovered from the thrown exception, as this calc itself throws no exception.

Alternatively, we could handle it by throwing an exception of a different type or value.

fn calc(n i32) i32 throws i32 {
  factorial(n)? + 10;
	
  catch {
    throw 0;
  }
}

If we need more information about the exception, a variable name (and optionally a type) may also be specified on the catch statement. This binds to the exception value, so that it may be interrogated: 

fn calc(n i32) i32 throws i32 {
  factorial(n)? + 10;

  catch err {
    if err {
      panic("factorial failed");
    } else {
      throw 0;
    }
  }
}

This handler will trigger a panic if the thrown exception value is false. Otherwise, it will throw a new exception value of 0.

Panics

Recovering from a thrown exception may be possible and the right thing to do in certain circumstances. However, sometimes the right response to a bad condition is to intentionally shut the program down: something that must not happen has, and going on would only compound it. A panic is a bug report, not a way to handle an error. The core library's panic does it:

fn half(n i32) i32 {
  if n % 2 == 1 {panic("half of an odd number");}
  n / 2;
}

A panic writes out whatever the program has printed to stdout, then one line to stderr, naming the source file and the line where panic was called, and the message:

panic at shapes.cone:2: half of an odd number

and then ends the program at once, through the C library's abort. Nothing unwinds: no finalizer runs, no caller sees the panic, and the program's other threads end with it. A panic on a thread other than the one the program started on names it: panic in thread 5828 at ....

The checks the compiler inserts panic the same way, naming what they found: an index out of bounds (index 5 is out of bounds for a count of 3), a slice's range (slice 2..7 is out of bounds for a count of 5), and an allocation whose region has no memory to give (out of memory allocating 24 bytes).

Never

panic returns Never, the type that says a call does not return. So it may end a block that must produce a value, as a return may, and gives that block no value on that path:

imm half = if n >= 0 {n / 2;} else {panic("negative");};

A function of a program's own may return Never, and must then end in a call that does not return, or in an if each of whose paths does; it may not say return. The C library's abort and exit return Never.

unreachable and todo

unreachable() marks code the author knows cannot be reached, and todo() code not written yet. Each returns Never, and panics if it runs, with a message of its own or one given:

match n {
  case ==1 {"one";}
  case ==2 {"two";}
  else {unreachable();}
}
fn area(sides i32, size i32) i32 {
  if sides == 4 {size * size;} else {todo("areas of other shapes");}
}

assert and requires

assert triggers a panic when its condition evaluates to false, with the message given, or assertion failed.

assert(idx < bound);
assert(idx < bound, "the index is within the table");

assert is performed in every build, release builds included. assertDebug is performed in debug builds only (conec --debug, and Congo's default): in a release build the whole use is dropped, and its condition is not evaluated, so a check may cost what it likes, and a condition with a side effect has it only in a debug build. assertDebugMsg is the same with a message of its own. The panic names the line where either is used, as assert's does, and says the same: assertion failed, or the message given.

assertDebug(isSorted(table));
assertDebugMsg(isSorted(table), "the table is kept sorted");

Both are macros in the core library, so the condition is substituted where they are used rather than evaluated before the call. Each expands to an if on isDebugBuild(), a constant that is true in a debug build, and a program may branch on it the same way. A macro takes no default argument, which is why the form with a message has a name of its own. This split, and these names, are Jon's ruling of 27 Sep 2026; the camelCase spelling of assertDebug is for now.

This page first had assert performed only in test builds, and a requires statement as the equivalent guarantee in production:

requires idx < bound;

That always-checked role is now assert's. requires and ensures are kept for the contract conditions below, which are not built yet.

Where it happened

Each of these reports where it was called, not where it is written in the core library. Each takes two more parameters, file &Array[u8] = srcFile() and line u32 = srcLine(), whose default values answer where the call taking them is. A function that panics on its caller's behalf may declare the same two and hand them on, and then reports its caller too:

fn at(list &Array[i32], i usize, file &Array[u8] = srcFile(), line u32 = srcLine()) i32 {
  if i >= list.len {panic("past the end", file, line);}
  list[i];
}

assertDebug and assertDebugMsg take neither parameter. They are macros, and srcFile() and srcLine() written in a macro's body answer where the macro is used. In a macro used inside another macro's body, they answer where the outermost one is used.

The panic hook

setPanicHook names a function a panic calls once its line is written and before the program ends, with the message and the location: to log the failure somewhere, or report it. The last one set is called, from whichever thread panicked. A panic inside it ends the program at once.

fn logPanic(msg &Array[u8], file &Array[u8], line u32) {
  // write it to the log
}

setPanicHook(&logPanic);

Contract conditions

Where we want a function to preserve some invariants on entry and exit from the function, the requires and ensures clauses may be added to a function signature. These provide a visibly strengthened contract that governs use of the function. If these conditions fail, a panic is triggered.

fn factorial(mut n i32) i32
  requires n > 0
  ensures result > 0 {

  mut result = 1;
  while n {
    result *= n--;
  }
  result;
}

This function expects that it will get a positive, non-zero number and return the same. Any other behavior is a bug which we want to catch quickly in testing and fix.
