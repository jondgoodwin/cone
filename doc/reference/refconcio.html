I/O and Concurrency

Note: The text under "The original exploration", below, is the original exploration of the question, kept as it was written. What is built is in library packages, Windows only for now:

  • Blocking, synchronous I/O: fs (files and folders), path and env (beneath them, the posix package maps POSIX onto the Windows C runtime), and process, which runs a program and waits for it, its insides written over Windows' own kernel32.
  • Asynchronous I/O, completion-based: iocore is the completion loop, over an I/O completion port. A program hands a loop a job (receive into this buffer, send these bytes, accept a connection, read a file at an offset, wake at a time) and later gets exactly one answer for it, carrying the buffer back. A job can carry a deadline and belong to a cancel group, and a blocking pool runs work that has no completion form. Beneath it: iobuf, owned buffers lent to an operation by moving them; timewheel, its timers; time and calendar, time values; and diag, records of where an operation's time went.
  • HTTP and TLS over it: http1, HTTP/1.1's connection core, sans-IO; httpconn, which joins it to real sockets on a loop, client and server; tls, TLS 1.2 and 1.3 over OpenSSL, also sans-IO, with a server's certificate checked by the operating system; url, URLs as data; and httpclient, which fetches an http:// or https:// URL in one call, with connection pooling, retries and redirects.
  • I/O an actor awaits: aio. An actor's behaviour may await a socket's operation — listen, accept, connect, read, write — and pauses there until the operation's answer comes, as it pauses for another actor's reply (Awaiting a reply; below, Awaiting I/O). TCP sockets only.

Awaiting I/O

An actor's behaviour waits for I/O the way it waits for another actor's reply: with await. The aio package makes each operation; awaited, the behaviour pauses, the actor goes on with its other messages, and when the operation has finished, the rest of the behaviour runs with its answer. A server and a client, each an actor:

// The Socket an answer holds, swapped out of it: Socket.none() if it failed
fn socketOf(r Result[Socket, IoError]) Socket {
  mut res = r;
  mut s = Socket.none();
  match &mut res {
    case mut ok &mut Ok {s <=> ok.value;}
    case imm e &mut Error {say("failed", u64.from(e.value.code));}
  }
  s;
}

actor Client {
  pool Pool;

  pub async do send(self, port u16) {
    imm conn = socketOf(await aio.connect(SocketAddr.localhost(port)));
    mut buf = pool.mustTake(64usize);
    buf.append("hello");
    imm sent = await conn.write(buf);          // pauses until all of it is sent
    match sent {
      case imm e Error {say("write failed", u64.from(e.value.code));}
      else {}
    }
  }                                           // conn closes here
}

actor Server {
  pool Pool;
  client Client;

  pub async do serve(self) u64 {
    imm listener = socketOf(await aio.listen(SocketAddr.localhost(0u16)));
    imm addr = await listener.localAddr();     // the port the system chose
    match addr {
      case imm a Ok {client.send(a.value.port());}
      case imm e Error {say("no address", u64.from(e.value.code));}
    }
    imm conn = socketOf(await listener.accept());
    imm none = await conn.read(IoBuf.empty());           // a buffer with no room
    match none {
      case imm e Error {say("no room: error", u64.from(e.value.code));}
      else {}
    }
    mut total = 0u64;
    mut more = true;
    while more {
      imm got = await conn.read(pool.mustTake(4096usize));
      match got {
        case imm b Ok {
          if b.value.len() == 0usize {
            say("end of stream", total);                 // the peer closed
            more = false;
          } else {
            say("received", u64.from(b.value.len()));
            total = total + u64.from(b.value.len());
          }
        }
        case imm e Error {
          say("read failed", u64.from(e.value.code));
          more = false;
        }
      }
    }
    total;
  }
}

(say prints a word and a number on a line; Pool and IoBuf are iobuf's, SocketAddr and IoError iocore's, and Socket aio's.) Sent serve(), the server prints:

no room: error 122
received 5
end of stream 5

Each await there pauses one behaviour, and only it. While the server waits for a connection, the client waits for its connect; the worker threads run neither until an answer comes.

What an operation answers

Each operation declares its own answer, and the await's value is exactly that: await adds nothing to it. An operation that can fail answers as a synchronous call that can fail does, with a Result: the success, or the operating system's failure, an IoError whose code is the system's error number.

  • aio.listen(addr), aio.connect(addr), listener.accept(): a Socket. Cone does not yet move a value out of a matched variant's field, so it comes out by a swap, as socketOf does.
  • conn.read(buf): the buffer, given back with what arrived appended to it. The buffer is moved into the read, which is how the system may write into it while the behaviour waits, and the read's answer is how it comes back. At the end of the stream, when the peer has closed, it comes back as it went, its length unchanged. A failed read's buffer goes home to its pool.
  • conn.write(buf): the count written, which is all of the buffer; the buffer goes home.
  • s.localAddr(): the address the socket is bound to.

An operation's answer must be used. An await on one that is a statement of its own would drop the failure unread, so it is refused:

  pub async do careless(self, conn Socket) {
    await conn.write(pool.mustTake(64usize));   // refused: the answer is not used
  }

This 'await' waits for an operation, which answers with a Result, and the answer is not
used. An operation's answer says whether it worked, a failure among what it may say, as a
synchronous call that can fail answers, and it must be looked at: bind it, 'imm r = await
...', and match on it.

An operation is made by the call (conn.read(buf)) and started by the await; one made and never awaited does nothing, and is dropped. An operation that did not finish — cancelled, because its socket was closed while it was in flight — has no answer to give, and the await panics, naming the line that made the operation. Nothing lets a behaviour put a time limit on an awaited operation, or cancel one.

Sockets

A Socket moves: it may be sent in a message to another actor. Dropping it closes the socket, after whatever operations were started on it before. A socket in a paused behaviour waits with the behaviour, as any value does (What crosses an await), so it stays open until the behaviour ends.

The I/O thread, and the program's end

The operations run on one thread of their own, the I/O thread, which the first operation awaited starts: it waits in iocore's completion loop, and hands each answer to the actor awaiting it as a message, in its mailbox. The worker threads never wait on I/O. An operation in flight keeps the actor awaiting it alive, whether or not anything else holds the actor, as a request to another actor does.

At the program's end, finalAll() waits until no actor is queued or running — an actor paused on I/O is neither — and then ends the I/O: every operation still in flight is cancelled and every socket closed, and the answers are not delivered. Each behaviour still paused on one is abandoned: the rest of it never runs, and every value it held when it paused is finalized, in the order it would have died in had the behaviour ended there, once nothing else holds its actor. A server waiting for a connection that never comes ends this way; so does a read from a peer that never sends.

Not built yet

  • Files, the blocking pool's work, UDP, and a socket's half-close, awaited.
  • More than one I/O thread.

The original exploration

I/O encompasses any processing activity that extends beyond the boundaries of CPU/memory computation, including user input and presentation, file or network requests, timers, etc. From the perspective of the CPU, I/O activity can often take a long, indeterminate amount of time, which presents a complicating challenge to efficiently scheduling concurrent work.

In essence, we want to satisfy these essential requirements:

  • We don't want I/O activity to block the CPU from performing other available work.
  • When any I/O activity reports progress, we often want to continue processing where we left off, based on a remembered execution and data state (context).
  • We sometimes want the option to "cancel" already-requested i/o work based on time-outs, failures or other changed conditions. Sometimes, we want to cascade cancellation through multiple levels of already-submitted requests.

There are several architectural approaches to satisfy these requirements:

  • Async/Await. I/O requests are always issued asynchronously (non-blocking), whose returned type is a promise. When I/O finishes or fails, the promise fires the appropriate pre-determined logic.

    Syntactic sugar is used to hide the complexity of the promise handling, so that the "before" and "after" code look like a single block of sequential code. Under the covers, they are actually independent logic, with the context of the "before" code captured as an implicit closure that is passed as a continuation to the "after" code.

    There are two significant drawbacks to this approach:

    • async/await logic infects all functions/methods above it in the execution stack
    • There is no graceful way to implement cancellability
  • Gothreads. I/O requests are synchronous (blocking). It is up to the runtime scheduler to detect that a gothread is effectively blocked on i/o and effectively re-balance work so that other gothreads keep all CPUs busy.

    Although this approach avoids the infectious coloring issue of async/await and is easier on the programmer (no extra annotations), it has its own drawbacks:

    • The runtime logic needed to detect that a gothread is blocked on i/o is not cheap, quick or foolproof. The same holds true for the reverse, noticing when the gothread becomes unblocked. As a result, this approach is likely slower than an equivalent async/await implementation.
    • There is no graceful way to implement cancellability
  • Actors. Whenever multi-step i/o is required, the requesting actor (Requester) spawns a new actor (Workflow). Part of the spawning message is the id of the Requester actor to return the final result to. Workflow issues i/o requests as asynchronous messages to some environmental i/o actor. Completed (or failed) i/o are sent as messages to the Workflow actor who can use its preserved context to know what to do next. When the Workflow actor is finished with all its processing, it returns a response to the Requester workflow as a message.

    Like async/await, this uses continuation-passing style. In this case, the continuation is an actor (and its state) able to support multiple kinds of messages. Since the actor accepts asynchronous messages from any actor, it can also support the notion of a cancel message, and even the ability to pass that cancel message on, dependending on its state. Unlike async/await, there is no notion of infectious function colors up the execution stack, as all actors are already found at the top of the execution stack from the point-of-view of the runtime scheduler.

    The primary challenge of this approach is that it requires the programmer to manage the concurrent workflow explicitly with actors. This may be a challenge for programmers who are only familiar with synchronous-style programming.

Currently, the projected design for Cone is leaning towards an Actor-based approach for handling asynchronous I/O, sequential workflows, and cancellability.
