Cone
Thread Communications

Note: Three things on this page are implemented: the channel of many senders and one receiver, Channel[T], unbounded or bounded, or of one sender and one receiver, as the sync library package, on Windows only; and the atomic primitives, as core's Atomic[T], over the raw atomic operations core declares, which are intrinsics. Immutable data is shared between threads through the same package's Arc region (import sync use Arc), whose count is atomic: Arc[imm, T] owners may be copied and dropped on any thread, and the value is freed once, after the last (regions); an Rc owner's count is not atomic, and it must stay on one thread. What is sent is checked: thread.start and the channel types take only a Sendable type, as Race condition safety describes. And actors: the actor declaration, made with new, each of its behaviours, declared async do, a message its handle sends, and each of its methods declared fn synchronous; and the actors library package it runs on, on Windows only: mailboxes, a work-stealing scheduler, quiescence, and handles counted through Arc, starting with the first actor and stopped by finalAll(), which a program calls itself until the entry that will call it exists. A behaviour may return a value, and await on a behaviour of an actor waits for it: the behaviour awaiting is cut there, what it still needs waits in its actor until the reply comes, and the rest of it runs then (Awaiting a reply); a call of such a behaviour whose value is kept gives a future, actors.Future[T], which may be stored, handed on and awaited later (Storing a future); an actor names its own handle selfactor, and self.m(), where m is one of its own behaviours, sends it. The compiler checks an await — that it stands in a behaviour, that what it awaits returns a value, and that no borrow but a 'static one is used after it, every other ending there — and builds it on a behaviour that returns a value, on a future, and on an I/O operation the aio package makes (Awaiting I/O); an await on anything else is refused. One in a few constructs the cut does not reach yet, or one whose continuation would hold a traced reference, is reported where it is written; nor is there a time limit on an await, a way to cancel one, or a way to await whichever of several futures arrives first (Not built yet). The compiler's --await-direct option, which is for testing the cut, runs the rest of the behaviour at once after an await on anything else, with the value awaited. Not implemented: actor trait, a generic actor. qfn and the other concurrent data structures are not implemented; the lock permissions Mutex and Rwlock are, on Arc. An enum's variant is constructed with its values in square brackets, as written here: that is the current spelling, and how a variant is constructed is an open design question (Enums).

It can be a huge performance benefit that threads share memory and other resources, particularly when the threads need to exchange or share large, complex data structures. However, thread-shared memory also opens up safety risks when communications are not properly synchronized.

To mediate these risks, Cone offers several mechanisms that facilitate fast, convenient, safe communications between threads.

Race condition safety

Any data passed or shared between threads must be done so safely. Cone ensures this by only allowing "sendable" data to be sent to another thread. The only type of data that is not sendable is a reference that has the "mut" or "ro" permission, or any aggregate type containing such a reference. Data of any other type is sendable, including shared, immutable references, unique references (which are moved from one thread to another), and any other move or copy type.

These restrictions apply to all mechanisms that support communications between threads, such as thread creation, concurrent data structures, and more.

What the compiler checks today. Library code marks what crosses threads with the built-in marker trait Sendable, as a constraint on a generic: thread.start and thread.startWith ask it of the argument and of what the thread returns, and Channel[T], Sender[T], SoloSender[T] and Receiver[T] of T. The compiler grants Sendable to a type unless it holds, directly or in a field, an array element, a tuple element or an enum's variant, one of these:

  • a borrowed reference, of any permission, &imm included: a borrow's lifetime is checked in one thread alone, until scoped threads join inside it (but for a borrow that lasts the whole program, below);
  • an owner that may be copied whose permission is not race-safe: Rc[mut, T], Arc[mut, T], and a lock permission for one thread, Rc[Rwcell, T]; a lock permission for threads crosses, Arc[Mutex, T] and Arc[Rwlock, T], where T may (Lock Permissions);
  • an owner that may be copied in a region that does not declare ThreadSafe, whatever its permission: Rc[imm, T], whose count is not atomic. Arc[imm, T] and Arc[opaq, T] cross;
  • a traced reference, Gc, whatever its permission, until each thread has its own collector;
  • a raw pointer, whose target nothing checks.

An owner that moves takes its value with it: a uni owner of any region, and any owner of So, crosses when what it points at may. So does an Arc[imm, T] owner: an Arc of a value holding a mut reference is refused. A reference to a function crosses. A type holding raw pointers it shares safely declares is Sendable, which the compiler takes on trust, as a channel's ends, ThreadRef, and the collections package's List and Dict do; an instance of a generic type declaring it is Sendable only where its type arguments are.

What is checked is the type of the value, not how a variable was declared: a local declared mut x = 5 holds a number, which is sendable, while &mut x is a borrow, which is not. A refusal names the part of the type that binds it to its thread:

struct Job {pub data &mut Counter;}
thread.start(job, &work);
// start requires A is Sendable, and Job is not Sendable: Job.data is &mut Counter,
// a borrowed reference, and no borrow may leave its thread ...

A borrow that lasts the whole program ('static, Lifetimes) is checked in no thread's scope, so it may cross threads and actors in either of two cases, and in no other:

  • it is imm or opaq, and what it reaches is safe for two threads to read at once, as the value of an Arc[imm, T] must be: no Rc and no Gc in it, no raw pointer, no borrow that is itself refused;
  • it is uni, and what it reaches is safe to move. A uni borrow moves, so one holder only has it.

An ro borrow never crosses, even of a global: ro only stops this holder from writing, and another holder (mut) may still change what it reads (Permissions). Nor does a mut one. Nor does a borrow of an invariant lifetime (&'=a T, a key): the lifetime is an arena's brand, and the arena dies when its owner drops it. A uni borrow of a named global is refused where it is made ("cannot obtain this permission"): any code reaches a global by name, so it is not unique. A uni borrow of an owner that nothing else can reach would be unique, and crosses; an owner leaked for the rest of the program, which would make one, is not built yet, but a signature may already take one: fn f(p &'static uni T).

A generic says that a type parameter may be such a borrow by bounding it, [A Sendable + 'static] as thread.start does, and the call is then checked to hand it only borrows of the whole program (Lifetime bounds); without the bound, Sendable refuses every borrow as before. An actor's initializer or behaviour takes one by writing it 'static, and what it reaches is asked the same way. So is a behaviour's reply: it may be &'static imm T, &'static opaq T or &'static uni T, or a struct holding one, under the same rule.

imm table Array[u64, 3] = [1u64, 2u64, 3u64];
fn sum(t &imm Array[u64, 3]) u64 { (*t)[0] + (*t)[1] + (*t)[2]; }
imm t = thread.start(&imm table, &sum);    // Ok: an imm borrow of a global

actor Reader {
  total u64;
  pub async do addTable(self, t &'static imm Array[u64, 3]) { total = total + (*t)[0]; }
}

thread.start(&table, &sum);                // Error: &ro Array is not Sendable: it is a borrowed
                                            // reference of permission ro ...
thread.start(&imm onTheStack, &sum);       // Error: must be global

Not checked yet: a mut global reached from several threads; a value's own methods that change it through & (sendable here also means safe to read from several threads at once behind Arc[imm, T], which a type declaring Sendable promises too). Actor messages are checked as a channel's values are: every parameter of an actor's behaviour, and of its initializer, must be Sendable, and one that is not is refused where it is declared; an actor's state is not asked, since it never crosses as a value (Actors).

Message-based Communications

An efficient model for thread-based concurrency is independent actors (threads) that throw work to each other in the form of messages placed on an actor's queue. Each actor pulls off messages from its queue in order, and then performs the work requested by the message. For now, let's assume that actors do not need shared, mutable access to objects nor do they perform any resource-blocking operations.

A straightforward way to implement this actor model involves using library-packaged actors that own and use concurrent message queues (or channels). Such multiple-producer-single-consumer (MPSC) channels are themselves library packaged-delivered concurrent FIFO data structures. Any actor that wants some actor to perform work adds that work to the actor's queue in the form of a message. As part of a continuous loop, the actor owning the queue pops a message off the queue and completely performs the non-blocking work it requests.

Channels

The sync package's Channel[T] is such a queue, usable directly between threads, with any number of sending ends and one receiving end. Channel[T].make() answers both ends of an unbounded channel, whose sends never wait; Channel[T].bounded(n), of a bounded one, holding at most n values (rounded up to a power of two), whose sends wait while it is full, so a sender faster than its receiver is held to its pace. The two kinds' ends are the same types, so code taking a Sender[T] takes either. Each end is a move type: another sender is made only by clone(), and the receiver has no clone, so exactly one thread takes from it.

Channel[T].spsc(n) makes the third kind, bounded as the second is, with one sender. Its sending end is a SoloSender[T], which has no clone(), and whose sends take it as &mut: there is exactly one, and one thread sends at a time. Knowing that from the type, the channel needs no atomic read-modify-write on either side, which makes it the fastest of the three where one thread feeds another: a pipeline's stages, or a logging thread's own buffer. Its receiving end is the same Receiver[T], and its methods are the others'.

import sync use *;

mut tx Sender[Job];
mut rx Receiver[Job];
tx, rx = Channel[Job].make();   // the two ends; or Channel[Job].bounded(64)
imm tx2 = tx.clone();           // a second sender, said out loud
tx <- job;                      // send: waits only while a bounded channel is full
match rx.recv() {               // waits while it is empty
  case imm j Some {run(j.value);}
  case is None[Job] {}          // closed, and every value taken
}

mut solo SoloSender[Job];
mut rx2 Receiver[Job];
solo, rx2 = Channel[Job].spsc(1024);  // one sender, no clone
solo <- job;
  • tx.send(v), or tx <- v, puts a value in, waiting while a bounded channel is full. It answers None, or, when the receiver has gone or closed the channel, Some holding the value, handed back rather than lost. A list after <- sends each entry in turn, tx <- a, 3 of next() (the append operator), and drops what each send answers. tx.trySend(v) never waits, handing the value back from a full channel too; tx.sendTimeout(v, d) waits at most d, a Duration of the time package, for room.
  • rx.recv() waits for the next value, oldest first; rx.tryRecv() never waits; rx.recvTimeout(d) waits at most d, a Duration. Each answers an Option.
  • Nothing panics, and no one has to close the channel by hand. The last sender's death closes it: the receiver takes what is left, and then recv answers None. rx.close() refuses later sends while what came before still drains. The receiver's death closes it too, wakes every send waiting for room to hand its value back, and finalizes each value still in it, once.
  • A send waiting on a full bounded channel waits for as long as it stays full: a receiver that stops taking without going leaves it waiting for good. Two threads that each send to the other through bounded channels can so wait on each other; where that may happen, trySend, sendTimeout or an unbounded channel is the answer.

A send is one compare-and-swap, into blocks of 32 slots allocated a block at a time (unbounded) or a ring of n slots allocated at the start (bounded); the receiver takes a value with no read-modify-write at all. A single-sender channel's send is a plain store as well, into Lamport's ring, each side keeping a copy of the other's index and reading the real one only when its copy says full or empty. A thread sleeps, on the futex, only when there is nothing to do: the receiver when the channel is empty, a sender when a bounded channel is full.

Actors

An actor is state that lives on, reached by nothing but messages. Each message is a call of one of the actor's behaviours, its methods declared async do, queued in its mailbox and run later, one at a time, on whichever of a pool of worker threads takes the actor up. A behaviour runs to completion, on that worker's own stack, with the actor's state mut, or to an await, where it is cut ("Awaiting", below); no other behaviour of the same actor runs until it returns there. An actor is declared with actor, and it runs on the actors package, which a module declaring one imports: the mailbox, the work-stealing scheduler, the counting that decides when an actor dies, and the quiescence a program ends at. The package starts and stops by itself: the first actor made starts the workers, and the module's finalizer waits until all is quiet and stops them.

import actors;

actor Counter {
  count u64;                       // its state: private to it

  fn init(self &new, start u64) {   // run by 'new Counter(start)', in the actor
    *self = new Self(count: start);
  }

  pub async do add(self, n u64) {  // a behaviour: sent as a message
    count = count + n;
  }

  pub async do report(self &, to Printer) {   // one carrying another actor's handle
    to.show(self.doubled());
  }

  fn doubled(self &) u64 {         // synchronous: called, inside the actor
    count * 2u64;
  }

  fn final(self &uni) {}           // when it dies
}

fn main() {
  initAll();
  {
    imm c = new Counter(0u64);     // the first actor starts the workers
    c.add(5u64);                   // a message: queued, and run later
    c.add(7u64);                   // run after the first
  }
  finalAll();                      // waits until all is quiet, stops the workers
}

Behaviours. A method declared async do is a behaviour: it runs asynchronously, when the actor is scheduled, and an await on one waits for its reply. async do is one keyword of two words, and neither means anything alone: written without the other, either is refused. async says when the behaviour runs, and pairs with await, as in C# and JavaScript, where a call of an asynchronous function need not be awaited; do is the declaration's verb, as fn is a function's. Unlike an asynchronous function there, a behaviour never starts on the sender's thread: a send only queues the message, so no thread but the actor's touches its state.

Synchronous methods. A method declared fn is synchronous: the actor's init and final, and any helper, which sees the actor's fields directly and runs inside the method that calls it, as a struct's method does (doubled above). It is the actor's alone: never pub, and not carried by the handle. It holds no await: an await belongs at the top of a behaviour, and the synchronous work between awaits is pushed down, onto a helper or onto a type the actor owns (Await in a behaviour).

Four shapes. Whether a behaviour declares a return type, and whether it holds an await, are independent, and each decides one thing: the return type, whether a reply is sent; the await, whether the behaviour is cut and waits. So a behaviour has one of four shapes, each known from its declaration alone:

  • Fire and forget: no return type, no await. It runs once and ends; nothing is sent back, and nothing waits. The cheapest shape.
  • A cheap query: a return type, no await. It runs once and replies with its value as it ends, to a caller that awaited it.
  • Awaits, owes nobody: an await, no return type. It waits for other actors' answers, and answers no one.
  • The full handshake: both. It waits for answers, then replies with its own value.
actor Store {
  total u64;

  pub async do add(self, k u64) {           // fire and forget
    total = self.plus(k);
  }

  pub async do count(self) u64 {total;}     // a cheap query

  fn plus(self &, k u64) u64 {total + k;}   // synchronous: an ordinary call
}

actor Client {
  store Store;

  pub async do run(self) {                  // awaits, owes nobody
    store.add(5u64);
    store.add(7u64);
    imm c = await store.count();
    say("count", c);
    imm r = await self.report();
    say("report", r);
  }

  pub async do report(self) u64 {           // the full handshake
    imm c = await store.count();
    c * 10u64;
  }
}

(say prints a word and a number on a line.) Sent client.run(), with a Store whose total starts at 0, this prints count 12, then report 120: both adds reach the Store before the count does, since one sender's messages are handled in the order sent.

The declaration. An actor's body is written as a struct's: fields, an init, behaviours, synchronous methods, a final. Its fields are its state, private to it: a field is never pub, and nothing outside the actor reaches one. A method's self is the state, lent to a behaviour for the message it handles, and to a synchronous method by its caller: written bare, it is self &mut, which the method has alone while it runs; self & only reads it. A behaviour that is not pub is a message all the same, which only its own module sends; a function without self is the actor's own, called from its methods as a struct's is. A behaviour is not generic, and every parameter it takes is Sendable, since the message carries its arguments to the thread the actor runs on; a borrow is refused unless it lasts the whole program, is written so (&'static imm T, &'static opaq T or &'static uni T) and reaches what may cross (above). A behaviour may return a value, which must be Sendable too, by the same rule, so a borrow in it is written 'static as a parameter's is: a send returns at once, before the behaviour runs, and the value is dropped, unless the behaviour was awaited ("Awaiting", below). An actor declares no static, macro, extern method or use, no type parameters, and names no abstraction: actor trait, its abstraction, is not built yet.

Making one. new Counter(args) makes an actor and answers its handle. The actor is real before its init runs: the runtime's part of it is made first, and the init then runs, on the calling thread, on the state where it will stay. So the init, and any synchronous method it calls, may send to the actor itself, with self.m() or selfactor, once *self = ... has filled the state (before that, self holds nothing, and every use through it is refused, as in any initializer), and may hand selfactor to another actor. The actor runs no message until its init has returned: a message sent meanwhile, by the init or by another actor already given the handle, waits in the mailbox and runs afterwards, in the order sent. A panic in the init is a panic, which ends the program.

actor Starter {
  count u64;

  fn init(self &new) {
    *self = new Self(count: 0u64);
    self.note(1u64);              // a send to itself: queued, run after the init
    self.helper();                // a helper the init calls may send too
    say("init ends", count);
  }

  fn helper(self) {
    selfactor.note(2u64);
  }

  pub async do note(self, k u64) {
    count = count + k;
    say("note", count);
  }
}

new Starter() prints init ends 0, then note 1 and note 3: both notes wait until the init has returned.

The state exists only inside its actor. It is constructed in one place, as the actor is made, where its init fills it, *self = new Self(count: 0u64). Any other construction of it, new Self(...) in one of the actor's methods or as an allocation's value, by its fields' names or by its init, is refused, since the state it made would be in no actor, and the sends it or a helper made to its actor would reach nothing. Nor is the state copied out of its actor: it is a move type whatever its fields are, so imm s = *self is refused, as taking any value out through a borrow is. For a value of the state's shape, declare a plain struct.

The initializer's parameters must be Sendable too, since the state made from them runs on other threads. An actor may declare several initializers, as a struct may, each joining the overload name init. One that declares none is made by its state's implicit initializer: new Counter(5u64) takes the fields whose types are written, in order, a field with a default taking it where the argument is left out. That initializer is the module's own, as a struct's implicit one is where its fields are private, except for a pub actor with no fields at all. There is no other way to make an actor, and no creation function: spawn stays reserved.

The handle. The actor's name names its handle, a value holding one counted owner of the actor's mailbox, the runtime's part of it: copying a handle (passing it, storing it, putting it in a message) makes another owner, and each going drops one. A handle carries the actor's behaviours and nothing else: calling one on it, c.add(5u64), sends that message, and reaching a field of the state or a synchronous method through it is refused as private. A handle is Sendable whatever the state holds: it may be sent to a thread, over a channel, in another actor's message, or kept in another actor's state. So the state may hold what may not cross threads (Rc, a mut owner, borrows inside a method), and never crosses as a value: only the runtime reaches it.

What the declaration stands for. The compiler turns an actor into four ordinary declarations the actors package runs: the state, a struct of the body as written, named Counter.State; the messages, an enum with one variant per behaviour, named for it, its fields the behaviour's parameters, named Counter.Msg; the handle, Counter, whose one field is an Arc[opaq, actors.Mailbox[Counter.Msg]], an initializer for each of the state's, which makes the actor's block with actors.makeActor, constructs the state in it in place, and starts the actor with actors.startActor, and a method per behaviour, as public as the behaviour, which calls actors.send; and the dispatch function, Counter.dispatch, which the runtime hands each message where it lies, and which moves each argument out of it into the behaviour's call. Those names are what a diagnostic about them says; no source can write them, so nothing but the actor reaches its state, its messages or its mailbox. The mailbox and the state are one allocation, so a send touches one block. Actors and the declarations that use them may be written in any order: a message enum holds handles by value, and a handle reaches the enum only through its owning reference to the mailbox, and a reference never needs what it points at to be laid out first.

An actor's life. While an actor is queued to run, or running, the scheduler holds one owner more, taken by the send that found it idle and dropped when its mailbox is found empty. So an actor dies exactly once, when its last handle has gone and its mailbox is empty: a handle dropped with messages still queued leaves the actor alive until they are handled. At its death its state is finalized (its final, then its fields, handles to other actors among them), on whichever thread let go last, then the block is freed. Actors that hold handles to each other in a cycle never die by counting, as a cycle of Arc owners never does, until one of them lets go.

Messages. A send is one-way: it queues the message and returns. An answer comes back only to an await (Awaiting a reply), or as a message sent back to a handle passed along. Each sender's messages to one actor are handled in the order sent, and a message is never overtaken by one it caused. Each argument arrives moved into the behaviour's call, once: a value that may only move (a uni or So owner) arrives whole, and a counted one (a handle, an Arc, a lock-managed Arc[Mutex, T]) is counted once.

Sending to itself. In the actor's own methods, self.m(args), where m is one of its behaviours, sends m to the actor itself, as selfactor.m(args) does: the message joins the end of the actor's own mailbox, the method goes on at once, and m runs later. A behaviour is never called, not even by its own actor: it runs only when its dispatcher takes up a message for it. A synchronous method is called, as a struct's is.

actor Echo {
  pub async do start(self) {
    say("start", 1u64);
    self.later(1u64);             // a send to itself: start goes on at once
    self.relay();                 // a synchronous helper, an ordinary call
    say("start ends", 1u64);
  }

  async do later(self, k u64) {
    say("later", k);
    if k == 2u64 {
      self.finish();
    }
  }

  fn relay(self) {
    later(2u64);                  // 'self.later(2)': a send, from a helper too
  }

  async do finish(self) {
    imm d = await self.double(21u64);
    say("finish", d);
    self.show(d / 2u64 - 11u64);
  }

  async do double(self, k u64) u64 {k * 2u64;}

  async do show(self, k u64) {
    say("show", k);
  }
}

Sent echo.start(), this prints start 1 and start ends 1 before either later runs, then later 1, later 2, finish 42 and show 10. A behaviour reached through anything but the method's own self — such as another borrow of a state, a parameter's — is refused, and so is one sent through self in the actor's final, as it dies. In its init it is a send like any other, run once the init has returned (Making one).

Awaiting. In a behaviour, await on a behaviour of an actor that returns a value sends it and waits for that value: the behaviour pauses there, the actor handles other messages meanwhile, and the reply resumes it (Awaiting a reply, below). In a method, selfactor is the actor's own handle, another owner of it, which may be sent anywhere a handle may; self is its state, which never leaves it.

Inside an actor a method may use what a single thread may: borrows, and So and Rc owners, whose count need not be atomic, since one worker at a time runs an actor and every hand-off of an actor between workers orders what the first did before anything the next does. Three things differ from a plain thread:

  • Gc is not supported inside an actor. The collector is single-threaded, and an actor runs on every worker in turn; a traced reference made, held, reached or dropped by an actor corrupts it. Nothing refuses one yet.
  • A thread-local global seen from an actor's method is the current worker's copy, not the actor's: its next message may run on another worker.
  • A method that blocks holds its worker while it does. Actors wait by being sent a message.

The runtime starts and stops by itself. The workers start with the first actor, on whichever thread starts it; two threads starting a first actor at once start them once. A program that starts no actor starts no thread. They start then, not in the module's initializer, which is initpure. Before the first actor, actors.configure(new actors.Options(workers: n, batch: b)) sets n workers (by default one per logical processor), each running at most b of an actor's messages at a turn (100 by default) before the actor goes to the back of the queue; once the workers run, it is a panic. The actors module's finalizer, run by finalAll(), waits until the runtime is quiescent — no actor queued or running, so no message in any mailbox — then stops the workers and joins them. finalAll() finalizes the program's own module first, so the handles its globals hold are let go before the wait; handles in main's locals go at the end of their block, which is why the example above starts its actors in one. The runtime is not started again: starting an actor or sending a message once the workers have stopped is a panic, since nothing would run the message. Quiescence assumes that once the finalizer has begun every message comes from an actor: another thread that goes on sending is joined first. actors.stats() answers what the workers have done so far (Stats: workers, messages handled, turns, steals, loop pieces stolen), without stopping them, and the run's totals once they have stopped. actors.workerIndex() is the index of the worker running the caller, or actors.noWorker.

Until the entry a program's framework will supply exists, a program calls initAll() and finalAll() itself (Running every module's initializer and finalizer). A program that does not call finalAll() ends when main returns, whatever its actors are doing: messages still in flight are silently dropped, and no actor still alive is finalized.

How it works. A mailbox is Vyukov's intrusive queue of many senders and one receiver, as Pony's runtime has it: a send is one atomic exchange and one store; the worker running the actor takes messages with no read-modify-write; a mark on the mailbox says the actor is idle, and the send that finds it queues the actor. Each worker has a run queue of its own, and there is one shared inject queue: an actor made runnable by a send from a worker is queued on that worker, one made runnable by any other thread on the inject queue. A worker with nothing of its own takes a share of the inject queue, then steals half of another worker's queue. An idle worker parks on the futex, and is woken, one at a time, as work arrives. Quiescence is found by counting the activations each worker begins and ends, and reading the counts twice.

A parallel loop runs on the same workers. The language writes one as parallel each, outside actors; below it is the low-level form it is written over, called as a library function:

import actors;

struct Job {
  pub out *u64;
}
fn square(data *u8, lo usize, hi usize) {      // the body: a sub-range [lo, hi)
  imm j = data as *Job;
  mut i = lo;
  while i < hi {*((*j).out + i) = u64.from(i) * u64.from(i); i = i + 1usize;}
}
actors.parallelRange(0usize, 100000usize, 256usize, &square, &mut job as *Job as *u8);

actors.parallelRange(lo, hi, grain, body, data) calls body(data, a, b) over pieces of [lo, hi) of at most grain items, on any worker and at once, and returns when every piece has finished. The loop starts as one task for the whole range; whoever runs a task splits it in half while it is longer than the grain, puts one half on top of its worker's queue of tasks, and works the other, and an idle worker steals the oldest, largest half, so uneven work spreads itself and nothing is divided ahead of time. A worker takes its own tasks before its actors, and a worker that steals prefers tasks to actors. The caller works on its own loop while it waits, so the loop may be called from main (it starts the workers if no actor has), from any thread, from inside the body of another loop, and from inside an actor's behaviour: there the actor is not run again until the loop has finished, while its mailbox goes on accepting messages, which are handled afterwards in order. It trusts its caller: the body must write only its own sub-range's items, must not await, and must not wait on another piece; nothing checks it. actors.parallelRangeThen(lo, hi, grain, body, data, onDone, doneArg) starts the same loop and returns at once, and the piece that finishes last calls onDone(doneArg) on whichever thread it runs. actors.parallelEach(lo, hi, body, data) is the loop a parallel each becomes: the same loop with the grain chosen for the workers (pieces of about an eighth of a worker's even share), and with the messages the pieces send to actors gathered: a piece's sends are kept, not made, and made after the loop by the code that began it, in the order of the passes, so that an actor sees the same order every run (parallelRange sends at once, in no defined order).

Any particular channel's messages are all the same type, but might very well be some sort of variant type, allowing different kinds of messages to be sent. Cone makes it easier to support this kind of message-passing by supporting the definition of queued-methods for the message type. For example: 

struct CommandMessage {
  pub counter u32;
  pub qfn increment() {
    ++counter;
  }
  pub qfn decrement() {
    --counter;
  }
}

A message can be sent to the actor in what looks like a normal method call:

actor.increment();

However, instead of executing the function right away, the message is appended to the actor's queue. Later, the actor can pop this message off and dispatch it, which automatically then dispatches to the appropriate method's logic, updating the counter that is part of the actor's state.

A "qfn" will never specify a return type, because it is always being performed asynchronously with no guarantee of any value ever being calculated or returned. If a return value is desired, then one can pass the along a reference to the actor to which a message back can be sent.

Awaiting a reply

A message is one-way: the sender goes on at once, and whatever the behaviour returns is dropped. Inside an actor's own behaviour, await sends a message and waits for what the behaviour it sends returns:

struct Conn {
  pub url u64;
  fn final(self &uni) {say("  close", url);}
}

struct Buffer {
  pub size u64;
}

actor Net {
  pub async do read(self, url u64) Buffer {
    say("  read", url);
    new Buffer(url * 100u64);
  }
}

actor Fetcher {
  net Net;

  pub async do fetch(self, url u64) Buffer {
    imm conn = new Conn(url);             // opened
    imm buf = await net.read(conn.url);   // conn waits, with the method
    say("  fetched", buf.size);
    buf;                                  // the reply to the 'await' on fetch
  }                                       // conn closes here
}

actor Page {
  fetcher Fetcher;
  body u64;

  pub async do load(self, u u64) {
    say("load", u);
    imm b = await fetcher.fetch(u);       // pauses here
    body = b.size;                        // and resumes when the reply comes
    say("loaded", body);
  }
}

(say prints a word and a number on a line.) Sent page.load(7u64), this prints:

load 7
  read 7
  fetched 700
  close 7
loaded 700

When load reaches its await, it sends fetch to the fetcher and pauses. The worker running Page does not wait with it: Page goes back to its mailbox, and its other messages run meanwhile. When fetch returns its Buffer, the value comes back to Page as a reply, and load resumes just after the await, whose value it is. Fetcher does the same at its own await: while Net reads, Fetcher is free to handle other fetches. Its connection, conn, is still open while it waits, and closes when fetch ends, after the reply came, just as it would if read had been an ordinary call.

An I/O operation is awaited the same way, its answer coming back as a reply does: a real read of a socket is await conn.read(buf) (Awaiting I/O).

Await in a behaviour

An await stands only in a behaviour: not in a plain function or a struct's method, and not in any fn of an actor's — its init, which runs on the thread making the actor, before the actor takes any message; its final, as it dies; or a helper, which runs inside the method that calls it and cannot pause partway through the call. A behaviour may hold any number of them. The behaviour's declaration says it may pause, and that is as far as the marking goes: a caller does not await a behaviour in order to call it, since the code that runs it is the actor's dispatcher, at the top of its worker's stack, and every message already runs later than it was sent. So an await pauses only the behaviour it is written in, and goes no further, where in C#, Rust and JavaScript a caller that waits for an asynchronous function's result must be asynchronous itself, and its callers in turn, all the way up the stack.

The awaits are at the top of an actor's work, in its behaviours, and the synchronous work between them is pushed down, onto a helper or a type the actor owns:

actor Reporter {
  clock Clock;
  last u64;

  pub async do report(self) {
    imm t = await clock.now();    // the 'await', at the top of the behaviour
    last = self.format(t);        // the synchronous work, pushed down
  }

  fn format(self &, t u64) u64 {
    t * 1000u64 + last;
  }

  fn stamp(self) {
    last = await clock.now();     // refused: stamp is a 'fn', synchronous
  }
}

'await' stands only in an actor's behaviour, declared 'async do', where the behaviour is
cut and returns to the actor's dispatcher to wait. This one is in stamp, a 'fn' of actor
Reporter's: synchronous, run inside the method that calls it, which cannot pause partway
through a call. An 'await' belongs at the top of a behaviour: await there, and push the
synchronous work down, onto a helper like this one or a type the actor owns, to run
between the awaits.

What an await does

  1. It asks. What follows await is a behaviour of an actor that returns a value. It is sent, as any message is, and the request carries where the reply goes. (Or it is a future, a request sent earlier: Storing a future.)
  2. The behaviour pauses. It returns to its actor's dispatcher. What the rest of the behaviour needs waits in the actor (below), not on a stack, so the worker goes on to other work.
  3. Other messages run. The actor handles the rest of its mailbox meanwhile, one message at a time, as always, messages it sends itself among them. So its state may have changed by the time the behaviour resumes: what it read from its fields before the await, it reads again after.
  4. The reply resumes it. When the behaviour asked returns, its value comes back to the actor that awaited, as a message in its mailbox. When that message's turn comes, the rest of the behaviour runs, with the value as the await's, perhaps on another worker thread.

It reads as one scope

The method runs in parts, with other messages between them, but it is still the one method written, with one scope. Every value it holds when it pauses dies where it would if the method had never paused, and in the same order:

struct Note {
  pub n u64;
  fn final(self &uni) {say("  drop", n);}
}

actor Clock {
  pub async do now(self) u64 {42u64;}
}

actor Logger {
  clock Clock;

  pub async do log(self) u64 {
    imm first = new Note(1u64);
    imm second = new Note(2u64);
    imm t = await clock.now();
    say("  at", t + first.n);             // 'second' is not named again
    t;
  }                                       // second dies, then first
}

logger.log() prints at 43, then drop 2, then drop 1. second is never named after the await, yet it waits too, and dies at the method's end, the last declared first, as it would in a method with no await. Nothing is dropped early at an await, so what a finalizer does (closing a file, giving back a buffer) happens where the method's text says. An await returns to the dispatcher, not to the author: the author reads one method, and the pause shows only in when the rest of it runs, and in what the actor's other messages did meanwhile.

What crosses an await

  • Values move. Every value the method still needs after the await, and every value with a finalizer it still holds, waits for the reply, and comes back to the same local when the method resumes. It is moved, never copied: a counted owner (an Arc, an actor's handle) is not counted again, and a value that may only move waits like any other. A local that is not used again and has nothing to do as it dies is simply left behind.
  • Borrows end. Every borrowed reference the method holds ends at the await, as if its scope ended there: while the method is paused, other messages run, and may change or drop what was borrowed. Holding one at an await is no error; using one after it is (next).
  • A 'static borrow does not end. A borrow of a global may already be returned from a function, since what it points at outlives every function; for the same reason it crosses an await: 
    imm limit u64 = 100u64;

actor Gauge {
  clock Clock;

  pub async do check(self) u64 {
    imm max = &limit;                     // a borrow of a global: 'static
    imm t = await clock.now();
    *max - t;                             // still valid after the 'await'
  }
}
  • A lock is given back. A borrow through a lock permission holds its lock for as long as the borrow lasts, so the borrow ends at the await and the lock is given back there. To reach the value again, the method borrows it again: 
    struct Count {pub n u64;}

actor Tally {
  count Arc[Mutex, Count];
  clock Clock;

  pub async do bump(self) u64 {
    imm c = &mut *count;                  // takes the lock
    c.n += 1u64;
    imm t = await clock.now();            // gives it back
    (&mut *count).n += t;                 // takes it again, for the statement
    (&*count).n;
  }
}
    A lock borrow is never 'static, since it borrows a hidden local that holds the lock, so it never crosses: no method holds a lock while it waits.
  • The state is lent afresh. self and the actor's fields may be used after an await: the dispatcher lends the state again when the method resumes. A borrow made through self before the await ends, as any borrow does.

Using a borrow after an await

A borrow used after the await that ended it is refused, with the error any borrow used after its end gets, pointing at the await as where it ended:

actor Meter {
  clock Clock;
  reading u64;

  pub async do stale(self) {
    imm r = &reading;
    imm t = await clock.now();  // refused: r's borrow ends here, and r is used below
    reading = *r + t;
  }

  pub async do fresh(self) {
    imm t = await clock.now();
    imm r = &reading;           // borrowed after the 'await'
    reading = *r + t;
  }

The borrow 'r' holds of '*self' (made at ..) ends at this 'await', where the method
returns to its actor's dispatcher to wait, and 'r' is used again at ..

A lock borrow used after the await is refused the same way, the message naming the lock it held.

The rest of the statement

An await may stand inside a larger expression. What follows await is worked out first, up to the request it sends; then the behaviour pauses, and the rest of the statement runs when the reply comes, as the first thing the behaviour does when it resumes:

actor Counter {
  pub async do next(self) u64 {2u64;}
}

actor Shelf {
  counter Counter;
  slots Array[u64, 4];
  total u64;

  fn put(self, n u64) {total = total + n;}

  pub async do stock(self) u64 {
    slots[await counter.next()] = 7u64;   // slots is reached after the 'await'
    self.put(await counter.next());       // and so is self, put's receiver
    total += await counter.next();        // total is read and written after it
    slots[2] + total;
  }
}

await shelf.stock() is 11. Each statement runs as if the value awaited were made first, into a local of its own: imm i = await counter.next(); slots[i] = 7u64;. So what the rest of the statement reaches — slots, the state through self, total — it reaches as it is when the behaviour resumes, after whatever the actor's other messages did meanwhile, and nothing of it is borrowed while the behaviour waits. A borrow written to the left of the await is taken then too: add(&x, await clock.now()) borrows x once the reply has come, and total += await counter.next() loses nothing another message added to total while it waited. Rust holds such a borrow across its await instead, which it can because nothing else may change what an exclusive borrow reaches while it waits; inside an actor, its other messages run meanwhile.

A value is not reached again. One made to the left of the await, in the order the statement is worked out — an argument before it, an operator's operand — is made before the request is sent and waits with the method: in total + await counter.next(), total is read before the await. The value an assignment stores is made before its place is reached, so in slots[await counter.next()] = f(), f runs first.

What is reached again is a plain path: a local, self, a field, an element at a plain index, or a borrow of one. A borrow a call made cannot be made again, so a borrow, or a place, made by a call to the left of the await is refused, and the message says to bind what the call makes to a local first. In Meter, where add is a function taking a &u64 and a number, and compute one returning a number:

  pub async do fromCall(self) {
    reading = add(&compute(), await clock.now());  // refused: compute() made what is borrowed
  }

  pub async do bound(self) {
    imm c = compute();
    reading = add(&c, await clock.now());          // c is borrowed after the 'await'
  }

This borrow, written to the left of an 'await' in the same statement, is made by a call
or a temporary, and is used after the 'await'. The rest of the statement runs after the
'await', which ends every borrow: only a plain path -- a local, 'self', a field, an
element at a plain index -- is reached again there, never what a call made. Bind what
the call makes to a local first, and use the local here.

self and selfactor

An actor has two selves. self is its state, lent to the method while it runs; it never leaves the actor. selfactor is its handle: another owner of the actor, a value that may go anywhere a handle may — into a message, into another actor's state, or to an await on one of its own behaviours:

actor Doubler {
  pub async do double(self, n u64) u64 {n * 2u64;}

  pub async do twice(self, n u64) u64 {
    imm once = await selfactor.double(n);  // a message to itself
    imm again = await selfactor.double(once);
    again;
  }
}

await doubler.twice(5u64) is 20. Each double is queued in Doubler's own mailbox, and runs because twice has paused and the actor is free. await self.double(n) is the same: a behaviour named through self is sent through the actor's handle (Sending to itself), never run at once. selfactor may be written in any of the actor's methods, its init among them once the state is filled (Making one), but not in its final, nor anywhere outside the actor.

One request, one reply

An await sends one request and takes exactly one reply. A message that returns a value answers once, when it returns, from whichever path it returns by:

actor Cache {
  net Net;
  hot u64;

  pub async do get(self, url u64) u64 {
    if url == hot {
      return 1u64;                        // answered here, at once
    }
    imm b = await net.read(url);
    b.size;                               // or here, once the reply came
  }
}

A reply always has an actor to go to: the request holds a counted handle of the actor that awaited, so that actor cannot die while its reply is owed. A behaviour that returns a value may also be sent with no await, and its value is then dropped.

Storing a future

A call of a behaviour that returns a value, written where its value is kept — bound to a local, passed on, returned — sends the request at once and gives back a future: a value standing for what the behaviour will return. An await on the future waits for that value. So several requests can be in flight at once, and their answers collected later:

actor Stock {
  pub async do price(self, item u64) u64 {item * 3u64;}
}

actor Basket {
  stock Stock;

  pub async do total(self) u64 {
    imm apples = stock.price(4u64);     // sent: a future comes back at once
    imm pears = stock.price(5u64);      // both requests are in flight
    imm a = await apples;               // waits for the first
    imm p = await pears;                // then for the second
    a + p;
  }
}

await basket.total() is 27. Both requests are sent before either is waited for, so Stock may work on the second while Basket waits for the first. A behaviour is declared once, and how it is called says what becomes of its value:

  • await stock.price(4u64) sends it and waits here: the await's value is the behaviour's, and no future is made.
  • imm f = stock.price(4u64) sends it and keeps its future, an actors.Future[u64], for an await later.
  • stock.price(4u64);, a statement of its own, sends it and forgets it: its value is dropped.

An await on a future pauses only if the value has not arrived. If it has, the behaviour goes on at once: nothing pauses, nothing waits in the actor, and none of the actor's other messages runs in between, so a future collected after other work is often free. If it has not, the behaviour pauses just as on a reply (What an await does), every borrow ending there, and resumes when the value arrives. Either way, what crosses the await is what crosses any await.

A future is a value like any other. It may be stored and awaited much later, and it may be handed to another actor in a message and awaited there: it belongs to whoever holds it, never to the actor that made the call, and whoever holds it may await it. It crosses to another thread where its value may: Future[T] is Sendable where T is. It copies or moves as its value does. Future[u64] copies, and each await on a copy gives the value again. A future of a value that moves, a Future[Report] where Report is a move type, moves too: the await takes the value out of it, and the future goes with it, so no second await could take the value again:

struct Report is Move {
  pub lines u64;
}

actor Printer {
  pub async do render(self, n u64) Report {new Report(n * 2u64);}
}

actor Archive {
  pub async do keep(self, f actors.Future[u64]) u64 {
    imm n = await f;                    // the value arrives here
    n + 1u64;
  }
}

actor Office {
  printer Printer;
  stock Stock;
  archive Archive;

  pub async do file(self) u64 {
    imm r = printer.render(10u64);      // a Future[Report], which moves
    imm report = await r;               // the Report is taken out of it
    report.lines;
  }

  pub async do pass(self) u64 {
    imm f = stock.price(2u64);
    await archive.keep(f);              // the future goes to Archive
  }
}

await office.file() is 20, and await office.pass() is 7. Awaiting r a second time is refused, as any use of a moved value is:

actor Desk {
  printer Printer;

  pub async do twice(self) u64 {
    imm r = printer.render(10u64);
    imm report = await r;
    imm again = await r;          // refused: r moved into the first 'await'
    report.lines;
  }
}

This variable's value has been moved out. It is no longer there to use.

A future nobody awaits is no error and costs nothing more: the behaviour runs, its value arrives, and it is finalized when the last holder of the future lets go, or when the value arrives, whichever is later. Letting go of a future does not stop its behaviour, which is already running on its own actor.

An await assumes the value arrives, as it nearly always does, and hands it over directly, with no wrapper to unwrap. When the behaviour owing it can never answer — its actor died while the behaviour was paused on something abandoned itself, as at the program's end — the future is abandoned. A behaviour already paused on it is abandoned with it, as one paused on the request itself would be: the rest of it never runs, and the values it held are finalized, in the order its one scope gives, once nothing else holds its actor. So the program's end, which ends what is outstanding, ends imm f = server.next(); await f as it ends await server.next(). An await that finds the future abandoned already panics, reported at the await:

actors: an awaited future will never arrive: the behaviour owing it (request 1) ended without answering

The request number counts the futures the program has made, so the report says which one it was. Where the failure is one the program should handle, the behaviour declares it in its return type, a Result, and the future's value is that Result.

Only a future, a behaviour's reply and an operation are awaited. An await on anything else waits for no answer, and is refused: an await on a function's call, whose value is there as soon as the call returns (below), or on a number. And a behaviour that returns nothing gives no future (next).

A behaviour that returns nothing

Whether a reply is sent is the behaviour's declaration to say, never its caller's: one with no return type sends none, so there is nothing to await, and an await on it is refused. A caller that needs to know a behaviour has finished needs to know whether it worked, too: the behaviour declares a return type, a status, and the caller awaits that.

actor Log {
  pub async do flush(self) {}             // owes its caller nothing
  pub async do commit(self) bool {true;}  // answers with a status
}

actor Writer {
  log Log;
  saved bool;

  pub async do save(self) {
    await log.flush();            // refused: flush sends no reply
    saved = await log.commit();   // waits until commit has run, and learns whether it worked
  }
}

'await' waits for a behaviour's reply, and flush returns nothing, so it sends none: a
behaviour with no return type owes its caller nothing. If the caller needs to know flush
finished, declare a return type -- a status saying whether it worked -- and await that.

For the same reason its call gives no future: one whose value is kept is refused. Written as a statement of its own, it sends the message and forgets it.

actor Keeper {
  log Log;

  pub async do keep(self) {
    log.flush();                  // sent, and forgotten
    imm f = log.flush();          // refused: flush gives no future
  }
}

flush returns nothing, so its call gives no future to keep: a behaviour with no return
type owes its caller nothing, and calling it sends a message and forgets it. Call it as a
statement of its own; or, if the caller needs to know flush finished, declare a return
type -- a status saying whether it worked -- and keep or await that.

An acknowledgement is not flow control. A sender that awaits each reply before sending again has one message outstanding at a time, so the two run in lockstep, a round trip each. To keep a fast sender from running far ahead of a slow receiver while both stay busy, send through a bounded channel: its capacity is how far ahead the sender may get, and a send blocks only when it is full.

An await in a loop

An await may stand in a loop, and a loop's variables cross it as any others do. It is legal, but poor practice:

actor Sizes {
  net Net;

  pub async do total(self, n u64) u64 {
    mut sum = 0u64;
    each i in 0u64 < n {
      imm b = await net.read(i);          // one request at a time
      sum = sum + b.size;
    }
    sum;
  }
}

Each pass sends one request and waits for its reply before the next is sent, so the requests run one after another, a round trip each, and the actor's other messages run in between the passes, perhaps changing what the loop reads. A borrow the loop holds ends at the await on every pass. Requests that do not depend on one another's replies need not wait in turn: each call's future kept, they are all in flight at once, and their values are awaited afterwards (Storing a future).

Not built yet

Each of these is reported where it is written, as not built:

  • A few places an await may not cut yet: in the index of a place whose base holds an await of its own (m[await f()][await g()]), in both places a swap exchanges, in a slice's bounds (&items[await f()..3]), in the places of a parallel assignment, among the entries one <- appends (v <- (1, await f())), and in an array's contents that repeat a value more than 16 times (<- fill await f()). Written as a statement of its own first, each await is built.
  • A traced reference waiting for a reply. An await at which the behaviour holds a Gc reference it would keep is refused: the collector does not see a paused behaviour's values. (Gc is not supported inside an actor at all yet, "Inside an actor", above.)
  • Timeouts and cancellation. A paused behaviour waits until its reply comes. There is no time limit on the wait, and no way to cancel a paused behaviour. Only the program's end ends one early: a behaviour paused on I/O is abandoned then, the rest of it never run, and its values are finalized once nothing else holds its actor (Awaiting I/O); a behaviour whose reply was owed by one abandoned so is abandoned with it, and a future it owed is abandoned (Storing a future).
  • Awaiting several futures at once. An await waits for one future. Waiting for whichever of several arrives first, or for all of them in one await, is not built: several are awaited one after another.
  • Looking at a future without opening it. An await opens the future and panics if its value never arrives. There is no way yet to ask whether it arrived, or to handle an abandoned one, without the panic.

Two of them, beside an await refused for what it awaits, where compute is a plain function and Cell a struct:

actor Waiter {
  clock Clock;
  last u64;

  pub async do onFunction(self) {
    last = await compute();       // refused: compute's u64 is no future
  }

  pub async do swapped(self) {
    mut items = [1u64, 2u64, 3u64];
    items[await clock.now()] <=> items[await clock.now()];  // not built: in both places
  }

  pub async do traced(self) {
    imm g = new Gc[mut, Cell](1u64);
    imm t = await clock.now();    // not built: g would wait for the reply
    last = t + g.n;
  }
}

Shared, Mutable Objects

In most cases, the above approach is the most efficient when threads do not require shared access to mutable objects. This is because using thread-shared, mutable objects carries at least these performance penalties: the run-time cost of the atomic synchronization primitives (especially locks), and the way mutation invalidates the memory cache for other threads.

For this reason (and to minimize the risk of deadlocks), it is desirable to send only small-sized messages between threads (typically references) and only use the static permissions on references. Static permissions offer the best performance, because they guarantee at compile-time that shared, mutable access to the same memory location cannot happen between threads. No run-time mechanisms are needed to enforce these guarantees. Although mutable objects cannot be shared between threads, immutable can be. Even better, it is possible to move a uniquely-owned object from one thread to another.

That said, there are definitely situations where we might want threads to share access to mutable objects. This can be supported using lock permissions, shared data structures or atomic primitives.

Lock Permissions

Cone's locked permissions have already been introduced. Lock permissions use runtime locks to synchronize when multiple threads need (mutable) access to the same object.

The locks provide an atomic envelope around a set of operations, so that no other thread can access the object while another has it locked. If threads request multiple locks at the same time, careful design is needed to avoid the risk of deadlocks.

Concurrent data structures

The message queue used by actor is one of several kinds of concurrent data structures. Other examples include concurrent arrays and dictionaries.

Concurrent data structures are implemented in a way that makes it always possible to access and mutate these structures across multiple threads. Every operation (method) on these types is essentially atomic. Importantly, these operations never use locks and never block.

Atomic primitives

Atomic primitives are a small collection of atomic (mutable) operations that are safe to perform on objects shared between threads. For example, it is safe to increment or decrement some shared integer.

These atomic operations are the building blocks that make possible many of the synchronized communication mechanisms already described. Underneath them are the raw atomic operations core declares in mem (Intrinsics), which act through a raw pointer and so need trust.
