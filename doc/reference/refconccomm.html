Cone
Thread Communications

Note: Three things on this page are implemented: the channel of many senders and one receiver, Channel[T], unbounded or bounded, or of one sender and one receiver, as the sync library package, on Windows only; and the atomic primitives, as core's Atomic[T], over the raw atomic operations core declares, which are intrinsics. Immutable data is shared between threads through the same package's Arc region (import sync use Arc), whose count is atomic: Arc[imm, T] owners may be copied and dropped on any thread, and the value is freed once, after the last (regions); an Rc owner's count is not atomic, and it must stay on one thread. What is sent is checked: thread.start and the channel types take only a Sendable type, as Race condition safety describes. And the runtime actors run on, as the actors library package, on Windows only: mailboxes, a work-stealing scheduler, quiescence, and handles counted through Arc, running actors written by hand in the shape the actor declaration is to generate, starting with the first actor and stopped by finalAll(), which a program calls itself until the entry that will call it exists. The actor declaration itself, qfn, the other concurrent data structures, and lock permissions are not implemented. An enum's variant is constructed with its values in square brackets, as written here: that is the current spelling, and how a variant is constructed is an open design question (Enums).

It can be a huge performance benefit that threads share memory and other resources, particularly when the threads need to exchange or share large, complex data structures. However, thread-shared memory also opens up safety risks when communications are not properly synchronized.

To mediate these risks, Cone offers several mechanisms that facilitate fast, convenient, safe communications between threads.

Race condition safety

Any data passed or shared between threads must be done so safely. Cone ensures this by only allowing "sendable" data to be sent to another thread. The only type of data that is not sendable is a reference that has the "mut" or "ro" permission, or any aggregate type containing such a reference. Data of any other type is sendable, including shared, immutable references, unique references (which are moved from one thread to another), and any other move or copy type.

These restrictions apply to all mechanisms that support communications between threads, such as thread creation, concurrent data structures, and more.

What the compiler checks today. Library code marks what crosses threads with the built-in marker trait Sendable, as a constraint on a generic: thread.start and thread.startWith ask it of the argument and of what the thread returns, and Channel[T], Sender[T], SoloSender[T] and Receiver[T] of T. The compiler grants Sendable to a type unless it holds, directly or in a field, an array element, a tuple element or an enum's variant, one of these:

  • a borrowed reference, of any permission, &imm included: a borrow's lifetime is checked in one thread alone, until scoped threads join inside it;
  • an owner that may be copied whose permission is not race-safe: Rc[mut, T], Arc[mut, T] (until lock permissions);
  • an owner that may be copied in a region that does not declare ThreadSafe, whatever its permission: Rc[imm, T], whose count is not atomic. Arc[imm, T] and Arc[opaq, T] cross;
  • a traced reference, Gc, whatever its permission, until each thread has its own collector;
  • a raw pointer, whose target nothing checks.

An owner that moves takes its value with it: a uni owner of any region, and any owner of So, crosses when what it points at may. So does an Arc[imm, T] owner: an Arc of a value holding a mut reference is refused. A reference to a function crosses. A type holding raw pointers it shares safely declares is Sendable, which the compiler takes on trust, as a channel's ends, ThreadRef, and the collections package's List and Dict do; an instance of a generic type declaring it is Sendable only where its type arguments are.

What is checked is the type of the value, not how a variable was declared: a local declared mut x = 5 holds a number, which is sendable, while &mut x is a borrow, which is not. A refusal names the part of the type that binds it to its thread:

struct Job {pub data &mut Counter;}
thread.start(job, &work);
// start requires A is Sendable, and Job is not Sendable: Job.data is &mut Counter,
// a borrowed reference, and no borrow may leave its thread ...

Not checked yet: a mut global reached from several threads; a value's own methods that change it through & (sendable here also means safe to read from several threads at once behind Arc[imm, T], which a type declaring Sendable promises too). Actor messages are checked as a channel's values are: the actors package's send and startActor ask Sendable of an actor's message enum, and so of every method's parameters; an actor's state is not asked, since it never crosses as a value (Actors).

Message-based Communications

An efficient model for thread-based concurrency is independent actors (threads) that throw work to each other in the form of messages placed on an actor's queue. Each actor pulls off messages from its queue in order, and then performs the work requested by the message. For now, let's assume that actors do not need shared, mutable access to objects nor do they perform any resource-blocking operations.

A straightforward way to implement this actor model involves using library-packaged actors that own and use concurrent message queues (or channels). Such multiple-producer-single-consumer (MPSC) channels are themselves library packaged-delivered concurrent FIFO data structures. Any actor that wants some actor to perform work adds that work to the actor's queue in the form of a message. As part of a continuous loop, the actor owning the queue pops a message off the queue and completely performs the non-blocking work it requests.

Channels

The sync package's Channel[T] is such a queue, usable directly between threads, with any number of sending ends and one receiving end. Channel[T].make() answers both ends of an unbounded channel, whose sends never wait; Channel[T].bounded(n), of a bounded one, holding at most n values (rounded up to a power of two), whose sends wait while it is full, so a sender faster than its receiver is held to its pace. The two kinds' ends are the same types, so code taking a Sender[T] takes either. Each end is a move type: another sender is made only by clone(), and the receiver has no clone, so exactly one thread takes from it.

Channel[T].spsc(n) makes the third kind, bounded as the second is, with one sender. Its sending end is a SoloSender[T], which has no clone(), and whose sends take it as &mut: there is exactly one, and one thread sends at a time. Knowing that from the type, the channel needs no atomic read-modify-write on either side, which makes it the fastest of the three where one thread feeds another: a pipeline's stages, or a logging thread's own buffer. Its receiving end is the same Receiver[T], and its methods are the others'.

import sync use *;

mut tx Sender[Job];
mut rx Receiver[Job];
tx, rx = Channel[Job].make();   // the two ends; or Channel[Job].bounded(64)
imm tx2 = tx.clone();           // a second sender, said out loud
tx <- job;                      // send: waits only while a bounded channel is full
match rx.recv() {               // waits while it is empty
  case imm j Some {run(j.value);}
  case is None[Job] {}          // closed, and every value taken
}

mut solo SoloSender[Job];
mut rx2 Receiver[Job];
solo, rx2 = Channel[Job].spsc(1024);  // one sender, no clone
solo <- job;
  • tx.send(v), or tx <- v, puts a value in, waiting while a bounded channel is full. It answers None, or, when the receiver has gone or closed the channel, Some holding the value, handed back rather than lost. A list after <- sends each entry in turn, tx <- a, 3 of next() (the append operator), and drops what each send answers. tx.trySend(v) never waits, handing the value back from a full channel too; tx.sendTimeout(v, ns) waits at most ns nanoseconds for room.
  • rx.recv() waits for the next value, oldest first; rx.tryRecv() never waits; rx.recvTimeout(ns) waits at most ns nanoseconds. Each answers an Option.
  • Nothing panics, and no one has to close the channel by hand. The last sender's death closes it: the receiver takes what is left, and then recv answers None. rx.close() refuses later sends while what came before still drains. The receiver's death closes it too, wakes every send waiting for room to hand its value back, and finalizes each value still in it, once.
  • A send waiting on a full bounded channel waits for as long as it stays full: a receiver that stops taking without going leaves it waiting for good. Two threads that each send to the other through bounded channels can so wait on each other; where that may happen, trySend, sendTimeout or an unbounded channel is the answer.

A send is one compare-and-swap, into blocks of 32 slots allocated a block at a time (unbounded) or a ring of n slots allocated at the start (bounded); the receiver takes a value with no read-modify-write at all. A single-sender channel's send is a plain store as well, into Lamport's ring, each side keeping a copy of the other's index and reading the real one only when its copy says full or empty. A thread sleeps, on the futex, only when there is nothing to do: the receiver when the channel is empty, a sender when a bounded channel is full.

Actors

An actor is state that lives on, reached by nothing but messages. Each message is a call of one of the actor's methods, queued in its mailbox and run later, one at a time, on whichever of a pool of worker threads takes the actor up. A method runs to completion, on that worker's own stack, with the actor's state mut; nothing is suspended or resumed, and no other method of the same actor runs until it returns. The actors package is the runtime: the mailbox, the work-stealing scheduler, the counting that decides when an actor dies, and the quiescence a program ends at. It starts and stops by itself: the first actor started starts the workers, and the module's finalizer waits until all is quiet and stops them. Its source, packages/actors/src/actors.cone, documents the same rules at greater length, and how each works.

import actors;

fn main() {
  initAll();
  {
    imm c = Counter.start(0u64);   // the first actor starts the workers
    c.add(5u64);                   // a message: queued, and run later
    c.add(7u64);                   // run after the first
  }
  finalAll();                      // waits until all is quiet, stops the workers
}

The shape of an actor. The actor declaration is to generate four things; until it does, they are written by hand, and the runtime is driven by them. For an actor Counter with a field count and a method add:

// (b) The messages: one variant per method, its fields the method's parameters
enum Counter_msg {
  struct Add {pub n u64;}
}

// (a) The state: the fields and the methods, unchanged
struct Counter_state {
  count u64;
  pub fn made(count u64) Counter_state {new Counter_state(count);}
  fn add(self &mut, n u64) {count = count + n;}
}

// (c) The handle: an Arc[opaq, T] owner of the actor's Mailbox, a send function per method, and start
struct Counter {
  mb Arc[opaq, actors.Mailbox[Counter_msg]];
  pub fn start(count u64) Counter {
    new Counter(actors.startActor[Counter_state, Counter_msg](
      Counter_state.made(actors.sendable(count)), &Counter_dispatch));
  }
  pub fn add(self &, n u64) {
    actors.send[Counter_msg](mb, Counter_msg.Add[n]);
  }
}

// (d) Dispatch: one match on the message, each arm calling its method
fn Counter_dispatch(self &mut Counter_state, msg Counter_msg) {
  match msg {
    case imm m Counter_msg.Add {self.add(m.n);}
  }
}

The message enum is named for the actor with _msg, the state with _state, the dispatch function with _dispatch. Creation is start, as a thread's is, since spawn is reserved. The message enum is declared first, before the state, the handle, and any other actor's message enum holding this actor's handle: declared after them, it is refused, today, as a type that would contain itself (a cycle through an owning reference is judged by the order the compiler meets its types).

The handle and the state. A handle is a struct over one Arc[opaq, T] owner of the actor's actors.Mailbox[M], the runtime's part of the actor, so the Arc region counts an actor's handles: copying a handle (passing it, storing it, putting it in a message) makes another owner, and each going drops one. What a Mailbox holds is the runtime's alone, in a field private to it, of a type private to the package; a handle's only use is to send, and send takes only the Mailbox's own message type. The state is not in the handle's type. It is made from its start arguments, which must be Sendable, and from then on reached only by the runtime: by the worker running the actor, and by its finalizer. So the state declares nothing about Sendable, and may hold what may not cross threads (Rc, a mut owner); it is itself refused wherever it would cross as a value, over a channel or to a thread. The handle is Sendable because Mailbox declares it, once, in the runtime, as a channel's ends do: the runtime orders every hand-off of an actor itself. The Mailbox and the state are one allocation, the Mailbox first, so a send touches one block.

An actor's life. While an actor is queued to run, or running, the scheduler holds one owner more, taken by the send that found it idle and dropped when its mailbox is found empty. So an actor dies exactly once, when its last handle has gone and its mailbox is empty: a handle dropped with messages still queued leaves the actor alive until they are handled. At its death the Mailbox's finalizer finalizes the state (its final, then its fields, handles to other actors among them), through a function made for the state's type when the actor started, since Arc sees only the Mailbox; then the block is freed. This runs on whichever thread let go last. Actors that hold handles to each other in a cycle never die by counting, as a cycle of Arc owners never does, until one of them lets go.

Messages. A send is one-way: it queues the message and returns, and a method returns nothing to its sender; an answer is a message sent back to a handle passed along. Each sender's messages to one actor are handled in the order sent, and a message is never overtaken by one it caused. What a message carries must be Sendable, which actors.Mailbox, actors.send and actors.startActor ask of the message enum, so of every method's parameters, and actors.sendable asks of each argument start hands to the state.

Inside an actor a method may use what a single thread may: borrows, and So and Rc owners, whose count need not be atomic, since one worker at a time runs an actor and every hand-off of an actor between workers orders what the first did before anything the next does. Three things differ from a plain thread:

  • Gc is not supported inside an actor. The collector is single-threaded, and an actor runs on every worker in turn; a traced reference made, held, reached or dropped by an actor corrupts it. Nothing refuses one yet.
  • A thread-local global seen from an actor's method is the current worker's copy, not the actor's: its next message may run on another worker.
  • A method that blocks holds its worker while it does. Actors wait by being sent a message.

The runtime starts and stops by itself. The workers start with the first actor, on whichever thread starts it; two threads starting a first actor at once start them once. A program that starts no actor starts no thread. They start then, not in the module's initializer, which is initpure. Before the first actor, actors.configure(new actors.Options(workers: n, batch: b)) sets n workers (by default one per logical processor), each running at most b of an actor's messages at a turn (100 by default) before the actor goes to the back of the queue; once the workers run, it is a panic. The actors module's finalizer, run by finalAll(), waits until the runtime is quiescent — no actor queued or running, so no message in any mailbox — then stops the workers and joins them. finalAll() finalizes the program's own module first, so the handles its globals hold are let go before the wait; handles in main's locals go at the end of their block, which is why the example above starts its actors in one. The runtime is not started again: starting an actor or sending a message once the workers have stopped is a panic, since nothing would run the message. Quiescence assumes that once the finalizer has begun every message comes from an actor: another thread that goes on sending is joined first. actors.stats() answers what the workers have done so far (Stats: workers, messages handled, turns, steals), without stopping them, and the run's totals once they have stopped. actors.workerIndex() is the index of the worker running the caller, or actors.noWorker.

Until the entry a program's framework will supply exists, a program calls initAll() and finalAll() itself (Running every module's initializer and finalizer). A program that does not call finalAll() ends when main returns, whatever its actors are doing: messages still in flight are silently dropped, and no actor still alive is finalized.

How it works. A mailbox is Vyukov's intrusive queue of many senders and one receiver, as Pony's runtime has it: a send is one atomic exchange and one store; the worker running the actor takes messages with no read-modify-write; a mark on the mailbox says the actor is idle, and the send that finds it queues the actor. Each worker has a run queue of its own, and there is one shared inject queue: an actor made runnable by a send from a worker is queued on that worker, one made runnable by any other thread on the inject queue. A worker with nothing of its own takes a share of the inject queue, then steals half of another worker's queue. An idle worker parks on the futex, and is woken, one at a time, as work arrives. Quiescence is found by counting the activations each worker begins and ends, and reading the counts twice.

Any particular channel's messages are all the same type, but might very well be some sort of variant type, allowing different kinds of messages to be sent. Cone makes it easier to support this kind of message-passing by supporting the definition of queued-methods for the message type. For example: 

struct CommandMessage {
  pub counter u32;
  pub qfn increment() {
    ++counter;
  }
  pub qfn decrement() {
    --counter;
  }
}

A message can be sent to the actor in what looks like a normal method call:

actor.increment();

However, instead of executing the function right away, the message is appended to the actor's queue. Later, the actor can pop this message off and dispatch it, which automatically then dispatches to the appropriate method's logic, updating the counter that is part of the actor's state.

A "qfn" will never specify a return type, because it is always being performed asynchronously with no guarantee of any value ever being calculated or returned. If a return value is desired, then one can pass the along a reference to the actor to which a message back can be sent.

Shared, Mutable Objects

In most cases, the above approach is the most efficient when threads do not require shared access to mutable objects. This is because using thread-shared, mutable objects carries at least these performance penalties: the run-time cost of the atomic synchronization primitives (especially locks), and the way mutation invalidates the memory cache for other threads.

For this reason (and to minimize the risk of deadlocks), it is desirable to send only small-sized messages between threads (typically references) and only use the static permissions on references. Static permissions offer the best performance, because they guarantee at compile-time that shared, mutable access to the same memory location cannot happen between threads. No run-time mechanisms are needed to enforce these guarantees. Although mutable objects cannot be shared between threads, immutable can be. Even better, it is possible to move a uniquely-owned object from one thread to another.

That said, there are definitely situations where we might want threads to share access to mutable objects. This can be supported using lock permissions, shared data structures or atomic primitives.

Lock Permissions

Cone's locked permissions have already been introduced. Lock permissions use runtime locks to synchronize when multiple threads need (mutable) access to the same object.

The locks provide an atomic envelope around a set of operations, so that no other thread can access the object while another has it locked. If threads request multiple locks at the same time, careful design is needed to avoid the risk of deadlocks.

Concurrent data structures

The message queue used by actor is one of several kinds of concurrent data structures. Other examples include concurrent arrays and dictionaries.

Concurrent data structures are implemented in a way that makes it always possible to access and mutate these structures across multiple threads. Every operation (method) on these types is essentially atomic. Importantly, these operations never use locks and never block.

Atomic primitives

Atomic primitives are a small collection of atomic (mutable) operations that are safe to perform on objects shared between threads. For example, it is safe to increment or decrement some shared integer.

These atomic operations are the building blocks that make possible many of the synchronized communication mechanisms already described. Underneath them are the raw atomic operations core declares in mem (Intrinsics), which act through a raw pointer and so need trust.
