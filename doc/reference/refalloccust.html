Custom Allocators

Note: The alloc declaration is not recognized. A custom allocator is written today as a struct declaring is RegionRef, which is how the core package's rc and so are written, and the compiler calls its methods at the events below, each method optional: fn alloc(size usize) *u8 (for allocate, static; the size includes the bookkeeping, and null fails), or fn alloc(size usize, ty *TypeRecord) *u8, which is also handed the allocated value's type record (its size, alignment, finalizer and trace, so the allocator can later finalize a value of any type itself; an owning slice's is its element type's), fn init() R (static; its result is stored as the bookkeeping), fn alias(self &uni R), fn dealias(self &uni R) Bool, which answers whether the last owner is gone rather than calling free itself, and fn free(self &uni R). Each is handed the bookkeeping data, not the value. An absent method's operation does not happen, and single ownership is declared rather than read off a missing alias: an allocator whose struct declares the built-in trait Move (struct so is RegionRef, Move) is single-owner, as described below, and may not also have alias. One with neither alias nor Move (the gc allocator's shape) shares its references freely, needing no alias method that does nothing; with no dealias either, an owner going away does nothing and the compiler never frees the value, which waits for a collector to be built. One with alias but no dealias never frees a value by count. When the last owner goes, the compiler runs the value's finalizer before calling free, as described below, and allocator methods are not trust blocks. An allocator whose struct also declares the built-in trait Traced (struct gc is RegionRef, Traced) has its references traced: it declares fn mark(self &uni R), or fn mark(self &uni R, perm u32, mode u32) to be told each reference's permission and the mode it was traced in, and every type record's trace (and mem.trace) hands it the bookkeeping of each of its references a value holds. It may not be Move. A traced reference may be held only where a collector can find it: in a local, a parameter, a temporary, a value held in one of those, or a value a traced allocator allocated. So the compiler refuses one held by an allocator that is not traced (a +rc or +so value holding it), in a global, or in memory placed by mem.writeRaw (an arena's, a pool's, a collection's); and refuses a traced allocator's value holding a borrowed reference, a traced owning slice or virtual reference, and a permission that takes room. A traced value may hold +rc and +so references, which its finalizer releases. No collector is built yet, and nothing finds the traced references on the stack.

Although Cone provides a rich collection of standard allocators, there are times that other allocators can prove valuable. For example: such as rc allocators that use tracing to break cycles or multi-threaded garbage collectors that use tracing for intrathread memory management and ref counting for inter-thread memory management (Pony's Orca).

This is why Cone supports the creation and use of custom allocators. Definition of a new allocator looks and acts very much like a struct with methods. For example:

// A simple reference counting allocator
alloc rc {
  refcnt usize;

  fn allocate(size usize) *uni rc {
    imm rcref = malloc(size) as *uni rc;
    rcref.refcnt = 1;
    rcref;
  }
  fn alias(self *mutx rc) {
    .refcnt += 1;
  }
  fn dealias(self *mutx rc) {
    .refcnt -= 1;
    if .refcnt == 0 {
      .free();
    }
  }
  fn free(self *mutx rc) {
    free(self as *u8);
  }
}

As this example shows, an allocator typically defines at least these four methods which are invoked automatically by the compiler based on key events in the lifetime of an owning reference:

  • allocate. This is invoked whenever a new owning reference is created using the & operator. The compiler supplies the sizeof the appropriate type of value to be stored in the allocated memory. This size is expanded to include runtime bookkeeping data for the allocator (e.g., refcnt) and permission. After allocate, the compiler will also initialize any runtime permission's fields, if needed. The compiler's final step is to adjust the pointer to point at the value's data (past the runtime bookkeeping data), and then to initialize its value based on the literal, initializer or a copy of another similar value.
  • alias. This is invoked whenever a new shared copy is made of the reference.
  • dealias. This is invoked whenever an owning reference is destroyed, typically when the variable holding the reference reaches the end of its lexical lifetime. It can also happen when overwriting a reference held by an existing variable or field.
  • free. This is invoked whenever the allocator determines the value is safe to free. Before executing its logic, the compiler will invoke the finalizer on the object, if it exist, which disposes of any resources obtained by the owning reference.

Any allocator which declares the built-in Move trait, and so does not define the alias method (e.g., the 'so' allocator), ensures single-owner move semantics, as it prevents multiple copies of the reference from being created. The single-owner reference is moved instead of being copied. This restriction also constrains the permissions on borrowed references, effectively disallowing mut and all other shared mutable permissions.

Alternatively, an allocator may declare neither Move nor the alias method (e.g., the gc allocator). In this case, multiple, sharable references to the same value become possible, and copying one costs nothing.

Notice also that allocators work with pointers (which have no assigned allocator). All allocator methods are considered wrapped as trust blocks, which allows the use of pointers as well as trusted functions like malloc() and free(). The pointers are automatically and correctly cast by the compiler back and forth from the correct pointer to the correct reference.
