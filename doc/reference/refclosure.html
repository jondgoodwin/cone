Closures

Note: Not implemented: a closure that calls itself, and calling a closure once and consuming it (a body that moves one of the closure's state entries out).

A closure may be viewed as a function that preserves its state from one invocation to the next. Because closures preserve their state, they are useful for:

  • Iterators, which retrieve a sequence of values one-at-a-time from a defined collection. An Iterator is already anything with a next method (Traits); what closures add is the adapters (map, filter, fold), written once as the methods every cursor declaring is Iterator[T] shares (Each and Iteration), and a source that runs its own loop around the body of an each (not built yet).
  • Generators that return a different value on each use. The generator a function declares with yields needs no closure (Co-routines).
  • Event-triggered callbacks, whose state guides what happens after an event is triggered.
  • Function-valued inputs of a library, such as the profile a sweep follows or the order a sort uses, whose numbers belong to the caller rather than to a fixed function.

Closure Definition

A closure is written where it is used, in the body of a function, in one of two forms.

The full form

The full form resembles a function definition. There are three key differences: the name is omitted, the return type may be omitted (and inferred), and the state the closure carries may be listed in square brackets after the parameters.

fn (parameters) [state] return_type { body }

For example:

mut counter = fn(n i32) [mut cnt = 0] { cnt += n; cnt; };

// Closure use
counter(1);        // 1
counter(2);        // 3

This closure takes one parameter, n. It infers that its return value is an integer, since the last expression is cnt, an i32.

The state list holds the variables the closure owns. Each entry is a field of the closure, written as a field is: a name with an initial value, cnt = 0, whose type is the value's. Entries are separated by commas. An entry is imm unless written mut, so a closure that changes its state lists it mut. The list may be left out. The brackets sit after the parameters because a bracket never begins a type, so they cannot be taken for the return type.

A parameter's type may be left out where the closure is given to something that says what the signature is (fn(x) { x + 1; }, below); nothing else may leave a type out. Three places say it: a parameter taken by &<fn(sig) or &<mut fn(sig) (a closure literal, lent), a generic parameter bound F fn(sig), and new So[fn(sig)](...) (an owner of a closure). A parameter of type So[fn(sig)] does not: it takes an owner, and a closure literal is not one, so a literal given straight to it is refused (for an untyped one, error 1391, "The type of a is not written, and nothing here says what it is"). Wrap it: c.set(new So[fn(a i64, b i64) bool]((a, b) => a < b)). An imm given an untyped closure is refused the same way, even where the imm is written with a &<fn(sig) type.

The short form

For a small closure the short form puts the parameter names, an arrow, and the body:

x => x * 2
(a, b) => a.len() < b.len()
() => 5
n => total += n
u => 1.0 + depth * sin(u * ribs)

The short form takes parameter names only, whose types come from the signature the closure is given to, and a body that is one expression, an assignment, or a block. It has no state list and no written return type; a closure that needs either is written in the full form. A comma after the body belongs to the list the closure is in, so f(x => x + 1, 3) is a call with two arguments.

The arrow is =>, not ->, which would read as "returns".

fn apply(f &<fn(x i32) i32, x i32) i32 { f(x); }

imm off = 10;
apply(x => x * 2, 21);                     // 42
apply(fn(x i32) i32 { x + off; }, 1);      // 11
apply(fn(x) { x + off; }, 1);              // 11: the type comes from the signature

What a closure captures

A closure's body may name variables of the function around it. Each one it names is borrowed: the closure holds a reference to it, & where the body only reads it and &mut where the body changes it, and the compiler works out which from the body. The variable around shows the change:

mut total = 10;
mut add = fn(x i32) { total += x; };   // borrows total as &mut
add(3);
add(4);
total;                                 // 17

Only a mut variable can be changed by a closure; changing any other is the ordinary "no permission to modify" error, reported inside the body. Because the closure holds a variable it changes by &mut, its body cannot lend that variable &uni (bump(&uni total) is refused): a shared reference does not see through to a unique one. The borrow is an ordinary one, so it holds the variable as borrows do. While a closure that reads a variable is still to be used, the variable cannot be changed or moved; after the closure's last use it can:

imm limit = 100;
mut count = 1;
imm sum = fn(x i32) i32 { x + limit + count; };
sum(1);        // 102
count = 5;     // ERROR if sum is called again below this line; fine once it is not

Borrowing is the default because a copy made silently would duplicate state: a closure that added to its own copy of total would leave total unchanged and would give no sign that it had. When a closure should hold its own value instead, it is listed.

Giving the closure its own value

A variable listed in the state list is no longer borrowed. The entry is a field with an initializer, so the ordinary rules for values decide what the closure holds:

imm ribs = 3;
imm shape = fn(u i32) [ribs, base = 2 * 5 + 1] i32 { u * ribs + base; };
shape(2);                              // 2 * 3 + 11: 17

mut xs = new List[i32]();
imm count = fn(x i32) [buf = xs] i32 { x + i32.from(buf.len()); };   // xs is moved in

imm p = new Pt(4, 5);
imm viaRef = fn(k i32) [r = &p] i32 { r.x * k; };              // a borrow, written out

imm mesh = new Rc[imm, Pt](7, 8);
imm h = fn() [mesh] i32 { mesh.y; };   // a counted owner is copied: mesh is still held
  • A copy: [ribs]. An entry with no = starts from the variable of that name around the closure. A value that copies is copied and one that moves is moved, as it would be passed to a function.
  • A move: [buf = xs], for a value that moves. The closure owns it, and xs can no longer be used.
  • Shared ownership: list a handle of a region that counts its owners, such as an Rc or an Arc. The closure holds one count and the original holds another. The permission of the handle decides whether the closure may change what it points at (Rc[mut, T]).
  • New state: [mut n = 0], which has no variable around it to mirror.
  • A borrow, written out: [r = &p]. The closure then has the lifetime of the borrow, as it does for a borrow it makes itself.

An entry's initial value is read in the code around the closure, not from the entries before it: in [a = 1, b = a] the a that b starts from is the one outside.

Naming the state has other benefits: it tells the reader which variables are the closure's own, and an entry may be given a name of its own, as a field may. Listing is optional where borrowing will do.

A closure written in a method that names a member of the object, hits or step, reaches it through the method's self, which it borrows as it borrows any variable. A closure sees exactly what the code around it sees, private members included, wherever it is later called from:

struct Tally {
  hits i32;
  step i32;
  pub fn run(self &mut) i32 {
    mut bump = fn(x i32) i32 { hits += x * step; hits; };
    bump(1) + bump(2);
  }
}

Whether the closure changes

A closure is a value whose one method, (), is the body. That method's self permission is not written: it follows the body. A body that only reads what the closure holds and borrows has self &. A body that changes a captured variable or a mut state entry has self &mut.

This decides what the closure may be used for. A closure whose () takes self &mut is held in a mut variable to be called, and goes only where a callable may change its state, &mut F and &<mut fn(sig) (Generics, Closure References). Given to a parameter that promises only to read it (&F, &<fn(sig)), it is refused, and the error says that this closure changes its state.

The return type

The return type is, in order of preference:

  1. the one written, fn(x i32) i64 { ... };
  2. the one the signature expected gives, where the closure is passed or assigned to one, every path being checked against it;
  3. read off the body's paths: the first return or final expression the check meets fixes it, and the others must fit it. A body whose last statement changes something (total += x;) returns nothing; any other last expression is the value;
  4. otherwise an error at the closure, "the paths give different types; write the closure's return type": fn(x i32) { if x > 0 { x; } else { 0u8; } }.

return in a closure returns from the closure, never from the function around it.

imm early = fn(x i32) i32 { if x > 5 { return 1; } x + 2; };
early(9);      // 1
early(3);      // 5

A closure that holds nothing

A closure that borrows nothing and has no state is a plain function. Where a function reference, &fn(sig), is wanted it becomes one: twice(x => x * 3, 1) to a parameter f &fn(x i32) i32. One that holds or borrows something is refused there; the parameter is then written &<fn(sig). An anonymous function written with the ampersand, &fn(x i32) i32 { x + 1; }, is not a closure: it is a function reference and sees no variable of the code around it.

Where a closure may go

A closure is a value of a struct of what it holds and borrows, so where it can go is decided by the rules for its fields, with nothing special for closures. A closure that borrows a variable cannot outlive it:

  • Down a call, passed to a function that uses it and returns, it may borrow any variable of the function around it, with one exception: a call that is also handed a &mut (or &uni) borrow, a method's receiver among them, of something that can hold borrows (a struct with a borrowed-reference field, a list of borrowed references) that the caller lent, since the call could store the closure's borrow there, where it would outlive the variable. That call is refused (error 1085) when the closure borrows a local of the function, or another argument is a borrow of a local, even though the callee only reads the closure. The error names the variable. A closure lists the variable, fn(x &i64) [k] bool { *x > k; }, to hold its own copy and borrow nothing. A receiver the function owns is not refused, and nor is one that cannot hold a borrow, such as a List[i64].
  • Kept in a local, it blocks moving or reshaping what it borrows until its last use.
  • Stored past the function or returned (in a field, in an owner such as So[fn(sig)], or as a returned borrow), it is refused if it borrows a local. The error names the variable and says to list it, so that the closure holds its own copy: fn (...) [k] ... { ... }.
  • Stored in the object that made it: a closure in a method that names a member borrows self, so it cannot be stored in self. The error says to copy the members it needs into its list ([tag = tag]), or to capture a counted handle to the object.
  • Sent to another thread or actor, or run in a parallel each, it must be Sendable, or Shareable for the loop, judged by what it holds (Sendable and Shareable). A closure that borrows a variable is neither; the error names the variable and says to list it. A closure holding an Rc is told to hold an Arc.
fn returned() So[fn(x i32) i32] {
  imm k = 3;
  // ERROR: The closure borrows 'k' because its body names it: list it ...
  return new So[fn(x i32) i32](fn(x i32) i32 { x * k; });
}

fn listed() So[fn(x i32) i32] {
  imm k = 3;
  return new So[fn(x i32) i32](fn(x i32) [k] i32 { x * k; });   // its own copy of k
}

The exception for a call down a function, with a holder of borrows that the caller lent:

struct Seen {
  pub items List[&i64];
  pub fn count[F fn(x &i64) bool](self &mut, f F) i64 {
    mut n = 0i64;
    mut i = 0usize;
    while i < self.items.len() {
      if f(*self.items[i]) { n = n + 1; }
      i = i + 1usize;
    }
    n;
  }
}

fn refused(seen &mut Seen) i64 {
  imm k = 3i64;
  // ERROR 1085: seen holds borrows and the call could store the closure's borrow of 'k' in it
  seen.count(x => *x > k);
}

fn listed(seen &mut Seen) i64 {
  imm k = 3i64;
  seen.count(fn(x &i64) [k] bool { *x > k; });   // its own copy of k: nothing borrowed
}

fn owned() i64 {
  imm base = 5i64;
  imm k = 3i64;
  mut seen = new Seen(List[&i64].empty());
  seen.items.push(&base);
  seen.count(x => *x > k);   // fine: this function owns seen
}

Calling a closure while a collection is borrowed

A call through a mutable virtual reference, a &<mut fn(sig) parameter, is assumed able to reshape any container, because the closure behind it may have captured one. A live view into a container that another path reaches (a &mut parameter, a field of self) is refused across the call (error 1339). A visitor that iterates a list while its closure may push to that list moves the block the iteration reads:

fn visit[T](xs &List[T], f &<mut fn(x &T)) {
  each x in xs.iter() { f(x); }          // Error 1339: f may push to xs
}
fn grow(list &mut List[i64]) {
  mut push = fn(x &i64) { list.push(*x); };
  visit(list, &mut push);
}

Lending the list &imm cures it: nothing can write it, so no closure handed in can have captured it by &mut (the caller's list is an imm variable). Marking the closure + ShapeKeeping, or copying what is needed out before the call, also works. A read-only &<fn is not affected.

fn visit[T](xs &imm List[T], f &<mut fn(x &T)) {
  each x in xs.iter() { f(x); }          // Ok
}
imm nums = numbers();
mut sum = 0i64;
visit(&imm nums, fn(x &i64) { sum += *x; });   // sum is 27 for 1, 5, 9, 12

A closure, read-only or not, may also write a mut global by its name, so a view into a global is refused across a call of a closure, read-only or not, and across a call of a function that makes one (A borrow into a mut global).

Rules that follow

  • A closure cannot call itself. The variable it is the value of is not a name inside it. Recursion uses a named function.
  • A closure is written in a function, never at the module level as a global's value or a field's default: there is nothing there to borrow.
  • On a GPU a closure is allowed in its static form only (Closures on the GPU).

Closures are values

Although closures may be viewed as functions with a persistent state, it is more useful and accurate to view them as a data value that carries an associated function (method):

  • A closure is syntactic sugar for an anonymous struct, whose fields are the state list's entries and a reference for each variable it borrows. The struct has no name that can be written, so a closure is held in a variable whose type is inferred, and given on as one of the references below.
  • Like any value, a closure may be allocated on the heap, in an owner such as So[fn(sig)].
  • A function that should accept any closure of a signature, without regard for the shape of its state, takes it as a closure reference, &<fn(sig), or as a generic over the signature, [F fn(sig)], which is compiled for each closure and inlined.
  • A closure may fill a trait with one required method as a struct does.
