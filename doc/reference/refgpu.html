Cone
GPU Compute

Note: Compute entry points are implemented for SPIR-V's Vulkan form (conec --triple=spirv1.6-unknown-vulkan1.3), with their buffers, their Invocation, their error buffer, atomics on buffer elements, workgroup memory and barriers as described below, and Congo builds a package's kernels (below, "A package's kernels"). Not yet: gpuwork binding the error buffer itself, refusing the features a GPU lacks where they are written, textures, a checked form of workgroup memory, a CPU twin that runs a workgroup's invocations together (so that one reading another's writes across a barrier gets the GPU's answer), and f16. Floating-point operations are not yet marked to keep the driver from fusing a multiply and an add, so a kernel's float arithmetic is not yet bit for bit the CPU's (below).

A GPU runs one function, a kernel, thousands of times at once, each run an invocation working on its own part of the data. Cone writes a kernel as an ordinary function marked as a compute entry point. Compiled for a GPU, it is a compute shader whose parameters are what the program's dispatch binds; compiled for the CPU, it is an ordinary function, which a loop over the invocations runs, so one source is both the GPU's work and its twin on the CPU.

Compute entry points

struct Part {
  pub w Array[f32, 4];
  pub k u32;
}

fn @compute(64) bake(inv Invocation, parts &[]Part, out &[]mut f32) {
  imm i = usize.from(inv.globalId[0]);
  if i < out.len {
    out[i] = parts[i].w[0] * f32.from(parts[i].k);
  }
}

@compute, written after fn, makes the function a compute entry point and gives its workgroup's size: how many invocations run together, along x, y and z, those not written being 1: @compute(64), @compute(8, 8), @compute(4, 4, 4). Each is a constant integer of at least 1, and a workgroup holds at most 256 invocations and 64 along z, the limits every WebGPU device guarantees. An entry point is a function of its module: not a method, not generic, not inline, not @c. An extern one, as a package's include file declares it, is called on the CPU as any function is.

An entry point returns nothing: what a kernel makes, it writes into a slice it was given. Its parameters are what a dispatch binds, each of one of three kinds, in any order:

  • Invocation, at most once: which invocation is running. It is core's Invocation, a plain struct: globalId, the invocation's id in the whole dispatch, localId, its id in its workgroup, and groupId, its workgroup's, each an Array[u32, 3]; localIndex, its place in its workgroup counted x fastest; and groupCount, how many workgroups the dispatch has each way. On the GPU it is filled from the invocation's built-in values; on the CPU, the loop that calls the function fills it.
  • A slice, one storage buffer: &[]T the kernel only reads, and &[]mut T it writes as well. Its length is the buffer's. Every invocation may write any element of a &[]mut buffer; that two do not write one element is the program's to arrange, a trusted exception to Cone's rule against threads sharing what they change, until a checked form is designed.
  • A struct taken by value, one small read-only storage buffer holding one value: the kernel's settings. (WebGPU has no push constants, and a uniform buffer lays an array out in 16-byte steps, which is not Cone's layout.)

A kernel binds at most seven buffers: WebGPU's eight storage buffers a stage, less the error buffer (below).

What a buffer holds is shared byte for byte between the CPU and the GPU, so it may hold only what the two lay out alike: 32-bit numbers (i32, u32, f32), their atomics (Atomic[u32] and Atomic[i32], below), and structs and fixed arrays of them, nested as deep as wanted. A Bool, a number of 8, 16 or 64 bits, usize or isize (as wide as each target's addresses), a reference, slice or pointer, an enum or an Option is refused, with the field that holds it. A struct of three f32s is twelve bytes on both sides: Cone never makes one of a GPU's vector types, which a buffer aligns to sixteen.

The kernel's interface

The buffers are bound in descriptor set 0, numbered by their place among the buffer parameters, from 0: in bake above, parts is binding 0 and out binding 1. The kernel's entry point in the SPIR-V module is named as the function is.

Failures: the error buffer

A GPU has no program to end. On one, a failed index or range check, a panic, an assert, an unreachable or a todo records what failed in the kernel's error buffer and stops that invocation, the others going on. The checks are kept in every build. The error buffer is a read-write storage buffer bound after the last of the kernel's buffers (binding 2 in bake), of eight 32-bit words, zero before the dispatch:

WordHolds
0How many invocations failed; 0 when none did
1What failed: 1 an index past the end, 2 a range not within its array or slice, 3 a panic (an assert among them), 4 an allocation
2The source file's id: the name its module lists for it, in the debug string "cone.file <id> <name>" (an OpSourceExtension); 0 when not known
3The line
4, 5, 6The failed invocation's globalId
7The index that was out of bounds, or the end of the range; else 0

The first invocation to fail writes words 1 to 7, so they describe one failure whole; any that fail after it only count. The program reads the buffer after the dispatch. (To come: the gpuwork package binding and reading it itself, and reporting a failure there as a panic on the CPU.)

Slices on the GPU

A GPU has no pointer arithmetic: it reaches an element from the variable that holds it. So in a kernel a slice is indexed in what it came from: a buffer parameter, or a fixed array, all of it or part, a local, a constant or a field of a buffer's struct, however many functions it was handed through and however it was cut. A slice that came from anything else, a pointer to a single value say, is refused where it is indexed.

Math on the GPU

No GPU has the C library. A call to one of its math functions, the libc package's or any @c function of the same C name, is on a GPU the GPU's own instruction (GLSL.std.450's, in SPIR-V), as are f32's and f64's sqrt, sin and cos methods. On the CPU nothing changes: the C library is called.

What was measured was an RTX 4060 against the Windows C runtime, 65,536 arguments a function. Where a precision is an approximation, two GPUs differ from each other as well as from the CPU, and nothing computed from such a function is the same everywhere. The f64 forms of the exact functions and of sqrt and fmod are the GPU's at 64 bits, which needs a device with 64-bit floats (WebGPU has none); Vulkan has no 64-bit sin, cos, tan, inverse trigonometry, exp, log or pow, and refuses a module that asks for one.

A GPU's driver may also fuse a multiply and an add into one rounding, or reorder a sum, which the CPU does not. conec forbids both in everything it compiles for the GPU: each float addition, subtraction, multiplication, division and negation is rounded on its own, in the order written, as the CPU rounds it (SPIR-V's NoContraction, on every such result). Vulkan rounds an addition, a subtraction and a multiplication correctly, so arithmetic built only from those, floor, ceil, fabs and comparisons gives the same bits on every GPU as on the CPU, a subnormal result aside, which Vulkan lets a GPU flush to zero. noise's fBm, measured, matches the CPU at every one of its bake's 262,144 points, value and derivatives, as do its value and gradient noise, its other fractal sums and its warps. What takes a square root, a division (Vulkan's bound 2.5 ulp, measured within 2) or another function of the table above is close, not identical. A remainder, fmod, is left free to fuse, since that is how the RTX 4060 computes C's exact remainder: forbidden, it matched at 62% of arguments. The CPU never fuses, on any CPU conec targets, one with fused multiply-add instructions too (--cpu=native).

A package's kernels

Whether a package may run on a GPU is said by the package: its manifest marks it, targets = ["native", "gpu"] in Congo's congo.toml (a spelling that may yet change). Congo compiles a marked library whose source holds compute entry points for the GPU as well as for the CPU, into one SPIR-V module, <package>.spv, holding each of its kernels, and copies it beside every program that imports the package, where gpuwork's readSpirv reads it. Every package a kernel's package imports, at any depth, must be marked too, or Congo refuses the build before compiling anything, naming the imports that reached the unmarked one.

On a GPU every function a kernel calls is inlined into it, so no function is marked for the GPU on its own and none carries its body in an include file: the marked packages a kernel imports are compiled into its module from their source. Only what a kernel reaches becomes part of it. Which of a marked package's features a GPU lacks is the compiler's to say, where they are used. (tools/congo/README.md, "Kernels for the GPU", is how Congo does it.)

Atomics

fn @compute(64) compact(inv Invocation, input &[]u32, count &[]mut Atomic[u32], out &[]mut u32) {
  imm i = usize.from(inv.globalId[0]);
  if i < input.len and input[i] % 3u32 == 0u32 {
    imm slot = count[0usize].addOrdered(1u32, MemOrder.Relaxed[]);
    out[usize.from(slot)] = input[i];
  }
}

A buffer of Atomic[u32] or Atomic[i32] holds numbers that invocations change together, each change indivisible: a counter several invocations add to, or one that hands each kept element its slot, as above. It is core's Atomic, the same type and the same methods as on the CPU: four bytes, its number and nothing more, as WebGPU's atomic<u32> is, so the CPU reads the buffer as numbers. An atomic may also be a field of a buffer's struct, or an element of a workgroup global. An Atomic of anything else (a u64, a Bool, a pointer) is refused in a buffer, as its number would be.

Every method an integer Atomic has works on a GPU: load, store, swap, add, sub, min, max (signed for an i32, unsigned for a u32), bitAnd, bitOr, bitXor and compareSwap, each with its Ordered form. Each acts at the scope of the memory it changes: a buffer's is the device, every invocation of the dispatch; a workgroup global's is its workgroup. Vulkan has no sequentially consistent ordering, so on a GPU SeqCst, what the everyday forms promise, is acquire-release; Relaxed, Acquire, Release and AcqRel are as written. A counter needs no ordering beyond its own change, so Relaxed is the right one for claiming a slot.

An atomic acts on memory invocations share. One on a local Atomic, or on a module's global that is not @workgroup, each invocation's own, is refused in the kernel.

Workgroup memory

mut @workgroup scan Array[u32, 256];

fn @compute(256) prefix(inv Invocation, input &[]u32, out &[]mut u32) {
  imm g = usize.from(inv.globalId[0]);
  imm l = usize.from(inv.localIndex);
  scan[l] = if g < input.len {input[g];} else {0u32;};
  workgroupBarrier();
  mut step = 1usize;
  while step < 256usize {
    imm add = if l >= step {scan[l - step];} else {0u32;};
    workgroupBarrier();
    scan[l] = scan[l] + add;
    workgroupBarrier();
    step = step * 2usize;
  }
  if g < out.len { out[g] = scan[l]; }
}

A module's global written with @workgroup after its permission is workgroup memory: on a GPU, one copy for each workgroup, which its invocations share, and which is far faster than a buffer. It is written as @threadlocal is: a module's global, mut, of a fixed size, holding what a buffer may hold (32-bit numbers, their atomics, and structs and fixed arrays of them) and nothing that needs finalizing. It has no initial value: a workgroup's copy starts undefined, so the invocations write what they will read, then wait at a barrier before reading what the others wrote. An initial value is refused, zero among them.

Invocations reading and writing one global is a trusted exception to Cone's rule against threads sharing what they change, as a &[]mut buffer is: that one invocation does not read a place another is writing, without a barrier between, is the program's to arrange. (A checked form, each invocation owning its own place and reading the others' only after a barrier, is to come.)

On the CPU a workgroup global is an ordinary global, one copy, and the loop that runs a kernel runs one invocation at a time, workgroup by workgroup. A kernel whose invocations read, after a barrier, only what the invocations before them in that order wrote (the last invocation of a workgroup gathering what the others counted, say) gives the same answer on both. One whose invocations read what invocations after them write, as the prefix sum above does, needs its workgroup's invocations run together, which the CPU's loop does not yet do.

Barriers

pub fn @intrinsic workgroupBarrier()
pub fn @intrinsic storageBarrier()

Core's two barriers: every invocation of the workgroup waits at one until all have reached it, and what each wrote before it every other reads after it. After workgroupBarrier, that is what was written to workgroup memory; after storageBarrier, what was written to the buffers the kernel binds, as the other invocations of the same workgroup see it. Every invocation of a workgroup must reach the same barrier, so one is never written where some invocations of a workgroup go and others do not. On the CPU each is nothing.
