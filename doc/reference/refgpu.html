GPU Compute

Note: Compute entry points are implemented for SPIR-V's Vulkan form (conec --triple=spirv1.6-unknown-vulkan1.3), with their buffers, their Invocation and their error buffer as described below. Not yet: Congo building a package's kernels (each module is compiled with conec directly), gpuwork binding the error buffer itself, deciding which packages may run on a GPU, refusing the features a GPU lacks where they are written, textures, atomics in buffers, workgroup memory and f16. The math functions Cone takes from the C library (floorf and its kind) are not yet a GPU's built-ins, so a kernel calling one is not yet a module Vulkan accepts.

A GPU runs one function, a kernel, thousands of times at once, each run an invocation working on its own part of the data. Cone writes a kernel as an ordinary function marked as a compute entry point. Compiled for a GPU, it is a compute shader whose parameters are what the program's dispatch binds; compiled for the CPU, it is an ordinary function, which a loop over the invocations runs, so one source is both the GPU's work and its twin on the CPU.

Compute entry points

struct Part {
  pub w Array[f32, 4];
  pub k u32;
}

fn @compute(64) bake(inv Invocation, parts &[]Part, out &[]mut f32) {
  imm i = usize.from(inv.globalId[0]);
  if i < out.len {
    out[i] = parts[i].w[0] * f32.from(parts[i].k);
  }
}

@compute, written after fn, makes the function a compute entry point and gives its workgroup's size: how many invocations run together, along x, y and z, those not written being 1: @compute(64), @compute(8, 8), @compute(4, 4, 4). Each is a constant integer of at least 1, and a workgroup holds at most 256 invocations and 64 along z, the limits every WebGPU device guarantees. An entry point is a function of its module: not a method, not generic, not inline, not @c. An extern one, as a package's include file declares it, is called on the CPU as any function is.

An entry point returns nothing: what a kernel makes, it writes into a slice it was given. Its parameters are what a dispatch binds, each of one of three kinds, in any order:

  • Invocation, at most once: which invocation is running. It is core's Invocation, a plain struct: globalId, the invocation's id in the whole dispatch, localId, its id in its workgroup, and groupId, its workgroup's, each an Array[u32, 3]; localIndex, its place in its workgroup counted x fastest; and groupCount, how many workgroups the dispatch has each way. On the GPU it is filled from the invocation's built-in values; on the CPU, the loop that calls the function fills it.
  • A slice, one storage buffer: &[]T the kernel only reads, and &[]mut T it writes as well. Its length is the buffer's. Every invocation may write any element of a &[]mut buffer; that two do not write one element is the program's to arrange, a trusted exception to Cone's rule against threads sharing what they change, until a checked form is designed.
  • A struct taken by value, one small read-only storage buffer holding one value: the kernel's settings. (WebGPU has no push constants, and a uniform buffer lays an array out in 16-byte steps, which is not Cone's layout.)

A kernel binds at most seven buffers: WebGPU's eight storage buffers a stage, less the error buffer (below).

What a buffer holds is shared byte for byte between the CPU and the GPU, so it may hold only what the two lay out alike: 32-bit numbers (i32, u32, f32), and structs and fixed arrays of them, nested as deep as wanted. A Bool, a number of 8, 16 or 64 bits, usize or isize (as wide as each target's addresses), a reference, slice or pointer, an enum or an Option is refused, with the field that holds it. A struct of three f32s is twelve bytes on both sides: Cone never makes one of a GPU's vector types, which a buffer aligns to sixteen.

The kernel's interface

The buffers are bound in descriptor set 0, numbered by their place among the buffer parameters, from 0: in bake above, parts is binding 0 and out binding 1. The kernel's entry point in the SPIR-V module is named as the function is.

Failures: the error buffer

A GPU has no program to end. On one, a failed index or range check, a panic, an assert, an unreachable or a todo records what failed in the kernel's error buffer and stops that invocation, the others going on. The checks are kept in every build. The error buffer is a read-write storage buffer bound after the last of the kernel's buffers (binding 2 in bake), of eight 32-bit words, zero before the dispatch:

WordHolds
0How many invocations failed; 0 when none did
1What failed: 1 an index past the end, 2 a range not within its array or slice, 3 a panic (an assert among them), 4 an allocation
2The source file's id: the name its module lists for it, in the debug string "cone.file <id> <name>" (an OpSourceExtension); 0 when not known
3The line
4, 5, 6The failed invocation's globalId
7The index that was out of bounds, or the end of the range; else 0

The first invocation to fail writes words 1 to 7, so they describe one failure whole; any that fail after it only count. The program reads the buffer after the dispatch. (To come: the gpuwork package binding and reading it itself, and reporting a failure there as a panic on the CPU.)

Slices on the GPU

A GPU has no pointer arithmetic: it reaches an element from the variable that holds it. So in a kernel a slice is indexed in what it came from: a buffer parameter, or a fixed array, all of it or part, a local, a constant or a field of a buffer's struct, however many functions it was handed through and however it was cut. A slice that came from anything else, a pointer to a single value say, is refused where it is indexed.
