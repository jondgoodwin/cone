Concurrency

Note: Of the models below, only OS threads are implemented, on Windows only, as the thread library package: starting, joining (a handle dropped unjoined joins) and detaching a thread, its identity, sleep, parking, and the futex, all described at the end of this page. Nothing checks yet that what is handed to a thread is safe to share. Co-routines, green threads, processes, distributed computing, and splitting work across threads are not implemented.

Concurrency and parallelism can sometimes improve program throughput, by:

  • Distributing work across multiple CPUs (many hands make light work).
  • Keeping the CPU(s) busy with other work, rather than pausing all work while waiting on i/o to complete.

Most of the heavy lifting for Cone's concurrency and parallelism capability is baked into library packages. Depending on the library packages chosen, many work distribution and scheduling approaches can be taken (ordered by context switching cost):

  • Cooperative concurrency (generators or co-routines), where context switching is explicitly baked into the logic.
  • Green (mxn) threads, where context-switching is cooperatively handled by the runtime's work-stealing scheduler, rather than the OS.
  • OS threads, where context-switching is handled by the OS scheduler. Threads share memory and resources.
  • OS processes, where context-switching is handled by the OS. Processes are isolated, largely communicating via pipes.
  • Distributed computing, where work is distributed across different machines, communicating via network sockets.

As always there are trade-offs: Sometimes the loss in context-switching cost (latency) can be justified by improvements in scalability, fault tolerance, i/o handling, etc.

All the above models support structured concurrency. All new processes or threads are effectively owned resources. Like all owned resources, there is a programmatic point-in-time when owned threads are joined, terminated and freed according to the logic of the finalizer. Libraries also support the ability to split m pieces of work across n independent processes/logic.

Concurrency (and parallelism) introduce safety risks, when implemented poorly:

  • Race conditions, where a system's behavior varies inconsistently, depending on the sequence or timing of independent operations.
  • Deadlocks, where forward progress has stalled out because independent operations have unresolved contention over the temporary ownership of multiple resources.
  • Livelocks, where forward progress has stalled out because of resource starvation that is not caused by deadlocks.

Subsequent pages highlight Cone language features (e.g., permissions and queued methods) that can be used to make synchronized, inter-thread communications easier and safer.

OS threads: the thread package

The thread package is the operating-system layer every other model is to be built on: starting and joining OS threads, and the futex, the one blocking primitive the locks, the channels and the schedulers are to be written over. It is deliberately small, and it is ordinary library code, bound to the operating system through extern functions; the compiler knows nothing of it. Its source, packages/thread/src/thread.cone, documents the same rules at greater length.

import thread;

fn triangle(n i64) i64 { ... }

fn main() {
  imm t = thread.start[i64, i64](100, &triangle);  // a new thread runs triangle(100)
  ...                                              // while main goes on
  imm total = t.join();                            // wait for it: 5050
}

Starting a thread

thread.start[A, R](arg, &f) starts a new OS thread running f(arg) and returns its handle at once, a Thread[R]. The thread is given a function and one value:

  • The value is moved in. The thread owns it, and it dies there when f is done with it. A struct carries more than one value.
  • f is a plain function taking an A and returning an R, which may be void. A closure cannot capture yet, which is why a thread is given a value beside its function.
  • Both type arguments must be written: the compiler does not yet infer a type parameter from a function reference's signature.
  • The function comes after the value, because a function-reference parameter with a return type can only be a function's last parameter today (a comma after it is read as the start of a second return type).
  • What is handed to a thread is not checked yet. Safe to hand over is a value the thread will own outright (a number, a struct of them, a +so owner, a uni reference) or an imm or opaq reference, which the permission rules already mark as safe to share. A mut or ro reference, an rc owner (its count is not atomic), a borrowed reference into the starting thread's stack, or a raw pointer to memory another thread also writes all compile today, and are the program's to get right, with atomics or the futex. The compiler's check comes later.

thread.startWith[A, R](thread.Options[name: n, stackSize: s], arg, &f) does the same with options, each of which has a default and may be left out:

  • name, empty by default, is copied as the thread starts. It is Cone's own, seen through name(); the operating system's debuggers do not see it.
  • stackSize, 0 by default, is how many bytes of address space to reserve for the thread's stack; 0 is the executable's default. Windows rounds a size up to its allocation granularity, and one of 4 GB or more is taken as 4 GB less one byte.

A thread that cannot be started, or memory that cannot be allocated for it, ends the program with a message on stderr. A trap on any thread ends the whole process.

The handle: join, detach, and join on drop

A Thread[R] is its thread's one owner, a move type.

  • t.join() waits for the thread to finish and returns what f returned. It consumes the handle, so a thread is joined once.
  • t.detach() consumes the handle and lets the thread run on alone. What f returns is finalized on the thread, since nobody will read it.
  • A handle that dies unjoined joins: its finalizer waits for the thread and finalizes the result nobody took. This is tidiness, not safety. A handle can be kept where it never dies, and a process ends without finalizing what its threads hold, so nothing a program depends on may rest on that join. A thread whose work must be finished is joined.
  • t.id(), t.name() and t.unpark() are the thread's own, as below, and t.threadRef() is a ThreadRef to it.

A handle kept in a field or a collection cannot yet be moved out of it to be joined (Cone does not move a value out of a struct's field), so such a handle is joined by its container's death. When main returns, the process ends, and every thread still running ends with it; handles in main's locals have been joined by then.

The running thread

  • thread.current() is a ThreadRef to the calling thread: its identity, kept alive while the ThreadRef lives, which may be sent to other threads. It is a move type; r.copy() makes another. r.id() is the operating system's thread id, which it may reuse once a thread has ended and its handle is gone. r.name() is the name startWith gave, and empty for any other thread, the main thread included. A thread the package did not start takes up an identity the first time it asks for one, and keeps it, since nothing runs when such a thread ends.
  • thread.parallelism() is how many logical processors the machine has, at least 1. It does not count what an affinity mask takes away.
  • thread.sleep(ns) sleeps at least ns nanoseconds on Windows' high-resolution timer, so a 1 ms sleep takes 1 to 2 ms rather than the 15.6 ms of the system's timer tick. Where that timer is missing (before Windows 10 version 1803) it falls back to whole milliseconds, rounded up. sleep(0) gives up the rest of the time slice to another ready thread of the same priority.
  • thread.yieldNow() lets another thread ready to run on the same processor have it, and returns at once if there is none.

Parking

Each thread has one parking token, and starts without it. thread.park() takes the token, sleeping until there is one; unpark(), on the thread's handle or a ThreadRef to it, makes it available. An unpark sent before the park is therefore not lost, and the park returns at once. Unparks do not add up: two before a park are one token. park never returns without a token, but a parked thread still checks what it was waiting for, since a token may have been meant for an earlier park.

The futex

A futex is a 32-bit word that threads sleep on while it holds a value.

  • thread.futexWait(word, expected, timeoutNs): if *word still equals expected, checked atomically with going to sleep, sleep until woken or until the timeout passes. It returns false only when the timeout passed, and true when woken, when the word already differed, or spuriously, which the operating system permits. So a waiter loops, re-reading the word.
  • timeoutNs is nanoseconds, thread.forever by default, rounded up to whole milliseconds; its resolution is the system's timer tick, up to 15.6 ms. A timeout of 232 - 1 ms or more is that long, not forever. A timeout of 0 returns false at once if the word still holds expected.
  • thread.futexWake(word) wakes one waiting thread, and thread.futexWakeAll(word) every one. A wake with no thread waiting does nothing and is not remembered, so a thread stores the new value first and wakes after.
  • The word is a raw *u32, 4-byte aligned, and the caller keeps it alive while any thread may wait on it or wake it: nothing checks that. It is to become a reference to an atomic type. Waits and wakes reach only the threads of one process.
while mem.atomicLoad[u32](word, MemOrder.Acquire[]) == 0u32 {
  thread.futexWait(word, 0u32);     // sleeps only while the word is still 0
}

What a started thread may not use yet

The collector package's +gc collector is single threaded: its roots are one chain and its heap is not synchronized. A traced reference made, held, reached or dropped on a thread the package started corrupts it. Nothing checks this. A thread-local global gives each thread a copy starting from its initial value, and nothing finalizes a thread's copies when it ends.

Deliberately not provided: killing a thread, priorities, pinning a thread to a processor, a flag asking a thread to stop, and scoped threads, which would join before a function returns so that their threads could borrow. The package runs on Windows only.
