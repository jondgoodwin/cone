Traits

Note: All of this capability is implemented, except for actor trait, whose shape the grammar accepts and which the compiler does not build, as actors are not declared in source yet. mod trait is implemented, and described with modules.

Similar to struct, the definition for a trait type specifies named methods (and, possibly, fields). For example:

trait Id {
  pub id u32;
  pub fn print();
}

However, trait types accomplish a very different purpose than struct types. Instead of specifying the complete field layout and behavior of concrete data, trait types abstractly specify a common pattern of shared behavior (methods) and state (fields) across multiple concrete types. By this understanding, the Id trait above expresses the idea that there are other types out there which define a print method (that accepts no arguments and return no values) as well as an unsigned integer field named id.

Because traits abstract over other types, their use differs from concrete types (like structs) in two important ways:

  • One cannot explicitly create a value whose type is a trait. Thus, it is not possible to use a constructor of this type (e.g., imm node = Id[12] is illegal). Instead, you create a concrete-type value, and then you view that concrete value through the lens of a compatible trait.
  • A trait usually specifies methods that have no implementation logic, as the print method above demonstrates. When a method is called on a trait-based value, it will automatically substitute in the method implementation logic defined by the concrete value's type.

A trait is an abstract kind

A trait is not a kind of its own. trait is a modifier on a kind, and a trait is the abstraction of whatever kind it modifies. The full spelling of the declaration above is:

struct trait Id {
  pub id u32;
  pub fn print();
}

trait Id and struct trait Id are the same declaration, written two ways. The short form is the one you will normally write, and it means the struct family, because that is what a trait has always abstracted over.

Two more kinds take the modifier. A mod trait is the interface a module conforms to, with functions and globals as its members, and its defaults copied into each module that says it conforms: see modules. An actor trait is the abstraction of an actor; it is accepted by the grammar so that its spelling is settled, and the compiler reports it as not built yet.

The kind keyword is what says which family an abstraction belongs to, and composition requires the families to match: a struct composes a struct or a struct-trait, and an actor will compose an actor or an actor-trait. Nothing else on the declaration says which family it serves, and nothing about it is inferred.

enum does not take the modifier, and the omission is deliberate. An enum is concrete: its identity is the set of variants it declares, so anything you could hold behind an abstraction of one either is that set — and so is the enum — or is open, and so is a trait. enum trait is rejected.

Complying with a trait

A concrete type complies with a trait when it declares everything the trait requires: a method of each required signature, and a field of each required name and type. Compliance is noticed structurally. A type that happens to declare what a trait requires may be viewed through that trait, whether or not it has ever heard of it — which is what lets you apply a trait to a library type you did not write, and saves you from defining interfaces defensively in case you need them later.

Declaring it, with is

A type may also say so in its own declaration:

trait Id {
  pub id u32;
  pub fn describe(self &) u32;
}

struct Node is Id {
  pub id u32;
  pub value u32;

  pub fn describe(self &) u32 {id + value;}
}

This is the only place in Cone where a subtype relationship is asserted rather than noticed. The compiler verifies the compliance where it is written, and rejects the declaration if it does not hold.

It is the same is you already know. p is Mobile asks of a value what struct Node is Id asserts of a type, and X is Y means “X is a Y” in both. The difference is the operand, not the question: a value's variant is dynamic, so the value form is answered at runtime, while a type's relationships are fixed, so the declaration form is settled where it is written. One predicate over two kinds of operand — not two mechanisms that happen to share a word.

The obvious objection is that structural compliance makes the declaration redundant. It does not, for two reasons.

A marker trait is empty, so nothing structural can ever notice it. Plenty of useful traits carry no fields and no methods at all — they are testable invariants, adjectives a type either claims or does not. There is no such thing as a structural match to a trait that declares nothing: every type would match it, so the match would say nothing at all. Such a trait can only be carried by the types that nominate it, which is what is is for. Nothing else in the language can express it.

And a declaration forces compliance at the moment of declaring, rather than later at the point of use. If a type is meant to satisfy a trait, saying so is what makes the compiler tell you the day you break it, at the type itself, instead of the day something far away tries to view a value through the trait and fails there.

The two kinds of compliance exist alongside each other on purpose. Structural compliance keeps traits applicable to types that never anticipated them; is lets a type commit, and makes the empty trait expressible at all.

What the declaration takes, and what it gives

  • A comma-separated list. A type may declare is against any number of traits: struct Ledger is Audited, Sealed, Sendable.
  • The trait contributes no fields. What a trait's fields state is a requirement, and the type declares them itself — the same names, the same types, in the trait's order, ahead of any field of its own. That prefix is what lets a plain &Id reference read the trait's fields straight out of the value, and what makes a same-size conversion to the trait a pure recast rather than a copy. Declaring them in another order, or behind a field of your own, is rejected.
  • Only the first trait in the list may require fields, since only one set of them can occupy the front of the layout. The rest must require none — which is no restriction in practice, because a field two traits want is declared once and satisfies both.
  • A method the trait implements and the type does not is inherited free. A trait may give a method a body, which becomes the default for any complying type that does not declare its own. Declaring it is the primary case; taking the trait's implementation is the fallback. Either way the method is the complying type's own, called on a value or named through that type: Node.describe. A trait's method named through the trait, Id.describe, is an error, since the trait keeps no copy of it; only a trait's static functions are reached that way.
  • A trait may itself declare is against another trait, layering a deeper abstraction over a shallower one. It complies with the field requirement the way any type does, by declaring the fields.
  • It folds nothing. There is no use clause on an is: a trait is an abstraction, so there is no value for a folded name to be reached through. Delegation is what a field's own use clause is for.
  • An enum and its variants declare it too. enum Shape is Named gives every variant the trait's requirements and defaults, and a variant may name traits of its own beyond its enum: struct Square is Sized, written inside the enum. Neither list has a base, so neither may name a trait that requires fields; Complying with a trait has the details.
  • Every name in the list is an open trait. An enum is closed: its variants are all declared inside it, so naming one anywhere in an is list, first or later, is rejected.
  • It is the one way to take a trait in. The retired mixin statement, which did the same from inside a type's body, is an error that points here.

Subtypes in Cone are always abstractions. A concrete type is never a subtype of another concrete type, so the base of an is must be a trait; naming a struct is rejected. Reusing another concrete type's code is a separate question, answered by delegated inheritance through a field, and by enrichment with extends over a concrete base. Neither grants subtyping, and a type may write extends and is together, in either order: they assert different things.

Traits make possible several valuable kinds of polymorphism, particularly:

  • Trait-based variants, which enable definition of multiple variant structs that share some base trait's common fields and methods.
  • Virtual reference interface, enabling the use of methods (and fields) on values whose concrete type can only be determined at runtime.
  • Generic constraints, which can be use to restrict which parametric types can be successfully substituted in to instantiate (monomorphize) a generic type.
