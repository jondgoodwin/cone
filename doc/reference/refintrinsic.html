Cone
Intrinsics

Note: Everything on this page is implemented, except that no call is yet required to be inside trust, because trust itself is not implemented.

Library code sometimes needs something only the compiler can do: say how large a type is, run a value's finalizer where it sits, or make a slice from a pointer and a count. An intrinsic is how Cone hands such a capability to library code. It looks like a function, and is called like one, but the compiler supplies what it does, expanding it where it is called.

Each intrinsic is defined by what it means in Cone, stated below with every edge case: never as "whatever the code generator's instruction does". A code generator is one way to implement that meaning. This is what lets an intrinsic mean the same thing on any back end.

Declaring an intrinsic

An intrinsic is declared with the @intrinsic attribute after fn, and an ordinary Cone signature:

pub fn @intrinsic sizeof[T]() usize;

Only the core package may declare one: as a function of one of its modules, or as a function (taking no self) of a plain struct one of them declares. Anywhere else, @intrinsic is an error.

Core declares every intrinsic below inside mem, and every module, core being its prelude, reaches them through that one name:

imm p = malloc(mem.sizeof[Point]() * 4usize) as *Point;
mem.writeRaw[Point](p, Point[1., 2.]);

So the intrinsics' own names are free: a module may declare its own finalize or sizeof. Only mem itself is a name every module has.

Why mem is a struct

mem is meant to be a submodule of core, core.mem. A submodule of core cannot yet be reached from outside it: a compile that finds core by itself reads only core's one source file, and the include file other packages compile against keeps a package's submodules private. So mem is declared as an @opaque struct, which holds no value, whose functions are reached by the same path a submodule's would be. When it becomes a submodule, no call changes.

The compiler keeps a registry of the intrinsics it defines. A declaration must name one of them, and must say exactly what the registry says: the same type parameters, parameters and result. An unknown name or a different signature is an error. An intrinsic has no symbol of its own, so it may not be extern, carry @c, or have a reference to it borrowed.

A type argument must be of the kind the intrinsic accepts. Every intrinsic below needs a type with a size: one declared @opaque, for example, is refused where the intrinsic is instantiated for it.

Fallback bodies

Where the registry allows it, the declaration may give a body written in Cone:

pub fn @intrinsic readRaw[T](p *T) T {*p;}

The body is the fallback: a back end with no implementation of its own for the intrinsic runs it instead, expanded at each call as an inline function would be. It must mean exactly what the intrinsic means. An intrinsic that nothing written in Cone can express, such as sizeof, has no fallback, and a body for it is an error. The compiler's --intrinsic-fallback option runs every fallback body in place of the compiler's own implementation, so that the two can be tested to agree.

Today's LLVM back end implements every intrinsic itself. Those with a fallback body are readRaw and moveRaw.

The intrinsics

Each is declared in core's mem and called as mem.name[T](...). Where an argument is a pointer to T or a T, the type argument may be left for the call to infer: mem.finalize(p) for a p *Point. Several intrinsics take a raw pointer and trust the caller's promise about it. Misused, they break memory safety in ways the compiler cannot see, so a call to one belongs inside trust. That is marked below as "needs trust" (not yet enforced).

sizeof

fn @intrinsic sizeof[T]() usize

The number of bytes from one T to the next in an array: its size, including the padding at its end that keeps the next one aligned. mem.sizeof[T]() * n is the memory n values need. A struct with no fields has size 0. The answer is a constant for the target: no code runs to compute it. It is not yet usable where the compiler itself needs a number, such as an array's length, because the compiler asks the target's layout for it when it generates code. No fallback.

alignof

fn @intrinsic alignof[T]() usize

The alignment in bytes the target requires of a T in memory: always a power of two, at least 1, and sizeof[T]() is always a multiple of it. A struct's alignment is its strictest field's. A constant for the target, as sizeof is. No fallback.

needsFinal

fn @intrinsic needsFinal[T]() Bool

Whether finalize[T] does anything: true when T is an owning reference, has a final method, has a field whose type needs finalizing (an owning reference among them), is a tuple or an array whose element type does, or is an enum one of whose variants does: true for Option[String], false for Option[i32]. False for numbers, raw pointers, borrowed references, and structs of them. A constant. It lets a collection skip the loop over its elements when there is nothing to do. No fallback.

finalize

fn @intrinsic finalize[T](p *T)

Runs the death of the T at p where it sits, exactly as a region-held value of type T dies, except that its memory is not given back: first T's own final, if it has one; then each field's death, in field order, recursively; then each owning reference its fields hold is released (which may finalize and free what that reference points at). If T is itself an owning reference, that reference is released: one owner goes away, and if it was the last, the value it points at dies. If T is an enum, the value dies as the variant it holds. If it is a tuple, each element dies in order; if it is a fixed-size array, each element dies in element order, first element first. For a type with nothing to finalize (needsFinal[T]() is false) it does nothing.

Needs trust: p must point at a live, initialized T, aligned for it. Afterwards that T is dead: reading it as a T or finalizing it again is a program error the compiler cannot detect. No fallback: the finalizer the compiler builds for T is the implementation.

typeRecord

fn @intrinsic typeRecord[T]() *TypeRecord

The address of T's type record, a constant holding what library code needs to handle a T it cannot name the type of: a region that keeps values of many types, and must later finalize each. TypeRecord is a struct core declares, so it is a name of every module:

pub struct TypeRecord {
  pub size usize;              // sizeof[T]()
  pub align usize;             // alignof[T]()
  pub finalize &fn(p *u8);     // what finalize[T] does to the T at p
  pub trace &fn(p *u8);        // for a tracing region; does nothing yet
  pub flags u32;               // bit 0: needsFinal[T](); bit 1: never set yet
}

size and align are what sizeof and alignof say. finalize is a function that, called with the address of a T, does exactly what finalize[T] does to it, with the same needs: a live, initialized T there, dead afterwards. Where T needs no finalizing it is a function that does nothing, and bit 0 of flags is clear, so a caller can skip the call. trace is meant for a tracing collector, to find the traced references a value holds; since none can be declared yet, it does nothing, and bit 1 of flags is never set. Neither function pointer is ever null.

imm rec = mem.typeRecord[Point]() as &TypeRecord;
imm fin = rec.finalize;
fin(p as *u8);          // p's Point dies where it sits

Asking twice in one compiled object gives the same address; nothing says two objects share one record, so records should not be compared across them. A region can also be handed the record of every value it allocates, by declaring its alloc to take one (Custom Allocators). A constant. No fallback.

sliceFromParts and sliceFromPartsMut

fn @intrinsic sliceFromParts[T](p *T, len usize) &[]T
fn @intrinsic sliceFromPartsMut[T](p *T, len usize) &[]mut T

A borrowed slice of the len consecutive T values starting at p: read-only from sliceFromParts, writable from sliceFromPartsMut. A len of 0 gives an empty slice, whatever p is.

Needs trust: the len values must be initialized, lie in one allocation, and stay there, unmoved and unfreed, for as long as the slice is used, which the compiler cannot see. A writable slice must be the only way those values are reached while it is used. No fallback.

readRaw

fn @intrinsic readRaw[T](p *T) T

Moves the T at p out and returns it: the value is the caller's now, and the slot is left dead. Nothing at the slot is finalized, and p may be used again (for another slot, or to write this one). This differs from *p, which, for a move type, marks the variable p itself as moved.

Needs trust: p must point at a live, initialized T. Reading the same live value twice gives two owners of it, and it dies twice. Fallback: {*p;}.

writeRaw

fn @intrinsic writeRaw[T](p *T, value T)

Moves value into the slot at p, which is treated as holding nothing: whatever was there is neither finalized nor released. This is how a value goes into memory that has just been allocated. *p = value is not the same: storing an owning reference that way releases the reference the slot is taken to hold, which in uninitialized memory is whatever bytes are there.

Needs trust: p must be aligned for T and point into memory the caller may write. If the slot held a live value, that value is simply forgotten, never finalized. No fallback: nothing written in Cone stores without releasing.

moveRaw

fn @intrinsic moveRaw[T](to *T, from *T, count usize)

Moves count consecutive values from from to to, as if each were read with readRaw and written with writeRaw. The two ranges may overlap, and the result is as if every value were read before any was written. Nothing is finalized: the values now live at to, and the slots of from that to does not cover are dead. A count of 0 does nothing.

Needs trust: both ranges must lie in memory the caller may use, and the values at from must be live. Fallback: a loop of readRaw and writeRaw, running upward when to is below from and downward otherwise. The LLVM back end does it as one block move.
