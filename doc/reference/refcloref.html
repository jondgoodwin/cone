Closure References

Note: Built: the closure reference, spelled as the signature it calls (&<fn(x i32) i32, &<mut fn(x i32) i32), the owners So[fn(x i32) i32] and Rc[fn(x i32) i32] made with new, a closure literal lent for a statement, a callable held in a field and called by its name, and the markers + Sendable and + Shareable on a reference or an owner. Not built: calling a closure once, which consumes it, through an owner; and + joining any trait but those two markers.

Earlier, we introduced value-based closures. A closure is a value of a struct that has no name, and its size and fields depend on what it holds. Value-based closures struggle when we need a function to take any closure that has a specific calling signature, whatever struct holds its state. To satisfy this requirement, a closure may be passed as a reference to the signature it calls.

Let's illustrate this with a simple event-handling example:

struct Button {
  pub label i32;
  pub onClick So[fn(n i32)];
  pub fn setHandler(self &mut, f So[fn(n i32)]) { onClick = f; }
  pub fn press(self &mut, n i32) { onClick(n); }
}

imm w = new Window(7);       // a Window has an id field
mut b = new Button(1, new So[fn(n i32)](fn(n i32) { }));
b.setHandler(new So[fn(n i32)](fn(n i32) [id = w.id] { print <- id + n, "\n"; }));
b.press(5);      // 12

Here we allocate a new click-handling closure using the single-owner region (ensuring it is automatically freed after being replaced or discarded). The closure's state remembers the window's id, which its logic uses when the button is pressed. The Button holds the closure as a So[fn(n i32)]: it accepts any closure, whatever its underlying state, so long as its function signature matches (it accepts one i32 and returns no value). The button calls the handler by the field's name, onClick(n).

The forms of a closure reference

The reference is written as the signature of the call, fn(x i32) i32, behind a reference or an owner. The signature stands for the idea "anything that can be called like this", a trait that needs no declaring, and the reference is a virtual reference to it.

  • &<fn(x i32) i32, a borrowed reference that may read what it points at. The closure's () takes self &.
  • &<mut fn(x i32) i32, a borrowed reference that may change what it points at: a closure that counts, or changes a variable it borrows.
  • So[fn(x i32) i32], an owner of a closure on the heap. The permission of an owner works as it does for any owner: So[fn(sig)] may change the closure's state, So[imm, fn(sig)] only reads it.
  • Rc[imm, fn(x i32) i32], shared owners of a closure that only reads; Rc[mut, fn(x i32) i32], shared owners of a state they all change, so every holder sees one count. Rc[fn(x i32) i32] with no permission is uni, the sole owner, as for any Rc, and moves when copied.

These are the same permissions as elsewhere, so the call kind is the reference's permission, with no separate families of function types: a function that takes a callable it only reads takes &<fn(sig); one that lets it change takes &<mut fn(sig). The call is written as any call, and goes through the reference to the closure's code:

fn apply(f &<fn(x i32) i32, x i32) i32 { f(x); }
fn applyMut(f &<mut fn(x i32) i32, x i32) i32 { f(x); }
fn run(f So[fn(x i32) i32], x i32) i32 { f(x); }

What meets it

Anything that has a pub () method of the signature, parameters and return type exactly (the parameters' names do not matter):

struct Triple { pub k i32; pub fn `()`(self &, x i32) i32 { x * k; } }
struct Tally  { pub n i32; pub fn `()`(self &mut, x i32) i32 { n = n + x; n; } }
fn succ(x i32) i32 { x + 1; }

imm off = 10;
imm shift = fn(x i32) i32 { x + off; };
imm t = new Triple(3);
mut tally = new Tally(0);

apply(&shift, 5);              // 15: a closure
apply(&t, 5);                  // 15: a struct with a '()'
apply(&succ, 5);               // 6: a plain function
applyMut(&mut tally, 5);       // 5
applyMut(&mut tally, 7);       // 12, and tally.n is 12

A plain function needs no state, so a reference to it meets any of the references above. A callable that reads meets &<mut fn as well, since a reference that may change can read.

A callable that changes its state (its () takes self &mut) is refused behind &<fn(sig), which promises only to read, and the error says so: "&<fn(i32) i32 may only call a callable that reads its state; this closure changes it ... To let it change, the type is &<mut fn(i32) i32." Likewise a &<mut fn is not lent where a &<fn is wanted, nor is a So[fn(sig)], which may change: the callable behind it might. An owner meant to be lent to a reader is made So[imm, fn(sig)].

A closure literal, lent

A closure literal written as an argument to a parameter taken by &<fn or &<mut fn is lent as a temporary, dropped at the end of the statement. The permission lent is the parameter's, so a literal given to &<fn that changes a variable is refused by the message above. The literal's parameter types come from the signature:

apply(x => x * 2, 21);                                    // 42
applyMut(fn(x i32) i32 { total += x; total; }, 10);       // total is changed

A literal is lent only as an argument. To keep one, move it into an owner.

An owner of a closure

new So[fn(sig)](value) takes one value, a closure literal or a struct with a () of the signature, moves it into an allocation of its own, and gives the owner of that as the callable. The literal's parameter types may come from the signature. The same holds for Rc:

mut owned So[fn(x i32) i32] = new So[fn(x i32) i32](fn(x i32) [mut sum = 100] i32 { sum += x; sum; });
owned(1);        // 101
applyMut(owned, 2);   // 103: an owner is lent as &<mut
run(owned, 3);        // 106: or handed on whole, moved

imm shared = new Rc[imm, fn(x i32) i32](new Triple(4));
imm again = shared;               // another holder of the same closure

The owner holds whatever the closure holds, and finalizes it when the last owner dies. A closure that holds nothing is allocated like any other. A plain function is wrapped by giving its reference, new So[fn(sig)](&f); a function of another signature, or a value with no () of the signature, is an error.

An owner outlives the function that made it, so the closure in it may not borrow a local. The refusal is the one in Closures: it names the variable and says to list it, so the closure holds its own copy.

Naming a signature

An alias gives a signature a name, and the name works wherever the signature does:

alias Profile = fn(u i32) i32;

fn viaAlias(f &<Profile, u i32) i32 { f(u); }

A bare fn(sig) is read as a signature in the brackets of a type (So[fn(i32) i32], Applied[fn(i32) i32]), as the target of an alias and as a generic's bound (Generics). It is not itself the type of a variable or a return value: write &<fn(..), So[fn(..)] or the alias. A signature is a trait, so it has no size, and a field of a generic type holds it by an owner or a reference, not by value:

struct Applied[F] { pub f So[F]; }     // Applied[fn(i32) i32] holds a So[fn(i32) i32]

A callable held in a field

A field that holds a callable is called by its name, with no parentheses around it: b.onClick(5) calls the closure in onClick, and (b.onClick)(5) keeps working. A field and a method of one name cannot both exist, so there is nothing to choose between. A field that cannot be called, an i32 given arguments, is an error that says what the field holds.

An owner whose state may change is called through a reference that may change, so a method that calls a So[fn(sig)] field takes self &mut, as press does above. The handler is replaced by assigning the field.

Saying what is behind a reference: Sendable and Shareable

A virtual reference hides the type behind it, so a reference to a callable or a trait is not Sendable or Shareable unless it says so. The markers follow the signature or the trait with a +, in either order:

fn work(f So[fn(x i32) i32 + Sendable]) i32 { f(1); }
fn read(f &<fn(x i32) i32 + Shareable, x i32) i32 { f(x); }
So[Shape + Sendable + Shareable]

The marker is a requirement on the closure put behind the reference, and a closure that does not meet it is refused where the reference is made, naming the variable it borrows or the owner it holds (Sendable and Shareable). An owner of a closure sent to a thread:

imm k = 3;
imm c = new So[fn(x i32) i32 + Sendable](fn(x i32) [k] i32 { x * k; });   // k is listed: its own copy
imm th = thread.start(c, &work);

Only Sendable and Shareable may follow the +. A reference to a known type takes no marker (ask the type, T is Sendable), and joining two traits with their methods, &<Shape + Named, is not built.

A literal that fills a trait

A closure literal also fills a trait that has exactly one required method, wherever that trait is wanted: as a generic's bound, [S Shape], as a reference, &<Shape, and as an owner, So[Shape]. That is described under Traits.

A signature as a generic bound

A function may instead be generic over the signature, [F fn(x i32) i32]. That form is compiled for each closure and inlined, where the references above are compiled once and call through the closure's code (Generics). The reference is what a field or a variable of unknown closure holds; the generic is what a function that only calls it uses.
