Modules and Namespaces

A module spans the files of its folder, its designated file declares it with mod, and a subfolder holding its own designated file is a submodule of it. A module reaches its own submodules by name, and a sister by importing her. A module cannot yet name a declaration of the module that contains it, so what a parent shares downward has to be a module. Modules nested within a source file, module initializers, and a module's abstraction (mod trait) are not implemented.

Many things are given names: variables, functions, types, fields, methods, etc. The collection of all names defined for a scope is called a namespace. Blocks and types are two different kinds of namespaces.

Namespaces facilitate a modular architecture by:

  • hiding implementation details visible within the namespace behind the simpler, durable API shown outside. This is called encapsulation.
  • lowering the accidental risk of name collisions, where two different items (possibly created by different authors) are given the same name.

The rules governing names vary according to the type of namespace it belongs to. Let's review those here, beginning with the introduction of a new kind of namespace: the module.

Modules

A module is a global namespace. You have seen code examples for modules already:

// A type declaration
struct Handler {
  pub id u32;
}

// a global variable
imm handler = Handler[0];

// A function
fn main() {
  // do some stuff
}

As this example shows, modules hold global variables, functions, and type declarations. They can also hold other named things, such as macros and even other named modules. Further, modules can import names from other modules.

Every program or library has a single main module. That main module may import other modules or types offering reusable, isolated capabilities it depends on.

A module is a folder's files

A module's source files are the files of a folder. One of them is the folder's designated file: the file named for the folder, as geometry/geometry.cone is for geometry. It is the file that declares the module, with mod written as its first statement:

mod geometry;

pub struct Point {
  pub x f32;
  pub y f32;
}

Point the compiler at that file and it finds the rest itself. Every other .cone file in the folder belongs to the same module, and so does every file of every subfolder that holds no designated file of its own, at any depth. Nothing lists them: putting files in a folder is what brings them together, and moving a file to another folder moves it to another module. Such a subfolder groups files without making a namespace of them, so a large module can be organized by topic with no new names to write and none to path through.

The folder names the module. A name written after mod may restate the folder's name and may not change it, because a name on the filesystem is one that any tool can read without parsing Cone. That name is what another module binds when it imports this one, the name a path through the module is written with, and the name the module's declarations carry in the symbols the linker sees.

Only the designated file declares the module. Because the declaration claims it, it comes before everything else in that file, and a module declares itself once. A file the folder brought in declares nothing, and neither does a source file brought in with include: its declarations join the including module.

Two files of one module may not share a name, however deep in the folder tree they sit, and a file belongs to one module: a file another module already holds cannot be brought into a second one.

A module's own name is one of the names in reach inside it. That matters where a local variable, a parameter or a type's member hides a name the module declares, since it is the only way to reach past the nearer one:

mod counters;

mut total = 0;

fn addTo(total i32) i32 {
  counters.total + total;   // the parameter hides the global; the module's name reaches it
}

A file that is not its folder's designated file is a module of one file: a complete program or library as it always was, named after the file, with the files beside it none of its business. A mod declaration in such a file still renames its module, and a file with no declaration at all has no name of its own to write before a hidden name.

Submodules

A subfolder that holds its own designated file is not organizing files: it is a submodule, a module of its own inside the module whose folder holds it. One rule decides both kinds of subfolder — does it hold the file named for it? — and it is the same rule that made the folder a module in the first place.

geometry/
  geometry.cone      the module 'geometry'
  shapes.cone        a file of 'geometry'
  detail/util.cone   also a file of 'geometry': 'detail' holds no detail.cone
  scaling/
    scaling.cone     the module 'geometry.scaling'
    matrix.cone      a file of 'geometry.scaling'

Its parent reaches into it by writing a path, the same way a path reaches into any module: scaling.twice(n) from inside geometry. What the parent may reach is what the submodule declares pub, because a submodule is a module and its private names are its own.

A submodule is private to its parent unless it says otherwise. Written pub mod scaling; it can be named from outside its parent as well, as geometry.scaling.twice; written mod scaling; only geometry may name it. The pub goes on the submodule's own declaration, since the parent declares nothing about a subfolder, and it means what it means everywhere else: this entry is visible outside this namespace.

A module folder must be a direct child of its parent module's folder, so the module tree has the shape of the folder tree. A designated file further down — inside a folder that holds none of its own — is an error rather than a deeper submodule.

Two submodules of one module may name each other, by importing. The module that holds them is the registry they are found in: they are public to each other and to it, and invisible outside it unless it publishes them. So import scaling; written inside a sister of scaling finds her there — see importing a sister module — and nothing arrives unasked, because a name nobody imported is not a name of the module.

That reach is one level and does not accumulate as you go down. A module sees the modules of its own parent, and not its grandparent's: if it needs one of those, its parent imports it and re-exports it with pub. And a submodule cannot name its parent — containment runs one way.

Name rules

Module names are:

  • unique. no two items in a module may have the same name. Several functions may nonetheless share one overload name, which is itself a single name in the module that maps to those functions.
  • order-independent. One can reference functions, variables, or types whose names are not defined until later in the module. The only exception to this are permissions and regions whose definition must precede their use.
  • private unless pub. A name declared pub may be referenced outside the module. Any other name may not: it is private to the module, whatever it is spelled. The interface of a module is what it says it is, and nothing more.

Global variables

Global variables across all modules (and types) are managed by the global region. Memory space for them is allocated automatically and all-at-once when a program is loaded for execution. The lifetime of all global variables is the same as the program's lifetime, since global variables come into being when the program starts and only disappear once the program stops. The lifetime annotation for this scope is 'static.

Global variable declarations have two important constraints:

  • The mut permission is not permitted if the program makes use of multiple threads.
  • Variables must be explicitly initialized with a valid value. In many cases, the initial value is a statically-computable constant value whose exact size is also known to the compiler.

A global variable may also fold its type's members in as names of the module, with the same use clause a struct's field carries:

mut config Config = Config[80i64, 24i64] use *;

Every public member of Config is now a name of this module, reached through config, so a function here writes area() where it would have written config.area(). A global is to a module what a field is to a type, with one difference that makes this the cheaper fold: there is exactly one of it, at an address known when the program is compiled. See Folding through a global for the whole of the clause, including what use pub lets another module see.

Folding an enum's variants in

An enum's variants are names of the enum, reached as Colors.Red. A module that wants them as names of its own writes a use statement naming the enum, and optionally which variants:

use Colors;                  // Red, Green and Blue are names of this module
use shapes.Shape Circle;     // one variant of an enum another module declares
use pub Suit;                // and names other modules may reach through this one

The names are this module's own and private to it unless the statement is written use pub, which is how a module re-exports an enum's variants: another module reaches them through it, and an import of it with .* brings them in bare. The core library does exactly this for Option and Result, which is why Some, None, Ok and Error are bare in every program. See Naming a variant.

Dynamic initialization of global variables

Sometimes, the initial value of a global variable is unknown, or too complex to specify, at compile-time. In such cases, we want to initialize the variable using run-time logic invoked when the program or library is loaded. To accomplish this, declare the variable without an initial value and then initialize that variable inside the module's initializer, a function called init.

imm handler;

fn @initpure init() {
  handler = Handler();
}

The initializer is declared with initpure, a less constrained version of pure. Any function marked as initpure may not read any uninitialized global variables in the current module and may only call functions marked as pure or initpure.

To ensure safe and complete dynamic initialization, the compiler:

  • Verifies that every uninitialized global variable is assigned a value at some point within the same module's initpure-marked init function.
  • Verifies that pure and initpure functions comply with their constraints.
  • Runs the initializers for any dependent modules before running the initializer for the module.

A finalizer might be automatically be created, where needed, to finalize any dynamically-initialized global variables. This is run when the program is shutting down.

Types as Namespaces

Declarations for struct and enum types are also namespaces. At a minimum, these hold the names of the type's fields and methods. They may also hold the names for the type's static functions, its static variables and the names of other types (e.g., enums). An enum's namespace holds its variants, which is why a variant is reached through its enum, Colors.Red, unless a module folds it in with use.

Static Functions

In addition to methods, a type may declare useful static functions that are not methods and do not work with a specific object of that type. All such functions should be declared within a static block.

struct Counter {
  static {
    fn zeroFactory() Counter {
      Counter[0];
    }
  }
}

To make use of the function outside the type, qualify the name with the name of the type:

mut cnt = Counter.factory();

Name Rules

A type's names are:

  • unique for every field, function and method. Every method and function has its own name, unique within the type. Several methods or functions may additionally share one overload name, which they declare with overload.
  • order-independent. A name may be referenced before its declaration, and the order in which the methods or functions sharing an overload name are declared never affects which one a call selects.
  • private unless pub. A field, method or function declared pub may be used by functions or methods not a part of the type. Any other member may not. Fields and methods are publicly accessed on a value using the dot (.) operator. A static function is reached with the same operator, on the type's name.

Function Blocks

All logic blocks inside functions and methods are namespaces that hold local (and parameter) variables.

Every block's names are:

  • unique. no two variables in a block may be declared with the same name. However, variables in a block might shadow same-named variables in outer scopes.
  • order-dependent. Logic may not reference a local variable until after it is declared.
  • private. Only the block logic may see and use local variables.
