Modules and Namespaces

A module spans the files of its folder, its designated file declares it with mod, and a subfolder holding its own designated file is a submodule of it. A module reaches its own submodules by name, folds their names in with a use statement, and reaches a sister by importing her, and a public name of its parent the same way. A module may extend another, reusing its names as its own, and may name on its mod line the names a bare import of it folds. A module is never declared inside a file: nesting is by folders. Module initializers, and a module's abstraction (mod trait), and so a module conforming to one, are not implemented.

Many things are given names: variables, functions, types, fields, methods, etc. The collection of all names defined for a scope is called a namespace. Blocks and types are two different kinds of namespaces.

Namespaces facilitate a modular architecture by:

  • hiding implementation details visible within the namespace behind the simpler, durable API shown outside. This is called encapsulation.
  • lowering the accidental risk of name collisions, where two different items (possibly created by different authors) are given the same name.

The rules governing names vary according to the type of namespace it belongs to. Let's review those here, beginning with the introduction of a new kind of namespace: the module.

Modules

A module is a global namespace. You have seen code examples for modules already:

// A type declaration
struct Handler {
  pub id u32;
}

// a global variable
imm handler = Handler[0];

// A function
fn main() {
  // do some stuff
}

As this example shows, modules hold global variables, functions, and type declarations. They can also hold other named things, such as macros and even other named modules. Further, modules can import names from other modules: an import binds the other module's name, and its use clause folds that module's public names in as names of this one.

Every program or library has a single main module. That main module may import other modules or types offering reusable, isolated capabilities it depends on.

A module is a folder's files

A module's source files are the files of a folder. One of them is the folder's designated file: the file named for the folder, as geometry/geometry.cone is for geometry. It is the file that declares the module, with mod written as its first statement:

mod geometry;

pub struct Point {
  pub x f32;
  pub y f32;
}

Point the compiler at that file and it finds the rest itself. Every other .cone file in the folder belongs to the same module, and so does every file of every subfolder that holds no designated file of its own, at any depth. Nothing lists them: putting files in a folder is what brings them together, and moving a file to another folder moves it to another module. Such a subfolder groups files without making a namespace of them, so a large module can be organized by topic with no new names to write and none to path through.

The folder names the module. A name written after mod may restate the folder's name and may not change it, because a name on the filesystem is one that any tool can read without parsing Cone. That name is what another module binds when it imports this one, the name a path through the module is written with, and the name the module's declarations carry in the symbols the linker sees.

Only the designated file declares the module. Because the declaration claims it, it comes before everything else in that file, and a module declares itself once. A file the folder brought in declares nothing.

The folder is the only thing that brings a file into a module: nothing written in one file brings another in, so a file's module can be told from where the file sits. include, which once brought a named file in, is retired.

Two files of one module may not share a name, however deep in the folder tree they sit, and a file belongs to one module: a file another module already holds cannot be brought into a second one.

A module's own name is one of the names in reach inside it. That matters where a local variable, a parameter or a type's member hides a name the module declares, since it is the only way to reach past the nearer one:

mod counters;

mut total = 0;

fn addTo(total i32) i32 {
  counters.total + total;   // the parameter hides the global; the module's name reaches it
}

A file that is not its folder's designated file is a module of one file: a complete program or library as it always was, named after the file, with the files beside it none of its business. A mod declaration in such a file still renames its module, and a file with no declaration at all has no name of its own to write before a hidden name.

Submodules

A subfolder that holds its own designated file is not organizing files: it is a submodule, a module of its own inside the module whose folder holds it. One rule decides both kinds of subfolder — does it hold the file named for it? — and it is the same rule that made the folder a module in the first place.

geometry/
  geometry.cone      the module 'geometry'
  shapes.cone        a file of 'geometry'
  detail/util.cone   also a file of 'geometry': 'detail' holds no detail.cone
  scaling/
    scaling.cone     the module 'geometry.scaling'
    matrix.cone      a file of 'geometry.scaling'

Its parent reaches into it by writing a path, the same way a path reaches into any module: scaling.twice(n) from inside geometry. What the parent may reach is what the submodule declares pub, because a submodule is a module and its private names are its own.

A parent folds a submodule's names in with use. A submodule is never imported — the subfolder is what brings it in — so a parent that wants its child's names bare writes a use statement naming the submodule, and the same clause an import's use takes follows the name:

mod geometry;

use scaling;                     // every public name of scaling: twice(n), not scaling.twice(n)
use measure inches as toInches;  // one name, spelled another way here
use units { metre, yard };       // a list, written as a block
use shapes but Hexagon;          // every public name but one
use scaling.fixed;               // a submodule's pub submodule, reached by a path
pub use detail;                  // detail's public names, re-exported as geometry's

Only a submodule's public names fold, and naming a private one is an error, whether in a list or after but, where there is nothing to leave out. The folded names are this module's own and private to it unless the statement is written pub use, which re-exports them: the parent's neighbours then reach them as names of the parent, while the submodule itself may stay private. A submodule is folded once: a second use of it is an error, so say everything in one.

A standalone use folds what a module reaches without importing it: an enum, below, or a submodule. A module brought in by import is folded by that import's own clause, import math3d use Point3;, and naming it in a use statement is an error — one spelling for each situation.

A submodule is private to its parent unless it says otherwise. Written pub mod scaling; it can be named from outside its parent as well, as geometry.scaling.twice; written mod scaling; only geometry may name it. The pub goes on the submodule's own declaration, since the parent declares nothing about a subfolder, and it means what it means everywhere else: this entry is visible outside this namespace.

A module folder must be a direct child of its parent module's folder, so the module tree has the shape of the folder tree. A designated file further down — inside a folder that holds none of its own — is an error rather than a deeper submodule.

Two submodules of one module may name each other, by importing. The module that holds them is the registry they are found in: they are public to each other and to it, and invisible outside it unless it publishes them. So import scaling; written inside a sister of scaling finds her there — see importing a sister module — and nothing arrives unasked, because a name nobody imported is not a name of the module.

A submodule imports its parent's public names the same way. The registry is the parent's namespace, so it holds what the parent declares as well as its modules: import Point; inside scaling binds geometry's public Point, a type, a function or a global alike — see importing a name of the parent. A name the parent keeps private cannot be imported, so pub shares a name downward to the parent's own modules as well as outward.

That reach is one level and does not accumulate as you go down. A module sees the names of its own parent, and not its grandparent's: if it needs one of those, its parent imports it and re-exports it with pub. And a submodule cannot name its parent — containment runs one way.

A module extending a module

A module can be built out of another one: it takes in everything the other declares, and adds its own functionality beside it. The module's declaration names the module it extends:

mod solids extends shapes;

// area, Point and count are shapes' public names, and now names of solids too;
// scale is private to shapes, and solids may use it as well
pub fn volume(w i64, h i64, d i64) i64 {
  area(w, h) * d * scale();
}

Everything shapes declares is now a name of solids, and inside solids it is written bare. So is every name a use clause of shapes folded in: if shapes writes import units use metre, then metre is a name of solids too. solids is inside shapes' boundary, the way a type that extends a type is inside its base's, so it reaches shapes' private names too.

What shapes imports stays shapes'. A module's imports are what it depends on, not what it contains, and each module says for itself what it depends on. So the name units, which that import binds in shapes, is not a name of solids: to write units.inch, solids imports units itself.

What solids shows is what shapes shows. A public name of shapes is a public name of solids: a module that imports solids reaches it as solids.area, or bare after import solids use *, exactly as it reaches what solids declares itself. A private name of shapes is private in solids, and no module outside solids reaches it through solids. A chain works the same way: if shapes extends another module, that module's names reach solids too, each as visible as it was.

For a module, extending is inheriting. A module has one instance, so there is nothing to copy: each name is a second name for the same thing, and the function, the type and the global stay shapes's. A global changed through solids.count is the one shapes.count reads.

The module it extends must already be in reach — a sister, found where an import of her would find her, or a module this one imports — and is named by that one name. The rest of the rules:

  • A module extends one module.
  • It adds and does not redeclare. A declaration spelled like one of the extended module's names, public or private, is an error, as it is for a type that extends a type: one name would otherwise mean two things. That includes a name the extended module folded in with a use clause, but not the name of a module it imports, which is not one of the names it passes on.
  • extends brings names, not the module's own name. shapes is a name of solids only if solids imports it.
  • A module may not extend itself, a module it contains, or its parent, and a chain of extends may not come back round.
  • extends names a module to reuse. A module conforming to a module's abstraction — mod arena extends Region, with Region a mod trait — is a different reading, and is not implemented.

A module's default fold

A package named for the one thing it provides would put that name in every path twice: bigint.BigInt. So a module may say, on its own mod line, what an importer gets when it imports the module and asks for nothing in particular. A package holding one thing then just becomes the thing:

mod bigint use BigInt;

pub struct BigInt {
  pub digits i64;
}

pub fn helper(n i64) i64 {
  n + 100;
}

Now a module that writes a bare import bigint; has BigInt directly, and bigint as well, so bigint.helper still reaches what the default leaves out. With extends, the clause comes last:

mod bigint extends base use BigInt;
  • The list is the default, however many names it holds. mod units use metre, foot; makes a bare import fold both. * and * but may be written too. Adding a name later only adds to what importers see.
  • An importer's own clause replaces the default entirely. import bigint use *, import bigint use helper or import bigint use * but BigInt folds what it says, and nothing of the default.
  • Here use runs the other way. Everywhere else, use folds names into the module where it is written. On the mod line it names what importers fold.
  • It is not an export list. pub still decides what is reachable, and every name the clause lists must already be a public name of the module: one the module has not got, or keeps private, is an error at the mod line. The clause only chooses which public names a bare import folds.
  • The importer decides the rest. The names are the importer's, private to it unless it writes pub import bigint;, which re-exports them with bigint. A default name that collides with one of the importer's own is an error there, settled by writing a clause of its own. For the same reason neither as nor pub may be written in the clause on a mod line.

The default applies wherever a module is imported with no clause of its own: a sister, a name of the parent, a module found by its file. A use of a submodule is not an import, and still folds every public name.

Name rules

Module names are:

  • unique. no two items in a module may have the same name. Several functions may nonetheless share one overload name, which is itself a single name in the module that maps to those functions. A module may not bring one name in twice, even for the same item: listing a name twice, writing the same use twice, importing a module twice, or importing a module and also listing it through another module that re-exports it, is an error. What a module never wrote is different. When a name arrives by a wildcard use *, by extends, or by the automatic import of core, and it is the same item the name already has, it is not two items: when two wildcard imports each re-export the same function, or a module that extends this one hands this one's own names back, the name is bound once, and it is public if either route made it public.
  • order-independent. One can reference functions, variables, or types whose names are not defined until later in the module. The only exception to this are permissions and regions whose definition must precede their use.
  • private unless pub. A name declared pub may be referenced outside the module. Any other name may not: it is private to the module, whatever it is spelled. The interface of a module is what it says it is, and nothing more.

Global variables

Global variables across all modules (and types) are managed by the global region. Memory space for them is allocated automatically and all-at-once when a program is loaded for execution. The lifetime of all global variables is the same as the program's lifetime, since global variables come into being when the program starts and only disappear once the program stops. The lifetime annotation for this scope is 'static.

Global variable declarations have two important constraints:

  • The mut permission is not permitted if the program makes use of multiple threads.
  • Variables must be explicitly initialized with a valid value. In many cases, the initial value is a statically-computable constant value whose exact size is also known to the compiler.

A global variable may also fold its type's members in as names of the module, with the same use clause a struct's field carries:

mut config Config = Config[80i64, 24i64] use *;

Every public member of Config is now a name of this module, reached through config, so a function here writes area() where it would have written config.area(). A global is to a module what a field is to a type, with one difference that makes this the cheaper fold: there is exactly one of it, at an address known when the program is compiled. See Folding through a global for the whole of the clause, including what pub use lets another module see.

Folding an enum's variants in

An enum's variants are names of the enum, reached as Colors.Red. A module that wants them as names of its own writes a use statement naming the enum, and optionally which variants — the same statement that folds a submodule's names in:

use Colors;                  // Red, Green and Blue are names of this module
use shapes.Shape Circle;     // one variant of an enum another module declares
pub use Suit;                // and names other modules may reach through this one

The names are this module's own and private to it unless the statement is written pub use, which is how a module re-exports an enum's variants: another module reaches them through it, and an import of it with use * brings them in bare. The core library does exactly this for Option and Result, which is why Some, None, Ok and Error are bare in every program. See Naming a variant.

Dynamic initialization of global variables

Sometimes, the initial value of a global variable is unknown, or too complex to specify, at compile-time. In such cases, we want to initialize the variable using run-time logic invoked when the program or library is loaded. To accomplish this, declare the variable without an initial value and then initialize that variable inside the module's initializer, a function called init.

imm handler;

fn @initpure init() {
  handler = Handler();
}

The initializer is declared with initpure, a less constrained version of pure. Any function marked as initpure may not read any uninitialized global variables in the current module and may only call functions marked as pure or initpure.

To ensure safe and complete dynamic initialization, the compiler:

  • Verifies that every uninitialized global variable is assigned a value at some point within the same module's initpure-marked init function.
  • Verifies that pure and initpure functions comply with their constraints.
  • Runs the initializers for any dependent modules before running the initializer for the module.

A finalizer might be automatically be created, where needed, to finalize any dynamically-initialized global variables. This is run when the program is shutting down.

Types as Namespaces

Declarations for struct and enum types are also namespaces. At a minimum, these hold the names of the type's fields and methods. They may also hold the names for the type's static functions, its static variables and the names of other types (e.g., enums). An enum's namespace holds its variants, which is why a variant is reached through its enum, Colors.Red, unless a module folds it in with use.

Static Functions

In addition to methods, a type may declare useful static functions that are not methods and do not work with a specific object of that type. A static function is declared among the type's methods, and what makes it static is that it has no self parameter. It is not marked static: that word declares a static variable, and before a function it is an error.

struct Counter {
  count i32;

  pub fn zeroFactory() Counter {
    Counter[0];
  }
}

To make use of the function outside the type, qualify the name with the name of the type:

mut cnt = Counter.zeroFactory();

Name Rules

A type's names are:

  • unique for every field, function and method. Every method and function has its own name, unique within the type. Several methods or functions may additionally share one overload name, which they declare with overload.
  • order-independent. A name may be referenced before its declaration, and the order in which the methods or functions sharing an overload name are declared never affects which one a call selects.
  • private unless pub. A field, method or function declared pub may be used by functions or methods not a part of the type. Any other member may not. Fields and methods are publicly accessed on a value using the dot (.) operator. A static function is reached with the same operator, on the type's name.

Function Blocks

All logic blocks inside functions and methods are namespaces that hold local (and parameter) variables.

Every block's names are:

  • unique. no two variables in a block may be declared with the same name. However, variables in a block might shadow same-named variables in outer scopes.
  • order-dependent. Logic may not reference a local variable until after it is declared.
  • private. Only the block logic may see and use local variables.
