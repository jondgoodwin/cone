Cone
enum types

Note: All of this capability is implemented except: comparing two values of an enum whose variants carry fields, and reaching a variant by a name qualified with its enum's. The examples that will not compile today are marked where they appear.

An enum declares a closed set of variants: a value of the enum is exactly one of them, and the whole set is written inside the declaration, so nothing elsewhere can add to it. That closedness is what buys an exhaustive match.

The variants may carry values of their own, or carry nothing at all. Both are the same construct:

enum PhoneType {
	Home, Work, Mobile;
}

enum Point {
	pub struct XyPoint {
		pub x f32;
		pub y f32;
	}
	pub struct AngPoint {
		pub dist f32;
		pub angle f32;
	}
}

A bare name is an empty struct variant. That one sentence is what makes a plain set of named symbols and a set of variant structs the same thing, and it is why there is no second construct to learn: Home above declares exactly what struct Home; would.

Two properties hold of every enum:

  • An enum is discriminated: there is a hidden "tag" field at the beginning of the value, holding a number the compiler assigns to each variant, which is what tells at runtime which variant a value is.
  • Every variant occupies the same size of memory — the size of the largest, plus the tag — so smaller variants are padded to fit. A value of the enum can therefore be held in a variable, copied, passed by value, and replaced in place by a different variant. Write @unsized to decline the padding.

Where you want a set of variants that other modules can add to, an enum is the wrong construct: use a trait and structs that declare is against it. That versatility costs something, and the cost is worth knowing: an open trait has no tag, so a value of it carries a pointer to type metadata and a match has to check the possibilities one at a time. A closed set is not only exhaustive, it is faster, because a tag is an index.

Declaration

The simplest form is a name and its variants. A variant written as a struct carries fields of its own; one written as a bare name carries none. It is permissible for a struct variant to be empty of fields too, as the presence of the tag ensures the overall value is not empty.

An enum may also declare members in common: fields every variant has, and methods every variant answers. Neither is something Rust's enums offer, and both are what let a caller do useful work with a value whose variant it has not yet recovered.

enum Event {
	pub time datetime;                             // a field every variant has

	pub fn stamp(self &) datetime {time;}          // a method with a body: a default
	pub fn describe(self &) String;                // a method without one: a requirement

	pub struct ButtonEvent {
		pub button u8;
		pub pushed Bool;
	}
	pub struct KeyEvent {
		pub key Unicode;
	}
	pub struct QuitEvent;
}

All three variants above begin with the time field, ahead of any fields they declare themselves. A method with a body is a default, which each variant gets unless it declares that name itself; a method without one is a requirement, which every variant must implement, and calling it through a reference to the enum dispatches on the variant — see Method dispatch below.

A common member may be written anywhere in the body. What makes a member common is its kind, not its position: a struct is a variant, and anything else is common. The layout still puts common fields first in every variant.

Tag values

Each variant's tag value is assigned for you, ascending from zero in declaration order. You may write a value instead, which is what lines an enum up with the constants of a library written in another language. Numbering resumes from the last value written, so only the variants that need a particular value have to say so.

An enum may also name the integer type its tag values are laid out in. That fixes the tag's width, so a value too large for it is an error rather than a silent widening away from the layout you asked for. Without it the tag is as wide as the largest value needs — note that this follows the largest value, not the number of variants.

enum Colors u32 {
	Red   = 0xFF0000,
	Green = 0x00FF00,
	Blue  = 0x0000FF;
}

The tag field cannot be accessed, referenced or mutated: which variant a value holds is reached by pattern matching, and compared with ==.

For alignment reasons it may be desirable to place the tag somewhere other than first. To do this, write an anonymous field of type tag where it should go. tag means this only where a field's type is written, so it is not a reserved word and a field may still be named tag.

enum Aligned {
	pub wide i64;
	_ tag;

	pub struct Small {pub n i32;}
	pub struct Large {pub a i64; pub b i64;}
}

Initialization

A value is built using a constructor for one of the variants:

mut event = QuitEvent[timestamp];
oddval = KeyEvent[timestamp, 's'];
imm phone = Work[];

Notice that the constructor supplies a value for every common field, and never for the tag: that one is settled by which variant was named.

The variants are part of the module's namespace rather than the enum's, so they are named without qualifying them.

Note: a variant will move into its enum's namespace, reached as Event.KeyEvent and folded into a module deliberately with use, so that two enums each declaring a Quit do not crowd a namespace neither of them was asked to share. That waits on the use that folds names into a module.

Copying

A value may be passed around, by copy, just like any other value. This is possible because every variant is the same size — the size of the largest, plus the tag.

Because they are all one size, allocated memory holding one variant can be given a value of a different variant instead, and a pool allocator can hand out and reclaim variants of one enum interchangeably.

Value Access

A common field is readable from a value whose variant is not yet known, because every variant holds it at the same offset. To reach a variant's own fields, use pattern matching to establish which variant the value holds. Once it has been narrowed it is used like any other struct value.

Method dispatch

Sometimes every variant should answer the same method with its own implementation. Declare the method on the enum without a body, and let each variant implement it:

enum Number {
	pub fn double(self &mut Self);

	pub struct Real {
		pub n f32;
		pub fn double(self &mut Self) {
			n *= 2;
		}
	}

	pub struct Complex {
		pub r f32;
		pub i f32;
		pub fn double(self &mut Self) {
			r *= 2;
			i *= 2;
		}
	}
}

Calling number.double() on a reference to a Number invokes the implementation belonging to whichever variant the reference points at. The tag says which variant it is, that selects the variant's vtable, and the vtable holds the method.

Comparing

A value may be compared for equivalence, and not for order: which variant a value holds is what a comparison can answer, and declaration order is not a magnitude.

Where every variant is empty, the value is the tag, so the comparison is exactly a tag comparison:

if phone == Mobile[] { ... }

Note: where a variant carries fields, comparing two values would have to compare those fields as well, and Cone has no comparison of a struct's contents for any kind of type yet. Comparing such an enum is an error today that names match as the way to recover the variant.

Declining the padding

Padding every variant to the largest costs memory, and whether to pay it for the convenience of a value is a choice only you can make. Write @unsized to decline it:

enum @unsized Shape {
	pub kind i32;

	pub struct Dot;
	pub struct Polygon {pub points [64; Point];}
}

Each variant then occupies only what it needs, and the enum has no single size. So no value of it may be held — not in a variable, not in a parameter, not in a field — and it is reached only by reference:

imm shape &Shape = &someDot;

Notice how a reference to a variant coerced automatically into a reference to the enum. Everything else is unchanged: the tag is still in the value, a common field is still readable through the reference, matching still recovers the variant, and dispatch still works. What is given up is the value semantics — holding one in a variable, copying it, passing it by value, and swapping a variant in place.

Most types that want this are graphs and trees, and those are usually better served by an open trait and structs that are-a it: once a type is reached by reference anyway, there is little left for a closed set to buy. So @unsized is for the case that is genuinely closed, wants exhaustive matching, and has variants whose sizes differ enough to matter — and it is what an extensible enum whose variants carry fields is written with, as the next section explains.

Extending an enum

An enum may be declared as an extension of another, adding variants to the ones the base declared:

enum Colors {
	Red, Green, Blue;
}

enum RichColors extends Colors {
	Cyan, Magenta;
}

The base's variants come first in the extension's set and keep their tag values there, so one variant is one thing however it is reached. A value built as Green[] is a value of Colors and a value of RichColors, and a match on either recovers it:

imm plain Colors = Green[];
imm rich RichColors = Green[];    // the same variant, the same tag value
imm added RichColors = Magenta[];

No substitutability runs between a base enum and its extension, in either direction. They are two distinct types, and the compiler enforces it: neither a value nor a reference nor a virtual reference of one may stand where the other is expected. What a variant belongs to is every set it was declared or taken into — that is membership, not substitution between the two enums.

So a match on the base is still exhaustive over the base's own variants, which is the property the whole construct rests on: a value typed as the base can only ever hold one of the base's variants, so a match naming those needs no else. A match on the extension must account for the added variants as well.

This is worth saying outright because the intuition points the other way. Everywhere else in Cone a subtype is an abstraction and a value of the concrete type stands in for it; here, adding variants would make a supertype — every value of the base is a valid value of the extension, and no value of the extension is a valid value of the base. Cone does not take that direction, and the two types stay unrelated.

What an extension may declare

An extension declares variants and nothing else. The variants it shares with its base are the base's own declarations, so anything every variant would have to carry — a common field, a method each variant answers — belongs on the base, whose common members come along with the variants. Its discriminant is the base's too, so an extension writes neither a tag field nor the integer type tag values are laid out in.

The base's common members work through the extension exactly as through the base: a common field is readable from a value whose variant is not yet known, a default method is available, and a requirement dispatches on the variant — which an added variant must therefore implement, as the base's own variants do.

Two restrictions follow from the variants being shared, and both are about padding:

  • An extension agrees with its base about @unsized: a variant cannot be padded in one of the two sets and unpadded in the other.
  • Where the variants are padded, an extension may not add a variant larger than the base's largest. Every variant is laid out to that size, the shared ones included, so a wider one has nowhere to live.

An @unsized enum has neither restriction, because nothing is padded: an extension of one adds variants of any size at all. That is what makes @unsized the way to write a payload-carrying enum you intend others to extend.

enum @unsized Packet {
	pub id i32;

	struct Ping;
	struct Payload {pub a i64; pub b i64;}
}

enum @unsized MorePackets extends Packet {
	struct Wide {pub a i64; pub b i64; pub c i64; pub d i64;}   // larger than either, and free
}

A tag value pinned by an added variant must still fit the discriminant the base lays its variants out in, and must not be one the set already holds. If you publish an enum others may extend, adding a variant to it in a later version shifts the values of every extension's own variants, since those are numbered after yours; writing the values out is how to keep them stable across that boundary.
