import and extern

An import folds names in with a use clause, as described below. An import is intended to follow a mod declaration, and only directly follow one, so that every dependency a module has is stated at its declaration. That restriction is not enforced yet: an import may stand anywhere at module level, and a file that declares no module may write one. include is retired, and reported wherever it is written.

After a program's source code gets big enough, it may become easier to work with when partitioned across multiple files. The files of one module need nothing to stitch them together: a module is the files of its folder, and the compiler finds every one of them itself. On this page, we introduce the two mechanisms that reach beyond a module: import, for another Cone module, and extern, for code written in another language.

include is retired

A file joins a module by being in the module's folder, so no statement brings one in. include, which once did, is a reserved word, and the compiler reports an include statement wherever it is written. Put the file in the folder of the module it belongs to instead.

import

Use import to import another module that has its own namespace. For example:

import math3d;
import opengl;

File names and Paths

An import names a module, or where the module's name is not found, a file path. If the file path includes characters that are not legal for a Cone name (such as periods or slashes), it should be enclosed in double quotes (and make use of the appropriate escape sequences where needed). If the file's extension is not specified, .cone is assumed.

In the simplest case, the file path specifies just the name of a source file to be found in the same folder as the source file which imports it. If a file of that name is not found there, the compiler will look for it in a folder of the same name (e.g., "useme/useme.cone"). This behavior allows source files to be organized across nested folders, where related source files are grouped together.

If desired, the file path may explicitly specify folders in front of the source file name. This can be an absolute path name, such as "/libs/math/trigfns". It can also be relative to the source file doing the importing, for example "nomnom/useme" or "../lib/useme".

If the file is not found in the current folder, the compiler will search for it in the list of folders provided to the compiler when invoked. This allows the name of an imported module to correspond to some externally-hosted packaged library.

More than one module may import the same module. The imported module will only be loaded once. Its information is then reused by all modules that imported it.

A module imports another module once. Writing the same import a second time does nothing. A second import of the same module that says something different — it folds in other names, spells one differently, or is pub where the first is not — is an error, which names both. Say everything in the one import.

A module's own submodule is not imported, and importing one is an error: the subfolder or the file that holds it is what brings it in, so its name is already there to be written. Its names are folded in with a use statement instead, which takes the same clause an import's use does.

Importing a sister module

A submodule imports one of its sisters by writing her name, not a path to her file:

mod engine;
import wheels;

pub fn drive(n i64) i64 {
  wheels.turn(n);
}

A module is the registry its own modules are found in. They are public to each other and to it, and invisible outside it unless it publishes them — so an import written inside one of them looks the name up in the enclosing module and finds a sister there, with no file to search for and nothing loaded. It is the same mechanism that reaches a separately built library; only the registry that answers is different.

What is in reach is the enclosing module's names and no further up than that. A module two levels down does not see its parent's sisters: if it needs one, its parent imports her and re-exports her with pub.

A module inside such a tree is reached by its name, never by a path to its file. Writing import "../wheels/wheels" is an error, and so is a module importing the module that contains it: containment runs one way, and what the enclosing module shares is imported by its own names instead.

Importing a name of the parent

The registry holds more than modules. It is the enclosing module's namespace, so what that module declares is there too, and a submodule imports any pub name of its parent — a type, a function, a global — the way it imports a sister:

mod scaling;
import Point;               // the parent's public struct
import area;                // its public function
import count;               // its public global

pub fn scaledArea(n i64) i64 {
  count = count + n;
  area(Point[n, n]);
}

The import binds the name here as a second name for the parent's declaration, under the import's own visibility, and nothing is copied: a global written through it is the parent's global. Nothing arrives unasked, since a bare name does not climb to the parent: a name of the parent is in reach where it is imported and nowhere else.

A name the parent keeps private is an error to import, as a private submodule is out of reach outside its parent: pub is what a module shares, downward to its own modules as well as outward. A name the parent binds rather than declares is imported the same way — a module the parent imported and re-exported with pub import is imported by its name, and a use clause folds from it as from any module. A use clause on a name that is not a module is an error: a type's members are reached through the type.

A name is imported once, and a name the submodule declares itself cannot also be imported. A sister and a name the parent declares cannot share a name, since both are names of the parent, so the import is never ambiguous.

Re-exporting what you import

What an import brings in belongs to the module that wrote it. A module importing that module sees only what it passed on, which it does by writing pub:

pub import wheels;          // 'wheels' is a public name here, so 'engine.wheels.turn' resolves
pub import rims use *;      // and so is 'rims', and every name folded in from it
import tyres pub use *;     // every name folded in from tyres is public, and 'tyres' is not
import bolts use *;         // while these are this module's own business

pub before import reaches every name the import binds: the module's own name, and each name it folds in. pub use reaches only the names the use clause folds in, so a module can pass on a library's names without passing on the library. Writing both is allowed and means what pub import means alone. pub says what it says everywhere else — this name is visible outside the module that holds it — and it never makes public something that was not public where it was declared.

A name made public this way travels on: a module that imports engine with use * receives what engine passed on, and nothing that it kept for itself. That holds round a cycle of imports too: where two modules import each other, what each re-exports reaches the other, as it would if neither imported the other back.

Module-qualified names

import is bringing in a module with its own namespace. By default, the names of an imported module are kept separate from the names in the module doing the importing. The only name that the importing module automically obtains is the name of the module it is importing — unless that module names a default fold on its mod line, which an import writing no use clause of its own folds in as well.

Since the namespaces of the modules stay separated by default, the importing module normally refers to names inside the imported module using a module-qualified name:

import opengl;

fn setColor(col Color) {
  opengl.setColor(col);
}

opengl.setColor references the setColor function to be found in the imported opengl module. The period separates the module name from the name of the function defined in that module. It is the same operator that reaches a member of a value: one period, for a path through a namespace and for a member of a value alike.

Module-qualified names can only access names the module declared pub. Every other name is private to its module and is not accessible to any other module.

Namespace folding

By default, an imported module does not pollute the namespace of the module importing it. This is often what you want. However, it can become tedious to read (and type) module-qualified names when they are used a lot by the importing module's code. To address this, an import may end with a use clause, which folds some or all of the module's public names into the importing module. It is the same clause a global variable carries, with the imported module in the place of the variable's type. The names being folded can be for anything: type, function, global variable, macro, etc. However, names folded in may not collide with any name the importing module already uses.

To fold in just a few specific names, list them after use, separated by commas:

import math3d use Point3, Mat3;

fn move(pos &Point3, delta Point3) {
  pos += delta;
}

Use as to give a folded name another spelling here, for instance when its own is already in use:

import math3d use Point3 as Point;

fn move(pos &Point, delta Point) {
  pos += delta;
}

A long list may be written as a block instead, which means the same thing:

import math3d use {
  Point3 as Point,
  Mat3,
  Quaternion,
};

Or one can fold in all public names from the module using *, and leave some out with but:

import math3d use *;
import opengl use * but Point3;   // math3d's Point3 is the one wanted here

An import's own use clause replaces whatever default fold the imported module names: import bigint; folds what mod bigint use BigInt; says, and import bigint use *; folds every public name instead.

The use clause is the only way an import folds names in. import math3d.*; and import math3d.Point3; are errors, each naming the clause to write instead.

A folded name is private to the importing module unless the import says otherwise, as Re-exporting describes. A name the module does not have, or does not make public, cannot be folded in, and it is an error to list one. Naming either after but is an error too: seen from outside the module a private name is as absent as a missing one, and * never folds it, so there is nothing to leave out. So is folding in a name the importing module already has for something else, whether it declared that name or folded it in from somewhere else: rename one with as, or leave it out with but. Writing the same thing in twice is an error too: listing a name twice, or listing it from two modules that each re-export it. A module imports another only once, so a second import of it, even an identical one, is an error. What a wildcard brings is different, since nothing was written twice: if two modules you fold in with * each re-export one function, say, folding in both is fine, and so is listing the function from one while the other's * brings it too. The name is bound once, and if either fold made it public, it is public.

extern

Sometimes we want to make use of functions and global variables that have been implemented in another language, such as C. Since the Cone compiler cannot process source files written in another language, import will not suffice. Instead, an extern block must be used to declare these entities and their types so that Cone logic may make use of them.

extern {
  // Functions
  fn printFloat(nbr f32);
  fn printInt(nbr i32);
  fn printString(str *u8) trust;

  // Global variables
  mut indentation;
}

The printString function has been marked as trustable. This indicates that we trust it to safely make use of the pointer it is given. If we had not done so, any attempt to call such a potentially unsafe extern function would require use of trust.

Although these extern names are effectively owned by some other module, this folds these names into the current module, so that they can be used by any logic in this module. Since they are owned by another module, that module is responsible for initializing its global variables and implementing its functions. Thus, no functions in an extern block should be given implementation code, nor should variables be initialized.

Associated types and methods

Not uncommonly, external functions and variables depend on custom types and constants defined by the external module. If so, these types should also be declared in the extern block. Constants can be defined using an enum. If the internal field structure of a type is unknown, an opaque struct may be used.

When custom types are defined, any externally defined function that take a value of that type as the first parameter may be declared as methods on that type. This allows the more convenient use of the dot operator when invoking functions on some data value.

extern in a file of its own

It can be helpful to put the extern block for some C-compatible library (e.g., libcurl or sdl2) into a file of its own. Placed in a module's folder, that file is one of the module's files like any other, so every file of the module can use its declarations.
