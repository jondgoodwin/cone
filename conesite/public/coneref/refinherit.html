Delegated Inheritance

Inheritance makes it easy to declare a new type that reuses (inherits) the fields or methods defined by some other type.

Cone's version of inheritance looks and behaves somewhat differently than in other languages, which is why it is called delegated inheritance. At its heart, Cone's inheritance is a composition-based approach that offers convenient namespace "sugar" for automatically forwarding certain method (or field) access requests. This makes method reuse (forwarding) easy to accomplish, where needed, while side-stepping the tightly-coupled complexity and fragility sometimes experienced when using traditional inheritance.

It is the same operation a module performs when it folds another module's names into its own: "the names in there are now names in here." A type can do it in two places, and they answer different needs. On a field it delegates to a part, which is the whole of this page until its last section. On the type itself, with extends, it starts from a concrete type and enriches it with methods — see Enriching a concrete type.

Selective Inheritance

Imagine we have this Engine type:

struct Engine {
  pub fuel   f32;
  pub torque f32;

  pub fn thrust(self &mut, amt f32) { ... }
  pub fn power(self &) f32 { ... }
}

Now, let's create a new Car type that includes, and inherits from, an Engine:

struct Car {
  pub engine Engine use fuel, thrust;
  pub body   SportyLook;
  pub wheels RimWheels;
}

The use clause on the engine field makes the fuel field and the thrust method of Engine names of Car, reached by way of engine:

  • any access to car.fuel is treated as equivalent to car.engine.fuel. It reads and writes the engine's own field; no second copy of the value exists.
  • (&mut car).thrust(23.2) is treated as equivalent to (&mut car.engine).thrust(23.2). It is important to note that thrust runs with self being the engine, and not the car. If one needs a thrust method that operates on the car, then don't have Car inherit it from engine. Implement it in Car and then explicitly call engine's thrust as part of its logic, if desired.

No forwarding method is generated for a folded name: a call to thrust through a Car is a call to Engine's own method, with its receiver shifted to the engine. Inside Car's own methods a folded name is named bare, exactly as Car's own members are.

A type may inherit names from more than one field. One clause reaches one level: use temp admits engine.temp, not engine.core.temp, unless Engine itself folded temp in from core. Folds chain through the types, not through the clause.

Name Aliasing

Inherited names must be unique. It is an error to inherit names that are otherwise defined by the type. Similarly, it is an error to inherit the same name from two different fields.

To avoid such name conflicts, a name may be inherited using an alias. For example use fuel as fuelamt, thrust would support the use of car.fuelamt as an alias for car.engine.fuel.

Total Inheritance

If a field specifies use *, every public field and method of the field's type is inherited, less any named after but. The rule for names is the same as for a listed fold: an inherited name may not collide with a name the type declares, so a type that implements a method of its own leaves the inherited one out by name. For example: 

struct SuperEngine {
  pub engine Engine use * but power;
  pub fn power(self &) f32 { ... }
}

SuperEngine inherits the fields fuel and torque, as well as the thrust method from engine. It does not inherit the power method, since it has its own implementation of it and says so. Should Engine later gain a member whose name SuperEngine also declares, the fold is refused where it is written rather than one quietly overriding the other.

What folds, and what does not

  • The field must be pub, and only public members fold. Visibility is transitive: a folded name is reached through the field, so a private field cannot lend its members out, and a private member of the field's type stays private. A folded name is public because its path is.
  • Fields, methods and macro methods fold. A static function or variable of the field's type does not: it is reached through the type rather than through a value, so there is no receiver to shift. Neither does a macro without a self parameter, nor Self, nor the field type's own final or clone.
  • A field held through a reference folds. With pub engine &mut Engine use fuel, thrust, the hop reaches through the reference as car.engine.fuel does, and the reference itself is the receiver of a folded method.
  • Only a struct folds. A trait and an enum are abstractions over their implementers, with no organizing details of their own to fold through; a use clause on one of their fields is refused.
  • A fold needs the field's type complete. A type cannot fold from a field of its own type, nor may two types each fold from the other.

Receivers

A folded method is reached exactly as the path written out would reach it. Through a reference to the folding type, the field is reborrowed with the reference's own permission, so (&mut car).thrust(1.0) and c.thrust(1.0) for a c &mut Car both hand thrust a &mut Engine. From a value of the folding type, the receiver is the field's value, which reaches a method that takes self by value and copies the field, as car.engine.rating() would. The fold adds no borrowing rule of its own.

What a fold grants

A fold grants names, and with them structural compliance with any trait those names satisfy: a type whose folded power matches a trait's requirement conforms to that trait, and may be reached through a virtual reference to it. Behind the virtual reference the compiler supplies the shift to the field, since the call site cannot know the type folded the method; nothing in the language can name what it supplies.

A fold grants no subtyping to the field's concrete type, and no layout: a Car is not an Engine, and &Car does not recast to &Engine. Subtyping in Cone is between a concrete type and an abstraction, a trait, never between two concrete types.

A folded field is not a field of the type. It is a name for storage inside another type's value, so it cannot be named in the type's literal (SuperEngine[engine: Engine[fuel: 1.0, torque: 2.0]] is the literal), and it meets no trait's field requirement. A folded method does count toward conformance.

Enriching a concrete type

Sometimes what you want is not a part but a better version of a whole. You have somebody's floating-point type, or matrix type, or parser state, and you want it plus trigonometry, plus logarithms, as if they had always been one type. You do not reach into their package and add methods to it. You declare a type of your own that names theirs as its base:

struct Meter {
  pub mut cm i32;
  scale     i32;

  pub fn scaled(self) i32 { cm * scale; }
  pub fn make() Meter { Meter[4, 5]; }
}

struct Gauge extends Meter {
  pub fn doubled(self) i32 { cm + cm; }
  pub fn reset(self &mut) { cm = 0; }
}

Gauge adds methods and no fields. Everything Meter has is a name of Gauge — its fields, its methods, its static functions — and Gauge's own methods read and write those fields by bare name, as doubled and reset do. What it may not do is declare a field. Reading and writing the fields it starts with is exactly what it is for; adding one is what would make the two types different shapes.

The two types interchange, in both directions, at no cost

Because the representations are identical, a Gauge may be used wherever a Meter is wanted, and a Meter wherever a Gauge is wanted — by value, through a & reference, and through a &mut reference. No conversion runs; there is nothing to convert.

fn wantsMeter(m Meter) i32 { m.scaled(); }

imm g Gauge = Meter.make();   // a Meter value, bound to the enriched name
wantsMeter(g);                // and a Gauge, passed as a Meter

That last pair is how values of an enriched type are obtained at all. The base's own constructors and static functions still return the base type — Gauge.make() hands back a Meter — and binding the result to the enriched type is all that is needed. A library that never heard of your enrichment can still produce values for it.

They remain two distinct types, and which one you name is what decides what is in view. A value typed as Meter cannot call doubled; you reach the added methods by naming Gauge somewhere. That is the whole difference between this and a language where extension methods drift into scope with an import: an enrichment here is owned, and it is reached deliberately.

The declaration is what licenses it

Two types interchange because one of them said the other was its base, not because they happen to look alike. Identical representation is why the license is safe to grant; the declaration is why it is granted at all.

  • Two look-alikes that named no base stay unrelated. A struct with the same fields in the same order as Meter is not a Meter and does not substitute for one. Cone has no structural typing between concrete types.
  • Nothing lifts through a container. Pair[Gauge] and Pair[Meter] are two instantiations of one generic, neither of which extends anything, so they are unrelated however their components are declared. Substitute at the element, never at the container.
  • A type enriches one base, and a chain is allowed: Fancy extends Gauge extends Meter. Every hop adds methods only, so all three are one representation and any of them substitutes for any other. Siblings interchange too: two types that both extend Meter both have its representation.
  • An enrichment may not override. A name the base already has may not be redeclared, whether the base's is a field or a method. One value would otherwise mean two different things depending on which of the two names was used to reach it.
  • Only a concrete struct may be enriched. An abstraction holds no value, so there is nothing of it to enrich — what a type asserts about an abstraction is conformance, which is is, and a type may write both clauses. An enum's variant set is its identity, so adding to an enum means adding variants, which is a separate relationship (see enum). A base that declares final or clone is refused as well: those belong to its own values' lifecycle and do not carry across.

An enrichment is inside its base's encapsulation

An enrichment is acting as the base, so it sees what the base's own methods see. Above, scale is private to Meter and Gauge's methods may read and write it — even when Meter lives in another module or another package. What comes across keeps the base's visibility, so Gauge's own clients cannot reach scale at all. The asymmetry with a field's fold is deliberate: a type that folds through a field is a client of the part and sees only what is public, while an enrichment is the whole.

A type that may be extended has its representation in its contract. This is the price of the paragraph above, and it is worth stating plainly because nothing in the language can warn you about it. extends is an intimate relationship, and its author takes the coupling knowingly. Adding a field to a base changes the size and shifts the positional literal, so it is a major version change and never a quiet one. But so is renaming or retyping a private field at the same size — invisible to everyone except an enrichment reading it, and the base's author has every reason to think private means free to change. If you publish a type others may extend, treat its field names and types as part of what you promised. Semantic versioning is the protection, and it works because two versions of one package may coexist in a binary.

Retroactive conformance

Cone notices trait conformance structurally: a type that happens to have the methods a trait requires may be passed where that trait is wanted, without declaring anything (virtual references). Put that together with the enrichment above and something useful falls out. Suppose a library's type implements three of a trait's four methods:

trait Area { pub fn area(self &) i32; }

struct Framed extends Meter {
  pub fn area(self &) i32 { cm * cm; }
}

fn areaOf(a &<Area) i32 { a.area(); }

imm f Framed = Meter.make();   // a Meter value
areaOf(&f);                    // reaching a trait Meter does not satisfy

You supply the fourth method in an enrichment of your own, and the library's own values reach the trait by being bound to your name. You did not modify their package and you did not need their permission. And because the conformance hangs off your named type and its own vtable, two people can enrich the same base in conflicting ways without colliding: each one's claim is reached only through the name that made it.

Generic types

A generic may enrich a generic — struct Rich[T] extends Holder[T] — and the license sits on that one declaration rather than on each instantiation, because no field may be added and so the shapes agree instance by instance. Inside such an enrichment, a member taken from the base is reached as self.name rather than by bare name, because the base is not a type yet when the enrichment's bodies are read. This is the same limit an inherited member of a generic trait has.
