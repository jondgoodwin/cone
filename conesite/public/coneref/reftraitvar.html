Trait-based Variants

Note: All of this capability is implemented.

Earlier, we introduced enum types, which declare a closed set of variants: the whole set is written inside the declaration, and nothing elsewhere can add to it.

Sometimes that is exactly what you do not want. Where other modules should be able to add variants of their own, the set cannot be enumerated anywhere, so a trait and the structs that declare is against it are what express it.

How an open set is written

The variants are declared separately from the trait rather than inside it, and may live anywhere — even in a different module. Each says which trait it belongs to by declaring that it is one. A trait contributes no fields, so each variant declares the trait's own fields itself, first and in the trait's order. That is what keeps the trait's layout a prefix of every variant's.

trait Event {
	pub time datetime;
}

struct ButtonEvent is Event {
	pub time datetime;
	pub button u8;
	pub pushed Bool;
}

struct KeyEvent is Event {
	pub time datetime;
	pub key Unicode;
}

struct QuitEvent is Event {
	pub time datetime;
}

What openness costs

Because the variants are open-ended, the compiler cannot know at compile time how many there will be, and so cannot give each one a guaranteed-unique number. An open trait therefore has no tag field, implicit or explicit.

Everything an enum does with its tag has to be done another way. Without a tag there is nothing in the value to say which variant it is, so neither pattern matching nor method dispatch works on a plain reference to the trait. Both need a virtual reference, which carries a pointer to the variant's vtable alongside the pointer to the value.

That is where the cost lands, and it is worth being concrete about it:

  • A virtual reference is a fat pointer, twice the size of a regular reference.
  • A match has to check the possibilities one at a time, because there is no number to index with. An enum's tag is an index, so a closed set is not only exhaustive, it is faster.
  • Variants differ in size, so no value of the trait may be held and nothing can swap one variant for another in the same storage. Pool allocation, which wants one size, is out.

Choosing between them

Only choose an open trait if you really need other modules to be able to add variants. Otherwise choose an enum, which is closed, tagged, exhaustively matchable, and by default holdable by value.

The middle case is a closed set whose variants differ enough in size that padding them all to the largest is not worth it. That is an enum too — written enum @unsized, which keeps the tag, the exhaustive match and the fast dispatch, and gives up only the value semantics.
